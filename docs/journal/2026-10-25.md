## 关键坑：systemd 服务 status=203/EXEC（Permission denied）
- 现象：ExecStart 写 `.venv/bin/uvicorn`，service 以 deploy 跑报 "Failed to execute ...uvicorn: Permission denied"，文件本身 -rwxr-xr-x 看着正常。
- 根因：venv 是 **`sudo uv sync`**（root）建的。uv 默认把 venv 的 python 做成软链接，指向 root 的 uv python（/root/.local/share/uv/python/...）。/root 是 700，deploy 进不去 → 执行 uvicorn 脚本时其 shebang 指向的 python 不可达。
- 修法：删 .venv，`sudo -u deploy -i` 切进去 `uv sync --frozen --no-dev` 重建（python 软链接改为 /home/deploy/.local/share/uv/...）。可选先把 /root/.cache/uv 拷给 deploy 省重新下载。
- 教训：服务器上装依赖必须 `sudo -u deploy` 切身份跑 uv，**绝不能 sudo uv**（会变 root 属主 + python 锁在 /root）。ExecStart 用 `python -m uvicorn` 比直接用 uvicorn 脚本更稳。

## v8 预研（13:4x）：容器化 + SQLite→MySQL 可行性评估（未动代码）
**结论：容器化与换库是两件独立的事，v8 应只做容器化，SQLite 保留（named volume）。**
- 硬理由：`job_service.py:67` 的 `_RUNTIMES`、JobBus、runtime 快照、连接池全在进程内 → 单 worker 是硬约束。换 MySQL 的**唯一大收益（多实例横向扩展）拿不到**，只换来「进程内并发写不打架」，而瓶颈是 LLM 生成不是 DB 写。要真扩展得先外置运行时（Redis/任务队列），是 v9 量级。
- v7/DEPLOYMENT.md 开头自己写了「需横向扩展时换 **Postgres**」，不是 MySQL。
- 若一定要换，**PG 改造量远小于 MySQL**。MySQL 的 5 处硬缺口（均已定位到行）：
  1. **TEXT 列不能直接建索引/主键**（必须前缀长度）→ 5 张表 TEXT 主键（auth_sessions.token_hash、invite_codes.code、system_config.key、model_providers.id）+ 十余个含 TEXT 的索引/唯一约束全要改 VARCHAR(n)。
  2. **部分唯一索引不支持**：`models.py:443` `ux_chat_turns_job_role ... sqlite_where=text("job_id IS NOT NULL")` 是「幂等写轮次」的 DB 级保证 → MySQL 无对应能力，需生成列+唯一索引或退回应用层。PG 用 `postgresql_where` 同 API。
  3. **UPSERT 指定冲突目标不支持**：`document_repo.py:452-465`（`on_conflict_do_nothing(index_elements=...)`，归属校验写在 SELECT 里）、`chat_session_repo.py:91-104`、`runtime_config_repo.py:66-73`。MySQL 的 `INSERT IGNORE` 会吞掉截断/超长错误，`ON DUPLICATE KEY` 冲突范围变宽。PG 语法 1:1。
  4. **TEXT 上限 64KB**：`document_versions.content`（整篇 PRD）、`solutions.data`（会话快照）→ MySQL 必须逐列判 MEDIUMTEXT/LONGTEXT，否则上线才炸。
  5. **`func.length()` 语义不同**（MySQL=字节，SQLite/PG=字符）：`document_repo.py:181` content_length。
  6. 附加：`admin_repo.py:286` `func.datetime(created_at,'+480 minutes')` 是 SQLite 专属（MySQL 无此函数）；MySQL 默认 `utf8mb4_0900_ai_ci` 不区分大小写，会反转 `users.username` 的**大小写敏感**语义（login_failures 的设计前提）。
- 换库的固定成本（不论 PG/MySQL）：`core/schema_snapshot.py`（300 行 PRAGMA 实现）整体重写、`schema.py::_is_empty` 判 `sqlite_sequence`、`_database_url` 拼 sqlite 前缀、`paths.default_db_file()`→DATABASE_URL、`engine._on_connect` 三条 PRAGMA、`BOOLEAN_COLUMNS`+`compare_type` 归一失效、975 例「模板库+每用例拷文件」测试基建重做、备份从 `VACUUM INTO` 改 `pg_dump/mysqldump --single-transaction`。
- 容器化注意事项（与换库无关，v8 必做）：①SQLite 数据目录**必须 named volume**，不能 bind mount Windows 目录（Docker Desktop grpc-fuse 不支持 SQLite 文件锁 + WAL `-shm` mmap，随机 `disk I/O error`）。②`/health` 恒 200 不能当 healthcheck，要另加 readiness（能连库 + revision==head）。③Vite 的 `import.meta.env` 是构建期注入 → 前端只能相对路径 `/api`。④`.dockerignore` 排除 node_modules/.venv/secrets/.env/prdwright.db；镜像必须含 `backend/migrations/` 与 `skills/`。⑤单副本不能 scale，重启丢在途任务 → preStop 排空 + 长 `stop_grace_period`。⑥SSE 三行 + `: ping` 心跳仍未实现（v7 遗留）。⑦`backend/uv.lock` 已存在，可 `uv sync --frozen`。

## 补：方案原稿漏了「语义差异」一整类（14:1x，用户追问"还有没有抹不平的"）
- 原稿只覆盖了「写法层」，漏了 4 条**语义差异**，已补成文档 3.6 节（285 行）：
  1. ⚠️ **事务隔离**（最危险）：全项目 `with_for_update` / `isolation_level` **各 0 处**。SQLite 单写者让所有「先查后写」天然正确。裸露的两条路径：`generation_job_repo.supersede_active` + 紧随的建任务（不变量「同 owner+solution+kind 至多一个 running」）、`quota_service` 额度检查（先算已用再放行）。已防御的两条：`chat_turn_repo`（SAVEPOINT+撞索引回查）、`document_repo._ensure_document`（upsert+唯一约束）。
  2. **`LIKE` 大小写**：4 处（`generation_job_repo.py:483/:514` 用户名搜索、`log_repo.py:196/:211` 日志搜索）。SQLite ASCII 不敏感 / MySQL 随 collation / **PG 的 LIKE 敏感**（要 ILIKE）→ 换 PG 后「搜 admin 搜不到 Admin」。
  3. **`ORDER BY` 排序**受 collation 影响（ci 下大小写混排）。
  4. **布尔默认值字面量**：`server_default=text("1")` 在 PG 的 BOOLEAN 列上报类型错误。
- 另补两条「永久适配」原稿没说透：Alembic `render_as_batch=True` 是 SQLite 专用（换库必须关）；池参数 `max_overflow=0` 的理由（WAL -shm）换库后消失，要补 `pool_pre_ping`/`pool_recycle`。
- 自我修正：上一轮说「partial index 不用等换库就能去掉」不成立 —— 去掉会改索引定义 → 结构快照变红，归到换库那次与列长度一起改。
- 新增契约 **C-D5**（搜索大小写必须显式，不依赖库默认）、**C-D6**（业务不变量不能只靠单写者保证，换库前每条要落成唯一约束/条件更新/显式锁）。
- 教训：「抹不平」要按**层**分（写法层 / 查询语义层 / 事务语义层 / DDL 能力层），只盘写法层会漏掉最危险的那层 —— 语义差异不报错，只让结果悄悄变。

## v8 追加（15:5x）：补强 MySQL 测试策略（MULTI-BACKEND.md §5 重写）
用户追问「计划里有没有把 MySQL 测试补上，避免写了没法验证」→ 查实后发现原 §5 不够，重写成 8 小节（文档 394→535 行）。
**关键修正**：原方案说「1006 例在两个后端都绿」**不成立**。
- 实测：**11 个测试文件直接触 SQLite**（PRAGMA / sqlite_sequence / sqlite3.）、**15 个文件用 `?` 占位符**、**21 处 `connect()`**、**并发用例只有 1 条且是 SQLite 专属**（`test_second_writer_waits_instead_of_failing` 验的就是 WAL 写锁等待）。
- 改为**三类用例**：契约类（双跑、断言相同）/ 特性类（只在对应后端跑）/ 并发类（双跑但断言不同）。
- **标记机制**：`@pytest.mark.sqlite_only` / `mysql_only` + `pytest_collection_modifyitems` hook。**默认不标记 = 契约类 = 必须双跑**（新用例自动纳入）；`--strict-markers` 防拼错。
- **隔离策略**：SQLite 保留「模板库+拷文件」；MySQL 用「全量建表一次 + 每例 `SET FOREIGN_KEY_CHECKS=0` + TRUNCATE」（约 10ms/例）；**否决「事务回滚」**——要让 `session_scope()` 绑注入 Connection，等于为测试改生产代码；也否决「每例一个 schema」（DDL 太慢，1006 例多 50 秒）。
- **并发怎么造**：线程 + `threading.Barrier(2)`（项目 repo 是同步的，不用 asyncio）。死锁用例只能 `mysql_only`（SQLite 无行锁造不出死锁）。

- **支持范围**：SQLite 3.35+；MySQL **8.0（CI 默认）+ 8.4（每月 schedule）**；不纳入 5.7（没有 `utf8mb4_0900_as_cs`）。
