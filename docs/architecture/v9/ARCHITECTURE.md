# v9 架构：容器化

> **一句话**：把 PRDwright 的运行形态从「裸机 + `uv run uvicorn` + 两个 `npm run dev`」
> 换成 `docker compose up -d`——两个镜像、一个入口、三个命名卷、两个探针与一次可预期的排空。
>
> **下层**：`../v8/`（方言收敛与清理，已完成）、`../v7/`（部署与上线）。
> 本层不改业务能力、不改数据契约、不改前端交互，只改「怎么被部署、怎么被重启、怎么被判断活着」。
> 时间线真源：**`../README.md`**

> **口径声明**：本文的「容器」**只指 Docker 容器**。产品概念里的「方案」是
> 「一次完整工作的承载单元」（见 [`GLOSSARY.md`](../../../GLOSSARY.md)），与容器无关；
> 旧文档里「方案 = 一次完整工作的容器」这个说法已废除。

## 1. 目标与范围

### 1.1 四句话目标

1. **能跑**：一台装了 Docker 的机器，准备好 `.env` 与主密钥后敲 `docker compose up -d`，
   浏览器打开 `http://<机器>/` 能登录并生成一篇 PRD，`/admin/` 能进管理后台。
2. **一个入口**：宿主机只开 80。用户端、管理端、接口、探针全部由同一个入口分派，
   API 端口不对外。
3. **重启有结论**：`docker compose restart` 之后，重启前正在跑的任务**要么跑完、要么被标成
   已取消**，不留一具 `running` 的尸体；数据、密钥、日志都在命名卷里，容器重建后还在。
4. **能判断**：一个探针只判生死，一个探针判就绪（库可写 + 技能包可加载）。
   库坏了，就绪探针会说不 OK，而不是永远「健康」。

### 1.2 本期范围（In）

| # | 范围 | 落到哪一节 |
| --- | --- | --- |
| 1 | 交付形态：`deploy/` 一个目录装全部部署件（compose、反代、env 样例、启动脚本、备份脚本、README） | §2.2 |
| 2 | 两个镜像：应用镜像（API 进程）与静态站点镜像（两个前端产物 + Nginx） | §3.1 |
| 3 | 单 worker 写死、技能包打进镜像、非 root 运行 + 启动脚本校正属主 | §3.2 – §3.4 |
| 4 | 镜像 tag、CI 只构建不推送、整栈冒烟 | §3.5 |
| 5 | 单入口：宿主只开 80，`api` 只 `expose` 不 `ports` | §2.3 |
| 6 | 三个命名卷（数据 / 密钥 / 日志）与「为什么不是宿主目录挂载」 | §4.1 – §4.2 |
| 7 | 主密钥缺失即拒绝启动 | §4.3 |
| 8 | 日志双写（stdout + 卷内文件） | §4.4 |

| 11 | 备份：一条命令、按后端分派、产物带 sha256 | §6 |

### 1.3 本期明确不做（Out）

| 事项 | 为什么本期不做 |
| --- | --- |
| **PostgreSQL 接入**（驱动、方言白名单、连接装配、迁移按方言、结构对拍、双后端 CI 矩阵） | 数据库仍是 SQLite。换库要连迁移链与结构对拍一起动，是下一版的整组工作 |
| **全库真类型化**（时间从 ISO 文本改真时间、布尔改原生） | 它自带 API 时间契约变更与两个前端的适配，必须与换库同一次做，否则要改两遍 |
| **MySQL** | 代码保留不动，但文档不再把它当「一等后端」；方言台账留在 `../v8/ARCHITECTURE.md 附录 B` |
| **k8s / Swarm** | 目标是单机 compose。滚动更新、探针权重这些能力还没有需要它的人 |
| **开发者热重载容器** | 开发仍走本机 `uv run uvicorn` 与两个 `npm run dev`；容器只承载部署形态 |
| **容器内 TLS** | 只做 HTTP。HTTPS 由前置反代或内网承担——证书生命周期不放进取舍受限的单机 compose |
| **多架构镜像** | 只出本机架构；Dockerfile 不写死平台，留好路 |
| **业务链路自动化测试** | 容器冒烟只验「主链路可达」（就绪探针 200 + 首页 + `/admin/` + 反代打一次健康端点），不跑「登录 → 生成」 |
| **老数据迁移** | SQLite 库不搬迁。下一版若改类型，旧库按「检测到旧结构就拒绝启动」处理 |
| **前端改动** | v9 不碰两个前端：Vite 构建期替换 `import.meta.env`，两个前端本来就用相对路径 `/api` |

## 2. 交付形态与拓扑

### 2.1 拓扑

```text
                     宿主机 :80（唯一对外端口）
                              │
                  ┌───────────▼────────────┐
                  │  web（静态站点镜像）     │
                  │  Nginx                  │
                  │   /          → 用户端 dist
                  │   /admin/    → 管理端 dist
                  │   /api/      → api:8000
                  │   /healthz   → api:8000
                  │   /readyz    → api:8000
                  └───────────┬────────────┘
                              │ 内部网络（不 publish）
                  ┌───────────▼────────────┐
                  │  api（应用镜像）         │  单 worker（硬约束）
                  │  uvicorn                │  lifespan: prepare_schema → warmup → 接请求
                  └──┬────────┬────────┬────┘
                     │        │        │
          volume:data   volume:logs   volume:secrets
          （SQLite）    （轮转日志）   （master.key，只读）
                              │
                              └─ 出网 → 模型供应商 API（唯一的外部依赖）
```

compose 里另有一个**默认关闭**的数据库服务（profile），只为下一版接 PostgreSQL 时不必重写编排；
`.env` 样例里注明「v9 不使用，见下一版」。它默认不启动，所以现在没有第三个服务在跑。

### 2.2 `deploy/`：一个目录装全部部署件

部署件集中在一个目录里，读者不必在仓库里到处找：

| 部署件 | 作用 |
| --- | --- |
| compose 编排（一份，全平台） | 起栈、卷、端口、`stop_grace_period` |
| 反向代理配置 | 三路分派（`/`、`/admin/`、`/api/`）+ SSE 三行 |
| env 样例 | 每个变量带中文说明与默认值，`CORS_ORIGINS=` 为空并有注释 |
| 启动脚本 | 以 root 校正数据 / 日志目录属主，然后降权执行 |
| 备份脚本 | 按后端分派，产物带 sha256 |
| 备份产物目录 | 被版本控制忽略；宿主可见的持久化产物 |
| README | 第一次部署照它敲命令：备 `.env` 与主密钥 → `docker compose up -d` |

**只做一份编排，不设平台专用覆盖文件。** 早期曾打算给 Windows 一份改宿主目录挂载的覆盖文件，
这个方案已作废（理由见 §4.2）——同一份「哪些目录要持久化、怎么挂」的知识写两遍，一定会分叉。

### 2.3 单入口：宿主只开 80

| 位置 | 端口 | 说明 |
| --- | --- | --- |
| 宿主机 | `80` | 唯一对外端口 |
| `web` 容器 | `80` | 由宿主机映射 |
| `api` 容器 | `8000` | **只 `expose`，不 `ports`**：宿主机上不可达，只能被 `web` 访问 |

这与 v7 的单域名前缀契约一致（`/`、`/admin/`、`/api/`），**不引入第二个子域**：
会话 Cookie 是 host-only，跨子域会「后台登录了、调 API 仍 401」；同域下 CORS 完全不参与。

v7 里 `/health` 的约束是「仅本机可访问」。容器化后「本机」等价于「同一网络内的 `web` 容器」，
这条约束不变：**`api` 的 8000 端口不得 publish 到宿主机**。

## 3. 镜像

### 3.1 两个镜像

| 镜像 | 基础 | 构建阶段 | 产物 |
| --- | --- | --- | --- |
| 应用镜像 | `python:3.12-slim` | builder（`uv sync --frozen --no-dev`）→ runtime | 只读代码 + `.venv`，`CMD` 里 `--workers 1` |
| 静态站点镜像 | `nginx:alpine` | node 构建两个前端 → nginx | `/` 与 `/admin/` 两份 dist + 反代配置 |

依赖用**锁定文件**安装（`backend/uv.lock`、`frontend/package-lock.json`、
`frontend_admin/package-lock.json`），所以同一份提交构建出来的镜像可复现。

**为什么是两个镜像而不是一个**：`npm install` 与 `uv sync` 的缓存键完全不同，合在一个
Dockerfile 里会让「只改后端」也重装一遍 node_modules；而两个进程的职责、重启策略、
资源画像也不同——合并后「重启 Nginx 会杀掉正在跑的任务」。

### 3.2 单 worker 写死，且没有开关

`api` 的进程数**恒为 1**。这不是性能选择，是正确性约束：

| 进程内状态 | 位置 | 多 worker 会怎样 |
| --- | --- | --- |
| `_RUNTIMES` 运行时表 | `backend/src/backend/services/job_service.py` | A 进程起的任务，B 进程的 SSE 找不到 → 客户端永远等不到分片 |
| `JobBus`（订阅与广播） | `backend/src/backend/services/job_bus.py` | 订阅方与生产方不在同一进程 → 任务永不推进 |
| runtime 配置快照（5 秒 TTL） | `backend/src/backend/core/runtime_config.py` | 后台改了配置，只有一半进程生效 |
| 固定连接池（`pool_size=4`、`max_overflow=0`） | `backend/src/backend/core/engine.py` | 多进程各自建满，SQLite 写锁冲突概率上升 |
| 技能包缓存 | `backend/src/backend/services/skill_registry.py` | 各进程各自扫盘，加载失败的时机不一致 |

配套三条纪律：

1. `--workers 1` **写死在镜像的 `CMD` 里**，不提供环境变量覆盖——一个「看起来能调」的参数
   迟早会被调；
2. compose 里不写 `replicas`，文档里也不提供 `--scale` 的说明；
3. 发布即中断：重建容器会让在途任务消失，所以发布与重启必须先排空（§5.3）。

### 3.3 技能包打进镜像

`skills/`（`prd-generator` 等三个技能包）随代码一起进镜像，**不挂载**。

理由只有一条：**镜像即完整交付物**。挂载会让「镜像里的代码」与「挂载进来的技能包」版本不一致
成为可能，而就绪探针检查的恰好是「技能包可加载」——挂载等于把探针要保证的东西交给运行时去赌。
要换技能就重建镜像，与代码同一个版本节奏，于是「线上跑的是哪套技能」永远可回答。

`PRDWRIGHT_SKILLS_STRICT=true` 在部署态保持开启：技能包缺失时启动直接失败，
而不是静默退回内置提示词。

### 3.4 非 root 运行 + 启动脚本校正属主

- 镜像内创建固定 uid 的非 root 用户，`USER` 切过去再启动；
- 代码层只读（镜像内的 `/app`），运行期不写任何镜像层；
- 启动脚本以 root 起步，**先把数据与日志目录的属主校正到运行用户**，再降权 `exec` 应用。

为什么必须自动校正：命名卷首次创建时属主是 root，而「记得手工 chown」是一条典型的
「忘了就表现为 `database is locked` 或 500」的命令。校正只发生在启动时，之后进程一直是非 root。

**迁移只由 `lifespan` 跑一次**，启动脚本不跑迁移——两个入口各跑一次的话，迁移日志与锁行为
都不可预测（C-V9-4）。

### 3.5 镜像 tag 与 CI

- 镜像 tag 用 `git describe` 的结果，线上跑的是哪份提交可查；
- CI **只构建，不推送**：没有镜像仓库凭据通道，而「镜像还能不能构建」这件事本身此前无人守；
- 新增一个 CI job：构建两个镜像 → 起 compose → 轮询就绪探针到 200 → 取首页与 `/admin/`
  → 走反向代理打一次健康端点 → 拆栈。约 2–3 分钟。

这也是 v9 唯一新增的测试接缝：容器能不能起来，在 pytest 里无法验证，只能在一台真的
Docker 上验证一次。

## 4. 数据、密钥与日志

### 4.1 三个命名卷

| 卷 | 挂载点 | 内容 | 丢了会怎样 |
| --- | --- | --- | --- |
| 数据卷 | `/var/lib/prdwright` | `prdwright.db`（含 WAL 的 `-wal` / `-shm` 边车） | **业务数据全丢** |
| 日志卷 | `/var/log/prdwright` | 轮转日志文件 | 丢历史日志（`app_logs` 表里还有一份派生数据，但那是可丢弃的） |
| 密钥卷 | 只读挂载 | `master.key` | 库里所有模型密钥都解不开（`/health` 的 `llm` 项变 `false`） |

备份产物落在 `deploy/` 下的备份目录里（被版本控制忽略），所以**宿主上仍有可见的持久化产物**。

### 4.2 为什么不是宿主目录挂载（这不是配置问题，是语义问题）

容器里的 SQLite 需要的不是「一个能读写的目录」，而是**文件锁与共享内存映射**：

- WAL 模式要在库文件旁创建 `-wal` 与 `-shm`，`-shm` 是 **mmap 的共享内存**；
- Docker Desktop for Windows 的 bind mount 走 grpc-fuse / 9p，**不支持** SQLite 需要的
  文件锁语义与 `-shm` 的 mmap；
- 症状不是「报错说挂载不对」，而是**随机** `disk I/O error`、`database is locked`，
  或者容器重启后看见一个「少了最近几分钟写入」的库。

命名卷在虚拟机内部是原生文件系统，语义与裸机一致。**代价**是实时库不能双击查看——
这份可见性由备份产物（§6）补上。

早期方案是「宿主目录挂载 + 一份 Windows 专用覆盖文件」。它被否决，因为它在 Windows 上
依然会坏（换文件系统才能解决），而两份编排会让「哪些目录要持久化」这份知识写两遍。

### 4.3 主密钥缺失即拒绝启动

`PRDWRIGHT_MASTER_KEY_PATH` 只经 `os.environ` 读取（`backend/src/backend/core/crypto.py`），
`backend/.env` 里的同名项读不到。容器里由 env 注入，指向只读卷里的 `master.key`。

**密钥缺失时直接退出**，并打印生成密钥的指引（`scripts/keygen/generate_keys.py`）。
绝不自动生成：自动生成的后果是「换机器时旧密文永久解不开」，而且当场不会有人发现。

### 4.4 日志双写

| 去处 | 谁看 | 为什么 |
| --- | --- | --- |
| stdout | `docker compose logs` | 运维的第一现场；不必进容器翻文件 |
| 日志卷里的文件（轮转） | 事后排查、跨容器重建保留 | 容器重建后历史还在 |

落库的那一份（`app_logs`）不变，仍受 `log_retention_days` 与 `log_max_rows` 两个闸门约束；
`LOG_DB_ENABLED=false` 可整体关掉落库，文件照写。

## 5. 探针与排空

### 5.1 两个新探针的分工

| 路径 | 回答的问题 | 判定 | 谁用 |
| --- | --- | --- | --- |
| `GET /healthz` | 「进程还活着吗」 | **恒 200**，不查库、不查配置、不发外部请求 | compose `healthcheck`、编排的 liveness |
| `GET /readyz` | 「现在能派活给它吗」 | **库可写** 且 **技能包可加载**，任一不满足返回 `503`，响应体指出是哪一项 | 发布脚本、摘流判断、编排的 readiness |

两条都放在 `backend/src/backend/api/health.py`，并加入 `backend/src/backend/api/deps.py`
的认证白名单——探针跑在未登录状态，漏了这一步的表现是「容器永远不健康」。

三条设计取舍：

1. **就绪探针查「库可写」而不是「库连得上」**：SQLite 在只读、锁死、磁盘满时连接照样成功，
   而目标能力是写。只连一下等于给装饰品。
2. **就绪探针不查模型供应商配置**：那依赖外部网络，高频探针会烧额度、会抖动。
   它仍是 `/health` 三项体检里的一项，由人看。
3. **两个探针都是深健康检查的补充，不是替代**：`/health` 说「能不能用」，探针说
   「进程活没活」「现在能不能接客」。

### 5.2 `/health` 不动

`/health` 仍是带三项体检（数据库 / 供应商 / 技能资产）的详情端点，`status` 只有
`ok` / `degraded`，**恒返回 200**（v7 契约）。这一版只加两条探针，不改它的语义——
改语义会动到已有监控与文档，而且它本来就是「人看的详情页」，不是「机器判断的闸门」。

### 5.3 排空语义：摘流 → 等 30 秒 → 超时落终态

收到 `SIGTERM`（`docker compose restart` / `stop` / 重新部署都会发）之后：

1. **就绪探针转 503**——给「摘流」留时间，让编排/反代不再派新活过来；
2. **停止接收新任务**：新的生成请求返回明确的失败，而不是排进一个马上要死的队列；
3. **等在途任务最多 30 秒**（这是等待上限，不是必须等满：任务都结束了就立刻退出）；
4. **超时者标为已取消**：落终态、向 SSE 订阅者发一条错误事件，客户端因此拿到确定结论；
5. 落一条日志写明「这次重启取消了几个任务」，最后 flush 日志队列再退出。

排空逻辑做成**可以直接调用的单元**（不起子进程、不发真信号），所以测试能在毫秒级验证
「给定在途任务，排空后它被标成已取消并落了终态」。

compose 的 `stop_grace_period` 必须**大于**这个 30 秒窗口（留出 flush 与进程退出的余量），
否则容器会在排空走完之前被硬杀，任务又变回 `running` 的尸体——那正是这一版要消灭的东西。

## 6. 备份与恢复

### 6.1 一条命令，产物带日期与 sha256

一条命令产出一个 `.db` 文件，文件名带日期，旁边落一份同名 `.sha256`；产物落 `deploy/` 下的
备份目录（被版本控制忽略）。脚本跑在项目自己的 uv 环境里（`backend/.venv`）：
SQLite 分支只用 Python stdlib，不要求在宿主机装 `sqlite3` CLI；PG 分支需要 `pg_dump`，
届时由承载它的镜像提供——不是让运维去目标机上装工具。

### 6.2 按后端分派

| 后端 | 手段 | 自检 |
| --- | --- | --- |
| SQLite（当前唯一在跑的） | `VACUUM INTO` 到新文件 | 能打开 + `PRAGMA integrity_check` = `ok` + 读得到 `alembic_version` |
| PostgreSQL（预留，下一版） | `pg_dump` 自定义格式（`-Fc`） | 归档可列出（`pg_restore --list`） |

现在只有 SQLite 分支会真的跑。PG 分支先写好的理由：**换库那天备份链不能断**，
而备份脚本的重写往往发生在最不该动它的时刻（迁移前夜）。

为什么不能 `cp`：开了 WAL，直接复制会静默丢掉最近几分钟的写入——文件看起来是完整的，
打开也不报错，只是少数据。

### 6.3 备份纪律

- **迁移之前必须先有备份**，备份没做成不许 `docker compose up`；
- **删列与改类型后的回滚方式是恢复备份，不是 `git revert`**：回退代码后的真实状态是
  「新结构 + 旧代码」，旧代码读不到那一列，启动即失败；
- 备份产物要能**在另一台机器上**被服务读起来，这才叫备份（`../v7/ARCHITECTURE.md` §8.5 的
  恢复演练要求，原样成立）。

## 7. 契约

| # | 契约 | 破了会怎样 |
| --- | --- | --- |
| **C-V9-1** | 宿主只发布 `80`；`api` 的 `8000` 只 `expose` 不 `ports` | v7 的「后端只听回环」退化成「后端直接对外」，CORS 与 Cookie 行为随之改变 |
| **C-V9-2** | `api` 副本恒为 1，`--workers 1` 写死在镜像 `CMD`，不提供覆盖 | 任务与 SSE 分属不同进程，客户端永远等不到输出 |
| **C-V9-3** | 数据、密钥、日志**必须是命名卷**，禁止 bind mount 宿主目录 | 随机 `disk I/O error`、静默丢最近写入，Windows 上必现 |
| **C-V9-4** | 迁移只在 `lifespan` 里跑一次，启动脚本不跑迁移 | 两个入口各跑一次，迁移日志与锁行为都不可预测 |
| **C-V9-5** | 技能包打进镜像，不挂载；`PRDWRIGHT_SKILLS_STRICT=true` | 镜像与技能包版本可能不一致，就绪探针失去意义 |
| **C-V9-6** | 主密钥缺失即拒绝启动，绝不自动生成 | 换机器时旧密文永久解不开，且当场无人发现 |
| **C-V9-7** | `/health` 语义不变（恒 200）；探针一律用 `/healthz` / `/readyz` | 可降级状态被当成故障，容器被反复重启 |
| **C-V9-8** | 排空窗口 30 秒；超时的在途任务落「已取消」终态，不留 `running` | 每次重启都留尸体，只能等下一条启动的 `reap_orphans` 收尾 |
| **C-V9-9** | 备份按后端分派，产物必须有 `sha256` 且自检通过 | 「备份完成」变成一句没有证据的话 |
| **C-V9-10** | CI 只构建镜像，不推送；tag 用 `git describe` | 没有凭据通道的推送会把 CI 变成不可复现的猜谜 |

## 8. 取舍与风险

### 8.1 接受的风险

| 风险 | 为什么接受 | 缓解 |
| --- | --- | --- |
| 单副本 → 重启必然中断在途任务 | 多副本要先外置 `_RUNTIMES` / `JobBus`，那是另一版的工作 | 排空 + `stop_grace_period` 大于 30 秒（C-V9-8） |
| 命名卷不能直接双击查看 | 它是 SQLite 在 Windows 上不坏的**唯一**做法 | 备份产物落宿主目录，可见性由它补上 |
| 镜像体积（含 langchain 全家桶） | 多阶段构建已把构建工具剥掉 | 只装 `--no-dev`；必要时按协议拆镜像 |
| 容器内时区是 UTC | 项目本来就按 UTC 存（`backend/src/backend/core/clock.py`） | 显式 `TZ=UTC`，不继承宿主机 |
| 就绪探针不覆盖「模型供应商配置是否可用」 | 依赖外部网络，探针高频触发会烧额度、会误报 | 留给 `/health` 三项体检与人工判断 |
| 容器冒烟不跑业务链路 | 登录 → 生成的端到端在 CI 上不稳定（真模型调用） | 冒烟覆盖「可达」，业务链路由既有 1000+ 用例守 |

### 8.2 否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 单容器塞 Nginx + uvicorn（supervisord） | 重启 Nginx 会杀掉生成任务；两个进程的失败语义不同 |
| 三个容器（再加一个 DB 容器） | 本期数据库仍是文件库，独立 DB 容器没有对象；换库时它才成为第三个服务 |
| Windows 专用 compose + 宿主目录挂载 | bind mount 在 Windows 上是语义问题不是配置问题；两份编排会让「哪些目录要持久化」写两遍 |
| 技能包挂载进容器 | 让「镜像与技能包版本不一致」成为可能，而这正是就绪探针要保证的事 |
| 用 `/health` 当 `healthcheck` | 恒 200，等于没配；技能包缺失时会把还能用的容器反复踢掉 |
| 自动生成主密钥 | 换机时旧密文永久解不开，且没人会发现 |
| 容器里跑两个前端 dev server / 热重载 | 开发体验不如本机；容器只承载部署形态 |
| 系统级 `sqlite3` / `pg_dump` CLI 做备份 | 多一个「目标机上装没装」的变量；用项目自己的 venv，脚本还能顺手做自检 |

**风险登记**

| 风险 | 缓解 |
| --- | --- |
| 排空窗口不够长，任务被硬杀 | `stop_grace_period` 大于 30 秒；实测一条真实长任务校准（见 `roadmap.md` 附录） |
| 就绪探针漏挂白名单 → 容器永远不健康 | 探针端点与白名单在同一个提交里改，用例钉住「未登录访问返回 200/503 而不是 401」 |
| 主密钥路径没进进程环境 | 启动即失败并给出下一步命令（C-V9-6），而不是降级到「未配置密钥」继续跑 |
| 卷被 `docker compose down -v` 删掉 | 文档把 `-v` 标为危险命令；备份产物在宿主目录，不在卷里 |

## 9. 与 v8 / v7 的关系

**不推翻 v7 的任一运维结论**，只换执行方式：

| v7 的做法 | v9 的做法 | 为什么不变 |
| --- | --- | --- |
| 单域名 + 路径前缀（`/`、`/admin/`、`/api/`） | 不变 | Cookie 是 host-only，跨子域会「登录了但调 API 401」 |
| 单 worker 硬约束 | 不变，且写死在镜像 `CMD` 里 | `_RUNTIMES` / `JobBus` / runtime 快照 / 连接池都在进程内 |
| 四目录分离（代码 / 数据 / 静态 / 日志） | 映射成三个命名卷 + 镜像内只读代码 | 「回滚代码」与「保住数据」仍必须是两个动作 |
| 回滚 = 恢复备份 | 不变，追加「回滚镜像 tag」 | 迁移只追加，回退代码后的真实状态是「新结构 + 旧代码」 |
| `VACUUM INTO` 备份（+自检） | 不变，产物移出卷、改为按后端分派 | 开了 WAL，`cp` 会静默缺最近写入 |
| SSE 三行 + `: ping` 心跳 | 不变，反代多一跳 | 分章生成与审核之间有长静默期 |
| 重启 = 跑迁移 | 不变（`lifespan` 里 `prepare_schema`） | 容器重启同样是「新进程 + 旧库」 |

**不碰 v8 的方言结论**：`core/dialect.py` 的收敛、`C-D1~C-D6` 契约、结构对拍保留 `PRAGMA`
这些都在 `../v8/ARCHITECTURE.md` 里原样成立。本版只把备份脚本写成「按后端分派」的形状，
作为下一版接 PostgreSQL 的接缝。

**容器的一切归 v9**：v8 不再讲容器形态、镜像、卷与探针；本层是仓库里唯一一处讲它们的地方。
