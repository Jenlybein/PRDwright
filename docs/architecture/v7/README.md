> ⚠️ **T17.1 排在部署之前**，不是排错了顺序：`warmup()` 现在只被测试调用
> （`tests/test_engine.py`），生产启动路径里没有它，而 `max_overflow=0` 意味着
> 运行期**不会**再新建连接——池子只有启动时借到的那几条。这个洞必须在第一次对外服务
> 之前补上，否则部署完再改就要重走一遍发布。理由见 ADR-084。

> 若 T17.6 尚未完成就要重启服务，至少手工执行一次 `VACUUM INTO`。

## 已拍板的决策（详见 `ADR.md`）

| # | 当时的选项 | 决定 | 记录 |
| --- | --- | --- | --- |
| 1 | 两个前端怎么对外：① 同域 + `/admin/` 路径；② 两个子域；③ 两个独立域 | **取 ①**。会话 Cookie 没有 `domain` 属性（host-only），跨子域会「后台登录了、调 API 仍 401」；同域则 CORS 完全不参与、Cookie 天然共享 | ADR-054 |
| 2 | 起几个进程：① 多 worker 容错；② 单 worker | **取 ②，且写死为硬约束**。`_RUNTIMES` / `JobBus` / runtime_config 5 秒快照 / SQLAlchemy 固定连接池都在进程内；不引 gunicorn | ADR-055 |
| 3 | 目录怎么摆：① 全留在 clone 出来的那棵树里；② 代码 / 数据 / 静态 / 日志四目录分离 | **取 ②**。混在一起会让「回滚代码」和「保住数据」变成同一个动作的两半 | ADR-056 |
| 4 | 回滚怎么做：① 反向迁移；② 恢复备份 | **取 ②**。迁移纪律是「只追加」，回退代码后的真实状态是「新结构 + 旧代码」 | ADR-057 |
| 5 | 数据库怎么备份：① `cp` 数据文件；② SQLite 在线备份 | **取 ②**（`VACUUM INTO`）。开了 WAL，`cp` 会静默缺最近几分钟写入；备份产物必须**自检**（能打开、`integrity_check`、有 `alembic_version`） | ADR-058 |
| 6 | SSE 保活：① 只放宽 Nginx 超时；② 长超时 + 服务端心跳 | **取 ②，且心跳从「可选」升为必做**。分章生成 + 审核 + 改写之间有长静默期，中间网关会按空闲超时静默断流 | ADR-059 |
| 7 | 连接池怎么预热：① 靠第一次请求懒建；② 启动期单线程建满 | **取 ②**。`max_overflow=0` 下池满即超时，而懒建会把「多线程首次映射 WAL `-shm`」的竞态请回来 | ADR-084 |

| 9 | 静态产物在哪构建：① 服务器上构建；② CI 构建后下载产物 | **取 ①**（本期）。没有制品库与构建机；串行构建 + 限制 Node 堆已足够，代价换成「发布窗口变长」 | ADR-086 |

## 与 v6 的关系

v7 **不改** v6 已定型的任何业务能力与数据层契约：生成链路、文档所有权与版本链、
管理员后台、日志子系统、运行时配置与密钥管理、仓库层「不碰事务边界」、
`session_scope()` 是唯一事务落点（ADR-073 ~ 083 继续有效）。

v7 的后端改动只有四处，且都是「部署前必须做」而不是「顺手做」：

1. `lifespan` 在 `prepare_schema()` 之后、开始接请求之前调 `engine.warmup()`（ADR-084）；
2. 公开的四条文档路由不注册，接口文档搬到 `/api/admin/{docs,redoc,openapi.json}`
   并逐条挂 `require_admin`（ADR-085）；
3. SSE 生成器加 `: ping` 心跳帧（ADR-059 修订）；
4. `frontend_admin` 两处构建配置（Vite `base: '/admin/'` + `createWebHistory(BASE_URL)`，✅ 已落地，ADR-054）；

管理端另加一页「接口文档」（`views/ApiDocsView.vue`，两个按钮打开上面两个 HTML 页）。
其余全是新增：`scripts/deploy/` 下的四个脚本、`deploy/backend.env.example` 模板。

## 与仓库外那份 v5 部署素材的关系

v5 时期那批部署文档**从未落盘**（`git log` 零命中，见 `../v5/ADR.md` 的 ADR-070），
唯一副本在仓库外（`C:\Users\Jen\Desktop\v5\`，四份：README / ARCHITECTURE / ADR / roadmap）。
v7 是**参考它的结构、按 v6 之后的实际重判**，不是照抄。被明确推翻或补强的几处：

| v5 素材的写法 | v7 的结论 | 原因 |
| --- | --- | --- |
| `lifespan` 里 `init_schema()` + `run_migrations()`（`user_version` 20 步链） | `prepare_schema()` + Alembic，三条分支，**旧库拒绝启动** | v6 换数据层（ADR-076 / 083），旧链已整体删除 |
| 内存态清单里的 `core/db.py`、444 行自建池 | `core/engine.py` 的 SQLAlchemy 固定池（`pool_size=4`、`max_overflow=0`） | v6 / T16.12 删除旧池 |
| 备份只说「用 `VACUUM INTO`，不能 `cp`」 | 追加三条：备份产物必须**自检**、必须记下 `alembic_version`、**恢复后第一次启动会再跑一次 upgrade** | 迁移链换了之后，「备份能不能配得上当前代码」成为新的失败模式 |
| SSE 心跳列为「可选」 | **升为必做** | 分章生成 + 审核 + 改写的静默期可长达数分钟，1800 秒 read_timeout 只解决我们自己那一跳 |
| 只写「重启 = 跑迁移」 | 追加「`stamp` 分支会先做结构对拍，需要可写的临时目录」 | `core/schema.py::_models_snapshot` 会建临时库；`PrivateTmp=yes` 与 `ProtectSystem=strict` 必须一起配 |
| 依赖 `sqlite3` CLI 备份 | 备份脚本用 Python（`sqlite3` stdlib） | 少一个「目标机上有没有装 sqlite3」的变量，且脚本能顺手做自检 |
| 部署项清单里没有 `LOG_DIR` / `AUTH_COOKIE_SECURE` / `PRDWRIGHT_MASTER_KEY_PATH` 的模板 | 新增 `deploy/backend.env.example`，逐项带生产值 | 现在 `backend/.env.example` 只列了一部分，照它配会漏掉「数据库与日志落回代码目录」这两个坑 |

反过来，v5 素材里**继续成立**的结论也一并保留：单域名 + 路径前缀、单 worker、
四目录分离、回滚 = 恢复备份、`VACUUM INTO`、Nginx 三行 SSE 配置、管理端挂 `/admin/`
的两处改动。逐条对照见 `roadmap.md` 末尾。

## 读完你会知道的三件反直觉的事

1. **`warmup()` 是承重的，而且曾经没人调它。** `max_overflow=0` 的设计前提是
   「连接只在启动期建满」，少了这一步，池子实际只会建到被同时用到的那一两条——
   而那一次「同时建」正好落在启动期的「主线程 vs `log-store` 线程」上，正是 T15 那个
   `SQLITE_READONLY` 竞态想躲开的东西。v7 把它接进了 `lifespan`，并用一条用例钉住
   （ADR-084）。**意外收获**：修的过程中发现 `engine_stats().idle` 原来是拿
   `maxsize - in_use` 算的，恒等于池容量；不修这个，任何「池子建满了没有」的断言都是假的。

2. **备份做成了 ≠ 能恢复。** 因为迁移随重启自动跑，「恢复备份」之后的第一次启动会
   再执行一次 `upgrade head`；如果备份里的 `alembic_version` 比代码新，启动会**报错**，
   比备份旧则会自动补。所以恢复演练必须用**当前代码**跑一遍，而不是用备份那天的代码。

3. **`/health` 恒返回 200。** 它的 `status` 只有 `ok` / `degraded` 两档，用来区分
   「能不能用」而不是「进程活没活」。把它当存活探针配成「非 200 就重启」，
   会在技能包缺失时把还能用的容器反复踢掉（`api/health.py` 的 docstring 写明了这一点）。
