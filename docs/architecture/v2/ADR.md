## ADR-001：会话状态的唯一真相放在后端数据库

**状态**：Accepted（已落地，P1 实施）

### Context

当前同一份会话状态存在两个地方：后端 `ConversationService._conversations` 的内存 dict（进程重启即丢），前端浏览器里的会话快照（刷新后靠它恢复）。两边靠「前端回传完整 history」缝合，靠匹配中文错误串 `会话不存在` 触发降级重试。

后果：改一次后端代码（`--reload`）会话就丢，调试 PRD 生成要重填问卷；无法跨设备；无法回溯历史会话；后端改一个字就能让前端降级逻辑静默失效。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 后端 DB 为唯一真相** | 语义清晰、可回溯、可跨设备、为登录预留 owner 维度 | 需要引入 Repository 与迁移；前端恢复逻辑要重写 |
| B. 前端为唯一真相（后端纯无状态） | 后端极简，天然支持多实例 | 历史随浏览器清理丢失；无法多端；长会话每次全量回传，token 成本高 |
| C. 维持现状双写 | 不用改 | 问题一个没解决，且会随功能增加而恶化 |

### Decision

**选 A。后端数据库是会话与文档的唯一权威来源。**

配套规则：
- 前端传入的 `history` **仅在会话不存在时**作为恢复来源，不作为覆盖依据。
- `continue-stream` 的响应 `data` 里回传 `history_source`（`server` / `client`），让前端明确知道这一轮用的是哪份历史。
- 浏览器本地快照降级为**离线草稿**：后端不可达时才展示，且明确标注。

### Consequences

- 变容易：回溯历史会话、跨设备、重启保活、按 owner 隔离。
- 变困难：`continue-stream` 需要多一次 DB 读取；需要处理「前端快照与后端不一致」的冲突（策略：以后端为准，提示用户）。
- 中立：无状态模式保留为兼容能力，不再是主路径。

## ADR-002：持久化用 SQLite 起步，通过 Repository 隔离

**状态**：Accepted（2026-10-13 已落地，首用于认证；P1 扩展至方案持久化）

### Context

需要持久化，但当前是单人本地开发，未来也只是「少量人使用」。选型的真实约束是**运维成本**，不是吞吐上限。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. SQLite 单文件 + Repository 抽象** | 零运维、备份就是拷文件、Python 标准库自带 | 并发写能力弱；将来切 Postgres 需迁移 |
| B. 直接上 Postgres | 一步到位，无迁移成本 | 本地开发要起容器/服务，拖慢 P0-P2 的迭代；当前负载完全用不上 |
| C. 文件（JSON per session） | 最简单 | 无查询能力，「会话列表」需求一出现就崩 |

### Decision

**选 A。** 服务层只依赖 Repository 协议（`UserRepository` / `AuthSessionRepository` / `InviteCodeRepository`
已落地；P1 再补 `SolutionRepository`），具体实现默认 SQLite。开启 `journal_mode=WAL`。

落地情况（2026-10-13）：`core/db.py` 负责连接与建表，`repositories/` 是**全项目唯一出现 SQL 的地方**，
服务层与路由层一律不得 import `sqlite3`。这条约束靠 review 与目录约定维持。

### Consequences

- 变容易：本地开发零依赖；备份与调试直观。
- 变困难：真正的多用户并发写场景需要评估（少量人场景应无压力）。
- 中立：切换到 Postgres 的成本被 Repository 限制在一个文件内；**前提是业务代码不得出现任何 SQL 或 sqlite3 import**。

## ADR-003：前端状态承载选 Pinia，但真正的解耦靠状态机外置

**状态**：Accepted（已实施：`stores/workflow.ts` 状态机 + `stores/auth.ts` 登录态）

### Context

`App.vue` 1305 行里，状态（三份文档、消息、会话 ID、流式缓冲、错误提示）与逻辑（状态机、持久化、生成流程）混在一起。拆分的收益主要来自**逻辑外置**，而不是「换成某个状态管理库」——如果只是把 `ref` 搬进 store，巨石问题依然存在。

`pinia` 已在 `package.json` 里但从未使用。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. Pinia store** | 依赖已装、有 devtools、跨视图共享天然、易测、可做持久化插件 | 多一层概念；团队需熟悉 |
| B. `useSession()` composable + provide/inject | 更轻、无额外依赖、Vue 原生 | 跨组件调试体验差；多个组件实例时作用域易踩坑 |
| C. 维持组件内 ref | 不用改 | 巨石问题不解决 |

### Decision

**选 A，但顺序很重要**：先做 `workflow.ts` 把状态机抽成纯函数并配单测（这一步贡献 80% 的收益），再让 Pinia store 只做**状态容器 + 调用 workflow 的纯函数**。store 里不写流程判断。

若实践中觉得 Pinia 过重，退回方案 B 的成本很低——因为逻辑已经在 `workflow.ts` 里，与状态容器解耦。

### Consequences

- 变容易：跨视图共享、devtools 调试、状态机单测。
- 变困难：多一层文件；需要约定「store 不放业务逻辑」并靠 review 维持。
- 中立：`vue-router` 的取舍与本文无关，单独见 ADR-006（2026-10-13 已修订为「引入，但只做页面级导航」）。

## ADR-004：长文档按章节生成，但保留整篇模式的开关

**状态**：Partially Implemented（分章节生成已落地 `prd_section_writer.py`；断点续传待 R1-T2）

### Context

PRD 生成目前是一次 `astream` 出整篇。默认 `ark_max_tokens=4096`（`core/config.py` 注释已自认会截断长文），一旦网络中断或被截断，整篇作废，只能从头再来。

需要说清楚的一件事：**分章节的主要收益是可靠性，不是省钱**——每一节都要重复携带背景上下文，token 总量通常不降反升。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 分章节生成 + 整篇开关** | 单节失败只重试单节；可断点续传；不受单次 max_tokens 限制 | 章节间口径可能不一致；总 token 可能上升；需要组装逻辑 |
| B. 只做整篇，但把 max_tokens 调大 | 改动最小、文气连贯 | 中断仍全废；超长上下文质量衰减；单次失败成本极高 |
| C. 生成后自动检测截断并续写 | 改动介于两者之间 | 「续写拼接」的语义边界难保证，容易接出半句话 |

### Decision

**选 A。** 按 `field-schema.json` 的章节拆成 N 次调用，中间产物落 `documents.sections`，支持断点续传。**同时保留整篇模式**作为配置开关（默认先用整篇，P3 期间 A/B 对比后再决定默认切换）。

配套：`max_tokens` 按文档类型分档配置，PRD 用大值、澄清对话用小值。

### Consequences

- 变容易：可重试、可续传、不再怕长文截断。
- 变困难：需要章节组装与一致性校验；成本可能上升，必须配合 ADR 里的成本计量（P3-T5）观察实际数字。
- 风险：章节间口径不一致。**缓解**：生成后续章节时把已生成章节的标题与关键结论作为上下文传入；上线前用同一份问卷跑两种模式人工比对。

## ADR-005：现在就把 `user_id` 埋进 schema，但不做鉴权

**状态**：Superseded by ADR-007 / ADR-009（原决策已于 2026-10-13 修订，见文末）

### Context

你已明确：终局会有简单登录系统供少量人使用，但**功能开发完成后才做**。若现在不预留，P4 加登录时要改表、改所有查询、迁移数据——那就从「填坑」变成「重构」了。

### Decision

- P1 建表时 `conversations.user_id` 即存在，**允许 NULL**，当前全部写 NULL，不影响任何现有流程。
- Repository 的查询方法**现在就接受可选的 `owner_id` 参数**（传 None 表示不过滤），但不在路由层暴露。
- **不做**任何登录、会话、中间件、密码存储相关代码。

### Consequences

- 变容易：P4 只需「填上 user_id + 在路由层注入当前用户」，零 schema 变更、零数据迁移。
- 变困难：schema 里有一个当前恒为 NULL 的列，需要一个注释说明它为何存在（否则后来者会以为是遗留字段而删掉）。
- 中立：这是典型的「为可逆性多花一点点」，成本接近于零。

### 修订（2026-10-13）：插槽被提前兑现，`user_id` 改为 NOT NULL

原先「P4 才做登录、期间 `user_id` 恒为 NULL」的安排已被推翻：**登录提前到持久化之前实施**
（顺序变更见 `../v3/roadmap.md` 第四节）。于是：

- 建表时不再需要「先留 NULL、日后回填」这一步。持久化落地即 `user_id NOT NULL`，
  外键指向 `users(id)`；**没有任何历史 NULL 数据需要迁移**（当前尚无持久数据）。
- 「预留插槽」的收益没有兑现，但也**没有变成损失**——它让登录与持久化的顺序可以自由调换
  而不产生返工，这正是当初埋插槽的价值所在。

原决策的其余部分（Repository 接受 `owner_id` 参数）继续有效，并在 ADR-009 中升级为
**强制过滤**而非「可选过滤」。

## ADR-006：不引入 vue-router，阶段流转用状态机而非 URL

**状态**：Amended（2026-10-13 修订：保留并启用 router，但仅用于页面级导航）

### Context

`vue-router` 已在 `package.json` 里但从未使用。当前是 Wizard 形态（问卷 → 对话 → PRD → 接口文档 → 提示词），9 个 `ViewState` 由 `App.vue` 内的状态机驱动。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 维持状态机，不用 router** | 契合 Wizard 线性推进；非法状态（无 PRD 却跳到接口文档）在状态机里天然被拦 | 无法分享/收藏到具体步骤的链接 |
| B. 引入 router，阶段 URL 化 | 可 deep link、可前进后退 | 必须处理「直接访问中间步骤但数据不存在」的非法态；刷新后需要先恢复数据再路由，复杂度转移到别处 |

### Decision

**选 A，维持现状。** 刷新恢复问题由 P1 的后端恢复接决（按 `conversation_id` 拉回完整状态），不依赖 URL。

### Consequences

- 变容易：非法状态在状态机一处收口（`workflow.ts` 可单测）；不用处理路由守卫与数据竞态。
- 变困难：将来若要「分享某个会话链接」或「多标签页独立流程」，需要重新评估——届时引入 router 的成本主要在把状态机映射到路由守卫，可控。
### 修订（2026-10-13）：引入 router，但只做页面级导航，阶段流转仍用状态机

原决策里的**行动项作废**（`vue-router` 保留并启用），但决策主体**依然成立**：

- 需要「打开某个已有方案」这一能力后，Wizard 之外出现了**第二个页面级入口**。
  若继续用 `viewState` 之外的布尔开关切换页面，`AppV2.vue` 会重新长成巨石。
- 因此引入 `vue-router`，但路由表只有**两条**：`/v2`（新建，尚无 id）、`/v2/:id`（打开某方案）。
  方案列表**不做独立页面**，而是常驻左侧边栏（顶部「新建任务」+ 下方列表）——
  列表是「工作台的一部分」而不是「另一个页面」，用户不该为了看一眼列表而离开正在做的事。
- **不变的是**：9 个 `ViewState` 的阶段流转**仍完全由 `workflow.ts` 状态机驱动，不映射到 URL**。
  用户不会看到 `/v2/xxx/chat` 这样的地址；刷新后一律按 `conversation_id` 从后端恢复数据，
  再由状态机决定展示哪个阶段，而不是试图从 URL 恢复到某个中间阶段。

一句话：**router 管「在哪一页」，状态机管「在这一页的哪一步」**，两者职责不重叠。

ADR-006 原有风险（直接访问中间步骤但数据不存在）因此**没有被引入**——URL 里从来不出现阶段。

## ADR-007：认证用服务端不透明会话 token + HttpOnly Cookie，不上 JWT

**状态**：Accepted（2026-10-13 已实施）

### Context

需要自建账号密码登录（少量人使用）。争议点只有一个：**会话凭据用无状态的 JWT，还是有状态的服务端 token**。

曾经考虑过 JWT，动机是「将来可能扩大用户范围」。但扩大用户范围真正带来的是**多实例部署**压力，
而当前连单机并发都不存在；为了一个尚未出现的约束提前引入密钥管理与吊销复杂度，是典型的过度设计。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 服务端不透明 token + 会话表 + HttpOnly Cookie** | 登出**即时失效**（删一行即可）；无签名密钥要管理；密码学攻击面小 | 每次请求多一次会话表读；多实例部署时会话表要共享 |
| B. JWT（无状态） | 无需查库，天然适配多实例 | 登出无法即时失效（要黑名单，等于又变回有状态）；密钥轮换复杂；当前无多实例需求 |
| C. 托管认证（邮箱 / 手机验证码） | 不用存密码 | 引入外部依赖与费用；本地开发必须联网；离线不可用 |

### Decision

**选 A，但把签发 / 校验 / 吊销封成 `TokenIssuer` 协议**（`issue` / `verify` / `revoke`），
当前实现是 `OpaqueSessionIssuer`。将来若真要换 JWT，只换一个实现类，业务代码零改动。

配套：
- 随机 token 用 `secrets.token_urlsafe(32)`，库里**只存 SHA-256**，不存明文——拖库也拿不到可用凭据。
- Cookie 设 `HttpOnly` + `SameSite=Lax` + `Path=/`；`Secure` 由 `AUTH_COOKIE_SECURE` 控制（本地 HTTP 开发默认关）。
- 密码用标准库 `hashlib.scrypt` + 每用户独立 salt，比对用 `hmac.compare_digest`；**零新增依赖**。
- 用户不存在时照常执行一次 dummy scrypt 再返回，抹平时序差异；登录失败统一文案「用户名或密码错误」，防账号枚举。
- 开放注册但需邀请码（`invite_codes` 表，支持 `max_uses` / `expires_at`）；核销走**单条原子 UPDATE**
  靠 `rowcount` 判定，防并发超发。注册顺序为「查重 → 核销邀请码 → 建号」，避免用户因重名白亏一次额度。

### Consequences

- 变容易：登出即时生效（已有测试覆盖：登出后偷回 cookie 仍 401）；无密钥轮换负担；`AUTH_ENABLED=false`
  时回落内置 dev 用户，保证 `user_id` 恒非空，将来开启鉴权**零迁移**。
- 变困难：每次请求一次会话表读（SQLite 本地读，成本可忽略）；横向扩展时会话表需共享——
  那正是换掉 `TokenIssuer` 实现的时机。
- 中立：不做角色权限体系。少量人场景，owner 过滤足够（见 ADR-009）。

## ADR-008：接口可见性用「默认拒绝 + 白名单」中间件，而不是逐接口挂依赖

**状态**：Accepted（2026-10-13 已实施）

### Context

需要一个「哪些接口要登录」的规则。**逐个接口挂 `Depends(get_current_user)` 的写法，漏一个就是裸奔，
而且没有任何机制能发现漏了**——接口越多，review 越容易疲劳，风险单调上升。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 中间件默认拦截 + 白名单** | 新增接口**自动受保护**；漏保护在结构上不可能发生 | 白名单是唯一改动点，放开接口必须显式改它 |
| B. 逐接口 `Depends` | 意图显式，读代码即知 | 漏挂即裸奔且无法自动检测；接口变多后 review 必然疲劳 |
| C. 路由前缀分组（`/api/public` vs `/api/private`） | 结构清晰 | 现有路径已定型，改名成本高；且仍依赖开发者放对位置 |

### Decision

**选 A。** 中间件必须用**纯 ASGI** 实现，不能用 `BaseHTTPMiddleware`——后者会把下游响应体重新包装成
`StreamingResponse`，而本项目有 6 条 SSE 流式接口（`/api/conversation/*-stream`），这是额外风险。
纯 ASGI 只在返回 401 时自己 `send` 两条消息，**放行时完全不碰响应体**。

配套约定（都是踩过坑才定下来的）：

- 白名单 = 精确路径集合（`/`、`/health`、`/api/conversation/questions`、`/docs`、`/redoc`、`/openapi.json`）
  + 前缀集合（`/api/auth`）。
- `OPTIONS` 预检**直接放行**：预检按规范不带凭据，拦它的表现是「接口凭空 401」，极难定位。
- 中间件注册顺序：`add_middleware(AuthMiddleware)` **在前**、`add_middleware(CORSMiddleware)` **在后**。
  Starlette 是「后加的在外层」，这样 CORS 才在最外层先应答预检。
- 中间件把用户写进 `scope["state"]["user"]`，路由层用 `request.state.user` 读。
- 前端 axios 加 `withCredentials: true`；**SSE 的 `fetch` 必须加 `credentials: 'same-origin'`**
  （`fetch` 默认不发 Cookie，漏了的表现是「普通接口没事、流式一直 401」）。
- 全局 401 拦截器**排除 `/api/auth/*` 前缀自身**：登录失败与 `me` 探测登录态都会正常返回 401，
  一并触发弹窗会导致「登录失败后又弹一次登录窗」。

**接口可见性分级**：
- 公开：`/health`、问卷配置、`/api/auth/*`。
- 需登录：**其余全部，包括 RAG 检索**（它返回的是团队内部接口规范资产，属内部资料，不应对匿名开放）。

**测试护栏**：遍历 `app.openapi()["paths"]`，断言任何非白名单路径未登录必须返回 401。
新增接口若忘了考虑鉴权，会被这条不变量测试直接拦下。

### Consequences

- 变容易：新增接口默认安全；可用性由测试保证，**不依赖 review 自觉**。
- 变困难：放开一个接口必须显式改白名单（这是刻意的摩擦）；排查 401 时第一直觉要想到白名单。
- 踩坑已固化：FastAPI 0.142 起 `app.routes` 里的 `include_router` 是惰性的 `_IncludedRouter`，
  **列路由必须用 `app.openapi()["paths"]`**，直接遍历 `app.routes` 看不到业务路由。

## ADR-009：方案持久化用「单表全量快照」，不拆 messages / documents 表

**状态**：Accepted（已落地，P1 实施）

### Context

原路线图 P1 计划建 `conversations` / `messages` / `documents` 三张表。但 V2 前端的状态模型本来就是
**一份全量快照** `SessionDataV2`（`viewState` / `entryMode` / `summary` / `messages` / `conversationId`
/ 四份文档内容）。拆表意味着每次自动保存都要做差集同步，而它带来的收益（按消息 / 文档粒度查询）
**当前没有任何需求用到**。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 单表 `solutions` 存全量 JSON + 冗余摘要列** | 保存就是一次 UPSERT，天然契合前端快照模型；防抖自动保存实现简单 | 无法按消息粒度查询统计；单行较大（一份 PRD 数十 KB） |
| B. 三表范式化 | 查询灵活，可做消息级统计 | 每次保存做差集同步；自动保存逻辑复杂；当前无查询需求 |
| C. 每方案一个 JSON 文件 | 最简单 | 无列表 / 排序 / 权限过滤能力，与「方案列表页」需求直接冲突 |

### Decision

**选 A。** `solutions(id, user_id NOT NULL 外键, title, mode, stage, data, created_at, updated_at)`，
其中 `data` 是整份 `SessionDataV2` 的 JSON 文本。

`title` / `mode` / `stage` 冗余成独立列，是为了**侧边栏列表不反序列化大 JSON** 就能渲染——
一份快照含三份文档正文，几十 KB 起步，列 20 条时差别很明显。这三个冗余列由前端随快照一起
提交（前端才理解 `product_name` 该从 `summary` 还是 `quickInput` 取），后端只做 trim 与长度校验；
后端**不解析 `data` 的内容**，保持「不透明快照」这个好处。

配套：
- 越权访问返回 **404 而非 403**——403 会泄露「这个资源确实存在」这一信息。
- 数据隔离**在 Repository 层强制 `owner_id` 过滤**，而不是靠每个路由记得检查：漏一次就是越权，
  不能把安全边界寄托在「每个写接口的人都记得」。Repository 方法**不接受 `owner_id=None`**，
  不给「不过滤」留逃生口。
- **方案「有内容了才建」**：快照的内容字段（`summary` / `messages` / `quickInput` /
  `debugPrdText` / 三份文档）任一非空时才 `POST` 创建，随后 `router.replace` 到 `/v2/{id}`；
  此后一律 `PUT`。因此保存天然分**创建 / 更新两条路径**（5 个接口而非 4 个）。
  代价是用户敲一个字就走会留下一项，靠侧边栏删除解决；收益是「填了半天刷新全丢」不会发生。
- **不改动 `conversation_service` 的内存 dict**：对话进行中的临时态仍在内存，只在用户保存 /
  进入下一阶段时落库，避免把流式生成的热路径绑上 DB 写。
- **列表不做独立页面**，改常驻左侧边栏（顶部「新建任务」+ 下方列表）。列表是工作台的一部分，
  不是另一个目的地。
- **顺带删掉** `stores/workflow.ts` 的 localStorage 快照：后端是唯一权威，留离线副本只会带来
  「恢复时该听谁的」的歧义。但它的快照校验与降级逻辑保留，改用于后端恢复。
- 接口前缀用 **`/api/solutions/*` 而非 `/api/session/*`**：引入登录后，「session」会和
  「登录会话（auth session）」语义撞车，两者是完全不同的东西。前端 service 文件同步命名
  `solutionService.ts`。

### Consequences

- 变容易：自动保存（防抖 UPSERT）实现直接；列表页查询轻量；权限只在一处强制。
- 变困难：将来若要「跨方案搜索某句话」需要扫描 JSON（届时再考虑 FTS5 或拆表）。
- 中立：单行体积可控——SQLite 单行上限远超需求，且少量人使用的场景下方案数量级有限。

## ADR-010：提示词归后端独占，前端只能「点名」场景，不能「递剧本」文本

**状态**：Accepted（2026-10-13 已实施）

### Context

提示词资产的分布极不对称：后端有 `services/prompts.py`（13 个模板）、`skills/prd-generator/**`
（4 份技能资源）、`core/question_config.json`；**前端只有 1 处**——`useClarificationChat.ts` 里的
澄清人设常量。

但这一处是通过 `system_prompt_override: str` 下发的，即**接口接受任意提示词文本**。三个后果：

1. **提示词成了公开 API 的一部分**：改一句措辞要动前端并重新部署，而它本质是后端的领域资产。
2. **同一份口径有两个家，必然漂移——并且已经真实发生**：前端人设写「每次只提 1-3 个问题」，
   后端开场白写「一次问 3-5 个」。开场白是对话里**最后、最具体**的一条 user 消息，实际把上限
   盖成了 5，表现为「首轮复述完理解后紧接一大串问题」。
3. **失败是静默的**：传错或传空会悄悄退回另一个人设，日志、响应里没有任何信号。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 后端注册表，前端零提示词** | 提示词只有一个家；改提示词不动前端；口径漂移在结构上不可能 | 前端无法临时换人设（当前无此需求） |
| B. 前端传 profile key，后端解析 | 保留「点名」能力，为多场景留门 | 仍是跨端契约（要处理拼错 key）；当前只有一个场景，字段是纯粹的负担 |
| C. 维持 `system_prompt_override` | 不改 | 问题一个不解决，且已经咬过人 |

### Decision

**选 A。** 对话类接口不再接受任何提示词参数，人设与开场白由后端按「对话档案」解析。

- 新增 `ConversationProfile`（frozen dataclass），把**系统人设 + 首轮开场白打包成同一个
  不可分割的对象**。它们是同一份口径的两半，必须一起改；打包之后由类型结构来保证，
  而不是靠人的记忆和 review。
- 注册表 `CONVERSATION_PROFILES` + `DEFAULT_CONVERSATION_PROFILE = "clarification"`。
  当前只有一个档案，但**保留注册表结构**：将来新增对话场景（如需求评审）只需登记一条，
  接口契约与前端都不必变动。
- **前端连 profile key 都不传**：对话接口在语义上只服务「澄清」这一件事，让前端再传一个
  恒为 `"clarification"` 的常量，只是把同一个默认值抄两遍（这也是否决 B 的核心理由）。
- 会话记录存 **profile key** 而非解析后的文本：改提示词对进行中的会话即时生效，库里也不会
  留下「冻结的旧人设」。代价是进行中的会话下一轮会换上新提示词——这正是想要的行为。
- 服务构造时先 `resolve_profile()` 校验一次：档案名写错在**启动阶段**就炸，而不是某次对话
  中途静默退回默认人设。
- `_build_lc_messages()` 的 `system_prompt` 参数**取消默认值**：忘记传时立刻 `TypeError`，
  而不是悄悄用上另一个人设（默认值是这类 bug 的温床）。

### Consequences

- 变容易：改提示词只动后端一个文件；「跨端口径漂移」这类 bug 从结构上消失；无状态重试不再
  需要前端补发人设，也不再存在「忘了补发 → 悄悄换人设」。
- 变困难：前端若真要临时换人设，得先在后端登记一个档案（当前无此需求，这是**有意的摩擦**）。
- 中立：接口从「客户端可配置」变成「后端决定」——但在单产品、自家前端的场景下，
  那份可配置性本来就没有消费者。
- **残留风险（已收口）**：`ChatStage.vue` 的副标题曾写作「每轮只问 1-2 个关键细节」，是同一份
  口径在 UI 层的副本。已改为不含数字的「AI 会追问关键细节，逐步澄清后再生成文档」——提问数量
  属于后端提示词的领域知识，用户可见文案不该复述具体数字，否则改上限又要手工同步。今后同类
  文案一律走「行为描述」而非「数值复述」。
- **测试护栏**（`backend/tests/test_conversation_prompt.py`）：断言 ① 同一档案内人设与开场白
  口径一致且不残留旧数字；② 两个请求模型不含提示词字段；③ **前端源码里搜不到任何提示词正文**
  （扫描 `frontend/src` 的全部 `.ts` / `.vue`，`__tests__` 除外——它需要引用片段做「不存在」断言）。
  以后谁把提示词写回前端，会被这条不变量测试直接拦下。

## ADR-011：生成前「双闸门」——先确认摘要、先检索再生成

**状态**：Accepted（2026-10-13 已落地，5766e7d）

### Context

PRD 生成之前，历史上直接拿「对话结果」去生成，带来两个隐患：

1. **对话理解可能跑偏，但用户看不到就直接生成了**：澄清对话产出一份「需求摘要」，若它与用户本意有偏差，下游三份文档会整体跑偏，且用户没有「在花钱生成前纠偏」的机会。
2. **接口文档生成缺乏依据**：PRD → 接口文档这一步，模型需要「团队内部的接口规范 / 约定」作为检索素材，但之前没有把这份资产接入生成链路，产出质量不稳定且不可控。

这两件事的本质是同一个决策：**「生成」不是一步动作，而是「先收敛输入、再消费输入」的两段式**。把收敛点显式化成闸门，用户能在每个闸门确认/勾选，而不是等产物出来才发现方向错了。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 双闸门（摘要 Diff + RAG 检索）** | 用户在「花钱生成前」纠偏；接口文档有可勾选的检索依据；每道闸门可独立测试 | 多两个前端面板（`SummaryDiffPanel` / `RagResultPanel`）+ 两个后端动作；流程状态机多两个节点 |
| B. 生成后整体审阅 | 改动最小 | 纠偏太晚——三份文档已生成，重来成本高；接口文档无依据 |
| C. 去掉摘要环节，直接生成 | 步骤最少 | 对话跑偏零兜底；与「用户体感最差的一环是生成不可靠」的目标相悖 |

### Decision

**选 A。** 在两处落闸：

- **闸门 1（摘要 Diff）**：澄清对话结束后，后端 `sync-summary-from-conversation` 产出结构化摘要；前端 `diffSummaries()` 把它与现有 `summary` 做 diff，经 `SummaryDiffPanel` **用户确认才回写**。回填失败 / 非法 JSON → 返回原摘要深拷贝，绝不弄丢用户已填需求。
- **闸门 2（RAG 检索）**：进入接口文档生成前，后端 `retrieve-api-docs-rag` 对 `core/api_doc_knowledge.json` 做**本地词法检索**（中文二元组 + TF-IDF 余弦，不依赖外部向量库），返回候选条目；前端 `RagResultPanel` 勾选后随生成请求下发，作为接口文档的依据。

配套约定：

- 两道闸门都**可跳过但默认呈现**——闸门是「确认点」而非「阻塞墙」，用户可一键接受默认。
- 检索是**本地词法**而非向量库：知识库体量小（单 JSON）、部署要零额外服务（ADR-002 的精神延伸），且避免引入 embedding 服务的运维负担。代价是召回精度弱于语义检索，但接口规范类文本词面命中率高，够用。
- `api_doc_knowledge.json` 因此成为**部署资产**（见路线图 R2-T8 / R3）：Docker 化时必须随镜像打包，否则检索静默失效。

### Consequences

- 变容易：生成方向在「花钱前」纠偏；接口文档有可追溯的依据；每道闸门有独立面板与状态，可单测。
- 变困难：流程状态机多两个节点（`workflow.ts` 的 `ViewState` 与 `STEP_OF_STATE` 需同步），且闸门 1 的「摘要回填」与闸门 2 的「检索勾选」都要在持久化快照里保存（否则刷新后闸门状态丢失）。
- 中立：闸门不改变「后端为唯一真相」的前提（ADR-001）——摘要与勾选结果最终都随方案快照落库。
- 风险点：若 `api_doc_knowledge.json` 缺失，检索会空手而归而非报错，接口文档质量悄悄下降。R2-T6/T8 通过「资源缺失显式告警 + 打包登记」收口。

## ADR-012：错误契约用「机器码 + 人类消息」，`code` 是唯一判据

**状态**：Accepted（2026-10-14 已落地，`7be5989`；R0-T5）

### Context

前端要靠**匹配后端返回的中文文案**来决定行为：

```ts
// frontend/src/composables/useClarificationChat.ts:128（改造前）
if (!conversationId.value || !message.includes('会话不存在')) throw error
```

这段判据有两个致命性质：

1. **静默失效**：后端只要把「会话不存在」改一个字，前端降级逻辑（清掉失效会话 ID 后无状态重试）就不再触发，用户直接卡死，**且没有任何测试会发现**——测试不会去改后端文案。
2. **来源被误判**：按表面看它像是在匹配 HTTP 响应的 `detail`，实测**该文案来自 HTTP 200 的 SSE 流内 `error` 事件**（`conversation_service.py:487` 的 `StreamEvent(type="error", ...)`）。只给 REST 响应加码**完全解决不了这条链路**。

同时后端错误有 **4 个产出来源**，只改一处会漏：`HTTPException` → `{"detail":...}`、`RequestValidationError`（422，`detail` 是列表）、中间件裸写的 ASGI JSON（`deps.py::_send_unauthorized`）、SSE `error` 事件。全仓库当时 grep `error_code` 零命中。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. `detail` 一字不改，并列新增 `code`** | 向后兼容：现有 93 个后端测试与前端 `readDetail()` 全部不受影响；`detail` 从此可随时改写而不影响逻辑 | 响应体多一个字段（冗余但无害） |
| B. 改成 `{"error": {"code":..,"message":..}}` 规范结构 | 结构上更"标准" | 推翻现有 93 个测试与前端读取逻辑，**收益与 A 相同**，纯破坏性 |
| C. 维持字符串匹配，只加测试 | 零改动 | 测试无法阻止后端改文案；契约仍然脆 |

### Decision

**选 A。**

- 响应体：`{"detail": <原文一字不改>, "code": "<UPPER_SNAKE_CASE>"}`；422 的 `detail` 仍保持 FastAPI 的列表结构。
- SSE `error` 事件：`code` 放在**顶层字段**（不塞进 `data`），`content` 仍是中文原文。
- 后端单一真源 `core/errors.py`（`ErrorCode` 8 个码 + `AppError` + `DEFAULT_STATUS` + `error_payload`）。放 `core/` 而非 `api/`，避免 services 反向依赖 api。
- **必须注册自定义异常处理器**：`HTTPException(detail={"detail":..,"code":..})` 会被 FastAPI 渲染成 `{"detail":{"detail":...}}` 嵌套结构，`register_error_handlers(app)` 是唯一能「一处保证所有错误响应都带 code」的做法。
- 前端单一真源 `services/errors.ts`（`BACKEND_ERROR_CODES` / `ApiError` / `isApiError` / `toErrorCode`）。**必须放独立模块**：`AppV2.spec.ts` 用 `vi.mock('../services/api', ...)` 整体替换 api 模块，若 `ApiError` 定义在 `api.ts` 里，`instanceof` 会抛 `TypeError`。
- 只定义 **8 个真正用得上的码**，不搞大而全枚举（错误码体系最容易膨胀成没人维护的摆设）。
- 已做对的部分**不动**：401 → `UnauthorizedError`、404 → `SolutionNotFoundError` 本就基于 HTTP 状态码，是正确的。

### Consequences

- 变容易：后端文案可随时改写（产品措辞调整不再牵动前端逻辑）；新增机器判据只需加码。
- 变困难：新增错误码必须**前后端同步**，否则不变量测试 `test_frontend_error_codes_match_backend`（正则解析 `errors.ts` 断言与后端枚举**双向严格相等**）立刻报红。这是刻意的——漂移应在 CI 暴露，而非运行时。
- 中立：框架级 404/405（如访问不存在的路径）仍无 `code`——为守住 8 个码的最小集合，未注册 `StarletteHTTPException` 兜底处理器。已知边界，接受。
- 防回退由 4 条不变量测试守护（每个错误响应带 `code`、前后端码值相等、前端源码禁中文串判断、`api/` 层禁裸 `HTTPException`），并用**变异测试**验证守卫不空转（删码 / 加裸 `HTTPException` / 加中文匹配 / 退回字符串判据 → 均正确报红）。

## ADR-013：流式编排收敛到 `stream_reply.py` 一处

**状态**：Accepted（2026-10-14 已落地，R0-T3）

### Context

「把模型流变成 SSE 事件」这件事在系统里有 **四份实现**（2026-10-14 实测）：

| # | 位置 | 规模 | 说明 |
| --- | --- | --- | --- |
| 1 | `conversation_service._stream_reply` | 366–408（44 行） | 带 `on_finish` 回调 |
| 2 | `document_service._stream_reply` | 626–668（48 行） | 无 `on_finish` |
| 3 | `prd_section_writer._error_event` | 775–786 | **第三份**「异常 → error 事件」转换，其注释自认「与 `document_service._stream_reply` 的口径一致」——**靠注释保证一致** |
| 4 | `conversation_service._extract_text` | 101–118 | 与 `llm_utils.extract_text`（21 行）**逐行相同**的副本 |

先前已抽出 `stream_guard.py::ensure_not_truncated`（截断检测），但**核心编排的重复没有消除**。三处「异常 → error 事件」各自维护的后果是：改错误码口径要改三处，漏一处则前端对同一种故障收到两种分类。

两份 `_stream_reply` 的差异仅三处：`on_finish`（conversation 用于回写历史，452/524 两处调用）、文本提取用哪个函数、截断检查放在 `_astream_text` 内还是内联（**两者都落在 `try` 内 → 语义等价**）。

> 附带更正：旧文档一度把「`conversation_service.py:366` / `document_service.py:626`」的**行号**当成行数，将本任务描述为「365 / 625 行的大手术」。真实规模约 90 行。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 新建 `services/stream_reply.py`，三处改为调用** | 单一实现；错误口径不可能漂移；`stream_guard.py` 保持只管截断检测 | 多一个模块 |
| B. 并入现有 `stream_guard.py` | 不新增文件 | `stream_guard` 的语义是「截断检测」，混入编排会让该文件失去单一职责 |
| C. 抽成基类/混入由两个 service 继承 | 不改调用点 | 引入继承只为复用一段函数，收益不抵复杂度；且两 service 并无真实 is-a 关系 |

### Decision

**选 A。** 新增 `services/stream_reply.py`，提供统一的事件流编排（`messages` / `status_text` / 可选 `on_finish` / `extra_data` / 错误码）与**唯一的**「异常 → error 事件」转换，供三个 service 复用；`stream_guard.py` 保持只管截断检测。

实施顺序是硬约束：**先写对照测试（`backend/tests/test_stream_reply.py`，用现有 `FakeLLM` 范式）钉死当前行为，再统一**。理由是两份 `_stream_reply` 当时**零直接单测**、`stream_guard` 无专属测试文件，只有 `test_prd_section_stream.py` 5 例覆盖分章节那条流——没有网不能动。

对照测试必须覆盖：事件序列 `status → chunk* → done`；异常 → `error` 事件（`code=LLM_UPSTREAM_ERROR`）**且之后不再发 `done`**；截断 → `error` 事件；`on_finish` 在 `done` 之前调用且**仅在成功时**调用；`extra_data` 透传进 `done.data`。conversation / document 两条路径参数化各跑一遍。

**不做**：不改事件序列、文案、错误码（对外契约零变化）；不合并 `_collect_reply`（语义是"收拢成整段文本"供审核解析 JSON，不是事件流）；不合并 `prd_section_writer._stream_text` / `_collect`（分章节有自己的 `stage`/`part` 语义，硬并会抹平差异）。

### Consequences

- 变容易：错误口径只有一处；加 `request_id` 打点（R2-T7）、加 token 计量（R1-T5）都有了唯一落点——这是本决策**最大的隐藏收益**。
- 变困难：统一实现的参数列表要同时满足三个调用方，若将来差异扩大需警惕「配置项膨胀」——届时宁可拆成两个具名函数，也不要往一个函数里堆开关。
- 中立：`document_service._collect_reply` 与 `prd_section_writer._collect` 保留为具名方法（语义是"收拢成整段文本"，不是事件流），但内部改为复用共享的 `collect_reply`，不再各自维护 `last_chunk` / 截断检查那段循环。

### 实施记录（2026-10-14）

- **先差分、后替换**：改动前用一次性脚本对旧实现与新实现跑了 **12 组场景**（正常多块 / 单块 / 截断 `length` 与 `max_tokens` / 空输出 / 中途异常 / 结构化列表分块 / 省略 `status_text`），比对逐事件的 `(type, content, data, code)`，**全部一致**后才删除旧代码（脚本已删除，不入库）。
- 删除：`conversation_service._stream_reply` / `_astream_text` / `_extract_text`、`document_service._stream_reply`、`prd_section_writer._error_event` 包装；6 处调用点改为直接调用共享函数。
- 新增 `backend/tests/test_stream_reply.py`（10 例）：事件序列、异常转 `error` 且不发 `done`、`on_finish` 仅成功时调用、结构化分块摊平、截断抛错、默认错误码；外加一条**源码扫描不变量**——`services/` 下（除 `stream_reply.py`）不许再出现 `async def _stream_reply` / `def _extract_text` / `def _astream_text`，防止重复悄悄复活。
- 回归：后端 **117**（107 + 10）、前端 **222**、`npm run build` 全绿。

## ADR-014：前端视觉走三层语义令牌，暗色只由 `<html class="dark">` 一处切换

**状态**：Accepted（2026-10-13 已落地 `1625e3c`，2026-10-14 补记；原提案见 `./archive/ui-redesign-plan.md`）

### Context

重构前全站靠**手写成对变体**表达暗色——`bg-white dark:bg-slate-900`、`text-slate-900 dark:text-slate-100` 之类共 400 余处。三个后果：

1. **漏一处就不可见**：侧栏方案标题曾出现 **1.2:1** 的对比度，等于隐形，而这件事没有任何测试会发现。
2. **对比度没有基线**：同样是「次要文字」，各处挑的灰不同；`slate-400` 在亮色下实测 **2.56:1**，远低于 WCAG AA 的 4.5:1。
3. **换主题等于全量回归**：改品牌色、加一套主题都要动 400 处。

此外还有两个与色板无关、但必须一起解决的问题：**跟随系统**要实时响应切换，**首帧不能闪白**（打包产物是异步加载的，等 Vue 起来再加类已经晚了一帧）。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 三层令牌（原始色阶 → 语义令牌 → 组件），暗色只换 L2 取值** | 组件不再知道「主题」的存在；对比度由一处保证；换主题只改一个文件 | 需要一次性把 400 处迁过来 |
| B. 保留 `dark:` 成对变体，只统一色板 | 零迁移成本 | 漏写风险原样保留；换主题仍需全量回归 |
| C. 运行时主题对象 / CSS-in-JS | 主题可任意组合 | 引入运行时开销与水合复杂度，收益不抵 |

### Decision

**选 A。** 三层分工写在 `frontend/src/index.css`：

- **L1 原始色阶**：`@theme` 里的 `--color-primary-50..950` 与圆角 / 阴影 / 缓动常量。**与主题无关**，任何主题下取值相同。
- **L2 语义令牌**：`@theme inline` 把 `--color-surface` / `--color-line` / `--color-muted` … 指向 `--ui-*` 变量；变量取值在 `:root`（亮）与 `.dark`（暗）两段**整体交换**。
- **L3 组件**：只写 `bg-surface` / `text-muted` 这类语义类。

三条隐式约束（破坏后**不报错、只静默失效**，因此写进了 `index.css` 的块注释）：

1. **`@theme inline` 的 `inline` 不能删**——它让工具类引用变量本身而非把值烤死在编译期，主题才能实时切换。
2. **`:root` 必须写在 `.dark` 之前**——两者选择器权重相同（0,1,0），靠书写顺序定胜负。
3. **`@theme` 块内保持零注释**——Tailwind v4 的解析器会把块内注释报成 `Invalid declaration: name`。

**主题状态的三个落点**：`composables/useTheme.ts`（模块级单例，唯一权威；此前这段逻辑散在 `SolutionSidebar` 里，登录前后、抽屉/桌面两套各持一份 `isDark`，出现过「按钮显示的状态」与 `<html>` 上的类不一致）、`ui/ThemeMenu.vue`、`index.html` 首帧内联脚本。**内联脚本与 `useTheme.readStoredMode` 共用 `theme` 键、解析规则必须同步改**；CSS 端只认 `<html class="dark">`。

**对比度基线写进令牌文件**：正文 / 次要 / 提示文字 ≥ 4.5:1，控件描边与图形 ≥ 3:1；禁用 `slate-400` 表达亮色正文、`slate-500` 表达暗色提示。

### Consequences

- 变容易：换主题只改 `index.css`；新组件天然拥有暗色，无需逐处适配。
- 变困难：`dark:` 从「默认做法」降级为**三类例外**——结构性判断、状态色 tint、模态遮罩。判断「这个颜色属于哪个语义令牌」成了新增视觉需求的第一步，不能随手挑色。
- 中立：`dark:` 目前仍有 **101 处 / 19 文件**残留（集中在 `SummaryDiffPanel` 11 处、`UiPageEditor` 与 `RequirementsForm` 各 6 处），属许可范围但是已知的未完成收敛项，留给 v3。

## ADR-015：交互控件收口到 `components/ui/`，底栏是全站唯一操作落点

**状态**：Accepted（2026-10-13 已落地：组件库 `08743c2`、底栏统一 `70ac82f`；2026-10-14 补记；2026-10-16 补记：内容行工具集与手改落库）

### Context

两个独立但同源的问题：

**控件各写各的**——12 处主按钮、10+ 处次按钮各自写一份样式；`AuthDialog` 手写 Teleport 与聚焦陷阱；保存提示 `flashSavedTip` 是内联药丸。改一个圆角要动十几处。

**操作散落**——主操作时而右对齐、时而整宽居中，次操作时而底部左侧、时而卡片头部右上，「清空 / 重新开始」更是四屏四个位置。用户每换一屏都要重新找「下一步该点哪」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 建 `ui/` 基础件 + 底栏作为唯一操作落点** | 视觉与交互各有单一落点；新增阶段不必重新设计操作区 | 底栏成为瓶颈，所有新操作都要挤进来 |
| B. 只建 `ui/`，操作仍各屏自管 | 改动小 | 「找不到下一步」的问题原样保留 |
| C. 引入第三方组件库（Element Plus / Naive UI） | 开箱即用 | 体积与设计语言不受控，且要覆盖已有 400 处样式，迁移成本反而更高 |

### Decision

**选 A。**

- **`components/ui/` 11 个基础件**：`AppButton` / `AppCard` / `AppIcon` / `AppBadge` / `AppDialog` / `AppToast` / `AppSpinner` / `AppEmpty` / `AppInput` / `AppActionBar` / `ThemeMenu`。
- **`AppActionBar.vue` 是全站唯一操作栏**，最多两行：
  - **内容行**（`#tools`，有内容才出现）：对「当前这份内容」做的事——文档工具（AI 优化 / 复制 / 下载）、对话输入框。
  - **流程行**（永远存在）：三段式且顺序不可变——`[破坏性] │ [返回 / 次操作 + 说明文字] ……… [主操作，永远最右且唯一]`。
  - 不合并成一行的理由：审阅页一行要塞 6 个按钮，对话页还要塞输入框，物理上放不下；分两行后每行职责单一、宽度稳定。
- **`DocumentReview.vue` 只渲染卡片、自带零控件**，通过 `defineExpose` 把能力交给底栏——「下载」的判据是「有正文」而不是「改过」。
- **吸底用 `fixed` 而不是 `sticky`**：`sticky` 的活动范围被包含块框住，滚到底时只能停在包含块底边，与窗口下缘裂出约 40px 的缝，正是「滚到底又不吸底」的观感来源。
- 底栏高度由 `ResizeObserver` 写进 `--shell-action-bar-h`，供 `<main>` 底部留白与窄屏浮动按钮避让读取（底栏最多两行、高度不固定，写死留白必然在某一头出错）。

### 实施现状（如实记录）

- 已接线：`AppButton` 在 **12** 处业务组件使用，`AppActionBar` 在 **12** 处使用。
- **未接线**：`AppDialog` / `AppToast` / `AppEmpty` / `AppInput` 目前**零外部引用**——`AuthDialog.vue` 仍手写 Teleport，表单输入仍是 `RequirementsForm` 自绘。组件库处于「已建、部分接线」状态，这四个是 v3 的收敛项。
- ⚠️ 底栏读子组件句柄有个坑：**模板 ref 在首次渲染之后才赋值**，首帧读到 null 要兜底；测试断言状态前必须 `await nextTick()`。

### Consequences

- 变容易：新增阶段不必重新设计操作区；改视觉改基础件即可。
- 变困难：「唯一落点」意味着任何新操作都必须进底栏，而两行是硬上限——超出时必须重新划分阶段，而不是加第三行。
- 中立：四个未接线的组件是已知债，不影响功能，但会让「改样式只改一处」的收益打折。

> **补记（2026-10-16）：内容行第三个工具由「保存」改为「下载」，手改正文改为自动防抖落库**
>
> 起因是一个「按钮点了没反应」的观感问题：审阅页的「保存」既不下载、平时也看不出它做了什么。查下去发现更实质的事——**当时根本不存在自动落库**：`documents.save(` 在生产代码里只有一个调用点，而它唯一的触发器就是这个按钮。store 里的防抖（800ms）/ 单飞 / `pending` / `changeEpoch` 记账早已写好并有测试覆盖，缺的只是「打字 → 入队」这一步。于是这次改动 90% 是接线。
>
> **不写新 ADR 的理由**：`stores/documents.ts` 开头就把「防抖 + 单飞」定为既定方案，本次只是**补上唯一缺失的触发点**，是既有决策的兑现；真正被改动的是本条 ADR 里「内容行工具集」与「『保存』判据」两句话，记回这里最连贯。
>
> 1. **按钮改名与数据源**：内容行第三个工具「保存」→「下载」，位置与外观不变（底栏内容行右端，紧邻「预览 / 编辑」）。载荷取**组件里的草稿**（`DocumentReview` 通过 `defineExpose` 交出的 `draftContent`）而不是 store 的工作副本——防抖窗口内工作副本还落后半拍，下载必须给出用户眼前这一版。完成页的下载仍读工作副本，两者共用 `utils/icons.ts` 的 `DOWNLOAD_ICON`，出口不同（一个是落库那一版、一个是当前草稿）。判据仍是「有正文」而非「改过」：空内容时 `downloadFile` 会静默返回，禁用态避免一次「点了没反应」的死点击。
> 2. **自动落库的触发与守卫**：`DocumentReview` 的草稿变化事件（`draftChange`，原名 `save`）驱动 `documents.save`，**逐次输入如实上报**、不在组件里自建第二层去抖。两道守卫：生成中不上报（可编辑区根本没渲染），草稿与 `props.content` 相等时不上报（那是父组件把权威正文同步下来，不是用户敲的）。守卫充分性依赖**注册顺序**——props 同步 watch 先于草稿 watch，同一 `pre` 队列按创建顺序执行，同步完再判等即恒成立；而 `documents.save` 会同步回写工作副本，使一次按键恰好一次上报，不会自激。
> 3. **静默，只在失败时提示**：成功不弹提示——每敲几秒弹一次会把界面淹没。失败由 `documents.saveError` 承载，`AppV2` 监听它闪一条**红色**药丸（`flashSavedTip` 增了 `variant`，图标随档位二选一；此前它只会渲染成功态的对勾，直接拿去报错是错的）。同一原因反复失败不重复闪，成功一次后再失败视为新问题重新提示。
> 4. **三处补冲未落库的草稿**：`solutions.openSolution()` 拉取文档之前、`beforeunload`、`onBeforeUnmount`。**顺带修掉一个既有缺陷**：`openSolution` 原先不冲文档队列，而 `loadAll` 会把未落库的 `pending` 盖在新方案的响应之上，防抖定时器随后把旧稿 PUT 到**新** `solutionId`——800ms 窗口内切换方案就会串稿。冲盘必须发生在 `loadAll` 之前，用的是此刻仍是旧值的 `solutionId`。
> 5. **阶段切换（`goTo`）不冲**：文档队列是 store 内部状态，不随组件卸载消失，切阶段没有丢稿风险；在那里冲等于每点一次进度条就多发一个 PUT。
> 6. **落库路径不变**：仍走 ADR-021 确立的唯一写入口（后端 `documents` 表 + `PUT /api/solutions/{id}/documents/{kind}`），前端新增的只是一条触发它的输入源。
>
> 已知残余风险（本期记录、不修）：一次旧稿 PUT 的在途时间若恰好跨越任务收尾（`finishDoc → setLocal`），旧稿可能盖回任务成果。该竞态在改动**前后概率相同**（今天「点保存后立刻点 AI 优化」同样会撞上），本次并未加剧它；彻底关闭需在 5 处 `job.start` 之前统一冲盘，回归面偏大，留待后续。



## ADR-016：不做运行时自动供应商切换，改为同供应商自愈

**状态**：Accepted（2026-10-15 裁决）

### Context

原架构把 R1-T4 定为「供应商 failover」：`llm_factory` 接受有序供应商列表，调用抛异常或超时就切下一个供应商重跑。动手前重新审视，发现三件与当初假设不同的事：

**一，三家密钥齐备，但齐备不构成必须自动切换的理由。** 自动切换买的是「供应商整体下线时仍能生成」这一份保险，它并不解决更常发生的故障——连接抖动、5xx、单次调用卡住。这些故障换供应商也要重跑一次，收益与「重试一次」几乎相同，代价却是一整套失败的抽象（还要多大模型命名、参数差异、切换次数上限）。

**二，我们原以为「没有超时、没有重试」，实测发现三家 SDK 一直在偷偷重试。** 默认都是 2 次：ark 见 `arkruntime/_constants.py:45`、anthropic 见 `ChatAnthropic.max_retries`、openai 透给 SDK 后见 `openai/_constants.py:8`。项目从未显式配置过这些值。**不知道重试在发生**，比没有重试更糟——偶发的一次调用偏慢无从解释，成本归因也天然缺一块。

**三，SDK 那层的重试边界是安全的，但对我们的归因不可见。** `openai/_base_client.py:885` 的 `_should_retry(self, response: httpx.Response)` 收的是 Response 对象，判定发生在「拿到响应」层；`stream=True` 时响应体尚未读取，一旦开始消费流，异常直接冒泡、不在重试循环里——等价于「只在首字之前重试」。三家同构，边界同款。但它内部的废弃尝试对本层不存在，账上只看到一次成功调用，这与 R1-T5 刚确立的「判定与记账同源」冲突。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 跨供应商自动 failover（原设计） | 供应商整体下线时仍能生成 | 引入「按 provider + model 建模」的复杂度；切换后成本归因要重建（T5 的 `RunMeter` 在任务开始时就把 provider 写死了）；`文本一半换个供应商接着写`的风险需要整节重跑语义去兜 |
| **B. 不切换，只做同供应商自愈并接管重试（推荐）** | 覆盖绝大多数真实故障；不需要新的供应商抽象；失败的尝试能被计量 | **单供应商故障期间不可生成**——接受这个敞口，兜底是手动冷切换 |
| C. 什么都不做，继续隐式依赖 SDK 默认 | 零成本 | 「不知道它在重试」的现状保留，归因继续偏乐观，且各家策略会随 SDK 升级漂移 |

### Decision

**选 B。** 一次调用生命周期上排三个守卫，全部 `.env` 可调：

1. **调用前预算检查**（T5 已有）。
2. **帧间隔超时** `LLM_TIMEOUT`：必须明确它是 inter-byte 语义—— httpx 的 read timeout 约束的是相邻两次数据之间的等待，一个每 59 秒吐一个字的模型能把单次调用无限拖下去。
3. **整次调用墙钟硬顶** `LLM_TOTAL_TIMEOUT`：由上一条推导出必须存在，用 `asyncio.timeout` 在 `stream_reply.astream_text` 里自己包一层。

**重试只在首字之前**（尚未 yield 过任何增量），判定用白名单：连接类异常、超时、5xx；`AppError`（含预算超顶）、4xx、以及内容性质的 `OutputTruncatedError` 一律不重试。这个边界有两条独立理由——**安全**（增量一旦交付给前端就撤不回，中途重来会重现 T0 时代「整章重复、表格单元格成对」的老症状）与**便宜**（首字前失败通常还没产出 output tokens，重来几乎不花钱）。

**重试由本层自管，三个适配器的 `max_retries` 显式设为 0。** 不是因为 SDK 的重试不安全，而是因为它看不见：接管之后废弃的尝试才能计入 `failed_calls`，回执上的数字才诚实。同时避免出现「SDK 2 次 × 自管 1 次」的叠加。

### Consequences

- **变容易**：单次调用有了确定性的失败上界，不再是「依赖各家 SDK 碰巧一致的 600 秒」；失败次数进了回执，排查「为什么这次偏慢」有据可查；整个方案不需要触碰供应商抽象，T5 落地那批代码一个字不用改（`RunMeter` 的 provider 不会因为不再换供应商而失真）。
- **变困难**：**单供应商故障期间不可生成**，这是显式接受的风险。兜底是手动冷切换 provider——但这条退路目前有个已知缺口：`.env.example` 未提示「换 provider 必须同时换 model」，误配会以「模型不存在」的形式在流式出口才炸，看不出是配置问题。本期不做修补，登记在 `v3/roadmap.md` 第八节。
- **中立**：原设计中「切换后整节重跑」的语义仍然有用，只是现在服务于同一供应商内的重试，而不是跨供应商切换。

## ADR-017：技能资源的加载策略——热重载、双向可见、可选 fail-fast

**状态**：Accepted（2026-10-15 裁决，随 R2-T6 落地）

### Context

PRD 生成的提示词资产（`skills/prd-generator` 下的模板、字段契约、写作规范）原先挂在一个 `@lru_cache` 上，**缓存到进程结束**：改一行 `prd-template.md` 必须重启后端才能生效。开发态每改一次模板就重启一次，而重启会把正在跑的生成任务一并废掉（`reap_orphans()` 把残留 running 全部置 failed）——两件事叠在一起，调提示词的成本远高于改提示词本身。

更隐蔽的是另一个默认行为：技能资源缺失时 `load_prd_skill_artifacts()` 返回 `None`，调用方**静默降级**到 `prompts.py` 的内置提示词。这意味着部署时漏打包 `skills/` 目录，服务照样起、PRD 照样出，只是章节结构与写作规范悄悄换了一套——而没有任何地方告诉你这件事发生了。**在流式的输出里，一次静默降级和一个正常结果长得一模一样。**

两个问题指向同一件事：**加载技能资源这件事对用户是不可见的**。热不热重载、降没降级，都没处看。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 保持 `lru_cache`，改模板就重启 | 零改动 | 开发与重启成本转嫁给用户；且不能解决静默降级 |
| B. 直接每次调用都读盘 | 最简单、绝不会有陈旧内容 | 一次 PRD 生成有十几次 LLM 调用，每次都重读同一批文件；文件不大所以真实开销有限，但白付 |
| **C. 按文件戳缓存 + 身份进回执 + 可选 fail-fast（推荐）** | 改完立刻生效、读了哪一套回执上看得到、生产可强制就位 | 多一层「文件戳比对」的判定逻辑；契约要多一个 `SkillRef` 结构化字段 |
| D. 启动时把资源读进内存并全部 fail-fast | 最快、最严格 | 开发态不能改；且 fail-fast 无开关会让本地没配 skills 的调试体验变差 |

### Decision

**选 C。**

1. **缓存键换成「修改时间 + 大小」** `（st_mtime_ns, st_size）`，而不是只有 mtime：编辑器在同一秒内连续保存时，秒级时间戳可能不变而字节数多半变了，双条件比单条件稳。**只有读成功才写缓存**，所以资源补齐后下一次调用立刻能读到，不需要额外失效机制。文件被删时连同缓存条目一起丢掉——「文件没了还在拿旧内容生成」是最坏的一种静默。
2. **每次 PRD 生成把技能身份写进回执**：`run_summary.injected_skills` 从恒空的字符串数组改成 `SkillRef{name, version, fingerprint}`，指纹是 `sha256(版本 + 各资源路径与内容)[:12]`。它同时解决了 `job_fingerprint.PRD_TEMPLATE_VERSION` 要求人工 +1 的脆弱性——改了模板指纹自己会变，不依赖人记得改版本号。
3. **缺失一律显式**：技能包不在位时 `describe_skill()` 返回 `None`，`run_summary.injected_skills` 为空数组，前端对 PRD 任务据此显示一条告警「未加载技能包，本次使用的是内置兜底提示词」。
4. **是否 fail-fast 交给部署决定**（`.env` 的 `PRDWRIGHT_SKILLS_STRICT`，默认 false）：本地没配 skills 也能起服务练手；部署环境设 true，启动时就把漏洞说出来。

### Consequences

- **变容易**：改模板即时生效，不必重启，也就不会顺手废掉正在跑的生成任务；回执上能回答「这份文档是按哪一套模板写的」；部署漏打包会在启动或回执上暴露，而不是藏在输出里。
- **变困难**：多了一个 process-level 的缓存字典需要理解（它不是 `lru_cache`，有显式的清空入口，测试里用它隔离）；`run_summary` 契约加了一个结构化字段类型，前后端契约要做一次同步。
- **中立**：仍然会有「读到正在保存的半截文件」的极小概率场景——编辑器写入不是原子的。重发一次生成即可，不做额外加锁：为这个概率引入锁机制，收益远小于复杂度。

## ADR-018：可观测性——日志带号靠格式化器，体检只报实情

**状态**：Accepted（2026-10-15 裁决，随 R2-T7 落地）

### Context

`request_id` 早在 R1-T5 就贯通了：中间件生成、`ContextVar` 传递、响应头回写、回执上展示并允许用户选中复制。**唯独日志里没有它。** 后端一直在用 `logging` 的默认兜底输出——没有时间戳、没有来源、没有请求号，出问题时只能按时间顺序猜「这几行属于哪一次生成」。同一个号出现在响应头上、却在日志里搜不到，追踪链断在最后一步，那个号也就白给了。

另一半是 `/health`：它只回 `{"status":"ok"}`。可「进程活着」和「东西能用」是两回事——数据库连不上、密钥没配、技能包文件丢了，这三种情况下它都会高兴地回 `ok`，而这三种恰好覆盖了「明明起着却用不了」的绝大多数场面。

三个具体取舍需要裁决：日志默认用什么格式、请求号怎么进日志、体检要不要发真实调用。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 日志只输出 JSON | 一条路，没有分支差异 | 本地开发读一屏 JSON 极其痛苦，而排查绝大多数发生在本地 |
| B. 日志只输出文本 | 可读性最好 | 生产上没法直接喂采集端，将来接日志系统要返工 |
| **C. 双格式，同一组字段（推荐）** | 本地读文本、线上喂 JSON；切换只改一个环境变量 | 两个格式化器要一起维护，**字段集必须保持同步** |
| D. 请求号由每个 `logger.xxx` 调用手写 `extra` | 显式、不依赖隐式上下文 | 将来新增一处日志就会漏一处，且漏了不报错、只是静默少一个字段 |
| **E. 请求号由格式化器从上下文变量现取（推荐）** | 业务代码零改动；加/改字段只发生在一个地方 | 隐式依赖 `ContextVar`，后台任务里取不取得到要理解上下文复制机制 |
| F. `/health` 发真实调用探活 | 能发现密钥过期、额度耗尽这类静态检查看不出的问题 | 探针高频触发会按次烧额度；网络抖动会把可用的服务判成不健康 |
| **G. `/health` 只校验配置就位（推荐）** | 零成本、零抖动 | 查不出「密钥在但已失效」，**必须在文案里说清这一点** |

### Decision

**日志取 C + E，体检取 G。**

1. **双格式、同一组字段**：`LOG_FORMAT` 取 `text`（默认，给人看）或 `json`（部署建议）。两种格式带**完全相同的字段集**，所以「本地能看懂」与「线上能检索」不冲突——切换格式不丢信息。格式名认不出时退回 `text`：一个拼错的配置不该把服务拦在启动之外。
2. **请求号由格式化器现取，业务代码一行不改**：`request_id` 从 `ContextVar` 读，调用方写 `logger.info("...")` 就够了。这不只是图省事——**它把「漏字段」从「每处调用点都可能犯的错」变成了「一处不可能犯的错」**。同理，`extra=` 挂的业务字段（`job_id` / `step` / `status` …）按「排除 `LogRecord` 标准属性」的办法自动带出：将来新增字段不需要回来登记，而白名单式做法漏登记就静默丢字段。
3. **访问日志写在最外层中间件里**：`RequestIdMiddleware` 已是最外层，日志记在它的 `finally` 里，于是**被认证拦下的 401 也有记录**——排查「用户说打不开」时，第一个要确认的正是「请求到底有没有到过后端」。耗时口径是「从收到请求到**开始**回响应」，对 SSE 就是建立流的耗时；整段生成多久由 `run_summary` 记，两者刻意不混：混成一个字段会让人以为「一次 PRD 生成只花了 40 毫秒」。
4. **`uvicorn.access` 的级别抬到 WARNING**：它那条访问日志的信息量是我们这条的子集，而且拿不到 `request_id`（它在协议层记录，不经过请求中间件，上下文变量早已还原）。留着就是同一次请求两行、一行有号一行没号。抬级别而不是 `disabled = True`，因为后者会让「我的访问日志去哪了」变成一个要翻代码才能回答的问题。
5. **体检三项、恒返回 200**：数据库 / 供应商 / 技能包分开报，`status` 取 `ok` 或 `degraded`。不返回非 200——技能包缺失时服务仍可降级运行，把状态码打成失败会让编排器踢掉还能用的容器；而数据库挂了也不该靠状态码表达，调用方看 `checks` 就能分清，这正是这个接口存在的意义。
6. **供应商一项只校验配置、不发真实调用**，`detail` 里如实写明「仅校验配置，未发起真实调用」。**不诚实的绿灯比红灯更贵**：它会让人在明知失败的时候先去怀疑别的地方。不报「备用供应商」是因为自动 failover 已随 ADR-016 取消，预警没有了对象。

### Consequences

- **变容易**：拿到回执上那个号就能在日志里搜出这一次生成的全部记录；「用不了」时第一眼分清是数据库、密钥还是技能包；日志结构化之后，将来接采集端不必改业务代码。
- **变困难**：两个格式化器要一起维护、字段集必须同步（靠测试守住：同一条记录在两种格式下都要取到同一组字段）；`request_id` 走隐式上下文，理解它依赖对 `ContextVar` 任务复制的认识。
- **中立**：仓库里已有的 `logger.warning(...)` 调用点**没有一个是为此改的**——它们自动获得请求号，这正是取 E 而不是 D 的回报。反过来，任何「靠上下文悄悄生效」的机制都有同一个代价：不看格式化器就看不出号是从哪来的，所以 `core/logging_setup.py` 的模块文档写清了整条链路。

## ADR-019：技能注册表——目录即注册，产物归属由技能包自述

**状态**：Accepted（2026-10-15 裁决，随 R2-T9-1 落地）

### Context

到 R2-T7 为止，「哪个产物该用哪个技能包」这件事写在 Python 里，具体是三处：`job_service._resolve_skill_refs()` 里的 `if kind != "prd": return []`、`prd_skill.PRD_SKILL_NAME`、以及 `prd_skill.PRD_SKILL_ARTIFACTS`（列举了包内哪三个文件是必需的）。

后果不是「不好看」，而是一连串**耦合的代价**：想给接口文档也配一套规范，就得改这三处代码；改代码要重启后端；而重启会触发 `reap_orphans()`，把当时正在跑的生成任务一并判死。一个本该是「加个目录」的动作，被拖成了「改代码 + 重启 + 顺手废掉别人正在跑的生成」。

同一个毛病在 RAG 知识库（`core/api_doc_knowledge.json`）那里还有一份拷贝：它同样挂着进程级缓存、同样在缺失时静默降级，只是换了个文件埋着。**这两处的病根是同一个——「生成器该读哪套规范」这件事对程序是不可见的。**

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持现状（写死在 Python） | 零改动 | 加一个技能包要改三处代码并重启；重启会废掉正在跑的任务 |
| B. 新建集中注册表 `config/skills.yaml`（原设计稿主张） | 一处看全所有技能包 | 加技能包要同时加目录**和**改这个文件——即「两处同步」，而这正是要消灭的东西；`config/` 目录此前已随重构删除，重开一层目录成本更高 |
| **C. 技能包自述 + 扫描建索引（推荐）** | **加技能包 = 加目录**，只有一处真相；体检与启动日志自动跟上 | `skill.yaml` 从「给人看的元数据」升级为「给人看 + 给程序读的契约」，字段改动要当真 |
| D. 用正则读 `skill.yaml` 的新字段 | 不引依赖（当时只用正则读一个 `version`） | 要读的是嵌套列表（`references` 里每项的 `path`/`key`），正则一旦失配是**静默的**——正是本轮要消灭的那类问题 |

### Decision

**选 C，并且为它引入 PyYAML。**

1. **产物归属写在技能包的 `applies_to` 里**（取值与任务类型 `kind` 一致）。程序扫 `<skills 根目录>/*/skill.yaml` 建索引，`job_service` 不再有任何种类判断。**「目录即注册」，没有第二处需要同步修改的地方。**
2. **必需资源清单写在 `references` 里**，每项的 `key` 是生成管线取用时的语义键。缺 `key` 时按文件名推（`references/writing-rules.md` → `writing_rules`）——这是确定性规则而非猜测，但显式写出来更稳：它意味着改文件名不会悄悄改掉契约。
3. **显式引入 PyYAML**，不再用正则。理由不只是「嵌套列表难解析」，而是**正则失配是静默的**：格式一变，读到的是空列表而不是报错，于是技能包看起来「加载成功但没有资源」。把隐式依赖变成显式依赖，比省一个依赖划算。
4. **两类缓存，但资源存在性不进缓存**：资源内容与元数据解析结果都按文件戳缓存（沿用 ADR-017 的口径），可**资源删没删不进缓存**——删文件不会改 `skill.yaml`，把存在性判定缓存起来就会出现「文件已经没了却还在报一切正常」，那正是这套机制最该避免的静默。
5. **问题一律显式**：元数据读不动、必需资源缺失、**同一产物被多个技能包声明**，三类都进 `SkillProblem` 清单，由启动日志、`/health` 与 `PRDWRIGHT_SKILLS_STRICT` 消费。多包抢同一产物时行为是确定的（按名字取第一个），但仍然报出来——它几乎一定是配置出错。
6. **`prd_skill` 相应瘦身**：定位、加载、指纹、自检这些**所有技能包共用的能力**整体搬进 `skill_registry`；`prd_skill` 只留 PRD 专属的材料格式化与提示词拼接。资源清单不再在本文件里冗余一份。

### Consequences

- **变容易**：加一个技能包 = 加一个目录。体检和启动日志会自动列出它、它认领的产物、以及它是否完整，不必回来改代码。新增的产物类型只要有一个技能包声明 `applies_to`，回执上就会出现它的身份。
- **变困难**：`skill.yaml` 的字段从此是**契约**——改 `key` 等于改接口；多了一个 PyYAML 依赖；多了一层「扫描 → manifest」的间接，理解成本从「读常量」变成「读一个模块」。
- **中立**：**指纹口径刻意保持不变**（`sha256(版本 + 各资源路径与内容)[:12]`，按 `key` 排序）。于是仓库里 `prd-generator` 的指纹在重构前后仍是同一个值——历史回执上那个指纹继续可对得上，重构没有把「过去那份文档是按哪套写的」变成悬案。这一条在改动时被当成约束而不是巧合：它由一条断言真实技能包能注册的用例守着（防的是 `skill.yaml` 格式漂移）。

## ADR-020：RAG 闸门从「只读展示」改为整条移除

**状态**：Accepted（2026-10-15 裁决，随 R2-T9 立项；删除动作在 T9-3 / T9-4 落地）

### Context

ADR-011 定下了生成前的双闸门：闸门 1 摘要 Diff、闸门 2 RAG 接口规范检索（本地词法检索 `core/api_doc_knowledge.json`，挑前 5 条 → `RagResultPanel` 让用户勾选）。R2 立项时（`ARCHITECTURE.md` §4.4）曾裁决**保留**闸门 2、只把「阻塞式确认」降级为「只读展示」，理由是「让用户知道模型参考了什么」有价值。

那个理由本身成立，但**它把两件不同的事混在了一起**。闸门 2 注入的是**固定不变的团队规范**（14 条、约 6000 字），不是每次生成都需要用户重新审一遍的临时素材。对一份静态资产要求逐条确认，不是「可见性」，是不必要的摩擦；而真正的可见性诉求（这份文档参考了哪套规范）另有更完整的承载方式。

同时，「只挑前 5 条」这件事本身是**用不确定性换取省下来的几千 token**——规范总量全量注入也远低于预算上限（12 万），而挑漏一条，那次生成的接口文档就少了对齐依据，且**从输出上看不出来**。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持原样（阻塞式确认 + 挑前 5 条） | 零改动 | 每次生成多一次无意义的人工确认；漏挑静默 |
| B. 原定方案（降级为只读展示 + 保留检索） | 去掉阻塞、保留「参考了什么」 | 检索代码（分词 / 打分 / 阈值）继续要养；**漏挑仍然是静默的**；只读面板仍是每次生成途中的一次打断 |
| **C. 整条移除，规范改由技能包全量注入（推荐）** | 点生成直接开始；注入内容可预期、无抖动；少一条路径与一份代码 | 注入 token 变多（约 6000 字，仍远低于预算）；用户不能再用「不勾选」表达异议 |
| D. 换成向量检索 | 语义召回比词法强 | 规范只有 14 条，为一个固定小集合引入 embedding + 向量库，是拿复杂度换一个不需要的精度 |

### Decision

**选 C。**

1. **规范迁入技能包、全量注入**：`core/api_doc_knowledge.json` 的 14 条迁成 `skills/api-docs-generator/` 下可读的 md，与 PRD 走同一条注入管线。**全量比检索更稳定也更可预期**——钱不是问题，一致性才是。
2. **删除检索实现、检索接口、以及请求里携带的「用户勾选结果」字段**，不留一条「以后可能用得上」的旁路：留着它就有两条真相，规范改了哪条生效会变成要读代码才能回答的问题。
3. **前端删掉确认页组件、相关状态与 `RagHit` 类型**，点「生成接口文档」直接开始。删状态机里的 `rag-preview` 登记时要**同步改四处**（`ViewState` / `VIEW_STATES` / `STEP_OF_STATE` / `STATE_DOWNGRADE`），否则状态机会指向一个不存在的页面。
4. **可见性由回执承担，而不是由勾选面板承担**：`run_summary.injected_skills` 已经记录技能包名、版本与内容指纹（ADR-017）。它回答的是「这份文档按哪一套规范写的」，比「列 5 条让用户看一眼」更完整，而且不阻塞、不打断。
5. **闸门 1（摘要 Diff）不动**。它是**用户输入**的确认，用户确实需要看见自己的话被理解成了什么；而闸门 2 是**静态资产的注入**，两者不是一回事。这条区别正是原来那版裁决没分清的地方。

### Consequences

- **变容易**：生成接口文档从「检索 → 展示 → 勾选 → 继续」变成一步；规范全量在场，不会再有「这次恰好没挑到某条」的抖动；少一份需要维护的检索代码与一个前端组件。
- **变困难**：注入的 token 变多——约 6000 字，相对预算上限可忽略，但它意味着**规范总量将来不能无节制增长**，这份资产需要保持精炼；用户对某条规范有异议时不能再靠不勾选绕过，得直接改技能包文件（这本来也更对：规范是团队资产，不该每次生成现场裁剪）。
- **中立**：这不是「RAG 没用」，而是**它的适用条件不成立**——检索解决的问题是「候选集远超上下文预算」，而这里候选集只有 14 条。将来规范真的长到装不下时，正确的做法是重新引入检索，而不是怀念现在这条只挑 5 条、还不告诉人挑了哪 5 条的实现。

## ADR-021：三份产物的正文归后端 `documents` 表所有

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P0–P2）

### Context

三份产物（PRD / 接口文档 / 提示词）的正文此前是**前端快照里的三个字符串**（`prdContent` / `apiDocsContent` / `promptsContent`），随会话快照一起塞进 `solutions.data`。这个形状在「单次生成」时看不出问题，一旦功能变多就连着暴露三件事：

1. **一个内容两个真源**。前端内存里一份工作副本、后端快照里一份，谁更权威没有裁决者。生成收尾时前端把正文写回快照，若那一次保存失败（网络抖动、页面关闭），后端那份就停在旧版本，而用户看到的是新的——直到下次刷新才「自己变回去」。
2. **「谁写、什么时候写」散在多个调用点**。生成、AI 优化、澄清改写三条路径各自负责把结果存回去；而「优化的是哪一份」只有前端知道（它按当前阶段猜），后端无法核对。
3. **快照被正文撑大**。`SessionDataV2` 是几十 KB 的 JSON，每次防抖保存都在重写整份文档；而快照本意是存「走到哪一步、键盘敲了什么」这类只属于本次会话的状态。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持现状（正文在前端 + 快照） | 零改动 | 双真源、写入口分散、快照被撑大，三个问题都在 |
| **B. 后端 `documents` 表为唯一真源，前端只读 + 提交用户手改（推荐）** | 一个真源、写入口唯一、「改的是哪一份」由后端按 `kind` 判定；快照回到只存流程状态 | 迁移要回填旧快照；前端多两条通道（读 / 提交）；读不到时要能退化 |
| C. 前端为真源，后端不存正文 | 后端最简 | 换设备 / 换浏览器就没了；生成任务收尾后没有落点，`optimize` 的「写回哪一份」照样无解 |

### Decision

**选 B。**

1. **新增 `documents` 单表**：`owner_id / solution_id / kind / content / pending_items / last_run_summary / content_sha / updated_at`，`(solution_id, kind)` 唯一。归属仍由 `solutions` 决定——仓储的每个查询都经 `JOIN solutions` 在 **SQL 层**过滤 `owner_id`，越权与不存在一样返回 404（沿用 ADR-009 的口径）。
2. **写正文的唯一入口是 job 收尾**（`job_service._write_document` → `document_store.commit_generated`）：正文、待确认清单、用量回执**同批替换**。失败的任务**不写**——半截输出不该顶掉一份完整文档。前端因此不再需要知道「正文该存哪」，也就没有第二处可能写错。
3. **前端只剩两条通道**：`GET /api/solutions/{id}/documents`（读）与 `PUT .../documents/{kind}`（用户手改）。手改**不碰**清单与回执——它们是「上一次生成」的事实，不因用户改几个字而改变；两条写入路径语义不同，刻意不合并成一个方法。
4. **`SessionDataV2` 退役六个字段**（三个 `*Content` + 三个 `*RunSummary`）。旧快照里残留的会被**忽略**而不做兼容读取——「兼容读取」等于长期维护两份真源，正是这一步要消灭的东西。旧数据由迁移一次性回填进 `documents`。

### Consequences

- **变容易**：一句话就能说清「正文在哪」（后端 `documents` 表）；生成 / 优化 / 澄清三条路径都自动落对位置；快照不再随正文大小增长；刷新后前端拉一次即得权威版本，不需要任何比对逻辑。
- **变困难**：前端多了一次网络读取，因此多了一套退化路径（404 → `DocumentsNotFoundError` → 清空工作副本并提示「方案不存在或已被删除」）；`documents` 的写入语义分成「生成收尾整批替换」与「用户手改只动正文」两套，接口多但**不能合并**；迁移必须处理「旧快照里的正文去哪」。
- **中立**：ADR-009 没有被破坏——`solutions.data` 仍是后端不解析的不透明快照，`documents` 是后端**自己的**表，读写它天经地义。快照里少了三份正文，反而更贴近 ADR-009 的本意。

## ADR-022：schema 迁移用 `PRAGMA user_version` + 有序幂等步骤

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P0）

### Context

`core/db.py::init_schema` 一直靠 `CREATE TABLE IF NOT EXISTS` 建表。这在「库只有开发机上的那一份、随时可以删」的阶段够用，但 `documents` 是**有真实数据**之后才加的表（还要回填旧快照里的正文），而 `IF NOT EXISTS` 对已存在的库**什么都不做**：旧库不会因此多出 `documents`，也不会多出后加的那一列。手工去改库则等于把「部署时要记得做某件事」写进人脑，而这正是最容易被跳过的一环。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 引入 alembic | 功能完整、社区标准 | 为一个单文件 SQLite 引入迁移框架与配置目录；它的模型是「连接 + 版本表 + 脚本目录」，对一个自研小项目是纯负担 |
| **B. `PRAGMA user_version` + 有序幂等步骤清单（推荐）** | 零依赖；版本号就在库里；每步是普通函数，可单测 | 得自己维护「step 编号 + 顺序」这条纪律；改动要写迁移而不能顺手改 `init_schema` |
| C. 手工 SQL / 文档说明 | 最快 | 「记得在部署时执行」不是机制；漏一次就是线上 500，且症状（缺列）离原因很远 |
| D. 每次启动删库重建 | 绝不会有版本问题 | 数据没了 |

### Decision

**选 B。** `core/migrations.py` 维护一份 `MIGRATIONS` 有序清单，每项是 `(version, name, apply)`：

1. **版本号落 `PRAGMA user_version`**（SQLite 自带，零依赖），只跑「版本号大于当前」的增量步骤。
2. **每步一个独立、显式的事务**：任一步抛错即停，版本停在上一档，重跑从断点续——**不会留下「改了一半」的库**。
3. **`init_schema` 只建基线表**，新表 / 新列一律走迁移。这条纪律很关键：在 `init_schema` 里加一列，对**新库**有效、对**旧库**静默无效，正是最难发现的那类问题。
4. **迁移在 `lifespan` 里随启动跑一次**，运维不需要记得任何事。

### Consequences

- **变容易**：加表 / 加列有唯一确定的做法；部署不必人工干预；「这个库到哪一版了」一句 SQL 就能问出来。
- **变困难**：多了一个要理解的模块；改 schema 时必须写迁移（不能图省事改 `init_schema`）——这条靠 review 守，测试里用 `run_migrations()` 的返回值把关键几步钉住；`apply` 步骤要自己保证幂等（重跑安全）。
- **中立**：将来真要换 alembic，这份清单是一组纯函数，转写成本很低。迁移里刻意不引入「回滚」（down）步骤：SQLite 的 `ALTER TABLE` 大多不可逆，写一个假装能回滚的脚本比不写更危险。

## ADR-023：待确认清单是生成的第一类产物

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P3）

### Context

文档里「待确认」原本只是正文中的一句自然语言（「分页上限：待确认」）。若想让它成为可操作的东西——列出来、逐条问清楚、答完回到文档里——就必须把它变成**结构化数据**。

难点在于**它和正文的同步**。清单若由正文之外的某个环节单独产出，就必然出现「正文换了一版、清单还是上一版的」这种状态：生成、优化、澄清改写三条路径都要记得重算，而漏掉任何一条都不会报错，只会静默留下过期结论。同一份文档里，正文说「已确认 50 条」而清单仍列着「分页上限取多少」，是最糟的一种不一致——它让用户以为问题还没定。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 前端从正文文本里解析「待确认」段落 | 后端零改动 | 解析口径在两端各写一遍；正文措辞一改就失配，且失配是静默的 |
| **B. 模型在正文末尾附标记块，收尾时剥离并解析（推荐）** | 清单与正文**来自同一次调用**，天然同步；与正文同一次写入落库 | 提示词要带格式说明；模型可能不守规矩，必须有降级 |
| C. 生成完再单独调一次模型产出清单 | 正文与清单互不干扰 | 多一次 LLM 调用；两次调用对同一份文档的理解可能不一致；仍要处理同步 |

### Decision

**选 B。**

1. **标记块用 HTML 注释哨兵**（`<!-- PENDING:BEGIN -->` … `<!-- PENDING:END -->`），块内是 JSON 数组。选 HTML 注释而不是别的定界符，是因为它有个兜底性质：**即使抑制逻辑漏了，Markdown 渲染里也不可见**，不会把半截 JSON 当正文闪现给用户。
2. **`services/pending_items.py` 是唯一实现**（`extract` 剥离 + 解析、`render_spec` 生成提示词说明、`PendingBlockSuppressor` 流式抑制）。三条生成线与澄清改写都调它，不各写一份。
3. **`id` 由后端分配**（`{章节 id}-{序号}`），不信任模型给的 id：保证全文档唯一、稳定，且能与正文位置对应。
4. **流式也要干净**：抑制器是有状态的、逐 chunk 的——块外态尾留「哨兵长度 − 1」个字符以应对哨兵被切在 chunk 边界；块内整段丢弃；流结束仍在块内则什么都不输出（半截 JSON 绝不能当正文）。
5. **降级不污染产物**：没找到块、JSON 非法、块未闭合 → 正文不受影响、生成不失败，只记一条 warning 并让该次清单为空。与「审核失败按通过处理」同一口径。
6. **清单与正文同批写入**（`commit_generated` 的 `pending_items` 参数），因此**「换了正文却忘了重算清单」在结构上没有落脚点**——所有会重生成正文的路径都走同一条收尾写入。唯一不重算的是用户手改，那是显式接受的（他改的是正文，没有声称清单是按新正文算的）。

### Consequences

- **变容易**：清单永远与正文同源；用户可以逐条澄清并写回；前端只需要展示，不解析、不重算。
- **变困难**：提示词里必须有一份「块长什么样」的说明（它是新增的、必须与实现同步的契约，由测试断言占位符存在守住）；必须为「模型不附块」准备降级路径；`generation_jobs` 与 `documents` 各多一列 JSON。
- **中立**：把清单做成「生成的第一类产物」而不是「正文的衍生物」，代价是提示词更长、解析逻辑更重，但换来的是**不需要任何同步机制**——同一处写入天然一致。

## ADR-024：会话用单点登录，不做 revision 乐观锁

**状态**：Accepted（2026-10-15 裁决并落地，P5）

### Context

「同一账号多端登录」这件事需要一个明确的处置：多端并存时，一个端改了密码、或者用户怀疑账号在别处被人用着，怎样才能干净地收回登录态？

原先倾向的做法是 **revision 版本号 + 乐观锁**：会话记录带一个版本号，客户端每次请求带上它，写时比对、不一致就重试。它能让多端并存且各自感知「自己落后了」。但推演下来，它要新增的东西不少：会话表加列、每次请求带版本号、冲突时的重试语义、以及前端「版本落后」的界面表达——而这些问题**全都是为了支持多端并存**才存在的。

真正要问的是：**这个产品需要多端同时在线吗？** 产品定位是单机需求工作台，真实使用场景是「一个人、一台设备、一份方案」。为它维护一套并发会话一致性机制，属于拿复杂度换一个用不到的能力。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. revision 乐观锁 | 支持多端并存，冲突可感知、可重试 | 多一列 + 每次请求带版本 + 重试语义 + 前端冲突 UI；而多端并存本身用不到 |
| **B. 单点登录：新登录吊销该用户此前全部会话（推荐）** | 零 schema 变更、语义一句话说完、天然覆盖「改密码/怀疑被盗」 | 多设备会互相踢下线（**明确接受的残余风险**） |
| C. 保持现状（多端并存，互不影响） | 零改动 | 账号被多处使用时无法收回；会话表随登录次数增长 |

### Decision

**选 B。**

1. **`AuthSessionRepository.replace_for_user()` 在一条事务里「先删后插」**（`DELETE FROM auth_sessions WHERE user_id = ?` → `INSERT`）。必须在同一事务：分开做的话，任何一步失败都会把用户留在「旧的已删、新的没立」——刚登录成功却判定未登录。插失败（如哈希撞主键）时**不提交**，连接关闭即回滚，旧会话照旧可用。
2. **刻意不按过期时间挑着删**：单点登录的语义是「新登录让旧的立刻失效」。只清过期记录等于留下一个可用的第二登录态，那正是要消灭的东西。
3. **登录与注册都走 `replace()`**。注册时该用户本来没有旧会话，这一步是空操作——但它保证「凡是签发登录态的地方只有一个入口」，不给「某个入口忘了吊销旧会话」留缝。
4. **零 schema 变更、中间件零改动**：`idx_auth_sessions_user` 已存在；旧 token 在新会话立起来后查不到 → 中间件判定未登录 → 401 → 前端 `onUnauthorized` 弹登录窗。整条回收链路复用的是既有机制。

### Consequences

- **变容易**：账号回收语义变成一句话；不需要维护版本号、冲突重试与「版本落后」的界面表达；会话表里「一个用户至多一条记录」成为可核对的不变量（`list_by_user` 即为此提供的第一手证据）。
- **变困难**：**多设备互相踢下线是明确接受的代价**，登记为残余风险——手机上看完的需求，回到电脑前要重新登录。这不是「暂时没做」，是范围决策。
- **中立**：仍保留「多端并存」的能力（`issue()` 还在，改动它只是一行），因此将来若真出现多端需求，反悔的成本极低——这一点也是选 B 的理由之一：**它的反转成本和它的实现成本一样小**。

## ADR-025：澄清以「对文档的逐条问答」形式进行，而不是生成时一次问完

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P4）

### Context

有了待确认清单（ADR-023），紧接着的问题是：**这些问题什么时候问、怎么问？**

两个现成的做法都不成立。「生成时一次问完」不现实——生成的过程中用户还没看到文档，指望他在写 PRD 的同时回答「第 6.1 节的指标口径」是反的。「让用户直接在正文里手改」也不行：改完之后，「为什么这么定」这个推理过程没有留下任何痕迹，下一个接手的人只能从结果反推。

而这份清单天然适合对话：它是**有限条**结构化问题，每条都有明确的对象（哪一章）和拍板人。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 生成时一次问完 | 不用新增界面 | 用户看不到文档，回答质量低；清单往往要等看完正文才判得清 |
| B. 让用户直接改正文 | 无新增流程 | 推理过程不留痕；改完清单过期（手改不重算清单） |
| **C. 独立的澄清对话 + 按结论就地改写（推荐）** | 问题逐条聊清楚、有记录；改写受约束、只动涉及章节；清单重算 | 多一个对话档案与阶段；改写质量依赖提示词约束；澄清会话要持久化 |

### Decision

**选 C，分「对话」与「改写」两半。**

1. **对话复用既有的会话框架，新增档案 `doc-clarification`**（人设 + 开场白，占位符 `{document}` / `{pending_items}`）。它与需求澄清**共用同一段提问规则常量**（`CLARIFICATION_QUESTION_RULE`）——历史上两处各写一个数字导致口径漂移，这次由共享常量把这件事从「靠人记得」变成「不可能写错」。
2. **`profile_key` 与模板占位符都是显式契约**：档案自己声明要用哪些占位符（`opening_fields`），服务层按声明取值；未注册的档案名直接 400、**不静默回退默认人设**。校验发生在构造 SSE 响应**之前**——进了流之后状态码恒为 200，400 就没意义了。
3. **改写走 `clarify` 任务（复用 job 框架），不是一次裸 SSE 请求**：改写可能跑很久，任务化之后刷新 / 断线只断订阅，后端照跑，重连凭 `activeJobId` 接上——与三份文档的生成同一套机制，不另造一套。
4. **改写规则写死在提示词里且必须可核对**：只改澄清涉及的章节、其余**逐字保留**（不覆盖用户手改）、已解答项从正文与清单一并移除、保持标题层级与结构、不足处继续标「待确认」不编造。末尾必须附**重算后**的清单——这就是「改写后重算」的落点。
5. **澄清会话的字段与需求澄清完全分开**（`clarifyMessages` / `clarifyConversationId` / `clarifyTarget`）。混在一起的话，「从对话回填需求摘要」那道闸门（ADR-011 的闸门 1）会把文档答疑也读成需求输入，Diff 里凭空冒出条目。
6. **不新增步骤**：澄清是对「当前这一份文档」做的事，进度条停在那一格上（`clarifying` 的步骤归属**按 `clarifyTarget` 现算**，而不是查静态表——否则澄清接口文档时进度条会跳回 PRD 那一格）。

### Consequences

- **变容易**：问题逐条有对象、有记录、有结论；改写范围受约束，用户不必担心稿子被整篇覆盖；澄清会话随快照持久化，刷新后接着聊。
- **变困难**：多一个对话档案、一个阶段、三个会话字段——而**加一个 `ViewState` 要同步改四处**，漏一处不报错、只表现为进度条算错或刷新后进不去（由一条不变量测试守着）；「只动涉及章节」这条**只能靠提示词约束**，代码层面保证不了，因此它被写进提示词、也被写进页面文案（提前说明比事后解释便宜）；清单文本要由前端摊平后随请求提交，多了一处「前端参与决定给模型看什么」的落点（只做摊平，不做语义判断）。
- **中立**：澄清不改变「谁拥有正文」——它写回的仍是 `documents`（ADR-021），只是多了一条会重算清单的写入路径，且这条路径与生成路径共用同一个收尾写入。

## ADR-026：技能包按「目标产物」注入，而不是按「做了一件什么事」

**状态**：Accepted（2026-10-15 裁决并落地，P4/P5 收口）

### Context

ADR-019 把「哪个产物用哪个技能包」交给了技能包自述（`applies_to`），R2-T9 又让三条生成线都从注册表取资源。但**剩下的两条路径没接上**：`optimize`（按指令优化）与 `clarify`（按澄清改写）——它们的 `kind` 回答的是「做了一件什么事」，而不是「作用在哪一份产物上」。按 `kind` 去找技能包，结果是：

1. **回执报错包**：优化接口文档的回执会标上 PRD 那个技能包。
2. **提示词里其实什么都没注入**：两条路径都没有把目标产物的规范拼进提示词——于是回执说「按 prd-generator 写的」，而模型手里并没有那份写作规范。**回执与实际注入不一致**，这正是这个项目反复要消灭的那类静默不一致：它不会报错，只会让人在排查时从错误的方向开始。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持现状（按 `kind` 找包） | 零改动 | 回执指错包；改写时实际没有规范可依 |
| **B. 新增 `_target_product_kind(kind, request)`：前三种取 `kind`，`optimize` / `clarify` 取 `doc_kind`（推荐）** | 一处判断，回执与注入共用；改写仍守团队规范 | 多一处对 `doc_kind` 的依赖（它本来也是落库的必需信息） |
| C. 干脆不注入、回执也不报 | 诚实（不假装） | 改写产物不受任何团队规范约束，质量必然漂移 |

### Decision

**选 B，并且注入内容做白名单。**

1. **一份判断供两处消费**：`_target_product_kind()` 同时服务「回执报哪个包」（`_resolve_skill_refs`）与「落库写哪一份」（`_document_kind`）。两处共用同一函数，就不会再出现「说的和做的不一致」。
2. **取不到目标产物时，既不注入也不报包**：`optimize` 漏传 `doc_kind` 时回执的 `injected_skills` 为**空数组**。报一个没注入的包，比不报更糟。
3. **注入内容按白名单选**：`prd → writing_rules`、`api_docs → api_specs`、`prompts → prompts_guide`，**不整包注入**。原因是 PRD 的 `prd_template` 是给「从零生成」用的骨架、里面带 `{{字段名}}` 占位符，塞进「改写既有文档」的提示词只会诱导模型重新渲染一遍占位符——反而破坏原文。字段契约同理：改写不需要它。
4. **规范不可用时给显式的降级说明**，而不是留空：提示词里什么都不写，模型会以为「没有规范要守」，而实际约定是被悄悄丢掉了。

### Consequences

- **变容易**：优化与澄清的产物同样受团队规范约束；回执上的技能身份与实际注入对得上，「这份文档是按哪套规范改的」可以查。
- **变困难**：`doc_kind` 从「落库用的附加信息」升级为「必需信息」（缺它就连规范都注入不了），校验因此前移到请求入口（400）；改写提示词变长（多一段规范 + 一段降级说明的位置）。
- **中立**：白名单是**取舍的显式落点**——将来某类产物的规范真需要多注入一份资源，改的是这张表而不是散落的提示词模板。

## ADR-027：PRD 澄清复用主对话线程，待确认项按 P0/P1/P2 分级

**状态**：Accepted（2026-10-16 裁决并落地）

> **补记（同日，`c08ec58`）**：第 4 条的档位随后从 P0/P1/P2 扩为 **P0~P6 七档**，并**取消兜底**——
> 等级缺失或非法的条目由后端**直接丢弃**并记 `pending.bad_importance` 告警（前端两处入口同口径，
> 不再落回 P1）。原因是「拿不准就标 P1」让大量条目挤在同一档，分级形同虚设。本文正文保留裁决
> 当时的形态，不回改。

### Context

ADR-025 把澄清做成了「对文档的逐条问答」，并为了防住闸门①，刻意让澄清会话与需求澄清**完全分开**（`clarifyMessages` / `clarifyConversationId` / `clarifyTarget` 三个独立字段）。

用下来暴露出两个问题：

1. **历史断裂**。PRD 生成完点「回到对话」，用户面对的是另一个空栏——前面和 AI 聊过的那一段全部看不见。而澄清 PRD 恰恰最需要那段上下文：AI 问的问题是从那份 PRD 里长出来的，用户却看不到自己当初是怎么描述这个产品的。
2. **清单没有轻重**。待确认清单是平铺的，用户不知道该先答哪个；AI 也不知缓急，可能先问一个无关紧要的。而这份清单的意义本来就是「不问就没法开工」，理应按这个标准排序。

分开的理由这次被核实掉了：闸门①（`diffSummaries`）只比对结构化的 `RequirementsSummary`，**根本不读 `messages`**。防的是一件不会发生的事，代价却是真实存在的。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持 ADR-025 的独立澄清栏 | 零改动 | 历史断裂；PRD 与接口文档的澄清在两个不同的栏，用户得自己记住「在哪聊过什么」 |
| B. 合并，且后端改成同一条 conversation 切换档案 | 后端也只有一条会话 | 要动 `conversation_service` 里「有记录就信 `record.profile_key`」那段逻辑——它目前会忽略档案切换，改动风险大、回归面广 |
| **C. 前端单线程 / 后端双会话（推荐）** | 用户看到一条连续时间线；`conversation_service` 一行都不用改 | 前端要多一套「当前该听哪套」的转发；后端是两条会话 id，各自重试 |

### Decision

**选 C，并把清单按 P0 / P1 / P2 分级。**

1. **前端单线程**：PRD 澄清复用同一个 `messages` 数组，用一个 `prdClarifying` 开关决定当前该听哪一套发送 / 渲染 / 加载状态（`activeChat`）。PRD **不再**走 `clarifying` 阶段；接口文档与提示词**仍走**既有的独立 `ClarifyStage`——本期范围只到 PRD，机制留待扩展。
2. **后端双会话**：第二次进入时后端**新开**一条会话（档案 `doc-clarification`，id 存在 `prdClarifyConversationId`），首轮开门白带 `{document}` 与 `{pending_items}`；它的回复**追加**进同一个 `messages`。用户看到一条连续的时间线，后端仍是两条干净的会话。
3. **闸门①改成双保险**：`messages` 里每条打一个 `stage`（`'requirement'` / `'document'`，缺省前者以兼容旧快照），回填用的 `conversationHistory()` **只取 `'requirement'` 的 turns**。即便将来有人改了闸门，也污染不到摘要 Diff。
4. **分级用 P0 / P1 / P2**（P0 最要紧），判据是「不问就没法开工」的程度。`extract` **先按等级稳定排序、再重分配 id**——这样 `p-1` 一定是最要紧那条，前端序号与提问顺序天然一致；模型给的等级缺失或非法一律兜底 P1。喂给模型的清单文本带 `[P0]` 前缀，让它开场就看到轻重。
5. **逐级播报写进共享常量，而不是只写进开场白**：「准备开始 P0 级问题的确认 / P0 级已确认完毕，准备开启 P1 级」这条规则加在 `CLARIFICATION_QUESTION_RULE` 里——两个档案的 system prompt 同时引用它。只写进开场白的话，模型聊过一轮就忘了还要播报。
6. **「按澄清结果改写」的判据是「这一轮聊过」**（存在 `stage === 'document'` 的消息），不是「改没改过」。空着聊城没有结论可用，所以第一轮追问出来之前这个按钮点不动。

### Consequences

- **变容易**：PRD 澄清接着需求澄清往下聊，是一条连续的时间线；清单按轻重排序、AI 逐等级播报，用户知道进行到哪一级、还剩多少。
- **变困难**：前端多一层状态转发（底栏、标题、发送都要跟着 `prdClarifying` 切）；后端两条会话各自维护 id 与无状态重试；`stage` 是一道**隐式契约**——漏打标不会报错，只会让回填悄悄多读几轮，因此由一条测试专门守着；本期同时存在两条澄清路径（PRD 走合并线程、其余走独立页），心智负担暂时是双份的。
- **中立**：闸门①的安全从「靠字段隔离」变成「靠字段隔离 + `stage` 过滤」；ADR-025 的第 5 条（两套记录必须分开）被**局部推翻**——分开的理由经核实不成立，留下的是它带来的另一半好处（接口文档 / 提示词的澄清仍各自独立）。

## ADR-028：四条澄清线程收进同一个对话页，用子标签栏切换

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

ADR-027 把 PRD 的澄清合进了主对话线程，但只在 PRD 上做——**接口文档 / 提示词仍走独立的 `clarifying` 页面**。它自己也在 Consequences 里写明了代价：「本期同时存在两条澄清路径，心智负担暂时是双份的」，并声明机制留待扩展。

这一版把扩展做了，触发点有三：

1. **同一件事写了两遍**。`ClarifyStage` 与 `ChatStage` 都在做「消息区 + 输入框 + 底栏主操作」，改一处要记得改另一处；连入口位置都是两套（PRD 在底栏次操作组、另两份在正文下方的普通区块）。
2. **刷新行为不一致**。`chatting` 随快照恢复；`clarifying` 当初被裁决为「不降级」，刷新即丢。同一个功能，三份文档里有一份的体验更差，而原因是历史路径不同而非设计意图。
3. **聊过什么无从分辨**。三条线程的历史散在「主时间线」与 `clarifyMessages` 两个地方，用户得自己记住「这段是在聊 PRD 还是接口文档」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持 ADR-027 的双路径 | 零改动 | 同一件事两套实现；刷新行为与入口位置都不一致；用户要自己记住在哪条线程上聊过 |
| B. 也搬进 `chatting`，但不做子标签，四条线程共用一条时间线 | 改动最小，删掉 `ClarifyStage` 即可 | 四条线程的消息混在一起，「这段是在聊 PRD 还是接口文档」无法分辨；底栏主操作也无法跟着线程切——只能永远显示「生成 PRD」 |
| **C. 搬进 `chatting` + 引入子标签栏，四条线程各自独立（推荐）** | 一个页面、一套实现；刷新与入口统一；底栏按线程给动作；标签本身即地图 | 前端多一层「当前线程」状态并要进快照；底栏与进度条都要按线程算 |

### Decision

**选 C。**

1. **一个对话页，四条线程**。`ChatStage = 'requirement' | 'prd-clarify' | 'api-docs-clarify' | 'prompts-clarify'`，`ViewState` 里的 `clarifying` 整个删掉，`ClarifyStage.vue` 一并删除。
2. **消息仍共用同一个 `messages` 数组**，每条打 `stage`；**对话区只渲染当前标签那一条线程**（按 `stage` 过滤）。共用数组是为了让「哪条线程聊过什么」有一个单一真源，而不是四条各有各的数组、再各自记得同步落库。
3. **标签常驻**：四条标签永远都在，未就绪的置灰、悬停给出理由（`title`）。理由是**标签本身就是地图**——藏起来用户就不知道后面还有哪些可以聊，而「四条线程」这个结构恰恰最该被一眼看见。
4. **`chatTab`（用户意图）与 `activeChatTab`（实际显示）分开**。文档还没生成时该标签置灰，显示归落到第一条可用线程，但 `chatTab` **保持原值不回写**——否则用户上次停在「接口澄清」、这次打开时接口文档尚未生成，意图就被永久抹掉了。
5. **底栏动作按线程算**：需求澄清是「重新开始 │ 改需求 │ 生成 PRD」；三条文档线程**只有**主操作「按澄清结果改写」。**澄清线程下不放「返回审阅」**——回审阅页靠顶部进度条，理由见下一条。
6. **回审阅页的唯一落点是进度条**（`ProgressSteps`），因此它的可点范围必须包含**当前所在的那一步**：对话页停在文档线程上时，高亮的正是那份文档的格子；若把「当前步」排除，这条路就成了死胡同——澄清线程的底栏里没有「返回」，进度条又点不回去。
7. **审阅页的澄清入口统一成同一个**：三份文档都是「和 AI 确认剩下的 N 个问题」，落点都是对话页对应的标签。PRD 那条仍在底栏次操作组、并在出现时**顶替**「返回」按钮（两者落点相同、名字近似，并排会让用户不知道点哪个），且只在 `entryMode === 'structured'` 下出现——PRD 快捷 / 提示词调试没有需求澄清那一段对话可回。
8. **整篇重生成才作废下游线程**：某一份文档被整篇重生成时，它自己这条线程与它下游的线程一起清掉（`dropChatThread`）；**就地改写（`optimize` / `clarify`）不作废任何线程**。

### Consequences

- **变容易**：澄清只有一个页面、一套实现，改一处就够；刷新行为与入口位置三份文档一致；底栏按线程给动作，「现在能干什么」看底栏就知道，不必先回忆自己在哪条线程上。
- **变困难**：`chatTab` / `conversationIds` 是新增的快照字段，过期快照要迁移（`clarifyMessages` / `clarifyConversationId` / `clarifyTarget` 按 `clarifyTarget` 重分发进四条线程，`'document'` 归一为 `'prd-clarify'`）；`ViewState` 少了一个值，但 `currentStepIndex` 要多一段「停在对话页的某条文档线程 → 映射回那份文档的步骤」的现算，否则进度条会算错；四条线程各有自己的 `streaming` / `chatError`，不能共用一个「发送中」。
- **中立**：后端一行没动——`doc-clarification` 档案、`CLARIFICATION_QUESTION_RULE`、`clarify` 任务、每条线程各自一条会话（`conversationIds`）全部沿用 ADR-027 的形态。这次只动「聊天区怎么摆」，不动「澄清怎么聊」。ADR-027 的「其余走独立页」被推翻，但它的另外两条（复用主线程、后端双会话）继续成立。

## ADR-029：正文全搬进 `document_versions`，`documents` 只留「当前版本」指针

**状态**：Accepted（2026-10-16 裁决并落地）

> **补记（同日）：删除历史版本**。第 2 条写的是「版本**何时产生**」，没写「版本**何时消失**」——
> 补上：**只有历史版本可以删除，当前版本不给删**（后端 `INVALID_REQUEST` / 400，`detail` 里说明
> 原因）。想换当前用的那一版请走 `restore`（**追加**一条新版本）；用「删掉当前版本」来换版本，
> 等于把这份文档的正文直接抽走，还要额外规定「删完当前指向谁」——两件事性质不同，不该由同一个
> 动作承担。这条限制**写在仓储的 SQL 里**（`WHERE ... AND v.id != d.current_version_id`）而不是
> 「先查一次、再决定删不删」：两次查询之间若有别的写入把它变成当前版本，先查后删就会放行，
> 而那时删掉的是文档正在用的正文。
> 另外，删除**只重拉版本列表、不重拉当前文档**——正文一点没变，多拉一次只会平白闪一下编辑器。
> 本文正文保留裁决当时的形态，不回改。

### Context

ADR-021 把正文从「前端快照里的三个字符串」搬进后端 `documents` 单表，解决了**一个内容两个真源**与**写入口分散**两件事。但那一步只做到「谁是主人」，没做到「改坏了能回头」：一次生成、一次 AI 优化都**直接覆盖**同一行的 `content`，覆盖之后就只剩当前这一份——想拿回上一版，唯一的办法是凭记忆重写。

ADR-021 与 v3 的 `ARCHITECTURE.md` 4.3 都把版本链标为「本期明确推迟」，并明确写了结构位置怎么留：**往上叠一张 `document_versions`，把 `documents.content` 换成指向 current 版本**，不推翻今天任何一条约束。触发这一版的，正是 ADR-021 自己把这两个条件凑齐了：

1. **文档已经归后端所有**，因此「这份文档一共几版」是一个后端答得清的问题（在此之前它散在前端内存里，刷新即无）；
2. **每次改写都留下了清单与回执**（ADR-023），因此「哪一版被谁改过、花在哪儿」有据可查。

今天连「改了几次」都还没有地方记。而 `optimize` 这种「对着文档反复迭代」的用法恰恰最需要回退——用户满意的那一版，很可能不是最后一版。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 继续不做（维持单表覆盖） | 零改动 | 改坏了回不去；AI 优化迭代几轮之后，之前满意的那一版永久丢失 |
| **B. 正文全搬进 `document_versions`，`documents` 只留 `current_version_id` 指针（推荐）** | 版本链成为正文的**唯一**家，「当前是哪一版」由指针显式表达；历史只增不改 | 单表读正文的代码全要改成 JOIN；删掉原表正文列是**单向门**，回滚只能靠备份 |
| C. 版本表只存「被替换掉的旧稿」，当前稿仍留在 `documents.content` | 读当前稿的代码零改动，改动面最小 | 正文有两个家（当前稿一列 + 历史一表），列版本列表要跨两处拼；且「当前稿」与「历史里最新那条」谁是权威只能靠约定维持，迟早漂移 |

### Decision

**选 B。**

1. **新增 `document_versions`**：`document_id / version_no / content / content_sha / pending_items / last_run_summary / source / note / metadata / created_at / updated_at`，`UNIQUE(document_id, version_no)`；`document_id` 外键 `ON DELETE CASCADE`。`documents` 退化为「**身份 + 当前版本指针**」（`current_version_id`，`ON DELETE SET NULL`）——正文只有一个家。
2. **版本产生时机**（这次裁决的核心口径，也是最容易写错的一处）：
   - **整篇生成**（`prd` / `api_docs` / `prompts`）→ **追加一条新版本**，并让下游产物失效；
   - **`optimize` / `clarify`**（对同一份文档的就地改写）与**用户手改** → **就地改当前版本**，**不新增条目**；
   - **「存为新版本」(checkpoint) 与「恢复」(restore)** → 追加新版本。
   前两条由 `job_service._regenerates_whole_document` 判定，且它同时驱动「是否追加版本」与「是否删下游」——两个语义**恒等**，因此收敛成同一个 `append_version` 标志，避免出现「该追加却不删下游」这种自相矛盾的组合。
3. **恢复的实现是「读源版本 → 追加一条 `source='restore'` 的新版本」**，**不把指针拨回旧版本**。拨指针会丢掉「曾经恢复到哪一版」的痕迹，更要紧的是：旧版本一旦被就地改（手改 / 优化），历史就被篡改了——「只增不改」是版本链唯一站得住的性质。
4. **待确认清单与用量回执随版本存档**：`pending_items` / `last_run_summary` 是版本行上的**显式列**（不塞进 `metadata` 口袋）——它们是「一次生成」的第一类产物（ADR-023），恢复某一版时连清单一起还原，而不是恢复出一份与正文对不上的旧清单。
5. **对外结构逐字段不变**：`DocumentItem`（`kind` / `content` / `pending_items` / `last_run_summary` / `updated_at`）照旧，因此**读文档的调用方（路由、前端 store）一行都不用改**；版本是一组**新增**的读 / 写能力，不是替换。`_to_item` 仍从「文档行 + 当前版本行」的 JOIN 结果上取同样的几个字段。
6. **迁移拆三步**（沿用 ADR-022 的清单纪律）：v4 建版本表 + 给 `documents` 加指针；v5 逐行容错地把现有文档回填成 `version_no=1, source='migrated'`；v6 删掉 `documents` 上的 `content / content_sha / pending_items / last_run_summary`。**v6 是单向门**，因此单独成步、并把备份写进部署注意事项。
7. **删除用原生 `ALTER TABLE ... DROP COLUMN`，不重建表**。理由不是省事：`PRAGMA foreign_keys` **在事务内是空操作**，而迁移运行器把每一步包在 `BEGIN ... COMMIT` 里（ADR-022），所以「关外键 → 重建表 → 拷数据 → 改名」那套在步骤内部根本关不掉外键。四列都是普通列（非主键、无 UNIQUE、未进索引 / 外键 / CHECK / 触发器 / 视图），原生删列直接可用。
8. **归属仍由 `solutions` 决定**（`document_versions → documents → solutions` 两级 JOIN），因此版本路由挂在 **solution 作用域**下：`/api/solutions/{id}/documents/{kind}/versions` 等，而不是 4.3 草稿里的 `/api/documents/{kind}/versions`——后者没法在 SQL 层过滤归属，会破坏「越权与不存在不可区分」的既有口径（ADR-009）。版本不存在复用 `SOLUTION_NOT_FOUND`（404），错误码表不膨胀（ADR-012）。

### Consequences

- **变容易**：「这份文档一共几版、每版是怎么来的、什么时候」一句 SQL 就问得出来；改坏了能回到任意一版；`metadata` 口袋为 v3.1 E 的 `quality_gate` 留好了位置，不必再动结构。
- **变困难**：删列是**单向门**——v6 之后旧代码读不到 `documents.content`，回滚只能恢复迁移前的库文件；`documents` ↔ `document_versions` 是一对**环形外键**（指针 SET NULL / 外键 CASCADE），写入顺序必须是「**先空指针插文档行 → 插版本 → 回填指针**」，反过来会撞上「指针指向还不存在的版本」，而删方案要把两级都清干净（由测试钉死）；读当前文档的查询一律变成 JOIN，「当前版本」这件事不再由数据摆放隐含表达，而是由指针显式给出。
- **中立**：ADR-009 没有被破坏——版本表是后端**自己的**表，`solutions.data` 仍是不透明快照。ADR-021 的三条（单表所有权、写入口唯一、前端两条通道）**全部成立**，这次只是把「正文」从那张表里挪进它自己的历史里；`commit_generated` 的调用方从「整批替换三列」变成「追加一版 / 就地改一版」，语义没变，落点没变。

## ADR-030：版本抽屉是 ADR-015 的一次有意例外——内容操作可以有自己的面板

**状态**：Accepted（2026-10-16 裁决并落地）

> **补记（同日）：预览的形态与删除的落点**。抽屉随后补了两个内容操作，都仍在这条边界的**内侧**：
>
> - **点某一版即预览该版正文**。形态选了「抽屉**就地加宽**到 640px」而不是「切到中间正文区」：
>   主区域由 `ViewState` 驱动，为「看一版历史」新增一个阶段要把阶段表、进度条、底栏都跟着改一遍，
>   而这件事并不需要它们参与。360px 窄栏读长文要频繁滚动的代价，由加宽抵掉——换来的是**零状态机
>   改动**。预览里也带「恢复此版本」，因为看完一版最自然的下一步就是「我就要这一版」。
> - **每一条历史版本自带「删除」**，两步确认（先展开「删除这一版？」再确认）。它就在那一行旁边，
>   正是第 1 条说的「上下文不丢」；当前版本不给这个按钮，也不给「恢复」（都是点了没用的动作），
>   只写一句「当前版本不能删除或覆盖」说明为什么。
>
> 两者都仍是**内容操作**：预览是只读的，删除删的是历史版本、不动当前正文。流程动作依旧只在底栏。
> 本文正文保留裁决当时的形态，不回改。

### Context

ADR-015 定下「底栏是全站唯一操作落点」，理由是不让用户面对「东一个西一个的按钮」，每换一屏都要重新找「下一步」在哪。这条一直被严格执行：新增入口一律先进底栏。

版本历史带来一个新形态：它天然是**一份列表**（第几版、怎么来的、什么时候），要么常驻在正文右侧、要么做成可收起的抽屉。无论哪种，如果坚持「按钮只能出现在底栏」，列表里的每一项就没法带自己的「恢复此版本」——用户得先选中某一版、再回头看底栏有没有变出按钮，**上下文（我选的是哪一版）还得额外存一份**。

而 ADR-015 真正要防的是**流程动作分散**（生成下一份 / 完成 / 返回在两处各有一个，用户不知道该点哪个），**不是「内容操作不能有自己的面板」**。把「内容操作」与「流程动作」混为一谈，会让这条规矩从「防止迷路」变成「限制表达」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 版本列表里的按钮也全部收进底栏 | 严格守住 ADR-015 的字面，无例外 | 列表项不能带自己的动作；「恢复的是哪一版」这个上下文要额外持久化；用户要来回看两处 |
| **B. 抽屉里放内容操作、流程动作仍只落底栏（推荐）** | 列表项自带动作、上下文就在眼前；ADR-015 要防的事一点没松 | ADR-015 的字面被开了一个口子，必须把边界写死，否则下次有人照此把「生成下一份」也搬进面板 |

### Decision

**选 B，并把边界钉死：**

1. **抽屉定位为内容区的一部分**，不是第二处流程落点。它内部只允许出现**内容操作**（存为新版本 / 恢复某一版）——都是「对这份文档本身做的事」。
2. **流程动作永远不进抽屉**：生成下一份、完成、返回、重新开始，一律仍只在底栏。
3. **进入抽屉的入口仍在底栏内容行**（审阅页的「版本」按钮）。用户找操作仍然只有一个地方，`ReviewStage` 也不持有抽屉状态——它只把「用户想开版本历史」这件事抛给上层。
4. **抽屉以 `--shell-action-bar-h` 作下边距，不遮底栏**：底栏永远可见、可点，主操作的位置与唯一性不受影响。
5. **抽屉是 `fixed` 浮层、默认收起**，因此**不挤中部布局**（正文仍是 768px 居中）——这次例外不牵连任何布局改造，代价仅限于「多一层浮层」。
6. 抽屉**不 import 任何 store**（纯 props in / events out），与底栏没有耦合；两个写动作的归属与加载都收在 `stores/documentVersions.ts`。

### Consequences

- **变容易**：版本列表与它自己的动作待在一处，用户不必记住「我选了第几版」再去找按钮；`AppActionBar` 的流程行一行未动，主操作仍最右且唯一。
- **变困难**：ADR-015 从「**一律**进底栏」变成「**流程动作**进底栏、**内容操作**可以有面板」，判断标准多了一条——每个新入口都要先回答「它是流程还是内容」。答案没有机器判据，只能靠 review 守，因此这条边界写在本 ADR 而不是散在代码注释里。
- **中立**：`ui/AppActionBar.vue` 的机制未变（仍是唯一**流程**落点）；本次例外只覆盖「内容操作」，`ui/VersionDrawer.vue` 是新增的独立组件，将来就算删掉它，底栏也不需要改动。

## ADR-031：入口页按「两组四叶子」重排，并把「我有 PRD + 接口文档」补成真流程

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

入口选择器（`EntryStage`）是 v2 落地的：一屏三张**平铺**卡片（完整流程 / PRD 快捷 / 提示词调试）。
它解决了「用 Tab 切换入口看不见全貌」的老问题，但自身留了一个新问题——**三张卡片是三个不同层面的东西混在一起**：
「完整流程」与「PRD 快捷」回答的是「我要自己说清楚需求，还是先出个稿」，而「提示词调试」回答的是
「我手上已经有材料了」。用户得逐张读文案才能认出哪张是自己的情况。

产品侧同时提出了第四条路：**手头同时有 PRD 和接口文档**时，应该能一次把两份材料都交进去。
这带来两个必须一并裁决的问题，否则「加一个叶子」会变成「加一个点不动的空壳」：

1. **它和「我有 PRD」的差别是什么？** 后端 `prompts` 任务当时的入参只有 `prd_content`
   （`prompts.py` 的模板占位符只有 `prd_content`），也就是说——**接口文档压根进不了那次请求**。
   照着文案做一个「双粘贴」页，用户贴进去的第二份材料会被**静默丢弃**。
2. **`prompt-debug` 这个名字还准不准？** 它成文于「靠反复 AI 优化调参」的用法，而现在的说法是
   「我有 PRD」，语义从「调试」变成了「导入」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 只做 UI 重排，第四条入口先不做 | 改动最小，纯前端 | 「导入已有素材」组只剩一个叶子，与「两组各两条」的对称结构不符；而缺的那条恰是「材料更全」的常见情况 |
| B. 四条都做，但第四条复用「贴 PRD」那一页 | 一屏四叶子，形状完全对称 | **骗人**：第二个输入框收进去的东西不参与生成，用户以为提示词读了接口文档，其实没有 |
| **C. 四条都做，把第二条材料真正接进生成链路（推荐）** | 文案与行为一致；提示词能对齐真实接口路径与字段名 | 这批改动里**唯一动后端**的部分（Job 入参 + 提示词模板两份） |
| D. 顺手把 `prompt-debug` 改名成 `prd-paste` | 键名与含义一致 | 快照里存着旧键，改名要配一套兼容旧值的解析；收益只是好看 |

### Decision

**入口排布选「一屏两组、四个叶子都可见」，第四条入口选 C，键名不动（放弃 D）。**

1. **分组的两轴是「起点」而不是「功能」**：`从零创建 PRD`（自己把需求说清楚）与
   `导入已有素材`（材料已经有了）。用户回答「我属于哪种情况」比「我要哪个功能」快得多，
   因此先分组再选；而**四个叶子同屏可见**——分组加的是语义层级，不是多一屏要点的关卡。
2. **第四入口的键名取 `prd-and-api-paste`**，落到同名的 `ViewState` 与录入页
   （`PastePairStage.vue`）。它和 `prompt-debug` 同属导入组：产物都只有**提示词套件**，
   进度条口径与完成条件因此完全一致（`MODE_STEP_IDS` / `REQUIRED_DOCS` 各加一行）。
3. **`prompt-debug` 这个键名不改**，只改对外的说法（「我有 PRD」）。理由：键名进快照，
   改名就要写一套「旧值也能过」的兼容层，而它解决的问题只是命名美感——
   真正会误导人的是**界面文案**，那个已经改了。这条留在 `EntryMode` 的 docstring 里备查。
4. **第二份材料真的接进链路**：`JobCreateRequest` 新增可选 `api_docs_content`，
   `job_service` 的 `prompts` 分支透传，`generate_prompts_stream` 多收一个参数，
   模板新增 `{api_docs_content}` 占位符（技能包版与 `prompts.py` 兜底版**两份同步**）。
   留空（默认，等于旧的「我有 PRD」）时那一节填 `NO_API_DOCS_NOTE`——
   写成「本次未提供」而**不是留空**：模板里那一节**始终存在**，留空会让模型看到
   「一个标题 + 一片空白」，它既可能当没看见，也可能自己补一份没人写过的接口契约出来。
5. **两份粘贴材料都不落 `documents`**：与 `prompt-debug` 同口径。那是「本工具生成的产物」
   的位置，混进用户自带的内容会让进度、完成条件与下载列表全部失真。它们只作为本次生成的输入。
6. **两份材料分开存快照**（`pastePairInput`，不共用 `debugPrdText`）：两条入口是两个页面各自的
   草稿，合用一个字段会让「在这页贴了、退回入口、又从另一页进去」看到上一页的内容，
   而用户的理解是「我换了一条路，输入框该是空的」。
7. **校验不对称且明写**：PRD 必填（空则主操作禁用 + 缺失提示常驻），接口文档选填——
   文案里直说「留空即按『只有 PRD』生成，与上一条入口效果一致」。用户不必猜截图里那个框能不能空着。

### Consequences

- **变容易**：用户第一眼就能排除掉与自己无关的一半；「材料更全」这条路从文案承诺变成了真实能力，
  提示词里的接口路径与字段名与真实契约对齐。
- **变困难**：`prompts` 生成线从此有**两个输入口**，它们的占位符集合构成一个跨文件的契约
  （技能包 `prompts-guide.md` + `prompts.py` 兜底版 + `document_service` 的 `format` 调用），
  少一处就是 `KeyError` 或永远空着的一节——因此测试同时验「两份模板都带这个占位符」
  「带材料时正文真的进了消息」「不带时写的是那句说明」。放弃 D 的后果是**键名与文案从此不一致**
  （`prompt-debug` 对外叫「我有 PRD」），由 docstring 与本节兜住。
- **中立**：四条入口的生成 / 审阅 / 下载链路仍是同一套，`MODE_STEP_IDS` 与 `REQUIRED_DOCS`
  只是多了两行同值数据；`AppActionBar` 的流程行、ADR-015 的唯一落点、ADR-030 的抽屉例外都不受影响。
  v3 `ARCHITECTURE.md` §8 里「优化四：三 Tab 改 chooser」那条裁决随之**改判**——
  当时判「整篇作废」是因为源文档的三个模式值与本仓库不符，而它要的**结构**（chooser）
  与这次的做法一致；缺的那条流程这次补上了，模式键沿用本仓库自己的那套。

## ADR-032：方案列表的位置与排序按「内容时间」，与「写库时间」分成两根轴

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

左侧「我的方案」那行时间与整个列表的顺序，一直用 `solutions.updated_at`——「最后一次写库」。
问题在于这份快照里同时住着两种性质完全不同的东西：

- **内容**：需求摘要、对话记录、粘贴的两份材料、三份产物；
- **相位**：`viewState`（我翻到哪一页）、`chatTab`（我在哪条对话线程）、`activeJobId`（在途任务指针）。

相位的变化频率比内容高一个数量级——切一下进度条、切一次对话标签都会写一次库。于是那行时间
会被刷成「刚刚」，跨会话的排序也把「刚点开看过的那份」顶到最前，而**作品一个字都没变**。

前两次收口治的是同一抱怨的另外两半，但都治不到这一半：

- `stage` 改成「最远里程碑」（ADR 见 v3 的进度裁决）——治的是「翻页让进度倒退」；
- `mergeIntoList` 改成原位刷新——治的是「当前会话里列表项自己往上蹦」。

只要**时间与排序**仍由 `updated_at` 决定，翻一下页就还是会改变列表（换台机器、刷新之后同样会）。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 什么都不加，界面上干脆不显示时间 | 噪声消失 | 用户丢掉「这份多久没动了」这个信号，而长列表里它恰好最有用 |
| B. 后端解析 `data` 逐字段比内容 | 不必加字段 | 违反「后端不解析 `data`」的既定约定（前端每加一个字段后端都要跟着改），而「哪些字段算内容」这张表也要在后端再维护一份 |
| C. 前端另提交一个「内容指纹」 | 后端不必解析 | 多一个需要两边对齐的派生量；而且指纹解决不了排序——排序仍然得存时间 |
| **D. 加 `content_updated_at` 列，由前端报 `content_changed` 决定是否推进（推荐）** | 两根轴各答一个问题；显示与排序都有依据；排序落在 SQL 里，跨会话成立 | 加一次迁移；保存载荷多一个字段；前端多一处「哪些改动算内容」的判断 |
| E. 让相位不进快照（`viewState` 等不落库） | 改动最小 | 「刷新后回到上次看的那一页」会消失——那是一条有真实用处的行为 |

### Decision

**选 D。**

1. **两根轴的职责写死**：`updated_at` = 「这份记录最近一次被写是什么时候」（诊断、备份口径）；
   `content_updated_at` = 「这份**东西**最近一次真的变了是什么时候」（给人看）。
   列表的时间显示与排序**都用后者**，前者照旧每次都写、也照旧在接口里。
2. **「哪次保存算内容变更」由前端判定，后端只转手**。后端不解析 `data`，分不出「翻了一页」
   与「改了内容」；让它去猜只能靠解析或 diff 快照，两条路都会把前端契约焊死在后端。
   字段名 `content_changed`，**缺省为假**——还没有这个字段的老前端发来的保存，不该把内容时间
   顶到当下（轴一旦被无意义的写入推着走，就再也读不出它本来的意思）。
3. **判定的两个来源分开记数，避免 store 互相引用成环**：`workflow.contentTick`（快照里的内容字段）
   与 `documents.contentWriteTick`（正文写入：生成 / AI 优化 / 手改 / 版本操作），在 `stores/solutions.ts`
   里合并成 `content_changed`。三份产物的正文住在后端 `documents` 表里、**不经过快照**，
   只有第二个计数能看到它们——否则「生成完 PRD，列表时间还停在填表单那一刻」会成为常态。
   不把这件事做进 `workflow` 是因为 `workflow` 已经依赖 `documents`（要按产物判断进度），
   反向再依赖就成环。
4. **基准只在写成功之后推进**。失败也推进的话，那次变更会被算作「已经记过」，下一次保存报
   `content_changed=false`——时间轴就永久丢掉一次内容变更，而且是静默的。
5. **迁移 v7 的回填取 `updated_at`**，不是迁移时刻：旧行没有依据可考，这是没有信息时的最保守
   选择，它**保住旧方案之间原有的相对顺序**；全部并列会让列表看起来像被重排过一遍。
6. **口径备案**（有意不含的也算决定）：「内容」= 用户输入（表单 / 对话 / 粘贴的两份材料）
   ＋ 三份产物的生成、AI 优化、手改、版本恢复与删除。**切阶段、翻看、切对话标签都不算**。

### Consequences

- **变容易**：列表那行时间成为可信信号；只翻看不再改变顺序，而且这条在刷新、换机器之后同样成立
  （排序落在 SQL 的 `ORDER BY`，不再依赖前端的原位刷新）。
- **变困难**：`solutions` 的时间轴从此由「前端判定 + 后端时间戳」共同决定，它的正确性依赖前端
  **不漏报**——将来新增任何「会改动作品」的路径，都必须在写成功后报告一次内容写入
  （`documents.markContentWritten()`）。漏了不会报错，只会表现为「列表时间不动」。
  这与「写正文的唯一入口 = job 成功收尾」是同一类约定：靠一处收口，而不是靠每个人都记得。
- **中立**：切阶段仍然照旧写库（相位要落盘），只是不再影响内容时间；`update` 的 SQL 语义是
  「整份覆盖 + 条件推进一根轴」，请求仍是幂等的整份覆盖，没有引入字段级补丁。

## ADR-033：澄清提问产出「结构化选择题」，前端渲染成可点选项卡

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

澄清对话里 AI 的提问一直是一段 Markdown 自由文本，用户只能自己组织一句话回答。
而 `CLARIFICATION_QUESTION_RULE` 早就要求「**提问要带引导**：先给一个可判断的参照，再问用户
怎么看」——参照已经给了，但**用户仍然只能打字**。参照越是几个并列方向，打字越累、答得越随意
（「都行」「看情况」），而这三个字对后续文档没有任何信息量。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 前端解析 Markdown 里的 A/B 列表 | 不必动后端 | 那是模型自由发挥的产物，解析规则只能靠猜；哪天它写成「方案一 / 方案二」就**静默失效**，没有报错、只是卡片不再出现 |
| B. 新增一种 SSE 事件类型携带结构化问题 | 语义最清晰（事件名本身就说清了） | 要动 SSE 契约与各事件消费点；而 `done` 的 `data` 本来就是任意 dict，加一个键即可 |
| C. 让模型直接输出 JSON 全文 | 结构最规整 | 用户要能读那段解释——纯 JSON 读不了，等于把「解释每个选项」这件事挤掉 |
| **D. 正文照常写 + 末尾附哨兵块，`done` 带上结构化数据（推荐）** | 复用已被验证的「哨兵块 + 流式抑制」机制；正文可读、数据可解析；哨兵是 HTML 注释，漏出也不可见 | 提示词变长；模型可能不产块（功能退化） |
| E. 复用待确认清单（`pending_items`）那条通道 | 零新机制 | 两者生命周期不同（那份要落库、要按 P0~P6 排序）；混在一起会让两套正交的校验互相牵连 |

### Decision

**选 D。**

1. **哨兵块**：`<!-- ASK:BEGIN -->` / `<!-- ASK:END -->`，与待确认清单同范式。抑制器**复用**
   `PendingBlockSuppressor`（只把哨兵参数化）——那段状态机的全部难度在「哨兵被切在 chunk
   边界」，复制一份等于把这个坑复制一份。
2. **数据挂在消息上**（`ChatMessage.asks`），**不加顶层快照字段**：消息经 `parseSessionSnapshot`
   是整对象展开的，未知字段天然保留；而加顶层字段要同步四处快照逻辑、还要改契约测试钉住的键清单。
3. **只有当前线程的最后一条消息可交互**。判据刻意**不是**「最后一条 assistant 消息」——
   用户一作答，推入的是 user 消息，用后者会让卡片一直可点（同一个问题能被反复回答）。
   用「最后一条消息」还顺带解决了流式期间的可点性：流式气泡挂在末尾，提问那条自动退成只读。
4. **作答是「先点选、再点提交回答」**。一轮可能问 1~2 题（`CLARIFICATION_QUESTION_CAP`），
   一次答完再发才成立——点一下就发的话，第二个问题没机会答。选项与「都不合适、我自己写」
   **互斥**而不是分优先级：两者并存再去定谁赢，用户永远不知道提交的到底是哪个。
5. **提交走既有的 `sendMessage`**：它就是一封普通的用户消息（带 `stage`、进本线程历史、
   `chatStreaming` 期间禁止再发）。分两条通道只会多出一处要同步的守卫。
6. **写回会话历史的是剥离后的干净正文**。带块的原文一旦回流，下一轮会被当作 assistant 消息
   喂回模型——既污染上下文，又会让模型学着继续吐块。
7. **选项的 `label` 与 `id` 由后端分配**（同「不信任模型给的 `id`」）；`multiple` 只认真正的
   布尔真，字符串形式的 `"true"` 一律按单选——把单选题渲染成多选，用户第一眼就会察觉不对。
8. **校验从宽、降级不报错**：坏项逐条丢弃（选项不足 2 个、没有题干、选项没有正文），
   但**绝不让这一轮失败**——退化成纯文本提问即可。「不产块」是常态，不是异常。

### Consequences

- **变容易**：带引导的提问终于能一键作答；提交文本自带题干与选项标号，模型不必猜「他答的是哪题」。
- **变困难**：多了一条**提示词 ↔ 解析器**的跨文件契约——规格文本由
  `clarification_ask.render_ask_spec()` 生成、提示词引用它（见 `prompts.py` 的导入注释），
  而不是两边各写一遍。⚠️ 另一处新债：**模型不产块时功能静默退化**，只在日志里留下空数组；
  这是刻意接受的（宁可退化，不能报错），但要靠观测去发现。
- **中立**：`api/schemas.py` 未变（提交的仍是 `content: str`）；待确认清单那套完全不动，
  连抑制器都只是参数化（默认行为逐字节不变，既有用例全绿）。

### 修订（2026-10-16，同日）

**「自行填写」的入口形态改了**——决策 4 提到的那个入口，原实现是「一行文字按钮『都不合适，我自己写』，
点它就地展开输入框、按钮文案变『收起』」。用户当天反馈：**不该靠一个按钮去调出输入框**，
直接在选项卡片下面放一张**同款卡片**、卡片里就是输入框即可（`placeholder` 恰为「都不合适，我自己写」）。
已按此改：

- **常驻**，没有展开/收起状态——`drafting` 状态与那个按钮一并删除。理由与决策 3 同源：
  「还能自己写」本该**一眼看见**，收在按钮后面等于没有。
- 卡片复用选项的视觉（圆角 / 边框 / 背景 / 内边距 / 阴影 / 字号逐项对齐），内嵌输入框**去掉自身边框与背景**——
  否则会出现「框里还有框」的双层边框。已有自填文字时整卡走高亮配色，与「选中了某个选项」同一种可见性。
- **互斥的判据从「原始输入非空」收紧到「去空白后非空」**（`setDraft` 里的 `text.trim()`）。
  改之前两处口径不一致：卡片高亮用的是 `.trim()`（纯空白不高亮），清选项用的却是原始输入——
  于是「点 A → 误敲一个空格」会把 A 的选中态静默清掉，而此刻**没有任何有效作答**（提交按钮仍是
  `disabled`），用户落到「什么都没选、也交不上去」。改完 **「卡片亮 ⇔ 该题选项已让位」恒等**。
  诚实记一笔：它**不**解决「敲了真实字符之后又删光」（那时已在首个真实字符处清掉了），
  只消除「空 → 空格 → 空」这类纯噪声触发。
- 只读态（历史消息）**不渲染这张卡片**——与「历史消息的选项本来就点不动」同一个取舍，
  再留一张打不了字的空框只是噪声。
- 决策 4~8 与降级口径**不受影响**：作答仍是「先点选 / 先写字，再点提交回答」，提交仍是一条普通用户消息。

### 再修订（同日，第二次调整）

**那张自填卡片被撤掉了。** 用户看过实际效果后反馈：「去掉选项卡附带的输入框吧，直接在选项提交按钮标注一行
『若不满意选项，可以自行在输入框输入想法』」。已按此改：

- 组件内**不再有任何输入框**：`drafts` / `setDraft()` / 互斥判据一并删除；`answered()` 只认「有选中项」，
  `answerOf()` 只剩选中项这一种写法（`（自填）…` 分支随之消失）。
- 提交按钮旁**常驻**一行指路文案：`若不满意选项，可以自行在输入框输入想法`（「输入框」指页面底部的聊天输入框）。
  它取代了原来 `answeredCount === 0` 那句「选一个选项，或自己写」——那句指的正是不再存在的卡片。
- 多题未答那句动态提示保留（`还有 N 题未作答，也可以先提交`）；这一行改用 `flex-wrap`，窄屏允许折行
  （实测：宽屏三者同行，窄屏自动折到第二行，不挤压）。

**为什么不做「两个输入框共存」**：底部聊天输入框**一直都能**直接打字作答，卡片里再放一个，会让人以为
「必须在这儿写才算数」，还多出「两个框以谁为准」的问题。**把既有的一条路说出来，好过再造一个控件。**

⚠️ 前一节修订（常驻卡片方案）**原样保留**，是因为它完整记下了「先做卡片、看过之后否掉」这个判断过程——
与本文其余部分一样，**决策的历史比决策的结论更值钱**。本日两次调整的净结果：
选项卡组 = 选项卡片 + 提交回答 + 一行指路，且**组件内零输入框**。

### 再修订（2026-10-19：提问机制整体换成原生工具调用）

**这是机制级更换，不是调参。** 起因是线上那个 bug：续聊几轮之后选项卡**静默不弹**。定位结论是模型停止产出
`<!-- ASK:BEGIN -->` 块——它在历史里见过自己「只写 A/B/C 文字、不附块」的写法之后，就会照着那个样式继续写。
哨兵机制把「结构」寄托在模型的**自由文本习惯**上，而习惯是会漂移的；更要命的是决策 8 那条「校验从宽、降级
不报错」在这里成了帮凶——退化得**毫无声音**，只在日志里留一个空数组。

改成原生 function calling（对齐 Claude Code `AskUserQuestion` / Codex `request_user_input`）：题目走**独立的
工具调用通道 + schema 强约束**，不再依赖模型「记得在自由文本里附标记」。正文照常写给人看，两者互不干扰——
正文天然干净，连抑制器都不再需要（它回到只服务待确认清单）。

**分三步落地**（Step 0 是硬闸门）：

0. **spike 先证**：一次性脚本直连 `doubao-seed-2-1-turbo-260628`，打印流式 `delta.tool_calls` 的**真实分片格式**
   ——不看真实分片就动手，等于拿猜的去写解析器。
1. **提问侧**：`build_ask_tool()`（1~2 题、每题 2~6 个选项，schema 里的数字与 `MIN_ASK_OPTIONS` /
   `MAX_ASK_OPTIONS` 同源，防漂移）；`render_ask_tool_instruction()` 取代 `render_ask_spec()`，仍由提示词
   **引用**（跨文件契约只此一处）。绑定口径 `tool_choice="auto"`（收尾轮 / 复述轮本来就不该提问，**不能强制**）
   + `parallel_tool_calls=False`（一轮至多一次调用 ⇒ 作答只需回一条工具结果）。
2. **作答侧**：`ConversationContinueRequest.tool_result = { tool_call_id, answers: [{ask_id, labels, question,
   texts}] }`，后端把它作为 `ToolMessage` 回给发起提问的那次调用。**这是「完整对齐」的关键**——只做提问侧的话，
   工具调用只是一条更华丽的传输通道，作答仍是人话，白白背上契约成本却没消掉退化。

**ark 怎么接**：`VolcanoArkChatModel` 从自写包装类改成 **`BaseChatModel` 子类**（`_llm_type` / `_generate` /
`_astream` / `bind_tools`），仍走官方 arkruntime SDK，thinking / `include_usage` / finish_reason 的既有语义一行
不动。为什么不直接换 `ChatOpenAI`：官方 SDK 那层我们还依赖着，换掉等于把方舟特有的东西再实现一遍。
`delta.tool_calls` 映射成 `AIMessageChunk.tool_call_chunks`，**分片拼装交给 LangChain**——那段拼接的坑在于
index 与参数分片，LangChain 已经踩过，不必自己再踩一次。

#### 作答侧四条容易写错的规则（都有用例钉住）

| 规则 | 为什么 | 位置 |
| --- | --- | --- |
| ⚠️ 流式工具调用要**逐片相加** | 只有 `AIMessageChunk.__add__` 会按 `index` 归类、**拼接 `args` 字符串**、补齐 `name`/`id`。把全部分片塞进一个 chunk 再读 `.tool_calls` 是**逐个分片独立解析**：首片（`args=""`）变空对象、残片各自解析失败，一次完整调用被拆成「一条空调用 + 若干条废调用」。真实代价：模型明明调了工具，题目却一个都取不到，**选项卡一张不弹**——详见下面那条诚实记录 | `stream_reply._merge_tool_calls` |
| ⚠️ 工具应答必须与发起调用**相邻成对** | `_reminded_history` 会往历史末尾插一条「格式重申」系统消息，它就排在悬空调用之后。按**下标插入**、不能追加到列表尾，否则上游 API 直接报错 | `conversation_service._build_lc_messages` |
| ⚠️ 作答轮**不再投喂人话** | 带 `tool_result` 时不再追加 `HumanMessage`。同一份作答在上下文里出现两次，模型会以为用户强调了两遍 | 同上 |
| 自由文本要能**兜住悬空调用** | 用户没点卡片、直接在底部输入框打字时，那段文本包成工具应答。否则历史里留下「调了工具却没人应答」的结构——**上游 API 直接报错**，这不是风格问题 | 同上 |
| 配不上就**降级** | `tool_call_id` 缺失或对不上任何悬空调用，一律降级成普通用户消息。绝不发一条没有对应 `tool_call` 的 `ToolMessage` | 同上 |

**落库**：assistant 条目带 `tool_calls`，作答轮把 `tool` 条目（含 `tool_call_id` + `tool_result`）插在提问
assistant 之后、不再另记一条 user 消息。⚠️ **这两件事必须一起上**——只落 `tool_calls` 不落应答，历史里就出现
悬空的 tool_call；这也是 Step 1 特意**不**落库的原因（宁可先不落，也不留半截）。

**待确认清单不跟着改**：它跟着**生成的文档**落库、进快照、按 P0~P6 排序，是文档产物的第一类元数据，生命周期
与选项卡完全不同（后者只随 `done` 下发）。`PendingBlockSuppressor` 保留给它，哨兵参数化不动（默认值不变 ⇒
既有用例逐字节仍绿）。

**前端定下的两条收敛口径**（顺带记下来，后面还会用到）：

- **持久化结构从严**：`ChatMessage` 曾短暂加过 `role: 'tool'` 与 `tool_call_id` / `tool_result`，最后**删掉**了
  ——前端根本不产生 tool 消息（`ToolMessage` 是后端拿请求体自己落的），而 `utils/workflow.ts` 的 `isChatMessage`
  白名单又不认 `'tool'`，于是「类型说可以、快照恢复时整条消息却被静默丢掉」。**类型与运行时打架比少一个字段更危险。**
- **接口契约镜像从宽**：`StreamResult`（`done` 事件的解析结果）保留 `toolCallId` / `toolCalls`——它不进快照、不被
  形状断言，契约发了什么就解析什么。真正的配对走 `asks[].tool_call_id`（一轮多题时每题带自己的来源调用，比顶层
  那个更准）。

### Consequences（本次修订带来的变化）

- **变容易**：选项卡不弹这类退化从根上消失（不再依赖模型的自由文本习惯）；正文天然干净，「半截块漏给用户」
  与「带块原文回流污染上下文」两类隐患一并消失。
- **变困难 / 新债**：① 多了一条「工具 schema ↔ 提示词 ↔ 解析器」的跨文件契约，改一头要动三处；
  ② 题目跨多个 tool_call 拼接时（`parallel_tool_calls` 被上游忽略的极端情况）题目 id 连续但 `tool_call_id` 各异，
  作答只回当前那一次；③ `extract_asks` / `render_ask_spec` **已退役**，文档里凡提到它们的都要改口径
  （本次已一并订正 `v3/README.md` 与 `v3/roadmap.md`）。
- **诚实记一笔**：这次改造**没有**证明「模型一定会调工具」——`tool_choice="auto"` 下它仍然可能不调，
  那时退化成纯文本提问（与旧机制不产块的表现相同）。区别在于：现在「不调工具」与「调了但参数坏」是**两件能分开
  观测**的事（日志里 `tool_called` 与 `asks_count` 两个信号），而旧机制下这两者都只是「没有卡片」。
- **再记一笔（上线后立刻暴露的回归）**：改造完成、前后端全绿之后，用户实测发现**选项卡一张都不弹**，
  比改造前还糟。根因就在上面那张表的第一行：把分片塞进一个 chunk 读 `.tool_calls`，参数从来没被拼起来。
  ⚠️ **真正的教训不在那行代码，而在测试**：所有假模型都是「一整片发完工具调用」——那种数据下错写法也照样通过。
  假模型必须复现**真实的分片形态**（首片带 `name`/`id`/空 `args`，随后每片只带一小段 JSON），
  否则测的是「理想世界」而不是生产环境。现已补 `_ShardedLLM` 与三条分片用例钉住。
- **用例**：改造后后端 **452**（新增 19 例：工具链组装语义、两轮往返、落库形状、四种降级、契约 schema、路由映射）、
  前端 **572**（新增 21 例：卡片结构化载荷与降级、接口收发、composable 挂载与反向断言、端到端 emit 链）。

### 修订（2026-10-21）：题干与选项说明改由卡片承载

**症状**。用户实际使用中发现卡片上只有几个短语：

```
AI：…P0 级还有一个关键流程点需要确认：
    A 填完点按钮一次性生成
    B 分章节逐步生成
    C 实时随填随生成预览
    D 都不合适，我补充
```

不知道在答什么，也看不出四个选项差在哪。原口径是「卡片只放选项名，题干与逐条解释交给正文」，
甚至有一条 `v-if="asks.length > 1"` 把**单题**的题干也省掉（理由是「正文里刚写过」）。

**根因**。这两条都依赖「模型会在正文里把题干和逐条解释再写一遍」，而它常常只写一句过渡话就
调工具。这与本 ADR 当初把哨兵块换成工具调用是**同一个教训**：凡是「要模型记得再写一遍」的东西
都会这样退化。而题干、背景本来就在工具参数里——载荷有，界面却不用，等于白拿。

**决定**。

1. **卡片自足**：题干与 `background` 总是显示（删掉 `asks.length > 1` 这个条件），
   每个选项渲染「标题 + 一句说明」两行。数据全来自载荷，不依赖正文。
2. **选项新增 `description`**（≤40 字，一句话说清「选它意味着什么 / 代价是什么」），
   schema 里**必填**——让它可选就等于允许模型省掉。只给标题时用户等于没得选。
3. **正文只写过渡**：一两句「为什么现在要问这件事」，**不再逐条列 A/B/C**。
   同一段话印两遍，用户还得来回对照。
4. **「名字：一句解释」里的尾巴挪进 `description`，不再丢掉**。旧实现直接删冒号后半段，
   前提是「解释归正文」；前提不成立时说明就两头落空——用户反馈的正是这个。
5. 模型漏写说明时**不让这一轮失败**：`description` 给空串、界面不渲染空行，
   同时打一条 `ask.option_without_description` 告警，便于事后统计发生率。

**代价**：卡片比从前高（每题多一行题干、每选项多一行说明），一屏能放的选项变少；
换来的是「用户不必先读正文才知道自己在答什么」。后者是硬需求，前者可以靠 `MAX_ASK_OPTIONS=6` 与
两题上限控住。

**被否决的替代方案**：只改提示词、让模型务必在正文复述题干与解释。否决理由是这条路已经试过
两轮（哨兵块、以及本 ADR 的正文解说口径），退化只是时间问题；而且它把「界面是否可读」押在
模型的自由文本上，本来就不该这么设计。

### 再修订（2026-10-21 续）：作答回执也要带上下文

上一版把卡片补成自足之后，**作答回执**还是老样子——一行「你选了 A」，刻意不重复题干与选项文本。
用户回看历史时否掉了这条：**卡片一作答就整块消失**（`interactive` 为 false 时整块不渲染），
题干与选项文本再没有第二个地方可看，只剩几个不知所谓的字母。

现在回执是一张轻卡：题干压到两行 + 一行「你选了 A 第一版就做离线同步」。数据全部来自已有的
`ClarificationAnswerItem`（`question` / `labels` / `texts` 本来就在载荷里），**不改契约、不动后端**。

1. **只列选中项**，不把未选中的选项搬上来——回执回答的是「我选了什么」，不是把卡片再印一遍。
2. **压缩交给 CSS**（`line-clamp-2`），不截断字符串：短题干一个字都不丢，长题干自动省略，
   前端也不必猜「多少字算短」。
3. **读屏文案与界面同口径**（`aria-label` 取「题干 + 标号 标题」）。只读标号时，读屏用户遇到的
   正是视力用户刚反馈的那个问题。
4. **残缺数据兜底**：`texts` 为空、题干为空时只渲染标号，不报错、也不用空行占位。

⚠️ 记一条教训：**「用户刚读过」是一次性理由，不是长期结构**。凡是「这段信息只在某个会消失的
界面上出现过一次」，就不能拿「刚看过」当作不落地的依据——回看、刷新、切线程都会把那个前提抹掉。

### 再修订（2026-10-21 三改）：档位式选项必须写清覆盖范围

**症状**。卡片上三个选项只有「轻量版 / 标准版 / 详尽版」，没有说明。这是**同一毛病第三次**出现：
题干与 `background` 已经补上了（见上一节），说明位也留好了，唯独 `description` 是空的。

**诊断**。这一类不是「模型忘了写」，而是「模型认为不必写」——档位词看起来自带含义。上一节定的规则是
「一句话说清**选它意味着什么 / 代价是什么**」，它对「想法快速录入」这种具体做法有效，对抽象档位词
基本失效：**代价是什么**？三档都是「写 PRD」，代价几乎一样，于是模型无话可写，就空着。

**决定（本期只改提示词）**。

1. **把判据从形容词换成可比较的量**：标题是档位 / 程度 / 策略名时，`description` 必须写**覆盖范围**
   ——含什么、不含什么，落到章节数 / 字段数 / 是否含接口与数据模型。
2. **给一组完整的三档示例**（正是用户截图里那道题的形状）：模型模仿整组示例比照抽象规则写更稳，
   单给一条正例不够。
3. **调用前逐题自查**，定义不出来的选项**删掉**：留一个裸标题，比少一个选项更糟。
4. **正文不描述界面形态**（不写「我列了几个选项」「请点选」）：卡片由参数渲染，正文一旦承诺，
   和实际渲染出来的东西就对不上——这也是上一节「正文只写过渡」的延伸。
5. schema 里 `options[].description` 的字段说明、以及续聊轮的 `CLARIFICATION_ASK_REMINDER`
   各补一句同一规则——后者是长对话里最先退化的位置。

**本期刻意不做**（用户明确要求先只动提示词）：

| 未做 | 它能买到什么 | 为什么先不做 |
| --- | --- | --- |
| `strict` 模式（约束解码） | 保证参数形状必然合规，是「第一次就对」唯一机制 | 需先 spike 验 Seed 2.1 + 方舟 tools 是否支持；且它只保证字段存在，保不了非空 |
| 后端准入（缺说明整题丢弃） | 「卡片上的选项必有说明」成为**不变式**，不依赖模型配合 | 会改变行为（模型不合格时这一轮没有卡片），先看提示词够不够 |
| 后端补写说明 | 缺失也能补上 | 用户明确否决：要求第一次生成就带解释，不接受事后补 |

⚠️ 诚实记一笔：提示词对模型是**概率约束**，改完不等于必然生效。观测点是既有的
`ask.option_without_description` 告警——若它仍在刷，就说明这条路到头了，该上「准入校验」
（缺说明的题不进 `asks`），而不是继续往提示词里加字。

## ADR-034：快捷流程并入同一条管线，审阅页的澄清入口拆成「自己去答」与「让 AI 拍板」

**状态**：Accepted（2026-10-17 裁决并落地）

### Context

ADR-031 把入口页重排成两组四叶子之后，「快捷流程」是一条**岔出去的短链**：一段话 → 直接逐章
生成 PRD，进度条只有四步、没有对话、没有澄清、只要 PRD 就算交付完成。实际用下来暴露两个问题：

1. **它省掉的正是最有价值的那一步**。结构化表单的作用是「把话说全」，而走快捷入口的用户往往说得
   最少——真正该补的是追问，不是省掉追问。同一段话走快捷流程产出的 PRD 明显更空，「待确认」
   也更多，用户拿到手还得自己回头找答案。
2. **两条链的差异散落在十来处配置里**（`MODE_STEP_IDS` / `REQUIRED_DOCS` / `STEP_OF_STATE` /
   完成判定 / 审阅页文案……），每加一个阶段要在两个地方各改一次；漏一处**不报错**，只表现为
   进度条算错或完成条件不认。

与此同时，审阅页的澄清入口只有一个按钮：**「回到对话，确认剩下的 N 个问题」**。它把**条数**写进
按钮文案，N 一变按钮宽度就抖；更关键的是它默认「澄清 = 用户自己去聊」，而很多待确认项（分页上限、
超时时间、重试次数）本来就是「给我一个行业默认值就行」的问题，把用户拽进一轮对话是浪费。

### Options

**关于快捷流程**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 保持现状（短链） | 快 | 省掉的正是补全需求的机会；两条链继续各自演化 |
| B. 给快捷流程单独复制一份对话页/进度条 | 两边互不牵连 | 复制的是**最容易写歪**的那部分（断线重试、半截内容、消息分线），改一处漏一处 |
| **C. 并进同一条管线，只换第一步的输入（推荐）** | 「有对话、有澄清、三份齐备」全部免费获得；差异只剩输入映射与两个开关 | 需要一处「极简输入 → 答案字典」的映射，且要保证不把空字段当成「用户答了空」 |

**关于澄清入口**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 保持一个按钮，条数留在文案里 | 改动最小 | 按钮宽度随条数抖动；只有一个出口，不想自己答的人没有退路 |
| B. 拆成两个按钮，条数放按钮旁 | 出口清晰（自己答 / 让 AI 拍板）；动作与状态分离 | 多一个任务类型 |
| C. 两个按钮 + 新开一个「AI 拍板」页面 | 可以展示拍板过程 | 又是一条新链路（新 ViewState、新阶段），与 ADR-015「操作只在底栏」冲突 |

### Decision

**快捷流程选 C，澄清入口选 B。**

> ⚠️ **本文有两处已被文末「修订（2026-10-20）」改动**：决策 1/2 里的「快捷流程也有需求澄清对话」
> 当天被撤回（改为「一段话直接进生成」），相关文案与进度条步数一并调整。照读决策 1/2 会看到
> 已经不成立的说法——以修订段为准。

1. **快捷流程 = 同一条管线，只换第一步输入**。`MODE_STEP_IDS['prd-quick']` 与 `structured`
   同值、`REQUIRED_DOCS` 同值、`STEP_OF_STATE['prd-quick'] = 'form'`、`hasRequirementChat()`
   认它。复用靠**共享配置**达成，不靠任何「if 快捷流程」的分支散落各处。

2. **差异只有三处，且都在数据层**：① `buildQuickAnswers` 只映射两个题号（`product_name` /
   `problem_to_solve`），其余题目对后端就是「问了没答」，正好成为追问清单；② 跳过闸门①
   （快捷入口没有结构化摘要可供回填）；③ 请求体带 `review_enabled: false`。

3. **关掉逐章审核就必须连 `review` 结论事件一起关**。没审却报一句「共 0 个待处理问题」，
   会被读成「审过了、没问题」——那是**假信号**，比不报更糟。`review_enabled` 走**请求体**
   而不是改共享单例：`_get_section_writer(None)` 才返回缓存实例，显式值构造临时实例，
   避免两个并发的 PRD 任务互相污染开关。

4. **审阅页拆两个按钮**：「前往澄清问题」（进当前那份文档的澄清线程）与「AI 自行澄清」；
   剩余条数是**独立芯片**（`#hint` 槽）。按钮名一旦带数字，宽度会随条数抖动，而按钮是**动作**、
   数字是**状态**，两者分开才读得清。落点相同的两种布局规则（顶替「返回」/ `keepBackButton`
   时并存）不变。

5. **「AI 自行澄清」是一个 `auto_clarify` 任务，不开对话**。它拿正文 + 清单，用
   `AUTO_CLARIFY_PROMPT` 让模型以「资深产品负责人」身份逐条拍板：必须给结论、取最保守的通用
   默认值、**不编造具体数字/主体/域名**、只改受影响的地方、清单只留真答不了的。落地视图复用
   `generating-<kind>`，完成后回审阅页——不新开一条链路。

6. **两条改写链路共用一段收尾**（`_rewrite_stream`）：流式 `chunk` 先过抑制器、`done` 时再
   `extract` 一次，得到干净正文 + 重算后的清单。澄清改写与 AI 拍板只差**提示词**；收尾各写一遍，
   「换了正文却忘了重算清单」就有了落脚点。

7. **清单以结构化数据交给后端**（`pending_items: list[dict]`），渲染成人话由
   `format_pending_items()` 负责。它与 `render_spec()` 是一对——后者教模型**产出**清单，
   前者把**已有的**清单念给它听。前端依旧不参与任何措辞（ADR-010）。

### Consequences

- **变容易**：快捷入口自动获得「AI 对话 → 需求澄清 → 三份齐备」的完整能力；进度条、完成条件、
  交付判定全都只有一份实现。用户不想答的问题有了另一个出口。
- **变困难 / 新债**：① 「AI 自行澄清」多一次模型调用，且**结果不可预本地校验**——它可能把
  一个本该由用户提供的事实「编」出来。目前只靠提示词规则兜（不编造数字/主体/域名）与
  「清单只留真答不了的」，没有硬校验；② `DocKind` 多了一个**动作**（`auto-clarify`），
  与两份「东西」并列，判断「哪一份」仍必须用 `isDocumentKind`；③ 快捷入口的主按钮与页面标题
  都改了文案（「直接生成 PRD」→「一句话描述需求」/「提交需求，开始 AI 澄清」），凡引用旧文案的
  地方都要同步。
- **中立**：后端 schema 只加了两列可选字段（`pending_items` / `review_enabled`），既有
  `clarify` 路径逐字节不动；`format_pending_items` 是纯新增函数。
- **用例**：后端 **498**、前端 **601**（后端新增 12 例：`test_auto_clarify.py` 7、
  `format_pending_items` 4、「审核关闭不发结论」1；前端新增 3 例：`autoClarify` 端到端 2、
  「快捷流程不显示需求澄清标签」1，另有 `hasRequirementChat` 1 例与按新语义订正的既有用例；
  `buildQuickAnswers` 的 4 例随该函数退役一并删除）。

### 修订（2026-10-20）：快捷流程**不要**需求澄清对话

决策 1/2 里「快捷流程复用需求澄清对话」这一半，当天就被撤回了。用户的原话是
「输入完极简需求之后直接进入 PRD 生成」——**选快捷入口的人就是不想多聊几轮**，
把追问塞回来等于取消这条路存在的理由。

改动只有三处，方向都是「减」，因此不改既有结论的其余部分：

1. **`hasRequirementChat()` 只认 `structured`**。快捷入口不再有那条线程；`MODE_STEP_IDS['prd-quick']`
   同步去掉 `chatting` 一格（六步 → 五步）。⚠️ **如实少一格**，而不是留一格永远点不亮的步骤：
   进度条是地图，画一条走不通的路比少画一条更糟。文档澄清仍走对话页，但它不是主线上的独立
   一站——停在文档线程上时进度条按那份文档的审阅步算（`stores/workflow.ts::currentStepIndex`
   的既有特例），因此去掉 `chatting` 不会让它错格。
2. **`AppV2` 不再给对话页传四条线程**：`chatTabs` 按模式过滤，快捷流程与两个导入入口只有三条
   文档线程。刻意**不渲染成禁用态**——`ChatThreadTabs` 的「常驻 + 置灰给理由」是为「以后会就绪」
   设计的，而这一格永远不会就绪，留着只会让人以为少了什么。
3. **入口按钮回到「生成 PRD」**，页面标题回到「直接生成 PRD」；`handleGenerateQuickPrd` 撤销，
   统一走 `handleGeneratePrd`（它把「快捷流程」的分支放在 `canGeneratePrd` 守卫**之前**——
   那条守卫的前提是「需求线程里至少有一轮 AI 回复」，快捷流程压根没有需求线程）。
   `buildQuickAnswers` 随之退役（它只为「提交答案开对话」而存在），连同 4 条用例一起删除。

**决策 2 不变**：`review_enabled: false` 依旧——「不追问」与「不审不改」是两件事，用户要的是两者。
缺的信息因此全部落到「待确认」清单上，正好由审阅页的「AI 自行澄清」一把拍板（决策 5）。

### 修订（2026-10-20 深夜）：两个澄清按钮叠成一列、加确认框、撤掉重复的「返回」

三处都是形状上的收敛，不动任何决策的实质：

1. **两个按钮上下叠成一列，合起来仍只占一个按钮的高度**（`h-[38px]`，即 `AppButton` 的 `md`
   实测高度，含边框）。它们回答的是同一个问题「这批待确认项怎么办」，只是出面的人不同；
   并排时四个元素挤在一行，叠起来又把底栏撑高一倍。折中是**带分隔线的双行块**——
   `divide-y` 加在子元素上（不额外插 div，否则两行高度不等），容器锁高、`flex-1` 均分。
2. **「AI 自行澄清」先弹确认框**。它会**直接改写正文**且就地改当前版本（不自动留旧稿），
   一次点击就发生太轻了。弹窗写清三件事：会做什么（逐条拍板并写进正文）、按什么规矩做
   （最保守的默认值、不编造具体数字/主体/域名）、不会做什么（真需要用户提供事实的仍留在
   清单里），并提示「想留原稿先在『版本』里存一版」。⚠️ 这句提示是**必须**的：就地改写不留
   旧版本，不能让用户以为随时能回滚。
3. **撤掉与进度条重复的「返回」**。两个从零创建的入口，录入页就是进度条第 1 步「描述产品」，
   点一下就回去，底栏再放一个「返回描述 / 返回对话」纯属重复。判据抽成
   `inputPageOnBar(mode)` → 审阅页 / **生成中** / **交付页**三个视图的 `hideBack`（漏掉后两个，
   用户在生成中与交付页仍会看到一个「返回描述」）。**两个导入入口照留**：它们的录入页
   （贴 PRD / 贴两份）不在进度条上，删了就是死路。生成中那一页的特殊之处是**整条底栏都不渲染**
   ——那里原本只有「返回」一个按钮，只藏按钮会留下一条空栏。
   ⚠️ 配套修了一处真 bug：`handleStepClick` 原来把步骤 id 直接当阶段用，快捷流程点
   「描述产品」会被送到**结构化表单**——而这一格正是撤掉「返回描述」后的唯一退路，送错等于没给退路。
### 修订（2026-10-21）：两处口径回补——「AI 对话」那格补回、快捷流程的后两份也一遍过

上一版修订把 `MODE_STEP_IDS['prd-quick']` 里的 `chatting` 去掉了，方向对了一半，但落下两个坑：

1. **「AI 对话」那一格必须补回**（六步而不是五步）。去掉它之后的症状不是「少一格」这么轻：
   `stepIndexOf('chatting', 'prd-quick')` 找不到该步就返回 `-1` 并归零，于是**用户在文档澄清
   页里聊天时，进度条高亮的是第 1 步「描述产品」**——一个明显错位的状态。修正后这一格的含义
   也就明确了：快捷流程没有**需求澄清**线程（`hasRequirementChat` 依旧只认 `structured`），
   但「AI 对话」承载的是**文档澄清**那三条线程——它们本来就在同一个对话页上。
   ⚠️ 教训：进度条是「阶段 → 位置」的映射表，删一格之前先问「这个阶段还可能被谁访问到」，
   而不是只看主线顺序。
2. **快捷流程的「不审不改」只对 PRD 生效过**。接口文档与提示词走的是另一条整篇链路
   （`generate_api_docs_stream` / `generate_prompts_stream` → `stream_review_and_rewrite`），
   它们的 `review_enabled` 从来没被接进去，因此快捷流程里 PRD 一遍过、后两份照样「审一次 →
   再改一轮」。修复方式是把同一个请求字段接到底：`job_service._build_event_stream` 对
   `api_docs` / `prompts` 两种 kind 也透传 `review_enabled`，两份产物各自在
   `review_enabled_for_whole_document()` 里判定。
   - 默认口径与 PRD **故意不同**：这两份没有对应的配置开关，`None` 一律视为**开启**
     （「只有 `False` 才是关」）——漏传字段不能悄悄把产出质量降一档；
   - 关掉时**连 `review` 结论事件一起不发**，与 PRD 侧同口径：只跳调用、照样发一条「通过」的
     结论，会被读成「审过了、没问题」，是假信号。
### 修订（2026-10-21 续）：界面上的「审核 / 改写」也要一并撤掉

后端跳过调用之后，前端还留着两处「画了走不通的路」的阶段指示，一并按入口裁剪：

1. **`DocPhaseProgress`（接口文档 / 提示词的胶囊条）**：原本写死「生成 → 审核 → 改写 → 完成」。
   快捷流程下后两格永远走不到，用户会读成「还没审到」而不是「这次不审」。
   现在由 `withReview` 决定：为 false 时只画「生成 → 完成」两格。
2. **`PrdProgress`（PRD 管道看板）**：四列「生成 / 审核 / 改写 / 定稿」，快捷流程下中间两列恒为 0，
   同样裁成「生成 / 定稿」两列（网格列数随之从 `grid-cols-4` 变 `grid-cols-2`）。

判据收在状态机里（`hasDocumentReview(mode)`，只有 `prd-quick` 为例外），由 `AppV2` 传给
`GeneratingStage`，再由它转发给两个子组件——**不允许**子组件自己去看入口模式。
写成黑名单而不是白名单：将来加新入口默认带上复核，漏配的代价只是多等一会儿，反过来则悄悄
把产出质量降了一档。

⚠️ **踩到一个 Vue 陷阱，值得记**：`withReview?: boolean` 这种「默认该开」的布尔 prop，
**未传时会被 Vue 自动转成 `false`**（Boolean casting），于是「没传」等于「关掉复核」，
完整流程的四车道被悄悄砍成两条——第一批用例正是靠这个才发现。修法是**显式给默认值**
（`withDefaults(..., { withReview: true })`）。本项目里凡「默认开」的开关 prop 都照此办理。

## ADR-035：「审核 + 改写」改成批注式与分节式，并把上游材料压成骨架

**背景**。三份产物都是「生成 → 审核 →（有问题）改写」。实际跑起来有两个问题叠在一起：

1. **慢**。PRD 是「章节数 ×（撰写 + 审核 + 改写 + 复审）」次调用；接口文档 / 提示词是
   「生成 + 审核 + 整篇重吐」。而改写那一步的输出是**整篇正文**，耗时约等于重新生成一次。
2. **审核在复述正文**。审核提示词只约束了「不要输出解释文字」，没有约束「不要摘录原文」；
   而每条 issue 又要求写清「哪一处、什么问题」——模型要定位「哪一处」，最省事的办法就是把
   那句话抄下来。于是审核输出里夹着大段正文，既费 token，也让「正在审核」的面板刷满正文。

**决定**。

### 一、审核输出改成「批注」，而不是「复述」

问题条目新增 `where` 锚点字段，定位靠**标题路径**（`## 3.2 创建订单 > 请求体`）而不是原文摘录；
提示词里**枚举本文档的章节标题清单**，要求 `where` 取自其中。同时硬性禁止摘录原文，`detail`
限长（超长在解析时截断）。系统提示词补一句人设：你在写批注，不是在重写文档。

配套：两条链路的审核调用各自拿一个**小输出窗口的模型实例**（整篇 `DOC_REVIEW_MAX_TOKENS=2048`、
单章 `PRD_SECTION_REVIEW_MAX_TOKENS=1024`）。审核只吐一个 JSON，用不着撰写级的上限；设了上限
之后模型被迫精简，也顺带掐掉一种隐蔽的最坏情况——输出尾部多吐东西会让 `extract_json_object`
（首个 `{` 到最后一个 `}`）解析失败，然后按「通过」处理，**审核白跑还看不出来**。

⚠️ 这个上限**只能靠换实例生效**：`VolcanoArkChatModel._astream` 读的是 `self.max_tokens`，
`astream(..., max_tokens=...)` 不报错也不生效。而 `llm_factory` 的方舟分支此前**完全忽略**
`**kwargs`、硬写 `settings.ark_max_tokens`——方舟正是本项目默认供应商，等于「按调用调小窗口」
这条路一直是死的。本次一并修掉。

### 二、整篇链路改成分节改写

审核给的 `where` 能定位到章节，就**只重写受影响的章节**，后端按标题替换后拼回全文；输出量
从「整篇」降到「一两节」，通常能砍掉大半时间。`part{replace}` 发的仍是**拼好的完整正文**
（前端是无条件整段覆盖，只发片段会把预览冲掉）。

兜底两条，任一命中就退回整篇重写：
- `where` **一条都定位不到**任何章节——宁可多花一次调用，也不能「报了 N 个问题却什么都没改」，
  那比慢更难解释；
- 拼回后正文比原文短太多（低于 `_MIN_KEPT_RATIO`）——说明分节改写把内容弄丢了。

`DOC_SECTION_REWRITE_ENABLED`（默认开）是一键回退开关。只重写 N 节时，未被改写章节的
待确认项**必须合并保留**：改一节却让清单少一半问题，是最难解释的一类 bug。

### 三、上游材料压成「骨架」

审核要核对的是「有没有编造 / 有没有漏」，需要的是**事实清单**而不是散文。新增纯字符串的
`skeletonize()`（零模型调用）：标题整行保留、表格保留整行（截断）、`-`/`1.` 条目整行保留、
含数字的行保留、代码块只留围栏首行，超长截断并标注省略量。表格**保留整行而不是只留首列**——
接口路径这类关键事实在第二列，只留首列会把它丢掉。

落点：整篇链路的 `requirements`；PRD 的审核输入与 `prior_sections`（前序章节从「全文」变骨架，
总输入从 O(N²) 降到 O(N)）。**撰写侧的需求输入不动**——那是唯一的事实来源。

### 四、PRD 链路三处对齐

1. **改写不再复用完整撰写提示词**。`_rewrite_messages()` 原来是把 `PRD_SECTION_GENERATION_PROMPT`
   整份重发（含 6000 字符字段契约、带 `{{字段名}}` 占位符的模板、对话记录），再追加一段附录——
   改写一次的输入比初次撰写还大。而 `document_service` 里的注释早就写明「模板里的占位符会诱导
   模型重新渲染一遍、字段契约改写不需要它」，**两处口径此前是自相矛盾的**。改用专用精简提示词，
   只含「本章标题 + 当前正文 + 写作规范 + 问题清单 + 指令 + 前序骨架」。顺带修掉两个「## 八」
   编号冲突（撰写提示词末节与改写附录都在用「八」）。
2. **只有 high 才触发改写**（`REVIEW_REWRITE_MIN_SEVERITY`，两条链路共用，默认 `high`）。
   `verdict` 如实反映（medium 照样报给用户），但**是否动笔**看最严重的那条。PRD 的 medium
   第 5 条是「空泛表述：出现『用户管理』『数据看板』这类无法开工的描述」——这几乎必然命中，
   按它改写等于每章都整章重吐一遍。
3. **改写后不再复审**。串行与并行两处循环都从 `while True` 收敛成单次；与整篇链路
   「审一次 → 改一次，不复审」统一口径。副作用是章节数 7 时审核调用 7 → 6。

**被否决的替代方案**。

- **审核原文不推前端**：一度想直接把审核的 `stage_chunk` 掐掉，反正结论在 `review` 事件里。
  否决原因是用户明确要求「要让用户知道审核正在发生」——静默几十秒会被读成卡死。改成批注式
  之后原文本身就短了，推着也没负担。
- **改写改「打补丁」（只输出定位锚点 + 新片段）**：省得更多，但锚点匹配失败率高，且要额外维护
  一套「锚点 → 位置」的容错。分节改写已经能拿到大部分收益，先把这一档做完再看。
- **PRD 改成「写完 6 章统一审一次」**：调用次数从 7 降到 1~2，但单次 prefill 变重、问题定位精度
  下降，且与「单章失败只影响单章」的降级设计冲突。不动。
- **骨架化只留表格首列**：第一版这么写的，测试用例暴露出「接口路径在第 2 列会丢」。改保留整行。

**代价与观察点**。

- 分节改写的定位精度依赖模型给对 `where`。给不准时的可观测信号：日志里出现「`where` 定位不到
  任何章节，退回整篇重写」。若这条频繁出现，说明提示词约束不够，再加严。
- 骨架化是纯规则压缩，可能有「该保留的散文被压掉」的漏网。撰写侧不受影响，审核侧最坏情况是
  少报一个问题——比反过来（拿骨架当事实来源）安全得多。
- `medium` 不再触发改写，意味着用户会看到「有 2 个中等问题」但正文没动。这是有意的：审阅页
  给了「AI 自行澄清」入口，让用户决定值不值得改。

## ADR-036：删除方案时同时取消在途任务，迟到结果按「会话代次」丢弃

**状态**：Accepted（2026-10-21 裁决并落地）

### Context

现象：生成过程中删掉整个方案，模型调用结束后，列表里冒出一份**「未命名方案」**。

根子是三条各自合理的设计叠在一起：

1. **任务与浏览器连接解耦**（R1-T0 的既定设计）：`detach()` 只退订 SSE，任务在后端照常跑完。
   这是「刷新页面不中断生成」的前提。
2. **删除方案只删 `solutions` 行**，`documents` 靠 `ON DELETE CASCADE` 一起走；
   `generation_jobs` 刻意没有外键，任务行留着供用量审计。
3. **前端收尾时无脑自动保存**：`run_summary` 到达 → 写 `documents` → `scheduleSave()`。
   此时 `currentId` 已是 `null`，`saveNow` 走「新建方案」分支，用一份 `entryMode` 为 `null`
   的脏快照建出一份新方案——界面上就是「未命名方案」。

所以问题不是某个 if 写漏了，而是**「删除方案」这件事从来没有裁决过在途任务的命运**：
删除是一个人做的动作，任务结束是另一条时间线上的事件，两者之间没有任何仲裁者。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 只在前端收尾处校验「方案还在吗」 | 改动最小，一行判断 | 后端仍在白跑（可能几分钟的 LLM 用量）；校验与 `run_summary` 之间还有窗口 |
| B. 删除时**后端取消任务**，同时前端按代次丢弃迟到结果（推荐） | 省钱 + 立即止损；两层各自独立成立，任一层单独生效都不会出现幽灵方案 | 要新写取消编排；前端要引入「会话代次」 |
| C. 删方案时顺手删任务行 | 表里干净 | 丢掉用量审计（`generation_jobs` 是唯一的 token 账单来源），且删行不能停掉协程 |
| D. 生成中禁止删除方案 | 不用改代码 | 与「任务与连接解耦」的初衷相悖：用户凭什么因为 AI 在跑就被锁住列表 |
| E. 任务强绑定连接，断连即取消 | 概念简单 | 直接废掉「刷新后重连继续看」——那是被反复验证过的主流程 |

### Decision

**选 B，两层独立生效。**

**后端：取消是「先落库、再打断」。**

1. 新增 `generation_job_repo.cancel_running(owner_id, *, solution_id)`：把该方案所有
   `status='running'` 的任务写成 `failed` + `error_code='CANCELLED'`。**不新增状态值**——
   `status` 是前后端共享的契约，加一个值意味着所有按状态分支的地方都要跟着改；
   `failed` + 明确的 `error_code` 已经够表达「被取消」，且前端本来就把 `failed` 当终态。
2. `job_service.cancel_for_solution(owner_id, solution_id)`：**先**落库，**再**遍历运行时把
   `JobRuntime.cancelled` 置真。顺序不能反——先置内存标记的话，若进程此刻退出，库里那条任务
   会永远停在 `running`。
3. `run_job` 的事件循环在 `_apply_event` **之前**判 `runtime.cancelled` 并 `break`：已经产出的
   片段照旧交给前端（用户可能正看着），但后续 LLM 调用不再发生。
4. `_finalize` 加两道防御，覆盖「取消信号来得比收尾晚」：`completed` 且 `cancelled` → 按失败处理、
   **不写文档**；`completed` 且方案已不存在 → 同样不写，并留 `job.solution_gone` 警告日志。
   这两道是纯兜底，正常路径由第 1~3 条负责。
5. 编排放在 `api/` 层：DELETE 路由在 404 判断之后调 `cancel_for_solution`。放这里而不是放进
   `solution_service`，是为了避开 `job_service ↔ solution_service` 的循环 import。

**前端：代次（epoch）是「我还是不是当初那个会话」的唯一判据。**

6. `stores/solutions.ts` 新增 `sessionEpoch`，在 `openSolution`（`applySnapshot` 之前）、
   `startNew`、`remove`（仅当删的是当前方案）三处自增。**删除失败路径刻意不自增**——
   方案没删掉，会话没变，在途任务的收尾应当继续有效。
7. `useDocumentPipeline.ts` 用 `isExpired(epoch)` 取代早先的模块级 `jobEpoch`：
   **代次由每条链在 `job.start` / `job.reconnect` 之前就地捕获，闭包持有、逐层下传**
   （`guardJobHandlers(raw, epoch)` / `handlersForKind(kind, epoch)` / `finishDoc(..., epoch)`）。
   用共享单值会串稿：A 生成中 → 删 A → 在 B 起新任务 → 共享值被覆盖成新代次 → A 的迟到事件
   被误判「没过期」→ A 的正文写进 B。这个缺陷在实现过程中真实发生过，靠变异验证抓出来。
8. `useClarificationChat.ts` 同构：`runStream` 开头定格 `chatEpoch`，增量 / `conversationId` 写入 /
   `chatError` / 消息入栈全部按代次丢弃；但 `streaming` 与 `chatStreaming` 两个开关
   **无条件归位**——它们是渲染状态，卡住就是永久 busy。
9. `saveNow` 两道闸：新建分支遇到 `workflow.entryMode === null` 直接 `dirty=false` 返回
   （历史快照没有这个字段，宁可这一轮不存）；更新分支 `currentId !== targetId` 直接返回，
   不 `mergeIntoList`、不 `documents.attach`——否则迟到的 PUT 会把别人的方案插回列表。

**口径备案（有意不做的事）**。

| 本期不做 | 理由 |
| --- | --- |
| 删方案时连 `generation_jobs` 行一起删 | 那是唯一的用量账单来源；无外键正是为了让它活过方案 |
| 生成中硬拦删除（弹窗「正在生成，确定删除？」） | 用户的删除意图是明确的，拦一下只增加摩擦；正确做法是删了就真停 |
| 新增 `cancelled` 状态值 | 状态是共享契约，扩枚举的收益比不上改动面 |
| 把 `_finalize` 的「查存在 → 写文档」做成事务 | 残留窗口极窄，且不产生任何可观测的幽灵数据（见下） |
| 对话流 HTTP 请求加 `AbortSignal` | 对话没有写文档的收尾，迟到增量的危害等级低一档；要做单独排 |

### Consequences

- **变容易**：删了就是删了——不再出现幽灵方案，也不再为一份已经不要的结果付模型费用；
  两层的判据都很窄（一个 `error_code`、一个整数比较），不依赖「调用方记得检查」。
- **变困难**：任何「会改变当前会话身份」的新路径都必须自增 `sessionEpoch`（切方案、新建、
  删当前方案），漏了不会报错，只表现为「删掉之后还是被写回来了」。同理，新增生成链必须
  **就地捕获代次并逐层下传**，不能图省事读共享变量。
- **中立**：任务与连接仍然解耦，刷新重连的主流程没动；`detach()` 的语义也没动。
- **已知残留窗口（无害）**：`_finalize` 通过 `solution_exists` 之后、写文档之前，若 DELETE 恰好
  提交，任务会落 `completed`、文档被 CASCADE 清掉。此时库里没有孤儿正文、前端也收不到可渲染的
  结果，**无可观测幽灵数据**，因此不为此引入跨请求事务。
- **代价与观察点**：
  - 取消是「尽力而为」——`break` 只能在下一次事件边界生效，正在飞的那次 LLM 调用不会被掐断。
    可观测信号：删除后日志里出现 `job.cancelled` 与随后的 `job.solution_gone`。
  - 测试口径被这条改动重写了一次。真值断言不能只看「文档没写」——`_finalize` 的兜底会让它
    永远成立，看起来像守卫有效。**能露馅的是两样东西**：`documents` 的内容，以及
    `activeJobId` 这个指针（A 的迟到收尾若执行到 `clearActiveJob()`，会清掉 B 的指针，
    用户侧表现是「B 生成到一半，刷新后找不回任务」）。
  - 另一个测试陷阱：PRD 链路走 `onPart`，对 `prd` 链调 `onChunk` 是**空转**——把守卫整个删掉
    也不会红。四个链路的「迟到事件」用例必须各自走自己真实注册的回调，否则是假通过。
  - `docStreamingContent` 在 `finishDoc → goTo()` 时会清空，所以「迟到的增量有没有串进预览」
    在收尾之后不可观测。测的是文档与任务指针，不是缓冲。

## ADR-037：运行态去全局化——把「有没有任务在跑」换成一支带身份的运行态

**状态**：Accepted（2026-10-21 裁决并落地）

### Context

现象：**模型正在生成内容时，界面上其它页面全都点不进去。**

追下去是一条三环相扣的链：

1. `stores/workflow.ts` 里有一个无归属的全局布尔 `docGenerating`，它的语义被当成三件事
   一起用：渲染归属（这块界面是不是正被写）、重入守卫（能不能再发一次）、**导航闸门**
   （忙的时候不许切页面）。
2. 于是 `busy = chatStreaming || docGenerating`，而 `goTo()` 的第一行是 `if (busy) return false`。
3. 所有页面跳转都收口在 `goTo()`，**而所有调用方都忽略了它的返回值**。

静默吞掉返回值，就是「点了没反应、也不报错」。侧栏切方案走 `router.push`、不经过 `goTo`，
所以现象才是「*一些*页面点不进去」而不是「全都不行」——这个不均匀本身就是根因的指纹。

根子不在 `if`，在那个布尔**没有归属**：它不说是谁在跑、跑的是哪一份、属于哪个方案。
于是「忙」只能被理解成「整个应用忙」，无法回答真正的那个问题——**忙的是不是我现在看的这一份**。

### Decision

**把布尔换成一支带身份的运行态（`stores/runs.ts`），并让三件用同一判据的事各取所需。**

一支 `ActiveRun` 记四个身份字段：

| 字段 | 回答什么问题 | 谁在判 |
| --- | --- | --- |
| `jobId` | 这是**哪一次**任务 | 收尾是否属于我、迟到事件是否作废 |
| `jobKind` | 这次**做了什么**（`prd` / `optimize` / `clarify` …） | 重连时选哪条处理链 |
| `docKind` | 这次写**哪一份产物** | 渲染归属、重入守卫（`isRunningFor(kind)`） |
| `solutionId` | 属于**哪个方案** | 切方案时整体退订、回来时校验 |

**三层判据分开用，互不代替**：`jobId` 管「哪一次」、`sessionEpoch` 管「同一方案被换掉又换回」、
`docKind` 管「写哪一份」。

1. **导航闸门撤掉**。`goTo()` 不再因「有任务在跑」而拒绝跳转；`busy` 只保留信息性语义
   （`hasActiveRun`），继续用于「生成中」这类渲染。
2. **重入守卫换判据**。七条生成链入口改成 `if (isRunInFlight()) return`——判的是
   「本标签页有一支任务在跑」，而不是「某个全局开关为真」。
3. **入口页的拦截保留，但必须给红提示**（`chooseEntry`）：生成中切换入口会把整条管线换掉，
   这一次仍然拦；区别是拦下来要说话（红色浮层），而不是静默 `return false`。
4. **预览与运行态同 store、不同对象**。`RunPreview`（正文 / 看板 / 阶段 / 审核结论 / 错误）
   与 `activeRun` 分开：任务收尾后身份该清，正文却还要继续显示。归属靠同一个 store 表达，
   不靠塞进同一个对象。
5. **订阅改成登记表**（`services/runSubscriptions.ts`）。原先单槽 `controller` + 一个
   `reconnectingJobId` 数字只记得住最近一次订阅，`detach()` 只能中止一路；
   现在按 `jobId` 登记，`detachAll()` 才真的等价于「切方案」。
6. **切方案三步走**：`openSolution` / `startNew` / `remove`（仅当前）在 `sessionEpoch += 1`
   **之前**先 `detachAll() + runs.detach()`。只退订不清运行态 → 新方案一打开就带上一份的正文；
   只清不退订 → 旧任务的 SSE 继续写进新方案。
   **服务端任务不取消**（回到原方案凭指针重连），这是刻意的。
7. **可写 computed 作门面**：`previewField(key)` 让 `useDocumentPipeline` 里几百处
   `xxx.value = …` 一字不改地落到 `runs.preview`，避免「搬运 600 行」这种高危机械改动。
8. **收尾不抢导航**（D1）：`finishDoc` 发现用户已经不在生成页时，只在浮层提示
   「XX 已生成完毕，可在进度条上查看」，不把人拽回审阅页。

**后端补一半：同 kind 的新任务顶替旧的。**

前端不再靠一个全局布尔拦重复发起之后，「同一份文档被两支任务同时写」就必须由后端裁决：
`create_job` 先 `GenerationJobRepository.supersede_active` 把同 owner + solution + kind 下
旧的 `running` 落成 `failed + error_code='SUPERSEDED'`，**再**把内存里旧运行时的
`JobRuntime.superseded` 置真。只落库不够——旧协程并不知道自己的行已经改了，它照旧会跑到
`_write_document`，把新任务的稿覆盖成旧结果。`run_job` 在事件循环里与 `cancelled` 同点判
`superseded`，`_finalize` 据此走「不写文档」分支。

`SUPERSEDED` 与 `CANCELLED` 分开：前者是「被新任务顶替」，后者是「用户删了方案」，
排查时混在一起会得出完全相反的结论。

### 口径备案（本期不做的事）

| 本期不做 | 理由 |
| --- | --- |
| 同一标签页同时跟两支任务 | 界面每一刻只有一个发起入口，正常路径不可达；真发生也只表现为看不到旧任务，不会串稿（落哪一份由后端 `doc_kind` 决定） |
| 跨标签页协同（一处开任务、别处实时看到） | 需要服务端广播通道，与「任务与连接解耦」不是同一件事，单独排 |
| 把 `runs` 扩成任务列表 | 单槽够用，且多槽会立刻要求「哪一支是主」的仲裁规则——收益不明 |
| 生成中允许切换入口 | 会换掉整条管线（含摘要与澄清线程），不是跳转问题；保留拦截 + 红提示 |
| 收尾时自动跳转到审阅页 | 用户明确要求「留在原地，只提示」 |

### Consequences

- **变容易**：任何新页面都可以自由进出，不必再问「现在忙不忙」；「忙」有了明确主语，
  新增判据时只要说清判的是哪一个字段，不必再维护一个全局开关。
- **变困难 / 必须记住**：
  - `docKind` 是**唯一**的「写哪一份」判据。新增任务种类时，若它推不出产物种类
    （`optimize` / `clarify` 那样），后端必须随快照给出 `doc_kind`，前端**不得猜默认值**——
    猜错等于拿 A 的结果覆盖 B。
  - `sessionEpoch` 必须在**发起之前就地捕获并逐层下传**，读共享变量会串稿（ADR-036 已踩过）。
  - `runs.begin` / `runs.restore` 必须返回**响应式代理**。返回裸对象时计时器写入不触发更新，
    症状是「已用时永远 0 秒」这种看起来像别处 bug 的现象。
  - `begin` **不清预览**：预览的唯一写入方是 `useDocumentPipeline`，它在发起前就摆好了现场
    （PRD 要先建空看板，否则首批 `part` 无处可落）。清预览是 `resetDocTransient()` 的事。
  - 顶部提示一律走 `AppV2` 的统一浮层；收尾提示不能和各处内联文案各说一套。
- **测试陷阱（真踩过）**：
  - 「切走时退订」不能只断言 `activeRun` 为空——`applySnapshot` 无指针时本来就会 `clear()`，
    假通过。**能露馅的是订阅登记的 `AbortController.signal.aborted`**。
  - 「切回来还能连」要断言 `runs.pointer` 三个字段齐全，并且「退订在恢复之前」的顺序——
    顺序反了会把刚重建的那一支一起摘掉，症状是「切回来以后再也不重连」。
  - 迁移用例里的版本号不能写死。`test_documents` 曾断言 `run_migrations() == 7`，
    新增第八步迁移后两个用例一起红，而它们与迁移内容毫无关系——改成与 `len(MIGRATIONS)` 比。

## ADR-038：审核侧需求输入不再骨架化，字段契约改走压缩清单

**状态**：Accepted（2026-10-21 裁决并落地）

### Context

一次真实生成暴露出：审核结论里 12 条问题，其中 6 条 `high` 是「编造」——技术栈、部署方式、
性能数值都判成无据可依。逐条追下去，分布很有规律：

- `high` 全部落在「必须对照需求输入才能判定」的章节（页面 / 技术规格 / 非功能需求）；
- `medium` 全部落在「格式与标注规则多」的章节（功能需求 / 项目范围）。

两类问题的成因完全不同，而前者本不该出现。

**根因**：ADR-035 把「上游材料压成骨架」一并落到了 PRD 审核的 `requirements` 上。
`doc_skeleton.skeletonize` 是为 **Markdown 正文**设计的规则压缩器，第五条规则是
「代码块只留围栏首行、块体整块丢」。而结构化摘要（完整流程的输入形态）整篇就是一个
```` ```json ```` 代码块——实测 **6027 字符压成 7 个字符 `'```json'`**，JSON 里的
`technical_constraints` / `ui_pages` / `v2_features` 全部消失；自由文本入口若不含数字，
压出来是空串。

审核提示词里那一节叫「需求输入（唯一的事实来源）」。事实来源被压成空壳之后，
「编造（high）：写了需求输入里检索不到的技术栈」这条判定就退化成**有罪推定**——
输入里什么都没有，任何具体内容都符合定义。撰写侧与改写侧用的都是全文，
所以模型其实按事实写了，是审核在对着空材料指控它。

ADR-035 当时的取舍写的是「审核侧最坏情况是**少报**一个问题——比反过来（拿骨架当
事实来源）安全得多」。这条推理在本案里正好反了：`requirements` 不是「可有可无的散文」，
它就是事实来源本身，拿骨架当事实来源正是那个「反过来」。

### Decision

1. **审核侧的需求输入原样传递，不做骨架化。** 骨架化真正要治的是 `prior_sections` 的
   O(N²) 增长，而需求输入每章都一样、大小固定，本就不属于那个问题——把它一起压掉是
   优化误伤。`prior_sections` 继续骨架化（那是 Markdown 正文，用对了地方）。
2. **提示词把「取证」与「判定」绑死**：评审口径改为「先取证，再判定」——正文里的具体事实
   要逐条拿到需求输入里检索，检索得到就不算问题，输入没提到而正文写「待确认」也不算问题。
3. **严重度由类别决定，不许模型自行升降。** 严重度是改写门槛（默认只有 `high` 动笔）的
   唯一输入，自行裁量意味着「真编造」被判成 `medium` 就永远不会被修。实测里出现过
   detail 写着「属于编造」而 severity 是 `medium` 的条目。
4. **补齐缺失的类目。** 写作规范定义了「事实 / 建议 / 待确认」三态，而审核口径只有
   「编造 / 缺失信息处理」两类，「建议未标注」无处落，只能被塞进别的桶并带走错误的严重度。
   新增「建议未标注（medium）」。
5. **删掉 `low`。** 只有 `low` 时判定口径是 `pass`，问题根本不会出现在结论里——
   留一个永远不生效的等级，只会成为模型「不重要也要写」的出口，把结论灌水。
6. **撰写侧的字段契约改走压缩清单。** 整份 `field-schema.json` 有 8.6KB，而撰写只需要
   三件事：哪些字段必填、每字段是什么、有哪些枚举取值。`examples` / `minLength` /
   `anyOf` / `x_source_aliases` 是给归一化与校验用的，照着写正文时一条都用不上，
   却是每一章都要原样付一遍的输入。`prd_skill.format_field_contract` 把它压成
   约 1.1KB 的清单，字段说明**逐字取自 schema 的 description**（单一真源，不另写一份）。
   整篇生成链路（一次调用）保留完整 schema。
7. **模板与去重的冲突给出仲裁**：第 4 章「认证方式」与第 5 章「安全」在模板里都是必填，
   而「同一条需求只写一次」禁止重复——两条规则同时为真才能不违规，实测每次必报。
   `writing-rules.md` 补第二条仲裁原则：模板优先于去重，两章各写一句不算重复描述。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 机检（把可机判的规则写成代码断言，替掉 LLM 审核） | 结构类规则确实该由代码判，但那是另一套架构；本次先修「判定依据」与「判定口径」这两处地基，机检留待单独立项 |
| 改写后复审 | 每次复审是一整章的输入。口径不变（审一次 → 至多改一次） |
| 审核结论落库 | `document_versions.metadata` 早已为 `quality_gate` 预留，但存什么要先定清「改写后仍存在的问题」怎么算，否则存的还是改写前的旧账 |
| 功能需求要点进一步瘦身 | 已从一整段拆成逐条换行；再削要靠实测哪些条目仍被漏，属另一轮 |

### Consequences

- **变容易**：审核的输入与它的判断依据终于一致了；「事实来源」这四个字第一次名副其实。
  撰写侧单章输入从约 1.5 万字符降到约 2.9 千（字段契约一项就省下约 4.9 千）。
- **变困难 / 必须记住**：
  - **`skeletonize` 只许用在 Markdown 正文上。** 它有一条「代码块只留围栏首行」的规则，
    拿它去处理被 fenced JSON 包住的输入，等于把内容整个扔掉且不报错。
  - 判「编造」的前提是「需求输入里确实没有」。做不出这个前提时唯一合理的表现是**不报**，
    不是有罪推定——这条写进了提示词，但提示词只是约束，不是机制。
  - 新增审核类目时必须同时定 severity：它是改写门槛，缺了这一环等于默认不修。
- **测试陷阱（真踩过）**：
  - 假 LLM 返回固定审核 JSON、用例需求是「做一个演示产品」（骨架化后同样是空的），
    没有任何一条断言**审核提示词里含有需求事实**——于是空材料能一路绿灯跑过全部用例。
    补的 `test_review_sees_the_whole_requirements_not_a_skeleton` 就是钉这一条。
  - 验证「用例真能抓 bug」的办法是把被修的那一行放回去跑一次（红），再还原（绿）。
