## 二、已经做对、明确不要动的设计

重构最容易犯的错是把好的一起推翻。以下仍是全项目最干净的部分，**任何阶段都只复用不替换**：

- **`llm_factory` 的三供应商抽象**：ark / anthropic / openai 统一 `astream`，业务层无感——R1-T4 的超时与重试统一挂在 `stream_reply` 这一个出口上，正是靠这层抽象才不必每个供应商各写一遍。
- **路由层 / service 层 / repository 层分离**：`api` 只解析封装，`schemas.py` 集中契约，`repositories/` 是全项目唯一写 SQL 的地方（review 红线）。
- **SSE 事件协议**：`status / chunk / part / stage / done / error` + 末尾 `[DONE]`，两层异常兜底；PRD 正文以 `part` 事件为准（预览与最终同源，见 8ea4896）。
- **技能包驱动 + 自动降级**：`skills/prd-generator` 缺失时退回内置提示词，服务不中断（R2 只把「静默降级」改成「显式告警 + 可选 fail-fast」）。
- **默认拒绝中间件**（纯 ASGI，避开 `BaseHTTPMiddleware` 对 SSE 的响应体重包）+ 遍历 OpenAPI 路径的不变量测试。
- **快照范式 + owner 强制过滤**（ADR-009）：单表全量 JSON、`Repository` 不接受 `owner_id=None`。

## 三、重订路线图（剩余工作 R0 → R3）

排序原则升级为：**先给手上的测试装上自动执行的网（R0，现 508 个 = 235 + 273），再补核心交付物的可靠性（R1），再工程化资产与可观测性（R2），最后把「能跑」变成「能部署」（R3）。**

> 命名 `R0–R3`（Revised）是为了和已完成的 `P0–P4` 区分——它们不是推翻重来，而是收尾。

---

### R0 · 安全网收尾：CI + 两个未结的护栏项

**周期**：3–5 天（T1 / T3 / T5 已全部完成）　**功能变化**：零　**风险**：低（T3 需对照测试）

**目标**：在动任何有风险的结构之前，先把「测试靠人手跑」和「两个半吊子护栏」解决掉。

| 任务 | 具体动作 | 状态 |
| --- | --- | --- |
| T1 建 CI | GitHub Actions 双 job：backend `uv sync` + `uv run pytest`；frontend `npm ci` + `npm run test:unit -- --run` + `npm run build`（含 `vue-tsc`）。push/PR 触发，红灯拦合并 | ✅ 已落地并跑绿 |
| T5 错误码化 | `code` 与 `detail` 并列（`detail` 一字不改），8 个机器码；**SSE `error` 事件也带顶层 `code`**（原判据来自流内而非 HTTP 响应，见 ADR-012）；前端改判 `isApiError(error, 'SESSION_NOT_FOUND')` | ✅ `7be5989` |
| T3 收尾流式去重 | 把四份重复（两份 `_stream_reply` + `_error_event` + `_extract_text` 副本）收敛到 `services/stream_reply.py` 一处，三个 service 改为调用它；`stream_guard.py` 保持只管截断检测。**先写对照测试固定当前行为，再统一**（详见 ADR-013） | ✅ 已落地 |

**验收**：
- ✅ 推一个空 PR，CI 能红灯拦下「漏跑测试 / 类型错误」。
- ✅ 前端源码零中文错误串判据（由 `tests/test_error_contract.py` 的扫描不变量永久守护）。
- ✅ 合并后：`grep -rn "async def _stream_reply\|def _extract_text" backend/src/backend/services` 归零（由 `tests/test_stream_reply.py::test_services_hold_no_duplicate_stream_implementation` 永久守护）；
  合并前用**差分比对**跑了 12 组场景（正常多块 / 单块 / 截断 / 空输出 / 中途异常 / 结构化分块 / 无 status_text），新旧实现**逐事件完全一致**。

**不做**：不碰持久化、不改 UI、不动提示词内容。

**风险**：T3 合并时两份实现的边角行为可能不一致（`on_finish` 的调用时机、异常后是否还发 `done`）。这是旧路线图 P0-T3 遗留的坑，**必须先用对照测试钉死**再动。

> ⚠️ **规模更正（2026-10-14 实测）**：此前把「`conversation_service.py:366` / `document_service.py:626`」的**行号**误读成了行数，
> 一度把 T3 描述为「365 / 625 行的大手术」。实测两个函数本体分别只有 **44 行**与 **48 行**，
> 且签名只差一个 `on_finish` 参数。T3 的真实风险不在体量，而在**两处调用点各自依赖的边角行为**。

### R1 · 生成可靠性：核心交付物「放心用」

**周期**：2–3 周　**风险**：中（R1-T2 改动生成主链路）

**目标**：把「能生成 PRD」升级成「中断可续、供应商挂了能切、花了多少 token 看得见」。

| 任务 | 具体动作 | 关联债务 |
| --- | --- | --- |
| **T0 生成 Job 骨架** ✅ `1f2ad08` | 新增 `generation_jobs` 表 + 同进程后台任务 + 内存广播 `job_bus` + `GET /api/jobs/{id}/stream`（订阅 / 重连）；生成与浏览器连接解耦，刷新只凭快照里的任务指针重连。表内 `input_fingerprint` / `usage` / `max_provider_switches` 三列随骨架落地 | 新增能力（v3.0 地基） |
| T2 断点续传 | 续传依据是 `generation_jobs.completed_sections`（已完成节的标题→正文，落在**后端自有 Job 表**，不塞进 `solutions.data` 快照——塞快照会与 ADR-009「后端不解析 `data`」冲突）。生成请求带 `resume_from` 时，只补生成缺失节，已完成的节不重复消耗 token。单节失败只重试该节。展开方案见 `./ARCHITECTURE.md` 第 4.1 / 4.6 节 | D7 |
| T4 单次调用自愈（原「供应商 failover」） | 一次调用不可靠时的补救**只在同一供应商内**进行（ADR-016：不自动切换）。`stream_reply.astream_text` 上排三个守卫：调用前预算检查（T5）→ 帧间隔超时 → 整次调用墙钟硬顶；**只在首字之前**重试一次，白名单限定为连接类异常/超时/5xx。三个适配器的 `max_retries` 显式设为 0，重试由本层自管以便失败的尝试也能被计量（`failed_calls`）。全部阈值与次数走 `.env` | D12 |
| **T5 成本计量** ✅ | 每次生成从分块的 `usage_metadata` 取 `input_tokens` / `output_tokens`（LangChain 三个供应商的统一字段；方舟封装需先开 `stream_options.include_usage` 再映射，见第 4.6 节实测结论），经统一 LLM 包装层累加进 `generation_jobs.usage`，Job 完成发 `run_summary`（含总 tokens / 耗时 / 调用次数 / 注入技能）；方案详情可看「本次生成 token 与所用供应商/模型」。**落地细化**：累加点唯一化到 `stream_reply.astream_text`（一次覆盖全部约 10 个流式调用点）；计量器是 `ContextVar` 承载的 `RunMeter`，调用方式不变、`step` 由 `{kind}:{phase}` 自动派生；方舟用量在 `choices` 为空的独立帧上，取用必须在「有无 choices」判断**之前**（原循环在此静默吞帧）；`run_summary` 事件与 `generation_jobs.usage` 同源（同一份 JSON），终态任务重连补发该事件；计量**先于**截断检查，被截断的调用照样计费。
**事前预算同批落地**：有效预算 = min(物理顶 `core/model_registry` 按 provider+model 登记，业务顶 `.env` 按 step 覆盖)，发送前按字符启发式估算（不引 tiktoken，偏高估），超顶即在调用**发出之前**拒掉（复用 `INVALID_REQUEST`，8 码体系不膨胀），逼近上限记一条告警随 `run_summary.warnings` 回传；检查点与计量同在 `astream_text` | D9（成本部分） |

**验收**：
- 生成中途 kill 后端网络/进程，恢复后能从断点续，已完成节不重复计费。
- 把主供应商 key 置空，自动切备用供应商，业务代码零改动。
- 方案详情页能查到最近一次生成的 token 总量与模型名。

**不做**：不做**轮询式**异步任务队列（`POST /job` + 轮询查询会失去逐字流式体感；改为「同进程 `asyncio` 后台任务 + 内存广播 + SSE 订阅」，生成与浏览器连接解耦但保留真流式，见 `./ARCHITECTURE.md` 第 3/4.1 节）；不做多轮自评/批判式生成（先把单次可靠性做扎实）。

**风险**：T2 续传会改变 PRD「一气呵成」的连贯性——保留「整篇模式」开关（ADR-004 已定），两种模式由配置切换，续传仅作用于分章节模式。

### R2 · 资产工程化与可观测性

**周期**：1–2 周　**风险**：低

**目标**：让提示词/技能资产可调试、可审计、可部署；补上出问题时能归因的最低限度观测。

| 任务 | 具体动作 | 关联债务 |
| --- | --- | --- |
| **T6 技能资产加固** ✅ | 开发态（D10）：弃用 `lru_cache` 常驻缓存，改为按「修改时间 + 大小」比对的进程内缓存，改模板下一次生成即生效——顺带不再需要为改模板而重启后端，而重启正是会把正在跑的生成任务废掉的那个动作。生产态（D8）：新增 `.env` 开关 `PRDWRIGHT_SKILLS_STRICT`，缺失即在 `lifespan` 阶段中止启动并列出少了哪几个文件；默认仍为 false，但**降级不再静默**——每次 PRD 生成把 `SkillRef{name, version, fingerprint}` 写进 `run_summary.injected_skills`，没用上技能包时该列表为空，前端据此显示告警。指纹 `sha256(版本 + 各资源路径与内容)[:12]` 同时替掉了「版本号人工 +1」的脆弱约定（详见 ADR-017） | D8 / D10 ✅ |
| **T7 可观测性基线** ✅ | 结构化日志（`LOG_FORMAT` 取 `text` / `json`，两种格式带**同一组字段**）：`request_id` 由格式化器从上下文变量现取，**业务代码零改动**；`extra=` 挂的业务字段按「排除标准属性」自动带出。访问日志记在最外层 `RequestIdMiddleware`（**认证拦下的 401 同样留痕**），`uvicorn.access` 抬到 WARNING 避免同一次请求两行。`/health` 分三项报「DB 连通性 / 供应商配置就位 / 技能目录在位」，`status` 取 `ok` / `degraded` 且**恒返回 200**；供应商一项只校验配置、**不发真实调用**（探针会高频触发，不按次烧额度；`detail` 里如实写明）。**不报「备用供应商」**：自动 failover 已随 ADR-016 取消，预警没有了对象（详见 ADR-018） | D9 ✅ |
| **T9 技能知识层统一（RAG 下线）✅** | 让三条生成线（PRD / 接口文档 / 提示词）都从**同一个来源**取「团队规矩」，而且取的时候不打扰用户。**T9-1 技能注册表 ✅**：产物归属（`applies_to`）与必需资源清单（`references`）改为技能包在 `skill.yaml` 里自述，程序扫描建索引——`job_service` 不再写死种类判断，**加技能包 = 加目录**（ADR-019）。**T9-2 ✅** 把 `core/api_doc_knowledge.json` 的 14 条规范转成可读 md 迁入 `skills/api-docs-generator/`，并从代码中的提示词常量提炼 `skills/prompts-generator/`，验证通过后删除旧 JSON（**不留两份**，否则下次改规范会改错地方）。**T9-3 ✅** 两条生成线改从技能包取规范；删除本地词法检索（分词 / 打分 / 取前 5）、检索接口、以及请求里携带的「用户勾选结果」字段。**T9-4 ✅** 前端删除 RAG 确认页组件、相关状态与 `RagHit` 类型，点「生成接口文档」直接开始（状态机里 `rag-preview` 的登记已同步改四处）。**T9-5 ✅** 测试与文档收口：删除确认页测试、补 `load_skill_artifacts` 技能包测试、决策记录见 ADR-019 / ADR-020。**最后一段残余 ✅**（随 C 层）：`optimize` / `clarify` 按**目标产物**归包（ADR-026），回执报的包与实际注入的规范出自同一份判断 | D13 ✅ / D8 残余 ✅ / **原 T8 被吸收** |
| **C 文档生命周期（本期形态）✅** | 目标：三份产物不再是「会被覆盖的三个字符串」，而是后端拥有的一份东西。**单表所有权 + 迁移**（ADR-021 / 022）：`documents` 单表、写正文唯一入口是 job 成功收尾、前端只剩「读」与「手改」两条通道、`SessionDataV2` 退役六个字段（旧快照残留**被忽略**，不做兼容读）；加表 / 加列走 `PRAGMA user_version` 的有序幂等迁移，`init_schema` 只建基线表。**待确认清单**（ADR-023）：模型随正文产出 HTML 注释标记块，收尾剥离解析、与正文 / 回执**同批替换**，四条路径共用一份实现（`pending_items.py`）。**澄清工作流**（ADR-025）：独立档案 `doc-clarification` + `clarify` 任务 + `clarifying` 阶段，只改涉及章节、其余逐字保留、末尾附**重算后**的清单。**版本链本期推迟**（见下） | 原 v3.1 C |
| **P5 单点登录 + 两处顺带修复** ✅ | 会话改用单点登录：新登录吊销该用户此前全部会话，`replace_for_user` 在**一条事务**里先删后插（分开做会留下「旧的已删、新的没立」的窗口）；代价是多设备互相踢下线，作为残余风险明确登记（ADR-024）。`format_form_data` 把「配置里声明但留空的题」汇总成一行——否则模型分不清「问过、用户留空」与「根本没这道题」，而两者的处理方式正好相反（ADR-026 同批） | ADR-024 |

**验收**：
- ✅ 开发态改 `prd-template.md` 无需重启即生效；`PRDWRIGHT_SKILLS_STRICT=true` 且 `PRDWRIGHT_SKILLS_DIR` 指错目录时，后端启动即中止并列出少了哪几个文件。

## 四、为什么是这个顺序（含被否决的替代方案）

| 决策 | 理由 |
| --- | --- |
| **CI 提到 R0 而非留在 R3** | 旧路线图把 CI 放在部署阶段，但当时已有 287 个测试且 R0-T3 要动有风险的流式去重代码。先装自动执行的网，才能让后续每个改动「敢动手」——这是旧 P0 护栏思想的延续，只是落地时机随测试规模而前移（现 508 个测试，CI 已跑绿） |
| **R0 先于 R1** | T3 流式去重是已知风险点，必须先有 CI 兜底 + 对照测试钉死行为；T5 错误码是仍活着的 bug（前端字符串匹配），已于 2026-10-14 收掉 |
| **R1 紧随 R0** | PRD 是核心交付物，中断即全废（D7）、供应商单点（D12）、成本不可见（D9）直接决定「用户敢不敢用」。它们改的都是生成主链路，应在结构稳定后集中处理 |
| **R2 在 R1 之后** | 资产工程化（热重载/fail-fast）与可观测性不阻塞任何功能，但 R2-T9 要收编的那份 RAG 知识库是 R3 Docker 打包的清单项，故排在 R3 之前——**先统一资产形态，再定打包清单**，否则打完包还得再改一次 |
| **R3 最后** | Docker/CI/加固不阻塞开发，等全栈形态（含 R2 的资产清单）稳定后一次性做，且 R2-T9 明确要打包的资产后，R3 才不会漏项 |

**被否决的替代方案**：
- **直接上 Postgres + K8s**：当前少量人 + 单实例，SQLite + Docker Compose 的运维成本近乎为零；切 Postgres 的代价被 Repository 隔离在一个文件内（ADR-002）。否决。
- **续传另建 `documents.sections` 表**：与 ADR-009「单表全量快照」冲突，会 reintroduce 差集同步复杂度。否决——续传中间态复用同一份快照 JSON 内的字段。
- **现在就做多轮自评/批判式生成**：先把单次可靠性（续传、调用自愈）做扎实，再谈质量增强，避免把两个不确定因素叠在一起。

## 五、贯穿始终的检查点

每个阶段结束前自查：

1. **测试只增不减**：R0 起 CI 强制；每个阶段结束 `pytest` 与 `vitest` 用例数只增不减。
2. **依赖方向**：`api → services → repositories → db`，无反向 import；services 之间无横向 import（D2 收尾后流式编排只在 `stream_reply.py`）。
3. **契约一致**：后端 `schemas.py` 与前端 `types/index.ts` 字段名一致；**新增错误必须带 `code`**（R0-T5 后不得新增中文串匹配，由不变量测试守卫，见 ADR-012）。
4. **鉴权默认关闭风险**：新增接口若在白名单内必须说明原因；非白名单自动受保护，由 OpenAPI 路径不变量测试守卫（ADR-008）。
5. **owner 强制过滤**：任何查方案/文档的 Repository 方法都带 `owner_id`，不接受 `None`（ADR-009）。
6. **技能资产不静默降级**：**已生效**（ADR-017）。资源缺失在启动时告警（`PRDWRIGHT_SKILLS_STRICT=true` 时直接中止），并在每次 PRD 生成的回执上列出实际注入的技能版本与指纹；没注入技能包即为空列表，前端会显示「未加载技能包」告警，不再悄悄退回内置提示词。
7. **出了事查得到**：**已生效**（ADR-018）。每条日志自动带 `request_id`（含被认证拦下的 401），同一个号在响应头、回执、日志三处同名同值。两条给后来人的约定：**新增日志不要手写请求号**——格式化器会带上，把业务字段丢进 `extra=` 就行；**新增外部依赖时同步加进 `/health`**，否则「用不了」的第一诊断入口就会漏掉它。
8. **写正文只有一个入口**：**已生效**（ADR-021）。生成 / 优化 / 澄清改写都由 job 成功收尾写 `documents`（`commit_generated`，正文 + 清单 + 回执同批替换），失败不写；前端只有「读」与「提交用户手改」两条通道，且手改**不碰**清单与回执。新增一条会产出正文的路径时，**不要自己写库**——接进 `_build_event_stream` 的 `done` 事件即可。
9. **schema 变更一律走迁移**：**已生效**（ADR-022）。`init_schema` 只建基线表；在它里面加表 / 加列，对**新库**有效、对**旧库**静默无效，是最难发现的一类问题。新加一步就登记进 `core/migrations.py::MIGRATIONS`，并保证该步可重跑（幂等）。
10. **新增 `ViewState` 要同步改四处**：`ViewState` / `VIEW_STATES` / `STEP_OF_STATE` / `STATE_DOWNGRADE`。漏一处不报错，只表现为「进度条算错」或「刷新后进不去」。若新阶段依赖某个**非阶段本身**的上下文（如 `clarifying` 要知道「澄清的是哪一份」），还要把 `stepIndexOf` 的现算补上，别指望静态表答得出来。

## 六、风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| R0-T3 合并四份流式重复时边角行为漂移 | 生成输出突变（`on_finish` 不写历史 / 异常后多发了 `done`） | 先写对照测试钉死 `status→chunk→done` 序列、异常转 `error` 后不发 `done`、`on_finish` 仅成功时调用，再统一 |
| R1-T2 续传导致章节间口径不一致 | PRD 质量下降 | 保留整篇模式开关；续传仅作用于分章节模式；前向上下文已传 `prior_sections` |
| R1-T4 重试抬高调用成本 | 费用上升 | 只在首字之前重试（此时几乎没产出 output tokens）、次数上限 1；废弃的尝试计入 `failed_calls`，回执上可见而非被藏进 SDK |
| ~~R2-T6 热重载引入竞态~~ → **已落地**（ADR-017） | 读到半截模板 | 文件戳比对（修改时间 + 大小）+ **只有读成功才写缓存**，文件被删时连带丢掉旧条目。残余概率来自编辑器写入不是原子的：此刻读到半截文件的应对是重发一次，不为它引入加锁——收益远小于复杂度 |
| R2-T7 日志把内容也记进去 | 隐私泄露（用户需求、生成正文、密钥被写进日志文件） | 只记**结构性字段**（`request_id` / `job_id` / `step` / `status` / 耗时），不记 prompt 与生成正文；`/health` 是公开路径，只报类型与状态、不带文件路径等内部细节（已按此实现）；密钥从不出现在日志里 |
| **多设备互相踢下线**（单点登录的代价） | 手机上看完的需求，回到电脑前要重新登录 | **不弥合，显式接受**（ADR-024）。产品定位是单机需求工作台，「一个人一台设备」是真实场景；多端并存的能力仍保留（`issue()` 还在），将来真需要时改动只有一行 |
| **C 层迁移在有数据的旧库上跑** | 迁移失败 → 服务起不来 | 每步**独立显式事务**，失败即停、版本停在上一档、重跑从断点续（不会留下「改了一半」的库）；迁移在 `lifespan` 里跑，问题在启动时暴露而不是某次请求时。回填走「坏 JSON 行跳过但迁移仍完成」，宁可少回填一条，也不让整次迁移失败 |
| **清单依赖模型守约** | 模型不附标记块 → 该次没有清单 | 降级不污染产物：正文照常、生成不失败、清单为空并记一条 warning（ADR-023）。提示词里给出字面量格式与示例，抑制器保证即使不守约也不会把块漏到正文 |
| **澄清改写「只动涉及章节」只能靠提示词约束** | 模型顺手润色了其余章节 | 代码层面保证不了，因此做了三件事：改写规则写进提示词（逐条、含「不编造」）、其余章节**逐字保留**作为硬要求、页面文案提前说明（用户的预期管理纳入设计）。改写结果与旧正文的 diff 由用户自己确认后才进入下一份产物 |
| SQLite 部署态并发写 | 写入卡顿 | 开 WAL（P1 已做）；真不够经 Repository 切 Postgres |

## 七、明确不做

- 微服务 / CQRS / 事件溯源 / GraphQL：单体 + 9 条 REST+SSE 完全够用。
- **轮询式**异步任务队列：改为「同进程后台任务 + 内存广播 + SSE 订阅」，既解耦浏览器连接又保留真流式（除非并发上来，届时执行层可换，Job 表与 API 形状不变）。
- 多租户 / 计费 / 角色权限：少量人场景，owner 过滤足够（ADR-009）。
- 自研 Agent 编排框架：LangChain 抽象当前够用。
- 多实例会话共享：当前单实例足够，真要扩再换 `TokenIssuer` 实现（ADR-007 已留接口）。

## 九、版本分期（2026-10-15 收口）

前面八节按「任务」组织，本节按「对外版本」组织——一次发版是一批任务的集合，
两者的对应关系在这里钉死，避免「v2 到底含什么」事后各说各话。

### v2 · 「能用」（已完成，tag `v2.0.0`，位于 `57b76ef` 之后的收口提交）

一句话：**一个能注册登录、能把需求变成 PRD/接口文档/提示词、能存方案、改坏了有 CI 拦着的产品。**

| 能力 | 内容 |
| --- | --- |
| 核心流程 | 三入口（完整流程 / 快捷入口 / 调试入口）→ 表单 → 对话澄清 → 双闸门（摘要 Diff + RAG 接口规范）→ PRD → 接口文档 → 提示词 |
| 生成 | 分章节撰写 + 审核 + 改写双 Agent（`prd_section_writer`）、`max_tokens` 分档、流式 SSE 实时预览 |
| 持久化 | 方案单表全量快照 + owner 强制过滤 + 左侧栏 + 防抖保存 |
| 账号 | 注册（需邀请码）/ 登录 / HttpOnly Cookie / 默认拒绝中间件 / 未登录禁止建任务 |
| 前端 | `App.vue` 巨石已拆（`AppV2` + `stages/` + `ui/` + `composables/`）、亮暗主题三层令牌、底栏为唯一操作落点 |
| 可靠性护栏 | CI 双 job（收口时后端 107 例 / 前端 222 例，全程离线零 token）、错误契约机器码化（ADR-012）、流式编排单一实现（ADR-013） |
| 品牌 | HarnessPRD → PRDwright 全量更名（仓库根目录名保留 `HarnessPRD`） |

**v2 的边界**：以上能力都成立，但一次「长文生成」仍是**乐观流程**——中断即全丢、供应商单点、成本不可见。
这三条不是 bug，是 v2 明确没做的事，由 v3 承接。

### v3 · 「放心用」（进行中，起点 = R1 生成可靠性）

一句话：**长文生成中断可续、供应商挂了能切、花了多少 token 看得见，最后能一条命令部署。**

| 版本阶段 | 对应本文件章节 | 目标 |
| --- | --- | --- |
| v3.0 生成可靠性 | R1（**骨架 ✅ T0** → **成本计量与预算 ✅ T5** → **单次调用自愈 ✅ T4** → ~~T2 断点续传~~ **已按实测延后**）**四项已到三项，本期收口** | 引入「生成 Job + run 中间态」，生成与浏览器连接解耦；**自动供应商切换已裁决不做**（ADR-016）。三项共享同一份记录与同一个 `stream_reply` 出口。T2 让位的理由见第八节——它要解决的问题（任务中途死掉）在日常使用中尚未出现，而它看似要解决的那个问题（刷新丢章节）早在 T0 就解决了 |
| v3.1 资产与观测 | R2（**技能加固 ✅ T6** / **可观测性 ✅ T7** / **技能知识层统一 ✅ T9**，原 T8 被吸收）+ **C 文档生命周期 ✅（本期形态）** / D Skill 注册表 ✅ / E 交付质量 | 技能热重载 + fail-fast（ADR-017）、结构化日志与 `/health` 三项体检（ADR-018）、**产物归属由技能包自述、RAG 下线改技能包驱动**（ADR-019 / 020）、**三份产物归后端所有 + 待确认清单 + 澄清工作流 + 单点登录**（ADR-021 ~ 026）。**C 的版本链明确推迟**——本期只做「所有权 + 清单 + 澄清」，它解决的问题（改坏了想回退）日常尚未出现，而结构位置已留好 |
| v3.2 部署 | R3（Docker / 生产加固 / 隔离验证） | `docker compose up` 起全栈 |

> 注：Token 预算与事后计量（原 R1-T5）已随 Job 化**提到 v3.0**——它与 Job 的 `run_summary`
> 是同一条链路上不可分割的两半（LLM 包装层同时产「事前估算」与「事后计量」），
> 详见 `./ARCHITECTURE.md` 第 2 / 4.2 / 9 节。

> 版本阶段与任务编号（R1/R2/R3）是**同一套工作的两种视图**：任务编号用于日常排期，
