> **2026-10-16 第二段收口（ADR-027 补记 / ADR-028）**：上面那条有两处**当日即被改掉**，以这条为准。其一，待确认项的档位从 P0 / P1 / P2 **扩为 P0~P6 七档**并**取消兜底**——等级缺失或非法（如 `P7`）的条目**直接丢弃**并记 `pending.bad_importance` 告警（前端两处入口同口径），理由是「拿不准就标 P1」会让大量条目挤在同一档、分级形同虚设。其二，**接口文档 / 提示词的澄清也并进了对话页**：`clarifying` 这个 `ViewState` 与 `ClarifyStage.vue` 都已删除，四条线程（需求 / PRD / 接口 / 提示词）共用同一个 `messages` 数组、用**常驻**的子标签栏切换（未就绪的置灰并给理由），对话区只渲染当前标签那一条；底栏按线程给动作，回审阅页靠顶部进度条。后端一行没动——档案、提问规则、`clarify` 任务、每条线程各一条会话全部沿用。现用例数：**后端 356 / 前端 391**（全程离线零 token）。

> **2026-10-16 第三段收口（ADR-029 / 030）：版本链落地**。前面几条里的「**版本链（`document_versions`）本期明确推迟**」**由此作废**。正文全搬进新表 `document_versions`，`documents` 退化为「身份 + 当前版本指针」（`current_version_id`）——兑现了 `ARCHITECTURE.md` 4.3 当初预留的结构位置，没有推翻此前任何一条约束。
>
> - **版本何时产生**（这次的核心口径）：整篇生成 = **追加新版本**；`optimize` / `clarify` 与用户手改 = **就地改当前版本**（不新增条目）；「存为新版本」(checkpoint) 与「恢复」(restore) = 追加新版本。
> - **恢复 = 读源版本 → 追加一条 `source='restore'` 的新版本**，不把指针拨回旧版本：历史**只增不改**（拨指针会篡改被就地改过的旧版本，也会丢掉「曾经恢复到哪一版」的痕迹）。
> - **待确认清单与用量回执随版本存档**（版本行上的显式列，不是塞进 `metadata`），恢复某一版时清单一起还原。
> - **对外结构 `DocumentItem` 逐字段不变**，读文档的调用方（路由、前端 store）一行未改；版本是一组**新增**能力。
> - **迁移三步**：v4 建表 + 加指针 → v5 逐行容错回填成 `version_no=1, source='migrated'` → v6 删 `documents` 的四个正文列。**v6 是单向门**（改完旧代码读不到 `documents.content`，回滚只能靠备份），用原生 `ALTER TABLE ... DROP COLUMN`——`PRAGMA foreign_keys` 在事务内是空操作，而迁移运行器把每步包在事务里，「关外键 + 重建表」那套在步骤内部关不掉外键。
> - **四个端点挂在 solution 作用域**下（`GET /api/solutions/{id}/documents/{kind}/versions`、`.../versions/{version_id}`、`POST .../{kind}/checkpoint`、`POST .../{kind}/restore`），与 4.3 草稿的 `/api/documents/{kind}/...` 不同——后者没法在 SQL 层过滤归属。版本不存在**复用** `SOLUTION_NOT_FOUND`（404），不新增错误码（ADR-012）。
> - **前端是右侧可收起抽屉**（`ui/VersionDrawer.vue`）：审阅页底栏内容行的「版本」按钮打开，默认收起、不遮底栏、不挤中部布局。**这是 ADR-015 的一次有意例外**（ADR-030）——抽屉里只放**内容操作**（预览 / 存为新版本 / 恢复 / 删除），**流程动作**（生成下一份 / 完成 / 返回）永远只在底栏。
> - **预览与删除**（同日补上，ADR-029 / 030 各一处补记）：点某一版即预览该版只读正文（抽屉就地加宽到 640px，不在主区域开新阶段——那要把 `ViewState` / 进度条 / 底栏都改一遍，而这件事不需要它们参与）；每条**历史**版本自带「删除」并二次确认，**当前版本不给删**（它是这份文档正在用的正文，换版本请用「恢复」；守卫写在仓储 SQL 的 `WHERE` 里，不是「先查后删」）。
> - 本版**不做两版 diff**（差异渲染）：版本链落地后它不再是「依赖未完成」，但「回看 + 恢复」已经能回答用户的问题。
>
> 现用例数：**后端 389 / 前端 477**（全程离线零 token）。

> **2026-10-16 第四段收口（ADR-031）：入口页改「两组四叶子」，补上第四条入口**。入口从 v2 的三张**平铺**卡片改成两组的四个叶子，并把产品侧提的第四条路（**我有 PRD + 接口文档**）做成真流程。
>
> - **分组的两轴是「起点」不是功能**：`从零创建 PRD`（自己把需求说清楚）/ `导入已有素材`（材料已经有了）。先答「我属于哪种情况」比先答「我要哪个功能」快；四个叶子**仍同屏可见**——分组加的是语义层级，不是多一屏要点的关卡。
> - **第四条入口不是「加个卡片」**：`prompts` 任务当时的入参只有 `prd_content`，照文案做一页双粘贴，用户贴的第二份材料会被**静默丢弃**。因此 `JobCreateRequest` 新增可选 `api_docs_content` → `job_service` 透传 → `generate_prompts_stream` 多收一个参数 → 模板新增 `{api_docs_content}` 占位符（技能包版与 `prompts.py` 兜底版**两份必须同步**，占位符集合是一份跨文件契约，少一个就是 `KeyError`）。留空时那一节填 `NO_API_DOCS_NOTE`（「本次未提供」）而不是留空——那一节在模板里始终存在，留空会让模型以为漏读了、转头自己编一份接口契约。
> - **模式键名不动**：`prompt-debug` 改名要配一套兼容旧快照的解析，只换来命名好看；真正会误导人的是界面文案，那个改成了「我有 PRD」。新入口的键取 `prd-and-api-paste`（**刻意不叫 `prompts`**：那已是 `DocKind` 的取值，同名会让「动作/东西」的区分当场失效）。
> - **两个导入入口的粘贴材料都不落 `documents`**：那是「本工具生成的产物」的位置，混进去会让进度、完成条件与下载列表全部失真。两份材料在快照里**分开存**（`pastePairInput`），不共用 `debugPrdText`——换一条路进去看到上一页的内容会让人以为走错了。
> - 顺带把 `ARCHITECTURE.md` §8 里「优化四：三 Tab 改 chooser」的裁决**改判**：chooser 这个**形态**与仓库一致，只有源文档给的三个模式值不适用；缺的那条流程这次补上了。

## 二、已经做对、明确不要动的设计

重构最容易犯的错是把好的一起推翻。以下仍是全项目最干净的部分，**任何阶段都只复用不替换**：

- **`llm_factory` 的三供应商抽象**：ark / anthropic / openai 统一 `astream`，业务层无感——R1-T4 的超时与重试统一挂在 `stream_reply` 这一个出口上，正是靠这层抽象才不必每个供应商各写一遍。
- **路由层 / service 层 / repository 层分离**：`api` 只解析封装，`schemas.py` 集中契约，`repositories/` 是全项目唯一写 SQL 的地方（review 红线）。
- **SSE 事件协议**：`status / chunk / part / stage / done / error` + 末尾 `[DONE]`，两层异常兜底；PRD 正文以 `part` 事件为准（预览与最终同源，见 8ea4896）。逐字增量 `chunk` 在分章节链路里**必须**带 `section_id` / `index`（否则多章并行会串字，前端只能整批丢弃）；快照的 `live_by_section` 让刷新后「正在写的几章」接着长。
- **技能包驱动 + 自动降级**：`skills/prd-generator` 缺失时退回内置提示词，服务不中断（R2 只把「静默降级」改成「显式告警 + 可选 fail-fast」）。
- **默认拒绝中间件**（纯 ASGI，避开 `BaseHTTPMiddleware` 对 SSE 的响应体重包）+ 遍历 OpenAPI 路径的不变量测试。
- **快照范式 + owner 强制过滤**（ADR-009）：单表全量 JSON、`Repository` 不接受 `owner_id=None`。

**验收**：
- ✅ 开发态改 `prd-template.md` 无需重启即生效；`PRDWRIGHT_SKILLS_STRICT=true` 且 `PRDWRIGHT_SKILLS_DIR` 指错目录时，后端启动即中止并列出少了哪几个文件。
- ✅ 任意一次请求日志含 `request_id`（**含被认证拦下的 401**）；`/health` 三项分开报，且**明说供应商一项未发真实调用**。

**不做**：不引入 Prometheus/Grafana（少量人场景，结构化日志 + `/health` 足够）；不做分布式追踪。

### R3 · 部署与多人加固

**周期**：1 周　**风险**：低（不动业务逻辑）

**目标**：把「本地能跑」变成「一条命令起全栈、CI 拦破坏性改动、两账号互不可见」。

| 任务 | 具体动作 | 关联债务 |
| --- | --- | --- |

## 四、为什么是这个顺序（含被否决的替代方案）

| 决策 | 理由 |
| --- | --- |
| **CI 提到 R0 而非留在 R3** | 旧路线图把 CI 放在部署阶段，但当时已有 287 个测试且 R0-T3 要动有风险的流式去重代码。先装自动执行的网，才能让后续每个改动「敢动手」——这是旧 P0 护栏思想的延续，只是落地时机随测试规模而前移（现 508 个测试，CI 已跑绿） |
| **R0 先于 R1** | T3 流式去重是已知风险点，必须先有 CI 兜底 + 对照测试钉死行为；T5 错误码是仍活着的 bug（前端字符串匹配），已于 2026-10-14 收掉 |
| **R1 紧随 R0** | PRD 是核心交付物，中断即全废（D7）、供应商单点（D12）、成本不可见（D9）直接决定「用户敢不敢用」。它们改的都是生成主链路，应在结构稳定后集中处理 |
| **R2 在 R1 之后** | 资产工程化（热重载/fail-fast）与可观测性不阻塞任何功能，但 R2-T9 要收编的那份 RAG 知识库是 R3 Docker 打包的清单项，故排在 R3 之前——**先统一资产形态，再定打包清单**，否则打完包还得再改一次 |
| **R3 最后** | Docker/CI/加固不阻塞开发，等全栈形态（含 R2 的资产清单）稳定后一次性做，且 R2-T9 明确要打包的资产后，R3 才不会漏项 |

**被否决的替代方案**：
- **直接上 Postgres + K8s**：当前少量人 + 单实例，SQLite + Docker Compose 的运维成本近乎为零；切 Postgres 的代价被 Repository 隔离在一个文件内（ADR-002）。否决。
- **续传另建 `documents.sections` 表**：与 ADR-009「单表全量快照」冲突，会 reintroduce 差集同步复杂度。否决——续传中间态复用同一份快照 JSON 内的字段。
- **现在就做多轮自评/批判式生成**：先把单次可靠性（续传、调用自愈）做扎实，再谈质量增强，避免把两个不确定因素叠在一起。

## 五、贯穿始终的检查点

每个阶段结束前自查：

1. **测试只增不减**：R0 起 CI 强制；每个阶段结束 `pytest` 与 `vitest` 用例数只增不减。
2. **依赖方向**：`api → services → repositories → db`，无反向 import；services 之间无横向 import（D2 收尾后流式编排只在 `stream_reply.py`）。
3. **契约一致**：后端 `schemas.py` 与前端 `types/index.ts` 字段名一致；**新增错误必须带 `code`**（R0-T5 后不得新增中文串匹配，由不变量测试守卫，见 ADR-012）。
4. **鉴权默认关闭风险**：新增接口若在白名单内必须说明原因；非白名单自动受保护，由 OpenAPI 路径不变量测试守卫（ADR-008）。
5. **owner 强制过滤**：任何查方案/文档的 Repository 方法都带 `owner_id`，不接受 `None`（ADR-009）。
6. **技能资产不静默降级**：**已生效**（ADR-017）。资源缺失在启动时告警（`PRDWRIGHT_SKILLS_STRICT=true` 时直接中止），并在每次 PRD 生成的回执上列出实际注入的技能版本与指纹；没注入技能包即为空列表，前端会显示「未加载技能包」告警，不再悄悄退回内置提示词。
7. **出了事查得到**：**已生效**（ADR-018）。每条日志自动带 `request_id`（含被认证拦下的 401），同一个号在响应头、回执、日志三处同名同值。两条给后来人的约定：**新增日志不要手写请求号**——格式化器会带上，把业务字段丢进 `extra=` 就行；**新增外部依赖时同步加进 `/health`**，否则「用不了」的第一诊断入口就会漏掉它。
8. **写正文只有一个入口**：**已生效**（ADR-021）。生成 / 优化 / 澄清改写都由 job 成功收尾写 `documents`（`commit_generated`，正文 + 清单 + 回执同批替换），失败不写；前端只有「读」与「提交用户手改」两条通道，且手改**不碰**清单与回执。新增一条会产出正文的路径时，**不要自己写库**——接进 `_build_event_stream` 的 `done` 事件即可。
9. **schema 变更一律走迁移**：**已生效**（ADR-022）。`init_schema` 只建基线表；在它里面加表 / 加列，对**新库**有效、对**旧库**静默无效，是最难发现的一类问题。新加一步就登记进 `core/migrations.py::MIGRATIONS`，并保证该步可重跑（幂等）。
10. **新增 `ViewState` 要同步改四处**：`ViewState` / `VIEW_STATES` / `STEP_OF_STATE` / `STATE_DOWNGRADE`。漏一处不报错，只表现为「进度条算错」或「刷新后进不去」。若新阶段依赖某个**非阶段本身**的上下文，还要把 `stepIndexOf` 的现算补上，别指望静态表答得出来——对话页现在就正是这种情形：`chatting` 一个阶段要服务四条澄清线程，进度条该高亮哪一格由 `activeChatTab` 现算（`currentStepIndex`），而 ADR-028 之前那套「多一个 `clarifying` 阶段 + 按 `clarifyTarget` 现算」的做法已经删掉了。

## 六、风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| R0-T3 合并四份流式重复时边角行为漂移 | 生成输出突变（`on_finish` 不写历史 / 异常后多发了 `done`） | 先写对照测试钉死 `status→chunk→done` 序列、异常转 `error` 后不发 `done`、`on_finish` 仅成功时调用，再统一 |
| R1-T2 续传导致章节间口径不一致 | PRD 质量下降 | 保留整篇模式开关；续传仅作用于分章节模式；前向上下文已传 `prior_sections` |
| R1-T4 重试抬高调用成本 | 费用上升 | 只在首字之前重试（此时几乎没产出 output tokens）、次数上限 1；废弃的尝试计入 `failed_calls`，回执上可见而非被藏进 SDK |
| ~~R2-T6 热重载引入竞态~~ → **已落地**（ADR-017） | 读到半截模板 | 文件戳比对（修改时间 + 大小）+ **只有读成功才写缓存**，文件被删时连带丢掉旧条目。残余概率来自编辑器写入不是原子的：此刻读到半截文件的应对是重发一次，不为它引入加锁——收益远小于复杂度 |
| R2-T7 日志把内容也记进去 | 隐私泄露（用户需求、生成正文、密钥被写进日志文件） | 只记**结构性字段**（`request_id` / `job_id` / `step` / `status` / 耗时），不记 prompt 与生成正文；`/health` 是公开路径，只报类型与状态、不带文件路径等内部细节（已按此实现）；密钥从不出现在日志里 |
| **多设备互相踢下线**（单点登录的代价） | 手机上看完的需求，回到电脑前要重新登录 | **不弥合，显式接受**（ADR-024）。产品定位是单机需求工作台，「一个人一台设备」是真实场景；多端并存的能力仍保留（`issue()` 还在），将来真需要时改动只有一行 |
| **C 层迁移在有数据的旧库上跑** | 迁移失败 → 服务起不来 | 每步**独立显式事务**，失败即停、版本停在上一档、重跑从断点续（不会留下「改了一半」的库）；迁移在 `lifespan` 里跑，问题在启动时暴露而不是某次请求时。回填走「坏 JSON 行跳过但迁移仍完成」，宁可少回填一条，也不让整次迁移失败 |
| **清单依赖模型守约** | 模型不附标记块 → 该次没有清单 | 降级不污染产物：正文照常、生成不失败、清单为空并记一条 warning（ADR-023）。提示词里给出字面量格式与示例，抑制器保证即使不守约也不会把块漏到正文 |
| **澄清改写「只动涉及章节」只能靠提示词约束** | 模型顺手润色了其余章节 | 代码层面保证不了，因此做了三件事：改写规则写进提示词（逐条、含「不编造」）、其余章节**逐字保留**作为硬要求、页面文案提前说明（用户的预期管理纳入设计）。改写结果与旧正文的 diff 由用户自己确认后才进入下一份产物 |
| SQLite 部署态并发写 | 写入卡顿 | 开 WAL（P1 已做）；真不够经 Repository 切 Postgres |

## 七、明确不做

- 微服务 / CQRS / 事件溯源 / GraphQL：单体 + 9 条 REST+SSE 完全够用。
- **轮询式**异步任务队列：改为「同进程后台任务 + 内存广播 + SSE 订阅」，既解耦浏览器连接又保留真流式（除非并发上来，届时执行层可换，Job 表与 API 形状不变）。
- 多租户 / 计费 / 角色权限：少量人场景，owner 过滤足够（ADR-009）。
- 自研 Agent 编排框架：LangChain 抽象当前够用。
- 多实例会话共享：当前单实例足够，真要扩再换 `TokenIssuer` 实现（ADR-007 已留接口）。

## 九、版本分期（2026-10-16 收口）

前面八节按「任务」组织，本节按「对外版本」组织——一次发版是一批任务的集合，
两者的对应关系在这里钉死，避免「v2 到底含什么」事后各说各话。

### v2 · 「能用」（已完成，tag `v2.0.0`，位于 `57b76ef` 之后的收口提交）

一句话：**一个能注册登录、能把需求变成 PRD/接口文档/提示词、能存方案、改坏了有 CI 拦着的产品。**

| 能力 | 内容 |
| --- | --- |
| 核心流程 | 三入口（完整流程 / 快捷入口 / 调试入口）→ 表单 → 对话澄清 → 双闸门（摘要 Diff + RAG 接口规范）→ PRD → 接口文档 → 提示词 |
| 生成 | 分章节撰写 + 审核 + 改写双 Agent（`prd_section_writer`）、`max_tokens` 分档、流式 SSE 实时预览 |
| 持久化 | 方案单表全量快照 + owner 强制过滤 + 左侧栏 + 防抖保存 |
| 账号 | 注册（需邀请码）/ 登录 / HttpOnly Cookie / 默认拒绝中间件 / 未登录禁止建任务 |
| 前端 | `App.vue` 巨石已拆（`AppV2` + `stages/` + `ui/` + `composables/`）、亮暗主题三层令牌、底栏为唯一操作落点 |
| 可靠性护栏 | CI 双 job（收口时后端 107 例 / 前端 222 例，全程离线零 token）、错误契约机器码化（ADR-012）、流式编排单一实现（ADR-013） |
| 品牌 | HarnessPRD → PRDwright 全量更名（仓库根目录名保留 `HarnessPRD`） |

**v2 的边界**：以上能力都成立，但一次「长文生成」仍是**乐观流程**——中断即全丢、供应商单点、成本不可见。
这三条不是 bug，是 v2 明确没做的事，由 v3 承接。

### v3 · 「放心用」（进行中，起点 = R1 生成可靠性）
