## ADR-039：管理员后台采用「根目录独立应用」，不嵌入也不组 monorepo

### Status

Accepted（2026-10-21）

### Context

需要新建平台管理员后台。三个候选：

1. **嵌入现有 `frontend/`**：加 `/admin/*` 路由与页面，作为一个 feature module；
2. **根目录单开 `frontend_admin/`**：独立 `package.json`、独立 Vite 应用；
3. **pnpm monorepo**：`frontend/` 下拆 `userpage` / `adminpage` 两个应用 + `packages/shared`。

讨论中先后提出过三类顾虑：

- **安全**：「一起放着是不是容易被黑客找到后台」；
- **开发冲撞**：「一起放着会不会互相冲撞」；
- **工程成本**：monorepo 的双份工具链与 shared 包维护。

其中「隐藏路径能挡住攻击者」这一点经核实不成立：SPA 的路由本就打进 JS 包，
攻击者直接扫 `/api/*`，前端怎么组织都不改变 API 的暴露面；且两个前端只要请求同一个 API 源，
会话 Cookie 本来就通用。真正的安全边界是**服务端 `require_admin`**，
与代码是否分开放置无关。

### Decision

取 **方案 2（根目录独立应用 `frontend_admin/`）**。

- 与 `backend/`、`frontend/` 并列，独立构建、独立部署。
- 两个前端共享同一后端 API 源，因此共享同一套会话 Cookie，**不做任何登录态桥接**。
- 管理员端**不 import** 用户端任何模块；自带一份薄 HTTP 封装与类型。
- 服务端对所有 `/api/admin/**` 强制 `require_admin`（这是唯一硬防线）。

### Consequences

**变容易**

- 独立构建与部署：管理员端可单独发布、可放独立子域或内网（这是「分离」唯一能带来
  真实安全增益的地方，且它靠的是部署边界，不是代码位置）。
- 硬隔离：TypeScript/Vite 天然阻止跨应用 import，不会因手滑把管理员组件带进用户端。

**变难 / 代价**

- 多一套工具链（Vite / 依赖 / CI），以及少量 HTTP 封装的重复。
- **git 冲突并不会因此减少**——两个应用仍在同一仓库、同一段提交历史；
  真要消除版本控制层面的冲撞只能拆独立仓库，那代价远大于收益。
- 部署时要处理两个 SPA 共存（反代分路径或独立子域）与 `cors_origins` 放行。

## ADR-040：日志采集「文件 + SQLite 双写」，且采集先行于 UI

### Status

Accepted（2026-10-21）

### Context

`core/logging_setup.py` 目前只装了一个 `StreamHandler(sys.stdout)`，
**没有任何持久化**：进程停止后历史全无，管理端也就无从查看。
日志格式本身已经很规整（ts / level / logger / msg / request_id / `extra=` 字段，
`LOG_FORMAT=json` 时一行一条 JSON），采集端几乎不需要改格式化逻辑。

候选方案：

1. **纯轮转文件**：简单，但后台检索要现解析文本、处理轮转与并发读；
2. **纯 SQLite 表**：查询灵活，但每次 `logger.info` 都写库，且丢了文件这个兜底；
3. **文件 + DB 双写**；
4. **交给外部采集**（Docker logs / ELK）：运维更专业，但与「自建小工具开箱即用」相悖，
   且用户明确要求后台内自带日志查看，必须自持。

### Decision

取 **方案 3（双写）**，并附加一条排期约束：

- 新增 `LogStoreHandler`，在 `configure_logging` 里与 stdout handler 并列装上，
  **业务代码一行都不用改**（与 `request_id` 自动注入同一条设计纪律）。
- **轮转文件始终开**（`logs/prdwright.log`，5MB × 5）：保证永不丢、可脱机排查、可外喂采集。
- **`app_logs` 表可开关**（默认开，异步批量写）：保证后台能过滤 / 分页 / 排序。
- **保留策略**：`log_retention_days`（默认 7 天）与 `log_max_rows`（默认 5 万条），
  启动时执行一次 + 写入时懒触发。
- ⚠️ **采集排在 T0，UI 排在 T4**：日志是「从现在开始攒」的数据，
  采集晚一步，后台上线那天就没有历史可看。
- 三条硬约束：绝不阻塞主流程（异步批量 + 队列上限 + 失败降级丢弃）；
  必须 `require_admin`；`log_db_min_level` 默认 INFO（DEBUG 不默认入 DB）。

### Consequences

**变容易**

- 后台能做级别 / 时间 / logger / event / `request_id` / 关键词的组合检索与分页。
- `request_id` 反查成为可能——用户回执上那个号粘进后台即可拉出该请求全部日志，
  把 R1 就贯通的追踪链补上最后一环。
- 文件与 DB 互为兜底：DB 出问题仍有文件，反之亦然。

**变难 / 代价**

- 多一份存储与保留策略要维护；日志写放大需要靠批量与级别下限控制。
- 日志可能含用户名、方案 id，属高权限数据，访问面必须收紧到管理员。

## ADR-041：系统配置「DB 覆盖 env，但只有白名单项可运行时改」

### Status

Accepted（2026-10-21）

### Context

当前所有可调项都由 `.env` 经 `get_settings()` 读成**进程内 `@lru_cache` 单例**，
进程启动后不变。要做到「管理员在后台改参数并生效」，必须有运行时可变的配置源。

三个选项：

1. 只改 `.env` + 重启：运维负担重，且不符合「后台可调」的诉求；
2. **全部搬进 DB**：看似统一，但 `db_path` / `host` / `port` / `auth_enabled` /
   `cors_origins` 这类**启动项**一旦进 DB，就会出现「改了却不生效」或「改了要不要重启」
   的认知混乱，甚至改坏之后服务起不来；
3. **DB 覆盖 env，但只有白名单项可进 DB**。

### Decision

取 **方案 3**。

- `system_config` 表 + `core/runtime_config.py`；解析顺序 **DB > env > 字段默认值**。
- **白名单**：配额、模型与调用参数、安全与会话、**日志参数**、维护模式。
- **永不进 DB**（启动项）：`db_path`、`host`、`port`、`auth_enabled`、`cors_origins`、
  供应商密钥、邀请码种子、`init_admin_*`、`skills_strict`。
- 进程内 **30 秒 TTL** 缓存；管理员写入时**立即失效**并记审计（多进程靠 TTL 兜底，
  不引入消息广播）。
- 写入在 `runtime_config` 集中校验，约束与 `config.py` 的 `Field(ge=, le=)` 同源；
  非法值 400，不静默截断。

### Consequences

**变容易**

- 绝大多数目标参数（`llm_timeout` / `llm_max_retries` / `prd_pipeline_concurrency` /
  `default_llm_provider` …）在 `config.py` 里**已经存在**，把它们从「只读 env」改成
  「优先读 runtime_config」即可，UI 是纯增量——这是整个 v4 性价比最高的一块。
- 配置变更有审计（before / after），可追溯。

**变难 / 代价**

- 让 `llm_factory` / `job_service` 等改读 runtime_config 会**碰到生成主链路**。
  缓解：只改白名单项的读取点，且每改一处配一条「默认行为零变化」的回归用例。
- 白名单本身需要维护：新增可调项时要显式登记，忘了就还是只能改 env。

## ADR-042：模型供应商只存「环境变量名引用」，明文密钥不落库

### Status

Accepted（2026-10-21）

### Context

v4 要建 `model_providers` 表并支持后台切换供应商。随之而来的问题是密钥放哪：

1. **明文落库**，由管理员在后台录入；
2. **库里只存环境变量名引用**（如 `ARK_API_KEY`），密钥仍由 `require_api_key()` 从环境取。

现有 `Settings.require_api_key()` 与 `API_KEY_ENV_VARS` 已经把「哪个供应商看哪个变量」
收敛在一处，密钥生命周期完全在环境里。

### Decision

取 **方案 2**。

- `model_providers` 表存 `api_key_env_var`（**变量名字符串**），不存密钥本身。
- 管理员可改：展示名、`provider_type`、`base_url`、`default_model`、`priority`、激活与否。
- 管理员**不可**在后台录入明文密钥；新增供应商仍需配置对应环境变量。
- 激活真源是 `system_config.active_provider_id`，**不靠表里加 `is_active` 列**——
  后者会出现「两行都是 1」的不一致态，前者天然只有一个值。
- `llm_factory` 改读「激活供应商行」（经 runtime_config 缓存），切换后立即失效缓存。

### Consequences

**变容易**

- 把明文凭据的泄漏面挡在数据库之外：库被读走也不会连带泄露 API 密钥。
- 与既有 `API_KEY_ENV_VARS` / `require_api_key()` 单一真源保持一致，不新增第二套密钥来源。

**变难 / 代价**

- 新增或轮换供应商仍需碰 `.env` 并重启（密钥层面），后台只能切「用哪一个」。
- 真要做密钥托管，需先解决加密存储与轮换流程——本期明确不做（见 `ARCHITECTURE.md` 1.3）。

## ADR-043：管理员身份的授予/撤销只留**一条**规则，且「撤销自己」不算违规

### Status

Accepted（2026-10-21）

### Context

T1 实现到「后台能不能授予/撤销管理员」时，冒出两个问题：

1. **规则写在哪？** `auth_service.set_admin` 里已有一条「不能撤销最后一位管理员」，
   而运维脚本 `auth_cli.py demote` 走的就是它。后台若另写一份校验，两条路迟早
   有一处漏改——后台就会成为绕过不变式的后门。
2. **「不能撤销自己」算不算一条独立规则？**

第 2 个问题的初稿答案是「算」，理由是「撤销自己 = 当场把自己踢出后台」。实现时
发现这个理由站不住：

- 管理员交接、临时让渡权限是**真实场景**。只要系统里还有别的管理员，
  撤销自己就是一次正常的「卸任」，而且**可逆**——另一位管理员随时能重新任命。
- 更关键的是：它和「不能撤销最后一位管理员」在 HTTP 路径上**必然重合**。
  只要操作者是管理员，「最后一位」就只可能是他自己。于是两条规则会互相遮蔽，
  报错信息也会打架（到底是「不能撤销自己」还是「最后一位管理员」）。

### Decision

1. **规则只有一条**，由 `auth_service.set_admin` 独家实现：
   不能撤销最后一位管理员。后台（`admin_service.set_admin`）只做委派，
   CLI 与后台共用同一份实现。
2. **「撤销自己」不被单独拦**。只要还有别的管理员，撤销自己是允许的；
   真正被拦的只有一种——撤销之后系统里一个管理员都不剩。
3. 相应地，**删号 / 停用自己**仍然单独拦（403）。这两件事性质不同：
   删号和停用会毁掉或冻结自己的账号，撤销管理员只是换了个角色。
4. 后台那侧的状态码用 `FORBIDDEN`（403）而不是 `AUTH_FAILED`（401）：
   401 在前端意味着「该去登录了」，而这里登录也没用。

### Consequences

**变容易**

- 后台与 CLI 的行为**逐条一致**，不存在「命令行能绕、后台不能」或反之。
- 管理员交接不用绕到命令行。
- 错误信息只有一种说法（「这是最后一位管理员，不能撤销」），管理员一眼知道该做什么。

**变难 / 代价**

- 管理员可以在后台里把自己降级，从而立刻失去后台访问权。这是**有意为之**：
  它是显式动作（点了「撤销管理员」），且可逆。刻意不做「禁止自降级」的保护，
  是因为那会挡住真实的交接场景。

**验证**

- 后端用例钉住两条：撤销最后一位 → 403；**有第二位时撤销自己 → 200**。
- 端到端冒烟走真实 HTTP：授予 → 撤销第一位（有第二位，200）→ 撤销最后一位（403）。

## ADR-044：运行时配置用「DB 只存覆盖项」+「一次生成冻结一份快照」

### 背景

v4 之前全部配置都在 `.env`：改一个值要改文件、重启服务。后台因此无法调参数，
「换模型供应商」更是要改代码里的 `Literal` 与分支。

难点不在「读出来的值能变」，而在两件事：

1. 配置的读取点有**三种形态**：每次调用读（`llm_factory`）、模块级快照（`main.py`）、
   **实例级快照**（`PrdSectionWriter.__init__` 拷了 5 个值、三处 LLM 实例缓存）。
   只清 `lru_cache` 覆盖不到后两种——表现是「改了配置，接口返回新值、生成还用旧值」。
2. 反过来，如果每个读取点都即时读，一次 20 分钟的生成跑到一半就会**参数漂移**。

### 决定

**一、`system_config` 只存覆盖项。** 没有某一行 = 用 env 或代码默认值。
所以「升级后行为零变化」是**结构保证**，而不是靠人记得别写默认值；
「恢复默认」就是删掉那一行。白名单是**硬编码常量**（不入表）：能通过配置扩展的
白名单等于没有白名单，而它是安全边界（`db_path` 一旦可改，配置层就与 `connect()`
形成递归）。

**二、一次生成冻结一份快照。** `dispatch` 取快照存进 `JobRuntime`，
`run_job` 用 `use_config` 挂到 ContextVar——与 `use_meter` 是同一套机制，学一次用两处。
直连 SSE 的路由（`/api/conversation/*-stream`）在 `make_sse_generator` 里统一冻结，
因为**事件流是在响应返回之后才被消费的**，放在路由函数体里的 `with` 早就退出了。

**三、构造期快照全部拆除。** `PrdSectionWriter` 的 5 个属性改成只读属性（12 处
使用点一行不用改），三处 LLM 缓存改按**同一个配置指纹**重建（`config_fingerprint()`）。
指纹集中在一处，否则会出现「撰写实例换了、审核实例还是旧的」——同一次生成里两个
实例参数不一致，正文与批注的口径就对不上。

**四、供应商按协议建模，不按厂商。** `protocol` 六值（`openai_compatible` /
`anthropic` / `ark` / `google_genai` / `nvidia` / `huggingface`）。已查证
`langchain-deepseek` 等包都是 `BaseChatOpenAI` 的薄封装（只把 `base_url` 写死），
所以接一家新厂商只需填 `base_url`，**不改代码、不加依赖**。

**五、所有适配器收敛进 `llm_factory.py`**（`ark_llm.py` 并入后删除）。
分层守卫的白名单从两个文件缩成一个，规则变成一句话：只有工厂能碰供应商 SDK。

**六、密钥只存变量名**（ADR-042 不变）。新增 `core/secrets.py` 按键名查找——
因为 `pydantic-settings` 读 `.env` 但**不写 `os.environ`**，运行时新增的供应商
按键名去 `os.environ` 找会永远为空，界面一直提示「未配置」。

### Consequences

**变容易**

- 后台改完即生效，不用重启；多 worker 靠 5 秒 TTL 收敛。
- 加一家 OpenAI 兼容的厂商是**数据操作**，不是代码改动。
- 排障时页面直接显示「改前 / 改后 / 是否真的生效」。

**变难 / 代价**

- 多了一层抽象：读配置要经 `get_runtime_config().settings`，而不是 `get_settings()`。
  好处是取值写法完全不变（`Settings` 的派生属性原样可用）。
- `llm_factory.py` 从 148 行长到约 550 行，同时装着工厂与一个 `BaseChatModel` 子类。
- 三个新协议依赖偏重（`protobuf` / `tokenizers`），装完必须跑全量确认没带崩别的包。

**验证**

- `test_runtime_config.py`（22 条）：默认行为零变化、白名单、降级不抛、不递归。
- `test_config_effect.py`（9 条）：死配置修复、指纹重建、快照拆除、任务冻结。
- `test_admin_config_api.py`（30 条）：门禁逐条、密钥不外泄、规则只在服务层。
- 端到端：改并发度 → 保存 → `revision` 变化 → 复读为 `source=db`。

## ADR-045：每日额度按「次数 / Token / 并发」三维度，且失败不吃额度

### 背景

邀请码只管「谁能进来」，不管「进来后用多少」。v4 之前一个账号能无限次生成，
而管理员在事前没有任何拦截手段——T2 的统计是**事后的账单**，它告诉你花了多少，
阻止不了继续花。T3 让「换哪家模型」变成数据操作之后，这件事更要紧：
切到便宜的模型省下的钱，一次滥用就还回去了。

### 决定

**一、三个维度，不是一个额度。**

| 维度 | 防的是什么 |
|---|---|
| 每人每日**次数** | 公平：一个人占满队列会拖慢所有人 |
| 每人每日 **Token** | 成本：真正烧钱的是 token，不是请求数 |
| 每人同时**运行数** | 队列：与钱无关，防的是并发挤占 |

只做「次数」的话，一天跑 3 次、每次 100k token 的人比跑 30 次短任务的人烧得多；
只做 Token 的话，连发 20 个请求能瞬间打满队列。

**二、上限用三态（`-1` / `0` / `N`），不是单个数字。**

- `-1` 跟随全局（`system_config` 的 `quota_*`，热生效）
- `0` 不限
- `N` 具体上限

少了 `-1`，「恢复成跟大家一样」做不到（只能一个个填当前全局值，之后全局改了
他还停在旧值）；少了 `0`，「给可信账号开口子」做不到。**两种意图必须能区分**，
所以前端编辑框回填的是三态值，而不是生效数字。

**三、三条统计口径，彼此刻意不同。**

- **次数只算「已收尾 + 在飞」**（`completed` / `running`）。失败、被取消
  （`CANCELLED`）、被新任务接管（`SUPERSEDED`）都**不吃额度**——一次上游故障
  就把所有人当天机会清零，用户完全无从申诉，他没做错任何事。
- **Token 算全部状态**的实际消耗。跑了就跑掉了，失败的任务同样花钱。
- **并发只数 `running`，且不受日界限制**。长文档生成会跨日；若并发检查也跟着
  日界过滤，「昨天那批 + 今天这批」就能同时开。

**四、「每天」由服务端定时区**（`quota_timezone_offset_minutes`，默认东八区）。
绝不接受前端传值：那等于让用户改一下浏览器时区就把日界挪走。这与 T2 统计的
「时区由前端传」是**相反的**决定，因为两者的可信模型不同——统计是给管理员看的
便利功能，额度是安全边界。

**五、拦截在建任务之前，`kind=chat` 豁免。**

检查放在 `job_service.create_job` 之前。放在之后的话，被拒的请求会先留下一行
`failed`，污染 T2 的失败率、也会出现在用户的任务列表里（「我什么都没生成，
却多了一条失败记录」）。对话豁免是因为它是生成的**前置**（澄清、改需求），
限了之后用户连「为什么被拒」都问不了。

**六、不新增错误码。** `ErrorCode` 是对外契约（前端 `BACKEND_ERROR_CODES`
与之逐字对应），配额超限复用 `INVALID_REQUEST` + `status_code=429`。
前端本来就把字符串 `detail` 原样显示（`describeJobError` 优先返回它），
不需要靠码分支。

### Consequences

**变容易**

- 管理员能事前设限，不必等月底看账单才发现。
- 用户列表直接显示「今日已用/上限」，超限的行标红——「谁被卡住了」一眼可见。
- `quota_enforce=false` 可以先观察真实分布再收紧，不必一上线就拒绝用户。

**变难 / 代价**

- 聚合直接查 `generation_jobs`，没有独立计数器。好处是单一份真源（多 worker
  不会各记各的），代价是每次创建任务多两条 SELECT——量级上可忽略。
- 检查与建任务之间在多 worker 下有极小竞态窗口（两个请求都读到「还没满」），
  可能超额 1–2 个任务。为这点误差引入跨进程锁不划算：防的是「一个人开一百个」，
  不是精确到个位。
- 在飞任务的 token 尚未落库，所以 Token 额度**拦不住同时开多个大任务**——
  它必须与并发上限配合使用。这一点写在配置项的 `description` 里。

### 验证

- `test_quota.py`（17 条）：默认零变化、三条口径（失败不计次 / Token 全算 /
  并发跨日）、三态、日界随时区变化、429 文案、只告警不拦截、**被拒不留任务行**。
- `test_admin_quota_api.py`（7 条）：设置 / 恢复继承 / 越界 422 / 未知用户 404 /
  非管理员 403 / 列表带字段 / 审计记「改前 → 改后」。
- 前端 `users.spec.ts` 新增 5 条：不限显示、已用/上限与标红、三态回填、
  提交值原样、后端回绝原因原样显示。

## ADR-046：任务监控「跨 owner 只读 + 复用同一条取消链路 + 协程式停止」

**背景**：v4.5 T5-1 要回答三个运营问题——谁在跑、有没有卡死、最近谁失败了；
并允许管理员手动掐掉卡死任务。`generation_jobs` 已有状态、时间、Token 与错误码，
本期**不加表、不加状态值**，只补查询与干预。

**一、管理面查询跨 owner，边界在 `require_admin`。**

`generation_job_repo` 原有纪律是「每个方法第一个参数都是 `owner_id`，不留不过滤的逃生口」。
监控必须跨 owner，因此新增 `admin_list / admin_count / get_for_admin` 三个方法，
并在文件里显式标注「管理面、跨 owner、安全性由路由层保证」。
不把这层判断塞进仓储：仓储若自己判身份，就同时混进了「取数」与「授权」两件事，
而授权一旦在两层各写一遍，迟早有一处漏改。`reap_running` 是同类先例（系统级维护）。

**二、「卡死」看 `updated_at`，不看 `created_at`，且由服务端判定。**

正文流式写入时 `updated_at` 会持续刷新，它停住不动恰恰说明「不再产出」；
用 `created_at` 会把「跑得久但一直在写」的长文档误报成卡死。
阈值 `STUCK_MINUTES = 30` 先用常量：够覆盖最慢的单章，也不会短到让管理员对红色脱敏。
`is_stuck / stuck_minutes / duration_seconds` 全部由服务端算一次——前端自己算会因
浏览器与服务器时钟差几分钟，出现「列表说卡死、点取消却说还在跑」的矛盾。

**三、取消复用 `job_service.cancel_job`，只多一个 `message`。**

用户点「停止」与管理员清理走**同一条链路**：标记内存运行时 + 落库
`failed + error_code='CANCELLED'`。新增的只有 `message` 参数，让 `error_message`
能区分「用户停止了生成」与「管理员手动停止了任务」——两者终态相同，但追责时要知道是谁动的手。
**不新增 `cancelled` 状态值**：状态是前后端共享契约，多一个取值意味着每处分支都要改，
漏一处界面就停在「生成中」；取消原因放 `error_code` 是代价最小的做法。

取消是**协作式**的：任务在下一个 await 点才跳出。卡在纯同步阻塞上的任务不会立刻退出，
但库里已是终态，重启后不会再显示「生成中」——卡死最多是临时的。

**四、`cancelled=false` 是正常结果，不是错误。**

管理员点取消时任务可能刚好自然结束。返回 200 + `cancelled=false`，前端提示
「已经结束了，无需取消」。若报错，管理员会以为操作失败而反复点击。
任务不存在才是 404——静默成功会让人以为「已经掐掉了」。

**五、自动刷新用轮询，不用 SSE；只在「在飞」页提供批量清理。**

监控页每 10 秒重新拉一次列表（`setInterval` + 静默加载，不闪烁加载态）。
刻意不走 SSE：T4 已评估实时尾随「风险高、收益低」，而监控页的时效要求只是「分钟级」。
「取消全部卡死」只放在「在飞」页：失败页没有 running 数据，按钮会恒为（0），
反而暗示「没有卡死任务」。

### Consequences

**变容易**

- 管理员不必翻日志或数据库就能回答「现在谁在跑、哪条卡了、刚才为什么失败」。
- 取消与用户侧共用一条链路，不会出现「后台能停、但内存里还在写」的分叉。
- 每次取消都进 `admin_audit_log`（`job.cancel` / `job.cancel_stuck`），可追责。

**变难 / 代价**

- 跨 owner 查询打破了仓储原有纪律，靠「文件内标注 + 路由守卫」维持边界；
  新增管理面查询时必须放在同一段注释下，避免被误用到用户面。
- 批量清理按「最久优先」取前 500 条 running；单机在飞任务远超 500 时可能漏清，
  但那种规模下瓶颈已不在这个页面。
- 多 worker 部署下，取消只能标记**本进程**的运行时；库里的终态仍然正确，
  但另一进程的协程要等自己的下一次检查才会退出（与用户侧取消的限制相同）。

### 验证

- `test_admin_jobs_api.py`（11 条）：状态过滤 / 卡死按 `updated_at` 判定 /
  用户名与类型筛选 / 取消落库 `failed+CANCELLED` / 已结束返回 false /
  未知任务 404 / 批量只动卡死 / 审计 / 非管理员 403。
- 前端 `jobs.spec.ts`（8 条）：卡死标红、取消二次确认、`cancelled=false` 文案、
  后端回绝原样显示、批量取消、筛选参数、自动刷新按 10 秒重拉。
- 端到端（临时库 + uvicorn + 无头 Chrome）：造「卡死 / 在跑 / 失败」三类任务，
  API 返回 `is_stuck=true, stuck_minutes=120`；取消后运行列表 3→2，
  失败列表出现 `CANCELLED / 管理员手动停止了任务`。

## ADR-047：登录失败用「渐进延时」而不是锁账号，配置一律读热快照

**背景**：v4.5 T5-3 之前，登录只做了两件防**账号枚举**的事（统一文案、用户不存在
也跑一次等价 scrypt），但对「反复猜密码」毫无防护——每秒几十次直到猜中。
这条路径在登录之前，会话、邀请码、配额都够不到。同一期补上「关闭自助注册」
「会话有效期可调」「管理员强制下线」。

**一、账号维度用延时递增，不用锁账号。**

硬锁（失败 N 次后拒绝该账号登录一段时间）挡得更死，但它有一个致命副作用：
**知道用户名就能把这个人锁在门外**——用防爆破的功能做出了拒绝服务的效果。
所以这里做的是「超过阈值后，每次校验前先等 2 / 4 / 8 秒（封顶）」：

| 窗口内失败次数 | 等待 |
| --- | --- |
| ≤ `login_max_attempts`（5） | 0 |
| 6 | 2s |
| 7 | 4s |
| ≥ 8 | 8s |

攻击者每秒几十次的吞吐被压到每 8 秒一次；而正确密码只是慢一点，永远进得去。
**封顶是必须的**：不封顶的话「久到进不去」与「锁号」对合法用户没有区别。

**二、延时在校验之前，且由路由层 `await`。**

放在校验之后，攻击者用响应快慢就能判断这次猜对没有，白送一个提示。
`auth_service.login` 是同步函数、跑在事件循环线程上，在里面 `time.sleep`
会停住**整个进程**（所有在途 SSE 流一起卡），所以 service 只**算**、路由层用
`await asyncio.sleep` **睡**。实测：一次 8 秒延时期间，另一个请求 53ms 返回。

**三、不存在的用户名同样计数、同样延时。**

只给真实账号计数，「有没有延时」本身就成了新的枚举信号，把原有的两条防枚举
全部作废。同理：失败计数按 `strip + lower` 归一存储——`users.username` 精确匹配，
不归一的话在 `admin` / `Admin` / `ADMIN` 之间轮换就永远触发不了阈值。

**四、只存失败，不存成功。**

登录成功即删掉该用户名的全部失败记录，于是「表里几行」就等于「还没清账的失败数」，
不需要 `ok` 列再在查询里过滤。不清的话「昨天错了 5 次」会让今天第一次登录白等 2 秒。

**五、配置必须读 `get_runtime_config().settings`。**

这是本期**唯一一个只有端到端才能发现的 bug**：所有读取点最初写的是
`get_settings()`，而它只反映环境变量；后台改的值存在 `system_config` 里，
要通过热快照才看得见。症状极具欺骗性——配置页显示「已关闭」、保存也成功，
接口却照旧放行。`auth_session_ttl_hours` 还有第二层：签发器是模块级单例，
若 TTL 在 `__init__` 里被转成 `timedelta` 存下来，改配置永远不生效。
所以 `OpaqueSessionIssuer.ttl()` 每次现读，单例只承载「用哪种签发方式」。

**六、强制下线只删会话。**

不改密码、不禁登录——「踢下线」与「封号」是后台两个分开的按钮。返回**吊销条数**
而不是 `ok`：单点登录下每人至多一条会话，`revoked=0` 表示「他当时并未登录」，
若只回 ok，管理员会以为踢掉了，排查「他为什么还能用」时被这句误导。
正在跑的任务不受影响（任务与连接本就解耦），要停任务去任务监控页。

**七、顺手清掉过期会话。**

`AuthSessionRepository.delete_expired` 从 v1 起就定义好、**从来没被调用过**，
`auth_sessions` 只增不减。挂在「登录成功」这条必经且低频的路径上，
不需要引入定时任务；同理 `login_failures` 的窗口外记录也在同一处清理。

### Consequences

**变容易**

- 在线爆破从「无限次」变成「每 8 秒一次」，且不会误伤任何合法用户。
- 关注册、调会话时长、踢人都不必改 env 重启。

**变难 / 代价**

- **不做 IP 维度**（用户明确取舍）：账号维度看不见「撞库」——每个账号只试 1 次、
  打一万个账号的攻击。这是**明确接受的残留风险**，将来若要补，表里已预留 `ip` 列
  （本期只记录、不参与判定），不必再走一次迁移。
- 延时会让忘记密码的人在多次失败后每次多等最多 8 秒；界面上不做额外提示
  （提示本身也会成为「你在被延时」的信号）。
- 会话有效期改小**不追溯**已发出的会话（`expires_at` 签发时已写死）。

### 验证

- `test_login_lockout.py`（15 条）：阈值内不延时 / 2-4-8 递增并封顶 /
  路由确实在校验前 `await` / 不存在的用户名同样计数 / 大小写变体共用一个计数器 /
  成功即清账 / 停用账号的正确密码不计失败 / 窗口外偏移不计 / 阈值 0 关闭限流 /
  登录顺手清别人过期的会话 / TTL 与阈值与注册开关**经后台配置**生效。
- `test_admin_sessions_api.py`（6 条）：吊销后凭据立即失效 / 不改密码 /
  未登录返回 0 / 未知用户 404 / 非管理员 403 / 审计留痕。
- 端到端（临时库 + uvicorn + curl 计时）：前 5 次失败 0.25s，第 6/7/8 次
  2.27s / 4.31s / 8.27s；8 秒延时期间并发请求 53ms；正确密码等 8 秒后 200，
  紧接着再错一次回到 0.25s（计数已清）；关闭注册后注册 403、原账号登录仍 200。
- 视觉（无头 Chrome）：「安全与登录」分组正常渲染、布尔项是开关而非文本框、
  用户页「强制下线」按钮与确认面板就位。

## ADR-048：数据合规——导出「用户看得见的」，删除「连带但留痕」

**背景**：v4.5 T5-4。此前后台能删账号，但没有导出；删除界面上只有一句
「确定删除？」，管理员并不知道自己点掉的是 1 份方案还是 30 份。

**一、级联删除的骨架本来是对的，本期只补「删前告知」与「删不干净的残留」。**

顺外键描一遍：`users` → `auth_sessions` / `solutions`（→ `documents`
→ `document_versions` / `chat_turns` / `chat_sessions`）/ `generation_jobs`，
全部 `ON DELETE CASCADE`（`connect()` 里 `PRAGMA foreign_keys=ON` 是前提）。
三处**有意不级联**：`admin_audit_log`（账号没了更要有据可查）、`app_logs`
（运维记录，不是用户业务数据）、`invite_codes` / `system_config` /
`model_providers`（全局配置）。

**二、`login_failures` 是唯一真正的漏洞——它按「用户名」记。**

登录失败计数不能按 `user_id` 存：那时用户可能压根不存在，而「不存在的用户名也要
计数」正是防枚举的关键（ADR-047）。代价是这张表不随账号走：删掉一个失败过 6 次的
`alice`、再注册一个同名 `alice`，新账号第一次登录就要先等 2 秒——它继承了一笔
没欠过的账。所以删除链路里补了一步 `auth_service.clear_login_failures(username)`，
归一化复用 `_attempt_key`（否则删的时候清的是另一种拼写，行还留着）。
这个问题在功能测试里完全看不出来，只有「删了再重建同名账号」才会显形。

**三、导出的是「用户看得见的」，不是数据库行镜像。**

包内：`manifest.json`（时间/条数/口径说明）+ `account.json`（**不含
`password_hash` / `salt`**）+ `solutions.json` + `documents/<方案>/<kind>.md` +
`chats/<方案>/<线程>.md` + `jobs.csv`。

- **不导 `solutions.data`**：它是 v9 之前的旧快照列，此后再没写过也没读过
  （ADR 早期记录的「不透明快照」已退役）。带上它只是把一份可能过期的重复数据
  塞进包里，还会让审核人分不清哪份才算数。
- **正文必须从 `document_versions` 取当前版本**，不是 `documents`（那一列 v6 已删）。
  用 `DocumentRepository.list_by_solution` 而不是自己拼 SQL，正是为了不绕过这条。
- **任务只导明细列，不导 `draft_content`**：那是未定稿的中间缓冲，单个任务可能几十 KB，
  既撑大文件又泄漏中间态。
- **CSV 带 UTF-8 BOM**：不带 BOM 的 UTF-8 在 Excel 里是乱码，而这份 CSV 的用途
  就是「用表格看」。

**四、文件名必须消毒，因为方案标题是用户输入的。**

`a/../../b` 这样的标题若原样当目录名，ZIP 里就出现了路径穿越——解压方（可能是
另一台机器上的审核人）的文件会被写到目标目录之外。`_safe_name` 替换 Windows 非法
字符与控制字符、抹掉 `..` 序列、去掉结尾的点与空格、并拦掉 `con`/`nul` 这类保留
设备名（叫 `con.md` 的文件在 Windows 上根本创建不出来，会让整个包解不开）。

⚠️ 这条的用例有个**假通过的陷阱**：只建方案不建文档时，该方案没有成员落进包里，
断言就在一个不含标题的集合上跑——消毒逻辑被删掉也不红。所以用例里每份方案都必须
真的写一份文档（已按此修正，并做过「删掉消毒 → 变红」的验证）。

**五、删除前先停任务，且必须把副作用说清楚。**

`job_service.cancel_for_user` 标记内存运行时的 `cancelled` 并落库 `CANCELLED`。
只改库不改内存的话，在途协程并不知道自己被取消——`_finalize` 里虽有
`solution_exists` 兜底（不会写出幽灵文档），但那只是**不写坏数据**，并不省钱：
它还会继续调上游烧 token 直到跑完。

⚠️ **删账号会让平台历史统计变小**：`generation_jobs` 是级联的，删完之后总任务数、
总 Token 与过去某天的图表都会一起减少。这是「彻底删除」的必然结果（合规要求就是
「当我没来过」），但不写清楚的话，管理员会以为统计坏了。所以确认面板里直接写了这句。

**六、确认方式从「点两下」改成「手打用户名 + 看清数字」。**

打开删除面板先拉 `deletion-preview`（方案/文档/版本/对话/任务/会话条数 + 会保留的
审计与日志条数）。**预览失败不拦着删除**——真删不动时后端会给理由，而「因为预览
挂了所以不能删」会让管理员卡在一个没有出口的界面里；此时面板显示「明细暂时取不到」，
删除照常可用。二次确认要求手打被删的用户名，防的是「按钮挨得近、手滑点两下」。

**七、导出虽然是只读，也要审计。**

`user.export` 记一条（含文件数与体积）。它把某人的全部内容搬出了系统，事后必须能
回答「谁在什么时候导走了谁的数据」。响应带 `Cache-Control: no-store`：个人数据不该
被任何中间层缓存。

### Consequences

**变容易**

- 「删之前知道删什么」：条数、会保留什么、以及对平台统计的影响，都在点之前摆出来。
- 同名重建的账号不再继承旧失败计数；删号不再留下仍在烧 token 的在途任务。
- 用户数据可以整包带走（正文是 `.md`，直接能读；CSV 直接能进 Excel）。

**变难 / 代价**

- 导出在内存里拼 ZIP，上限 50 MB（超了 413）。够大的账号会撞上限，需要分批或先清理；
  不设上限的话，一个数据量异常的账号可以把进程内存吃满。
- 手打用户名会增加一次操作成本——这是**故意**的：它把「误删」的概率降到很低。
- **不可逆**：包只是当时快照，删掉无法恢复。这一点只能靠文案说清，没有技术兜底。

### 验证

- `test_admin_export_api.py`（11 条）：包结构与正文 / 不含密码哈希与 salt /
  标题穿越被消毒（**每份方案都带文档，避免假通过**）/ 选择题与选中项渲染 /
  CSV 带 BOM / 下载响应头与 `no-store` / 审计留痕 / 非管理员 403 / 未知用户 404 /
  空账号可导出 / 导出不改状态（导完仍能登录）。
- `test_admin_erasure.py`（12 条）：预览各字段与库一致 / 在飞任务单独计数 /
  非管理员 403 / 未知用户 404 / 删后六类数据全为 0 / 在飞任务先取消（审计可见条数）/
  空账号可删 / 删后原密码登不进 / **审计保留而业务数据清空** /
  同名账号不再被延时 / `cancel_for_user` 同时落库与标记内存 / 已完成任务不受影响。
- 端到端（临时库 + uvicorn + curl）：造一个带方案/文档/对话/任务的账号，
  真下载 ZIP 并解包核对，再真删除并回查各表。

## ADR-049：管理后台只接受管理员账号登录，权限不足一律「账号不存在」

### Status

Accepted（2026-10-22）

### Context

v4 时管理后台的登录**复用**用户端那条 `POST /api/auth/login`：谁都能登进去，
进去之后前端再敲一次 `/api/admin/me` 判身份，非管理员停在「无权限页」。三个问题：

1. **越权入口在登录这一步就没关上。** 两个前端共用同一份 Cookie，普通账号在后台
   登录页输对密码会**真的登进主站**——后台顺手帮人登录了另一个产品，而那人当时
   只是「想看看能不能进后台」。
2. **无权限页把「账号存在」说出了口。** 它写着「已登录为 alice，但该账号不是平台
   管理员」。对运维对外的口径（后台只给管理员用）来说，这句话是反向的信息泄露：
   任何拿到一份普通凭据的人都能确认「这个用户名在系统里确实存在」。
3. 需求层面已经定调：后台只允许管理员账号登入，权限不足提示「账号不存在」。

三个候选：

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| A 只改文案 | 无权限页改写「账号不存在」 | 后端仍然谁都能登进后台，文案是假的；且「登录后才发现」这一步没消除 |
| **B 登录入口判身份** | 新增 `POST /api/admin/login`，判完身份再决定是否签发会话 | —— |
| C 403 改 401 | 让「不是管理员」与「未登录」在服务端也不可分 | 401/403 的分工是前端「去登录」与「身份不行」的唯一判据，全仓十几条用例与文档都按它写；收益只是少一个状态码，代价是排查时连服务端都分不清「会话过期」与「撤了管理员」 |

### Decision

取 **B**，并配套把四处口径统一：

1. **`POST /api/admin/login` 是后台唯一的登录入口**，注册进中间件的白名单（精确路径，
   不给 `/api/admin` 整个前缀开口子——前缀放行会让将来新增的管理接口默默变成公开接口）。
   它调用 `auth_service.login(..., require_admin=True)`：
   - **先验密码、再判 `is_admin`**。顺序反过来会让「这个用户名是不是管理员」变成一个
     不需要密码就能问出来的问题，等于送出一份管理员名单。
   - 密码正确但不是管理员 → 401「账号不存在」，**不记登录失败次数**（凭据本来有效，
     与爆破无关）、**不签发会话**、**不动他在主站上的那条会话**。
   - 密码错/用户不存在仍是「用户名或密码错误」，停用仍是「该账号已被停用」——
     能走到这两句的人还没证明自己是谁，口径不变。
2. **`require_admin` 仍是 403 `FORBIDDEN`，detail 改「账号不存在」**。已登录的非管理员
   直接敲管理接口时，也不该再被告知「你存在、只是不够格」。
3. **管理端会话收敛为三阶段** `unknown | anonymous | admin`，删掉无权限页。非管理员与
   未登录**落到同一页**（登录页），区别只是页面上多一句后端给的「账号不存在」。
   `unknown` 仍然不能猜——猜成 anonymous 会让管理员每次刷新被踢一次。
4. **Cookie 下发与渐进延时抽到 `api/login_flow.py`**，用户端与后台两条登录入口共用一份。
   写两份的代价不是重复几行，而是「一处改了 `secure` / `samesite`，另一处忘了改」——
   症状是管理端登录后立刻掉线，而排查会先怀疑会话表。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 给后台登录单独一套失败计数（`admin:` 前缀或按 IP） | 现有按用户名计数已经压住爆破；分开要动 `login_failures` 的键结构，而收益（避免一个人在主站被延时）很小 |
| 主站与后台各发一份 Cookie | 不签发就已经达到「失败不影响主站」，再拆一份反而多出「同一个人两套会话」的状态 |
| 管理员二次验证（TOTP） | 独立课题，与「谁能进这个入口」正交 |
| 后台登录失败也记审计 | 失败尝试里大量是打错密码；审计表留给「人做成了什么」 |

### Consequences

- **变容易**：后台只有两种可见状态（登录页 / 后台），少一整页与一整段分支；
  普通账号再也不会「在后台顺手登进主站」。
- **变困难 / 必须记住**：
  - 非管理员会在登录页看到「账号不存在」，而他可能正是主站的老用户，会来问
    「我账号是不是没了？」。这是**刻意的取舍**（对外只承认管理员账号），
    运维口径必须与之一致；页面上不要补一句「你可能只是没权限」——那等于把
    「账号存在」又说回去了。
  - 会话被撤销管理员之后（例如在另一台设备上被降权），他会直接回到登录页而不是
    某一页「你已无权限」，且不会被告知原因。
  - `test_login_lockout` 等用例的 monkeypatch 点从 `api/auth.py::_sleep` 挪到
    `api/login_flow.py::_sleep`；以后新增登录入口也必须走这个模块，否则等于给爆破
    开一条无成本通道（用例 `test_admin_login_waits_before_checking` 就是钉这个）。
- **测试陷阱（真踩过 / 想得到）**：
  - 只断言状态码会漏掉「拒绝了登录，但把人在主站上的会话顶掉了」——写成「先
    `auth_service.login` 再判 `is_admin`」就是这个后果。补的
    `test_rejected_login_does_not_kick_the_user_off_the_main_app` 对照的是**旧 Cookie
    还能不能用**，而不是「本次响应有没有 Cookie」。
  - 断言「没有下发凭据」要看响应头里没有 `set-cookie`，不能看「客户端当前没带
    Cookie」（后者在已登录的客户端里永远为真，看着像断言、其实什么都没验）。

## ADR-050：模型供应商改为「配置条目」，id 由后端生成、使用中只有一条、协议创建后不可改

### Status

Accepted（2026-10-22）

### Context

v16 的 `model_providers` 把「一家供应商 = 一个固定空位」当成了表结构：
`id` 就是厂商名（`ark` / `openai` / `anthropic` …），六行由迁移播种，`builtin` 标记它们「不许删」。
当时的隐含假设是「一个人只接一家」。真实使用很快打破它：

1. **同一家要配多条。** 「方舟-生产」与「方舟-测试」是两条不同的 endpoint / 模型 / 参数，
   而它们协议相同。id 由协议决定时，第二条无处安放——只能改那条共用的，于是测试一改
   生产就跟着变。
2. **「内置」这个锚点没有实际用处。** 它存在的理由只是「回到出厂状态」，而六行里
   五行是用户永远不用的。列表被它们占满，「哪些是我真配的」反而看不出来。
3. **回执说不清走了哪条。** 计量只记 `provider`（协议名）。同一协议两条配置时，
   「这次是谁在花钱」在账上无法回答，而事后改配置名就再也追不回来了。

三个候选：

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| A 保留六行，允许改 id | 让管理员把 `ark` 改名成 `ark-prod` | id 进了历史计量与任务回执，改名等于**重写历史**；而且「第二条」仍然只能靠在 id 里加后缀 |
| B 加 `(protocol, slot)` 唯一约束 | 一家允许多个固定槽位 | 槽位数是多少？没有答案；且「槽位 2 空着」是纯粹的表结构噪声 |
| **C 配置条目** | `id` 由后端生成（`cfg_xxx`），`name` 必填可重名，协议只属于这条配置 | —— |

### Decision

取 **C**，并把连带的口径一次定齐：

1. **`id` 由后端生成**（`cfg_` + 10 位十六进制）。同一协议可以有多行，让管理员手填 id
   只会撞名；而撞名后唯一可做的决定是「谁让」，没有业务价值。碰撞靠
   `sqlite3.IntegrityError` 重试 3 次兜底，而不是「先查再写」（后者有竞态）。
2. **`name` 必填、允许重名**。它只是给人看的标签（「方舟-生产」），**身份是 id**。
   拦重名会逼人起「方舟-2」这种谁也记不住的名字。
3. **`protocol` 创建后不可改**，改它显式报 400，而不是让仓储层静默丢字段。
   换协议等于换一家厂商：`max_tokens` / `thinking_enabled` / `extra` 的语义全变，
   就地改会留下「半新半旧」的字段，而错误要到某次生成才以「参数不认」的形式出现。
   静默丢的结果是「200 但没改」，比报错难查得多。
4. **「使用中」唯一，真源仍是 `system_config.active_provider_id`**（不在表里加
   `is_active`：那会允许「两行都是 1」）。⚠️ 判断某条是否使用中，读**原始指针**，
   不用 `config.active_provider`——那条配置一旦被停用，解析会回退到别的一条，
   于是「按解析结果判断」就会把悬空指针放过去，删完库里留下一个指向已删行的 key。
5. **所有条目一视同仁**：只有「使用中」的不能直删，其余随时可删。不再有
   「内置行」与「回到出厂状态」的锚点，`builtin` 列保留但一律为 0 且**代码不再读取**。
6. **`PRESETS` 降级为表单模板**，字段 `id` 改名 `key`。它只是「选一家自动填好协议、
   地址与变量名」的初值，创建后由后端发 id。名字必须与 id 区分开，否则前端会拿它当
   id 发请求。
7. **计量落 4 个快照列**（`generation_jobs`：`provider_protocol` / `provider_config_id` /
   `provider_name` / `provider_model`），**不是外键**。快照而非指针是这一层的既有纪律
   （`prompt_tokens` 同理）：配置事后改名或删掉，历史账单不该跟着变。
   `RunMeter` 与 `RunSummary` 同步拆成 `protocol` / `provider_config_id` / `provider_name`。
8. **迁移 v19（`provider_config_entries`）**：
   - 给 `generation_jobs` 补 4 列（`PRAGMA table_info` 守卫，`ADD COLUMN` 没有 `IF NOT EXISTS`）；
   - 从历史 `usage` JSON **回填** `provider_*`：`json_valid` + `json_type` 双重守卫，
     坏值跳过而不让整次迁移失败；只填 `provider_protocol = ''` 的行（幂等）；
   - 清掉六条播种行，判据是**四个条件同时成立**：
     `builtin = 1` **且** `created_at = updated_at`（从没被编辑过）**且** id 在播种清单里
     **且** **不是当前使用中的那条**。最后一条不能省——少了它会把用户唯一在用的
     那行删掉，装完就空了；
   - 其余 `builtin = 1` 一律置 0；指针指向已不存在的行时清空指针。
9. **回执解析只留一份**（`frontend/src/utils/runSummary.ts`）。事件与
   `documents.last_run_summary` 是**同一个 dict**（都是 snake_case），而前端原先两处各写
   一套、落库那侧直接断言成 camelCase 的 `RunSummary`，结果是**刷新页面后回执整块消失**
   且不报错。归一化两种键都认，缺字段只退化那一项。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 配置条目的「复制一份」按钮 | 与「新增时选同一个模板再改」等价，先看真实使用频率 |
| 按协议分组的折叠列表 | 条目数在个位数时分组只是多一层点击；等真到十几条再说 |
| `model_providers` 与任务的**外键** | 快照语义要求「配置删了账单还在」，外键会让删除变得不可能 |
| 管理员改密钥值（而非变量名） | 需要先解决加密存储与轮换（ADR-042 仍有效），与「多条配置」正交 |
| 把 `token_budget.evaluate(provider=...)` 参数改名为 `protocol` | 它的值域同时接受厂商名（`anthropic` / `openai` / `ark`）与协议名（`openai_compatible`），叫 `protocol` 反而不准；改为在 docstring 里写清值域并加一条守门用例 |
| 已删除配置的「撤销删除」 | 重新新增一条即可（30 秒的事），而回收站要引入软删除与清理策略 |

### Consequences

- **变容易**：同一家想配几条配几条；列表里只剩用户真配过的条目；回执上写得出
  「火山方舟 · doubao-…」，同一协议两条配置也能在账上分开。
- **变困难 / 必须记住**：
  - **装完列表是空的**。此时生成退回 `env:` 合成的降级项（`active_provider_id` 形如
    `env:ark`），它不是可编辑的条目。验收与排查的第一句话要改成「先在后台建一条」。
  - **`id` 不再是可读字符串**。凡是想「按 id 猜协议」的代码都会静默落空——
    `_resolve_active_provider` 的回退因此改成**按协议**匹配第一条可用条目，
    并保留 `openai → openai_compatible` 的别名表。
  - 测试里再没有「直接拿 `ark` 当 id 用」的写法：先 `create` 一条，再用返回的 id 操作。
    这不是用例啰嗦，而是真实前提——列表本来就是空的。
  - 消费方（前端、脚本）不得再读 `builtin`；接口已不返回，读到 `undefined` 的分支会静默失真。
- **迁移是不可逆的**（这是数据清理型迁移，与 schema 型不同）：六条播种行删除后无法从库里
  恢复，只能重新新增。因此删除判据刻意收紧到「四条件 AND」，并配套
  `test_v19_deletes_only_factory_seeds`（断言 `ark` 与被编辑过的行都活下来）与
  `test_v19_clears_dangling_active_pointer`。
- **测试陷阱（真踩过 / 想得到）**：
  - 「改坏也不红」的典型：删除判据少了「不是使用中」这一条，用例若只断言「播种行没了」
    就会绿着通过，而真实用户升级后列表被清空。
  - 回执解析只测 camelCase 夹具会全绿，而线上永远是 snake_case——真正的回归用例
    必须用后端那份形状（`runSummary.spec.ts` 的第一条 + `document-service.spec.ts`
    的「刷新后仍能读出」）。

### 补充（同日）：新增表单由「供应商」驱动

实现时确认的一处遗漏：v19 把「供应商」降级成一个标着「模板（只用来填表）」的下拉，
旁边还并排着协议、`base_url`、密钥变量名三个手填框。结果是**选了供应商仍然要手打
`ARK_API_KEY`**——而这三个字段本来就是「这家怎么接」的一组知识，拆开填只会得到
「ark 协议 + 火山地址 + DEEPSEEK_API_KEY」这种照抄文档都发现不了的错配。

定为：

1. **「供应商」是这张表单唯一的入口**（必选）。选中后协议、地址、变量名一起定下来。
   **没选供应商不给提交**：否则会得到一条「协议默认 `openai_compatible`、地址空着」的配置，
   看着建成了，第一次生成才报错，而报错里还看不出当初少选了一步。
2. **协议与密钥变量名都不进表单**。
   - 协议由供应商决定、创建后也不可改；
   - 变量名同样由供应商决定，它只是「去哪个环境变量取密钥」的指针——不是需要人
     来做的一个决定。管理界面不显示它，也就没有填错的机会。
   - 判据是**只读/禁用也算「给用户看见了」**：灰掉的下拉、`readonly` 的输入框都在暗示
     「这里本该能改」。真要表达「不可改」，就不渲染它，把信息放到展示区
     （协议在列表行与编辑面板标题、变量名在列表行元信息）。编辑面板同步照此办理，
     请求体里也不发这两个字段。
3. **下拉里没有「其他 / 自定义」**：预设即全部入口。要接自建接入点，选
   「本地 vLLM / Ollama」（不要密钥）或「自建网关（OpenAI 兼容，需密钥）」再改地址。
   这两条预设并列，正因为「要不要密钥」无法从协议推出来。
   ⚠️ 代价：**没被预设覆盖的厂商只能在预设上改地址**，而它的变量名也随预设走
   （例如接 Groq 得选带密钥的那条、把地址改掉）。这一取舍是为了让表单只剩能改的项。
4. **变量名取自预设并原样提交，包括空串**。前端不渲染它，但绝不能漏发：
   漏了配置照样建得出来，第一次生成才以「未指定密钥环境变量名」失败，而界面上无从修。
5. **`PROTOCOL_KEY_ENV_VARS` 只管「没传」**（脚本/第三方调 `POST /providers` 且
   `api_key_env_var=None`），按协议补默认值；**显式空串不补**——那是「不要密钥」的表达。
6. **空变量名 = 不需要密钥**，不是「配置漏了」。`lookup_provider_key` 给它占位值
   （OpenAI 兼容客户端要求 `api_key` 非空）。变量名写了、环境里没值的仍然报错并带
   变量名——那才是真正需要去 `.env` 补一行的情况。早先这里对空变量名直接抛错，
   等于把「本地模型」这条预设变成必挂的摆设。

## ADR-051：模型接入只住在后台面板，`.env` 只留密钥值

### Status

Accepted（2026-10-22）

### Context

ADR-050 把「一家供应商一个固定空位」改成了「配置条目」，v19 也清掉了六条播种行。
但**还有一份旧的配置源没撤**：`.env` 里仍然写着

```
DEFAULT_LLM_PROVIDER=ark
DEFAULT_LLM_MODEL=doubao-seed-2-1-turbo-260628
ARK_BASE_URL=… / ARK_MAX_TOKENS=… / ARK_THINKING_ENABLED=…
ANTHROPIC_API_URL=… / ANTHROPIC_MAX_TOKENS=… / OPENAI_…
```

而 `runtime_config._synthesize_from_env` 会在「表不可用 / 一条配置都没有」时
拿这些值合成一个 spec（id 形如 `env:ark`）继续跑。当时它是「升级后行为零变化」的
保险丝，现在变成了四个具体问题：

1. **两处真源。** 后台改了一条配置、env 里那份还在。出问题时要同时翻两个地方，
   而且没有任何提示告诉你去翻哪一个。
2. **界面与实际不一致。** 列表空着却能正常生成——用的是界面上不存在、也改不了的
   那条。管理员看到「还没有任何配置」却收到成功的回执，第一反应是「这个页面是不是假的」。
3. **回执里出现 `env:ark`。** 用户和运维都不知道那是什么，而账单需要它说得清。
4. **这套 env 本来就容易写错还不报错。** `ARK_API_BASE_URL` 被 `extra="ignore"`
   静默忽略、自定义地址从来没生效过——这个坑修过一次，但「键名对不上就没效果」
   的结构性问题还在。

另一个诱因是表单的两次反馈：**选了供应商仍要手打 `ARK_API_KEY`**、
**协议与密钥变量名这两个不可改的东西还摆在表单里**。它们的共同根因是
「同一件事有两个配置入口」——只要 env 还能配，后台就不是唯一入口。

### Decision

**配置进库，凭据留环境。**

1. **`Settings` 删除 10 个字段**：`default_llm_provider`、`default_llm_model`、
   `anthropic_api_url`、`openai_api_url`、`ark_base_url`、`ark_thinking_enabled`、
   `ark_max_tokens`、`anthropic_max_tokens`、`openai_max_tokens`，
   以及 `llm_context_window`（全局窗口覆盖）。
   连同一并删掉 `api_key_env_var()` / `require_api_key()`（它们的前提是「进程里只有一个供应商」）。
   **写进 `.env` 也不会有效果**——不是「不推荐」，是结构上没有地方读它。

   `llm_context_window` 一并删是因为它会**静默赢过**配置条目：
   原先是 `settings.llm_context_window or spec.context_window`，后台给某条填了 128k、
   env 里留着 32k，预算就按 32k 判——症状是「换了大窗口还老报超顶」。
   窗口现在只有一条链：**配置条目填的值 → `model_registry`**。
2. **删 `_synthesize_from_env` 与 `ENV_SPEC_PREFIX`。** `_resolve_active_provider`
   只剩两条规则：指针有效就用它；否则按 `sort_order` 取**第一条启用中**的。
   一条都没有时返回 `None`——这是正确答案，不是错误。
3. **第一条配置自动成为「使用中」。** 列表空着时它是唯一可选项，让用户再点一次
   「设为使用中」只是仪式；而忘了点就会得到「配好了却生成说没有配置」。
   已有指针时**不抢**：新建第二条不该把正在跑的那条顶掉。
4. **调用方直接说人话。** `get_llm()` 抛
   「还没有任何模型配置。请先在管理后台「模型配置」页新增一条……」；
   `/health` 的 llm 项同理；启动日志印「（尚无模型配置）」。这类文案本身就是修复指引，
   含糊一句「没有可用的模型供应商」会让人去翻 `.env`——而答案恰好是「`.env` 里没有了」。
5. **v16 迁移改成常量播种**（不再读 `Settings`）。老库不会重跑 v16，新库上它插下的
   六行随即被 v19 删除，所以改成常量对最终状态没有影响；不这么改，删字段就会让
   全新库的迁移直接 `AttributeError`。
6. **密钥值仍在环境里**（ADR-042 不变）。数据库只存**变量名**，按名取值的入口是
   `core/secrets.lookup_env`（不经过 `Settings`）。配置可以进库，凭据不行——
   这是两件事，不能因为「都迁到后台」就合并。
7. **`.env.example` 只留三把密钥**，并写明「供应商 / 协议 / 地址 / 型号 / 上限
   都不在这里配置」。
8. **空状态只留一个新增入口。** 右上角已有「+ 新增配置」，正文里再摆一个
   「新增第一条配置」会让人先愣一下「这两个是不是不一样」。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 密钥托管（把值也迁进后台） | 要先解决加密存储、轮换与泄露后处置，与「配置住哪儿」正交（ADR-042 仍有效） |
| 把 `token_budget.evaluate(provider=...)` 改名 `protocol` | 值域同时接受厂商名与协议名，改名反而不准；已在 docstring 写清并加守门用例 |
| 后台展示「旧 `.env` 里还残留哪些键」 | 这些键已经没有任何读取点，提示一个「写了但没用」的清单只会制造噪音 |

### Consequences

- **变容易**：只有一个地方配模型；列表与实际生效的东西永远一致；
  排查第一句话是「去后台看一眼」，不必再问「env 里那份是什么」。
- **变困难 / 必须记住**：
  - **装完不能直接用。** 生成会明确报「还没有任何模型配置」。验收清单、README、
    新机部署脚本都必须先建一条。
  - **表坏了就是不可用。** 以前「表损坏」会静默退回 env，现在会明确失败。
    这是有意的：静默降级让人以为配置生效了，而实际跑的是另一个东西。
  - **测试必须显式造配置。** 一批原本靠 env 默认值的用例（`test_llm_resilience`、
    `test_generation_job`、`test_observability`、`test_token_budget`、`test_runtime_config`）
    改成了「先 `ModelProviderRepository.create(...)` 再断言」。这不是用例啰嗦，
    而是真实前提：全新库上本来就是空的。
- **测试陷阱（真踩过）**：
  - 「改坏也不红」的一种形态：把回退删掉后，那些**只断言「拿到了 provider」**的用例
    会在有配置时照样绿。所以新增用例钉的是「一条都没有时 `None` + 报错文案」，
    而不是「能拿到东西」。
  - `test_default_cap_leaves_headroom_for_real_prompts` 曾因为「没有配置 → 32k 兜底」
    假失败：物理顶变了，断言却只看 `exceeded`。这类用例要显式声明自己依赖哪条配置。

## ADR-052：`.env` 只剩密钥与启动项，可热改参数一律不在模板里出现

### Status

Accepted（2026-10-22）

### Context

ADR-051 把**模型接入**从 `.env` 撤走了，但 `.env.example` 里还留着另外十六个键：
`LLM_BUDGET_*`、`LLM_TIMEOUT` / `LLM_TOTAL_TIMEOUT` / `LLM_MAX_RETRIES` / `LLM_RETRY_DELAY`、
`PRD_SECTION_*` / `PRD_PIPELINE_CONCURRENCY`、`DOC_REVIEW_MAX_TOKENS` /
`PRD_SECTION_REVIEW_MAX_TOKENS` / `REVIEW_REWRITE_MIN_SEVERITY` / `DOC_SECTION_REWRITE_ENABLED`、
`AUTH_SESSION_TTL_HOURS` / `AUTH_COOKIE_SECURE`。

它们**全部**在 `runtime_config.WHITELIST` 里，也就是后台早就能改。问题不是「能不能改」，
而是「两个入口」：

1. **模板被读成配置入口。** 它是所有人第一次接触配置的地方，注释写得越细，越像
   「正确答案在这里」。改完重启却发现没生效——因为 DB 覆盖在 env 之前，
   而那个覆盖是自己在后台点过的，早忘了。
2. **默认值会漂移。** 修「章节审核复用整篇 `review_llm`」那个死配置时，代码默认值
   从 1024 改成了 2048，模板里还写着 1024。**两处写同一件事，就一定有一处是错的**，
   而且错的那处不报错。这次就是这么发现的：把模板的值当真值核对时对不上。
3. **验收清单与部署脚本会照模板抄。** 抄到的是一份「看起来有、实际不生效」的配置。

### Decision

1. **模板只保留两类键**：
   - **密钥值**（`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `ARK_API_KEY`）——它们必须留在环境里（ADR-042）；
   - **启动项**——改了要重启、后台也改不了的那些：`AUTH_ENABLED`、`AUTH_COOKIE_NAME`、
     `INVITE_CODE`、`INIT_ADMIN_*`、`DB_PATH`、`PRDWRIGHT_SKILLS_DIR` /
     `PRDWRIGHT_SKILLS_STRICT`、`LOG_LEVEL` / `LOG_FORMAT`、`CORS_ORIGINS`、`HOST`、`PORT`。
2. **26 个白名单键一个都不出现**。代码里的 `Field(default=...)` 是它们的唯一真源，
   而且默认值就取「推荐值」（所以删掉模板行**不改变**任何运行行为——已逐项核对）。
3. **解释文案搬到 `_FIELD_META.help`**。模板删掉的那些注释里，只有两条是别处没有的
   ——「`llm_timeout` 是帧间隔、不是总时长」与「有效预算 = min(物理顶, 业务顶)」，
   已补进后台说明。其余在 help 里本来就有。
4. **用用例钉住模板**：`test_env_example_carries_only_startup_keys` 断言模板不含任何
   白名单键，**同时**断言三把密钥与启动项仍在——后一半是防「矫枉过正」：
   把 `DB_PATH` / `PORT` 也删掉，照模板建出来的 `.env` 就起不起来了。
5. **本地被手动调过的值先搬家再删行**。`PRD_SECTION_MAX_REWRITES=2`（默认 1）是先写进
   `system_config` 才删的：覆盖层本来就在 env 之上，所以**行为不变**，而且这一项从此
   出现在后台面板上——这正是它该在的地方。直接删行会静默把它变回 1。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 把启动项也搬进后台 | 它们「改了必须重启」，进白名单就是认知陷阱（ADR-041 已定过这条边界） |
| 给白名单项做一层「导出当前生效配置为 .env」 | 又造一个出口，且导出的那一刻就可能过期；要看生效值用 `GET /api/admin/config/effective` |
| 把默认值也挪进数据库 | 默认值的价值就是「表空时仍然有一套能跑的值」；挪进库等于把启动依赖又加一环 |

### Consequences

- **找配置只有一处**：后台「配置」页 / 「模型配置」页。模板顶部已经写明这一点。
- **模板短了很多**，但短的部分不是「没配就不好用」——那些默认值本来就是推荐值。
- **模板漂移由用例兜住**：谁再往里「顺手补个默认值」，CI 立刻红。
- **风险**：有人会以为「模板变短 = 功能变少」。所以模板开头那句必须一直留着：
  本文件只有密钥值与启动项，其余在后台。

### 补充（同日第二次）：连密钥行也退成注释，模板里一行生效配置都没有

第一版删完白名单项后，模板还留着三行**空值密钥**（`ANTHROPIC_API_KEY=` 等）。
被问到「这三行留着有什么用」——它确实不是配置：空值等于没写，写不写都能起服务。
它的唯一作用是**告诉部署者「这台机器要准备哪几把钥匙」**，而那件事用注释也能表达。

于是改为：三行一律注释，配一段说明讲清「密钥为什么不能进后台」：

- 面板管的是「用哪条配置、去哪个变量取钥匙」；**钥匙值本身是凭据**，进库就会跟着
  备份、导出包、拷给别人排查的库副本一起流动（导出功能明确不导 `.env`）。
- 钥匙要过页面就会经过请求体 / access log / 前端内存，白多几个泄露面。
- 权限边界不同：能看后台 ≠ 能登服务器。
- 附带好处：改 `.env` 里的值**不用重启**（按 mtime 重读）。

守门用例随之从「只该有三把密钥」收紧为 **`keys == set()`**：`.env.example` 里
一个生效行都不许有。这条断言比文档里的「请勿添加」有力——它会在 CI 上红。

同一次里还修了两个「模板给了开关但实际不生效」的死配置（都属于「多余」的另一种形态）：

1. `PRDWRIGHT_SKILLS_STRICT` 从来没生效过：字段叫 `skills_strict`，pydantic 按字段名
   匹配 `SKILLS_STRICT`，而模板与运维口径写的都是 `PRDWRIGHT_SKILLS_STRICT`
   （与 `PRDWRIGHT_SKILLS_DIR` 成对），于是被 `extra="ignore"` 静默吃掉——
   部署时「设了 fail-fast 却仍在悄悄降级」，正是这个开关要防的事。
   改为 `validation_alias=AliasChoices("PRDWRIGHT_SKILLS_STRICT", "SKILLS_STRICT")`，两个都认。
2. `PRDWRIGHT_SKILLS_DIR` 写在 `.env` 里无效：`skills_root()` 走 `os.environ`，
   而 pydantic 读 `.env` **不写进 `os.environ`**。只有 Docker / systemd 那种真环境变量才行，
   而 `cp .env.example .env` 恰恰是最常见的使用方式。改为走 `core/secrets.lookup_env`
   （先进程环境、再按 mtime 读 `.env`），与密钥同一条路。

## ADR-053：密钥加密入库，`.env` 不再放密钥（单主密钥方案）

**状态**：已实施。**取代 ADR-042**（「密钥不进库」）与 ADR-051 中「密钥值仍在环境里」一条。

### 背景

ADR-042 定的是「数据库只存变量名，密钥值留在 `.env`」。实际用起来有两个真实痛点：

1. **操作面分裂**：模型接入早就搬进后台了（ADR-051），偏偏密钥还得 SSH 进服务器改
   `.env`。管理员在同一个页面里配地址、配型号，却要切出去改文件。
2. **无痕迹**：谁在什么时候换了哪把密钥、换成了什么环境的，`.env` 上一概看不出来。

用户明确要求「密钥也放进管理员面板」。这不是偷懒——**面板可以给每一次变更留审计**，
比沉默地改 `.env` 更可追责。前提是：不能让明文进数据库。

### 决策

采用**单主密钥 + 应用层加密**：

- **主密钥**：`backend/secrets/master.key`，32 字节，文件权限 600，`.gitignore`。
  由 `scripts/keygen/generate_keys.py` 生成；**不进数据库、不进 `.env`**。
- **密钥值**：用主密钥加密（Fernet，密文自包含 nonce + 认证标签）后存
  `model_providers.value_token`。库里只有密文。
- **取值**：构造 LLM 的前一刻 `core/crypto.decrypt_value()` 解密；明文只在内存里短暂存在。
- **面板**：密钥作为模型配置的一部分录入（密码框），保存时后端加密；列表只回
  `key_present` 布尔；要看明文必须单独调 `POST /providers/{id}/reveal-key`，且写审计。

### 为什么是「单主密钥」而不是更花哨的方案

讨论过四条路，最终选了最简的一条：

| 方案 | 取舍 | 结论 |
|---|---|---|
| 明文入库 | 零加密代码，但数据库备份/导出/拷贝全部泄露真实密钥 | 否决 |
| **单主密钥（本 ADR）** | 代码最少；轮换要重加密全部 `value_token` | **采用** |
| 每密钥一把 DEK（信封加密） | 轮换只重包 DEK；多一层 `wrapped_dek` | 过度设计，本规模不需要 |
| KEK 版本注册表 / Vault | 轮换 O(1)、可零停机；要额外表或外部基建 | 过度设计 |

「轮换要重加密全部值」看着吓人，但本项目密钥只有寥寥几把、轮换极少，跑一次
`--rotate` 脚本即可；换来的是**没有额外的表、没有版本指针、没有 kek 文件**。
在这个规模上，简单比优雅值钱。

### 轮换的安全顺序

`generate_keys.py --rotate` 必须**先改库、最后换文件**：

1. 旧主密钥解密全部 `value_token` → 新主密钥重新加密 → 写回数据库；
2. **全部成功之后**，才把新的 `master.key` 原子写入（临时文件 + rename）。

反过来（先换文件再改库）一旦中断，旧密文就再也解不开，是不可逆的数据丢失。
同理，普通 `generate` 发现主密钥已存在时**拒绝覆盖**，只允许显式 `--rotate`。

### 接受的代价（写清楚，别以后当成 bug）

- **能登管理后台 = 能拿走密钥**：集中管理的固有代价。缓解：列表只回布尔；
  查看明文是独立动作且写审计；密钥接口请求体不进 access log。
- **主密钥文件丢了 = 所有密钥解不开**：设计内的自毁，也是它的安全价值。
  备份时主密钥必须与数据库分开存放。
- **轮换后旧数据库备份解不开**：需要恢复旧备份就得离线保管旧主密钥。
- **本机 `vLLM`/`Ollama` 这类不要密钥的接入点**：现在空 `value_token` 表示「未配置」，
  所以必须显式填一个占位值（如 `not-needed`）——OpenAI 兼容客户端要求 `api_key` 非空。

### 落地清单

- 新表列：`model_providers.value_token`（迁移 v20 删除旧的 `api_key_env_var`）。
- 新模块：`core/crypto.py`（加载主密钥、加解密、`is_configured`）。
- 生成/轮换：`scripts/keygen/generate_keys.py`（`--rotate` 走上述顺序）。
- 接口：模型配置保存接受明文 `api_key`；新增 `reveal-key`；列表不再回变量名。
- 导出：**不涉及**——导出本来就不包含全局配置表，`value_token` 不会随数据包流出。
- 模板：`.env.example` 第一节改为「密钥不在这里」，并给出生成主密钥的命令。

### 与既有决策的关系

- **ADR-042 被取代**：那是「凭据不进库」的绝对条款；本 ADR 把它改成
  「**凭据不以明文进库**」，并明确主密钥的位置与轮换顺序。
- **ADR-051 部分修订**：模型接入仍只住后台；但其中「密钥值仍在环境里」不再成立。
- **ADR-052 部分修订**：`.env` 仍然只剩启动项；但不再有「密钥值」这一节。
