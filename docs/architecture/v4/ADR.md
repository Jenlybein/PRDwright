## ADR-039：管理员后台采用「根目录独立应用」，不嵌入也不组 monorepo

### Status

Accepted（2026-10-21）

### Context

需要新建平台管理员后台。三个候选：

1. **嵌入现有 `frontend/`**：加 `/admin/*` 路由与页面，作为一个 feature module；
2. **根目录单开 `frontend_admin/`**：独立 `package.json`、独立 Vite 应用；
3. **pnpm monorepo**：`frontend/` 下拆 `userpage` / `adminpage` 两个应用 + `packages/shared`。

讨论中先后提出过三类顾虑：

- **安全**：「一起放着是不是容易被黑客找到后台」；
- **开发冲撞**：「一起放着会不会互相冲撞」；
- **工程成本**：monorepo 的双份工具链与 shared 包维护。

其中「隐藏路径能挡住攻击者」这一点经核实不成立：SPA 的路由本就打进 JS 包，
攻击者直接扫 `/api/*`，前端怎么组织都不改变 API 的暴露面；且两个前端只要请求同一个 API 源，
会话 Cookie 本来就通用。真正的安全边界是**服务端 `require_admin`**，
与代码是否分开放置无关。

### Decision

取 **方案 2（根目录独立应用 `frontend_admin/`）**。

- 与 `backend/`、`frontend/` 并列，独立构建、独立部署。
- 两个前端共享同一后端 API 源，因此共享同一套会话 Cookie，**不做任何登录态桥接**。
- 管理员端**不 import** 用户端任何模块；自带一份薄 HTTP 封装与类型。
- 服务端对所有 `/api/admin/**` 强制 `require_admin`（这是唯一硬防线）。

### Consequences

**变容易**

- 独立构建与部署：管理员端可单独发布、可放独立子域或内网（这是「分离」唯一能带来
  真实安全增益的地方，且它靠的是部署边界，不是代码位置）。
- 硬隔离：TypeScript/Vite 天然阻止跨应用 import，不会因手滑把管理员组件带进用户端。

**变难 / 代价**

- 多一套工具链（Vite / 依赖 / CI），以及少量 HTTP 封装的重复。
- **git 冲突并不会因此减少**——两个应用仍在同一仓库、同一段提交历史；
  真要消除版本控制层面的冲撞只能拆独立仓库，那代价远大于收益。
- 部署时要处理两个 SPA 共存（反代分路径或独立子域）与 `cors_origins` 放行。

## ADR-040：日志采集「文件 + SQLite 双写」，且采集先行于 UI

### Status

Accepted（2026-10-21）

### Context

`core/logging_setup.py` 目前只装了一个 `StreamHandler(sys.stdout)`，
**没有任何持久化**：进程停止后历史全无，管理端也就无从查看。
日志格式本身已经很规整（ts / level / logger / msg / request_id / `extra=` 字段，
`LOG_FORMAT=json` 时一行一条 JSON），采集端几乎不需要改格式化逻辑。

候选方案：

1. **纯轮转文件**：简单，但后台检索要现解析文本、处理轮转与并发读；
2. **纯 SQLite 表**：查询灵活，但每次 `logger.info` 都写库，且丢了文件这个兜底；
3. **文件 + DB 双写**；
4. **交给外部采集**（Docker logs / ELK）：运维更专业，但与「自建小工具开箱即用」相悖，
   且用户明确要求后台内自带日志查看，必须自持。

### Decision

取 **方案 3（双写）**，并附加一条排期约束：

- 新增 `LogStoreHandler`，在 `configure_logging` 里与 stdout handler 并列装上，
  **业务代码一行都不用改**（与 `request_id` 自动注入同一条设计纪律）。
- **轮转文件始终开**（`logs/prdwright.log`，5MB × 5）：保证永不丢、可脱机排查、可外喂采集。
- **`app_logs` 表可开关**（默认开，异步批量写）：保证后台能过滤 / 分页 / 排序。
- **保留策略**：`log_retention_days`（默认 7 天）与 `log_max_rows`（默认 5 万条），
  启动时执行一次 + 写入时懒触发。
- ⚠️ **采集排在 T0，UI 排在 T4**：日志是「从现在开始攒」的数据，
  采集晚一步，后台上线那天就没有历史可看。
- 三条硬约束：绝不阻塞主流程（异步批量 + 队列上限 + 失败降级丢弃）；
  必须 `require_admin`；`log_db_min_level` 默认 INFO（DEBUG 不默认入 DB）。

### Consequences

**变容易**

- 后台能做级别 / 时间 / logger / event / `request_id` / 关键词的组合检索与分页。
- `request_id` 反查成为可能——用户回执上那个号粘进后台即可拉出该请求全部日志，
  把 R1 就贯通的追踪链补上最后一环。
- 文件与 DB 互为兜底：DB 出问题仍有文件，反之亦然。

**变难 / 代价**

- 多一份存储与保留策略要维护；日志写放大需要靠批量与级别下限控制。
- 日志可能含用户名、方案 id，属高权限数据，访问面必须收紧到管理员。

## ADR-041：系统配置「DB 覆盖 env，但只有白名单项可运行时改」

### Status

Accepted（2026-10-21）

### Context

当前所有可调项都由 `.env` 经 `get_settings()` 读成**进程内 `@lru_cache` 单例**，
进程启动后不变。要做到「管理员在后台改参数并生效」，必须有运行时可变的配置源。

三个选项：

1. 只改 `.env` + 重启：运维负担重，且不符合「后台可调」的诉求；
2. **全部搬进 DB**：看似统一，但 `db_path` / `host` / `port` / `auth_enabled` /
   `cors_origins` 这类**启动项**一旦进 DB，就会出现「改了却不生效」或「改了要不要重启」
   的认知混乱，甚至改坏之后服务起不来；
3. **DB 覆盖 env，但只有白名单项可进 DB**。

### Decision

取 **方案 3**。

- `system_config` 表 + `core/runtime_config.py`；解析顺序 **DB > env > 字段默认值**。
- **白名单**：配额、模型与调用参数、安全与会话、**日志参数**、维护模式。
- **永不进 DB**（启动项）：`db_path`、`host`、`port`、`auth_enabled`、`cors_origins`、
  供应商密钥、邀请码种子、`init_admin_*`、`skills_strict`。
- 进程内 **30 秒 TTL** 缓存；管理员写入时**立即失效**并记审计（多进程靠 TTL 兜底，
  不引入消息广播）。
- 写入在 `runtime_config` 集中校验，约束与 `config.py` 的 `Field(ge=, le=)` 同源；
  非法值 400，不静默截断。

### Consequences

**变容易**

- 绝大多数目标参数（`llm_timeout` / `llm_max_retries` / `prd_pipeline_concurrency` /
  `default_llm_provider` …）在 `config.py` 里**已经存在**，把它们从「只读 env」改成
  「优先读 runtime_config」即可，UI 是纯增量——这是整个 v4 性价比最高的一块。
- 配置变更有审计（before / after），可追溯。

**变难 / 代价**

- 让 `llm_factory` / `job_service` 等改读 runtime_config 会**碰到生成主链路**。
  缓解：只改白名单项的读取点，且每改一处配一条「默认行为零变化」的回归用例。
- 白名单本身需要维护：新增可调项时要显式登记，忘了就还是只能改 env。

## ADR-042：模型供应商只存「环境变量名引用」，明文密钥不落库

### Status

Accepted（2026-10-21）

### Context

v4 要建 `model_providers` 表并支持后台切换供应商。随之而来的问题是密钥放哪：

1. **明文落库**，由管理员在后台录入；
2. **库里只存环境变量名引用**（如 `ARK_API_KEY`），密钥仍由 `require_api_key()` 从环境取。

现有 `Settings.require_api_key()` 与 `API_KEY_ENV_VARS` 已经把「哪个供应商看哪个变量」
收敛在一处，密钥生命周期完全在环境里。

### Decision

取 **方案 2**。

- `model_providers` 表存 `api_key_env_var`（**变量名字符串**），不存密钥本身。
- 管理员可改：展示名、`provider_type`、`base_url`、`default_model`、`priority`、激活与否。
- 管理员**不可**在后台录入明文密钥；新增供应商仍需配置对应环境变量。
- 激活真源是 `system_config.active_provider_id`，**不靠表里加 `is_active` 列**——
  后者会出现「两行都是 1」的不一致态，前者天然只有一个值。
- `llm_factory` 改读「激活供应商行」（经 runtime_config 缓存），切换后立即失效缓存。

### Consequences

**变容易**

- 把明文凭据的泄漏面挡在数据库之外：库被读走也不会连带泄露 API 密钥。
- 与既有 `API_KEY_ENV_VARS` / `require_api_key()` 单一真源保持一致，不新增第二套密钥来源。

**变难 / 代价**

- 新增或轮换供应商仍需碰 `.env` 并重启（密钥层面），后台只能切「用哪一个」。
- 真要做密钥托管，需先解决加密存储与轮换流程——本期明确不做（见 `ARCHITECTURE.md` 1.3）。

## ADR-043：管理员身份的授予/撤销只留**一条**规则，且「撤销自己」不算违规

### Status

Accepted（2026-10-21）

### Context

T1 实现到「后台能不能授予/撤销管理员」时，冒出两个问题：

1. **规则写在哪？** `auth_service.set_admin` 里已有一条「不能撤销最后一位管理员」，
   而运维脚本 `auth_cli.py demote` 走的就是它。后台若另写一份校验，两条路迟早
   有一处漏改——后台就会成为绕过不变式的后门。
2. **「不能撤销自己」算不算一条独立规则？**

第 2 个问题的初稿答案是「算」，理由是「撤销自己 = 当场把自己踢出后台」。实现时
发现这个理由站不住：

- 管理员交接、临时让渡权限是**真实场景**。只要系统里还有别的管理员，
  撤销自己就是一次正常的「卸任」，而且**可逆**——另一位管理员随时能重新任命。
- 更关键的是：它和「不能撤销最后一位管理员」在 HTTP 路径上**必然重合**。
  只要操作者是管理员，「最后一位」就只可能是他自己。于是两条规则会互相遮蔽，
  报错信息也会打架（到底是「不能撤销自己」还是「最后一位管理员」）。

### Decision

1. **规则只有一条**，由 `auth_service.set_admin` 独家实现：
   不能撤销最后一位管理员。后台（`admin_service.set_admin`）只做委派，
   CLI 与后台共用同一份实现。
2. **「撤销自己」不被单独拦**。只要还有别的管理员，撤销自己是允许的；
   真正被拦的只有一种——撤销之后系统里一个管理员都不剩。
3. 相应地，**删号 / 停用自己**仍然单独拦（403）。这两件事性质不同：
   删号和停用会毁掉或冻结自己的账号，撤销管理员只是换了个角色。
4. 后台那侧的状态码用 `FORBIDDEN`（403）而不是 `AUTH_FAILED`（401）：
   401 在前端意味着「该去登录了」，而这里登录也没用。

### Consequences

**变容易**

- 后台与 CLI 的行为**逐条一致**，不存在「命令行能绕、后台不能」或反之。
- 管理员交接不用绕到命令行。
- 错误信息只有一种说法（「这是最后一位管理员，不能撤销」），管理员一眼知道该做什么。

**变难 / 代价**

- 管理员可以在后台里把自己降级，从而立刻失去后台访问权。这是**有意为之**：
  它是显式动作（点了「撤销管理员」），且可逆。刻意不做「禁止自降级」的保护，
  是因为那会挡住真实的交接场景。

**验证**

- 后端用例钉住两条：撤销最后一位 → 403；**有第二位时撤销自己 → 200**。
- 端到端冒烟走真实 HTTP：授予 → 撤销第一位（有第二位，200）→ 撤销最后一位（403）。

## ADR-044：运行时配置用「DB 只存覆盖项」+「一次生成冻结一份快照」

### 背景

v4 之前全部配置都在 `.env`：改一个值要改文件、重启服务。后台因此无法调参数，
「换模型供应商」更是要改代码里的 `Literal` 与分支。

难点不在「读出来的值能变」，而在两件事：

1. 配置的读取点有**三种形态**：每次调用读（`llm_factory`）、模块级快照（`main.py`）、
   **实例级快照**（`PrdSectionWriter.__init__` 拷了 5 个值、三处 LLM 实例缓存）。
   只清 `lru_cache` 覆盖不到后两种——表现是「改了配置，接口返回新值、生成还用旧值」。
2. 反过来，如果每个读取点都即时读，一次 20 分钟的生成跑到一半就会**参数漂移**。

### 决定

**一、`system_config` 只存覆盖项。** 没有某一行 = 用 env 或代码默认值。
所以「升级后行为零变化」是**结构保证**，而不是靠人记得别写默认值；
「恢复默认」就是删掉那一行。白名单是**硬编码常量**（不入表）：能通过配置扩展的
白名单等于没有白名单，而它是安全边界（`db_path` 一旦可改，配置层就与 `connect()`
形成递归）。

**二、一次生成冻结一份快照。** `dispatch` 取快照存进 `JobRuntime`，
`run_job` 用 `use_config` 挂到 ContextVar——与 `use_meter` 是同一套机制，学一次用两处。
直连 SSE 的路由（`/api/conversation/*-stream`）在 `make_sse_generator` 里统一冻结，
因为**事件流是在响应返回之后才被消费的**，放在路由函数体里的 `with` 早就退出了。

**三、构造期快照全部拆除。** `PrdSectionWriter` 的 5 个属性改成只读属性（12 处
使用点一行不用改），三处 LLM 缓存改按**同一个配置指纹**重建（`config_fingerprint()`）。
指纹集中在一处，否则会出现「撰写实例换了、审核实例还是旧的」——同一次生成里两个
实例参数不一致，正文与批注的口径就对不上。

**四、供应商按协议建模，不按厂商。** `protocol` 六值（`openai_compatible` /
`anthropic` / `ark` / `google_genai` / `nvidia` / `huggingface`）。已查证
`langchain-deepseek` 等包都是 `BaseChatOpenAI` 的薄封装（只把 `base_url` 写死），
所以接一家新厂商只需填 `base_url`，**不改代码、不加依赖**。

**五、所有适配器收敛进 `llm_factory.py`**（`ark_llm.py` 并入后删除）。
分层守卫的白名单从两个文件缩成一个，规则变成一句话：只有工厂能碰供应商 SDK。

**六、密钥只存变量名**（ADR-042 不变）。新增 `core/secrets.py` 按键名查找——
因为 `pydantic-settings` 读 `.env` 但**不写 `os.environ`**，运行时新增的供应商
按键名去 `os.environ` 找会永远为空，界面一直提示「未配置」。

### Consequences

**变容易**

- 后台改完即生效，不用重启；多 worker 靠 5 秒 TTL 收敛。
- 加一家 OpenAI 兼容的厂商是**数据操作**，不是代码改动。
- 排障时页面直接显示「改前 / 改后 / 是否真的生效」。

**变难 / 代价**

- 多了一层抽象：读配置要经 `get_runtime_config().settings`，而不是 `get_settings()`。
  好处是取值写法完全不变（`Settings` 的派生属性原样可用）。
- `llm_factory.py` 从 148 行长到约 550 行，同时装着工厂与一个 `BaseChatModel` 子类。
- 三个新协议依赖偏重（`protobuf` / `tokenizers`），装完必须跑全量确认没带崩别的包。

**验证**

- `test_runtime_config.py`（22 条）：默认行为零变化、白名单、降级不抛、不递归。
- `test_config_effect.py`（9 条）：死配置修复、指纹重建、快照拆除、任务冻结。
- `test_admin_config_api.py`（30 条）：门禁逐条、密钥不外泄、规则只在服务层。
- 端到端：改并发度 → 保存 → `revision` 变化 → 复读为 `source=db`。

## ADR-045：每日额度按「次数 / Token / 并发」三维度，且失败不吃额度

### 背景

邀请码只管「谁能进来」，不管「进来后用多少」。v4 之前一个账号能无限次生成，
而管理员在事前没有任何拦截手段——T2 的统计是**事后的账单**，它告诉你花了多少，
阻止不了继续花。T3 让「换哪家模型」变成数据操作之后，这件事更要紧：
切到便宜的模型省下的钱，一次滥用就还回去了。

### 决定

**一、三个维度，不是一个额度。**

| 维度 | 防的是什么 |
|---|---|
| 每人每日**次数** | 公平：一个人占满队列会拖慢所有人 |
| 每人每日 **Token** | 成本：真正烧钱的是 token，不是请求数 |
| 每人同时**运行数** | 队列：与钱无关，防的是并发挤占 |

只做「次数」的话，一天跑 3 次、每次 100k token 的人比跑 30 次短任务的人烧得多；
只做 Token 的话，连发 20 个请求能瞬间打满队列。

**二、上限用三态（`-1` / `0` / `N`），不是单个数字。**

- `-1` 跟随全局（`system_config` 的 `quota_*`，热生效）
- `0` 不限
- `N` 具体上限

少了 `-1`，「恢复成跟大家一样」做不到（只能一个个填当前全局值，之后全局改了
他还停在旧值）；少了 `0`，「给可信账号开口子」做不到。**两种意图必须能区分**，
所以前端编辑框回填的是三态值，而不是生效数字。

**三、三条统计口径，彼此刻意不同。**

- **次数只算「已收尾 + 在飞」**（`completed` / `running`）。失败、被取消
  （`CANCELLED`）、被新任务接管（`SUPERSEDED`）都**不吃额度**——一次上游故障
  就把所有人当天机会清零，用户完全无从申诉，他没做错任何事。
- **Token 算全部状态**的实际消耗。跑了就跑掉了，失败的任务同样花钱。
- **并发只数 `running`，且不受日界限制**。长文档生成会跨日；若并发检查也跟着
  日界过滤，「昨天那批 + 今天这批」就能同时开。

**四、「每天」由服务端定时区**（`quota_timezone_offset_minutes`，默认东八区）。
绝不接受前端传值：那等于让用户改一下浏览器时区就把日界挪走。这与 T2 统计的
「时区由前端传」是**相反的**决定，因为两者的可信模型不同——统计是给管理员看的
便利功能，额度是安全边界。

**五、拦截在建任务之前，`kind=chat` 豁免。**

检查放在 `job_service.create_job` 之前。放在之后的话，被拒的请求会先留下一行
`failed`，污染 T2 的失败率、也会出现在用户的任务列表里（「我什么都没生成，
却多了一条失败记录」）。对话豁免是因为它是生成的**前置**（澄清、改需求），
限了之后用户连「为什么被拒」都问不了。

**六、不新增错误码。** `ErrorCode` 是对外契约（前端 `BACKEND_ERROR_CODES`
与之逐字对应），配额超限复用 `INVALID_REQUEST` + `status_code=429`。
前端本来就把字符串 `detail` 原样显示（`describeJobError` 优先返回它），
不需要靠码分支。

### Consequences

**变容易**

- 管理员能事前设限，不必等月底看账单才发现。
- 用户列表直接显示「今日已用/上限」，超限的行标红——「谁被卡住了」一眼可见。
- `quota_enforce=false` 可以先观察真实分布再收紧，不必一上线就拒绝用户。

**变难 / 代价**

- 聚合直接查 `generation_jobs`，没有独立计数器。好处是单一份真源（多 worker
  不会各记各的），代价是每次创建任务多两条 SELECT——量级上可忽略。
- 检查与建任务之间在多 worker 下有极小竞态窗口（两个请求都读到「还没满」），
  可能超额 1–2 个任务。为这点误差引入跨进程锁不划算：防的是「一个人开一百个」，
  不是精确到个位。
- 在飞任务的 token 尚未落库，所以 Token 额度**拦不住同时开多个大任务**——
  它必须与并发上限配合使用。这一点写在配置项的 `description` 里。
