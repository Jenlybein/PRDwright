## 版本 ↔ 任务对照

同一套工作的两种视图：**任务编号用于日常排期，版本号用于对外收口。**

| 版本阶段 | 任务阶段 | 目标 |
| --- | --- | --- |
| v4.0 | T0 | **地基**：管理员身份（`is_admin` + `require_admin`）、审计表、CORS 放开、`frontend_admin` 脚手架与登录守卫、**日志采集先行落地** |
| v4.1 | T1 | 用户管理 + 邀请码管理 |
| v4.2 | T2 | 平台统计（PRD 总量 / 用户用量 / 趋势） |
| v4.3 | T3 | 系统配置（运行时配置层 + 模型供应商表与切换） |

## 已拍板的四件事

| # | 当时的选项 | 决定 | 记录 |
| --- | --- | --- | --- |
| 1 | 管理员后台形态：① 嵌入 `frontend` 加 `/admin` 路由；② 根目录单开 `frontend_admin` 独立应用；③ pnpm monorepo 拆 `userpage` / `adminpage` | **取 ②**（独立应用）。理由：要独立构建与部署边界；③ 的双份工程运维税对当前规模不划算，① 的「隐藏路径」不构成真实安全收益 | ADR-039 |
| 2 | 日志存哪：① 纯轮转文件；② 纯 SQLite 表；③ 文件 + DB 混合；④ 交给外部采集（ELK/Docker logs） | **取 ③（混合，采集先行）**。文件保证「永不丢、可脱机排查」，DB 保证「后台能检索过滤分页」；④ 与「开箱即用」相悖 | ADR-040 |
| 3 | 系统配置怎么生效：① 只改 `.env` + 重启；② 全部搬进 DB；③ DB 覆盖 env，但**只有白名单项**可运行时改 | **取 ③**。`db_path`/`host`/`auth_enabled` 这类启动项绝不进 DB，否则会出现「改了却不生效／改了要重启」两类认知混乱 | ADR-041 |
| 4 | 供应商密钥怎么存：① 明文落库由管理员录入；② 库里只存**环境变量名引用** | **取 ②**。明文密钥落库等于把凭据泄漏面开在管理端；本期不做法密钥托管 | ADR-042 |

论证过程见 `ARCHITECTURE.md` 第 3 / 4 / 5 / 8 节与 `ADR.md`；这些已不再是待决项，
实施状态以 `roadmap.md` 为准。

## 与 v3 的关系

v4 **不改** v3 已定型的生成链路与文档所有权（ADR-021 ~ 038 继续有效）。它对前端用户端
（`frontend/`）几乎是零侵入——只多两处：后端 `cors_origins` 放行管理员源、`users` 表多一列。
**管理员后台不得反向依赖用户端的业务组件与状态**（两者是独立应用，见 ADR-039）。
