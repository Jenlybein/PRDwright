# v5 路线图：测试重构

> 排期真源本文件；架构依据见 `ARCHITECTURE.md`；决策依据见 `ADR.md`。
> 任务编号用于日常排期，版本号用于对外收口（对照见 `README.md`）。

## 0. 排期总原则

1. **诊断先行**：T00 不产出一行业务代码，但它决定 T02 及之后的形态。
   区分「测试缺陷」与「产品缺陷」只要 6 条命令，所以必须先跑。
2. **分流先于修复**（T00 结论带来的新增原则）：18 条已有机制的可以直接改，
   16 条待定的必须先按「**先改测试 → 仍红再查源码**」分流，再决定改哪一边。
   顺序颠倒会先把测试改成匹配新行为，等于销毁回归保护。
3. **绿基线先于夹具重构**：T04 要动 `conftest.py` 这个最危险的文件。
   动它之前必须有一个已知绿基线，动它之后才能对拍出「有没有少跑用例」。
   在红套件上做夹具重构，等于失去了唯一的裁判。
4. **提速的验收是对拍，不是耗时**：收集数必须与 T03 基线一致（**当前 867**；
   T06/T07 加用例之前是 863），pass / fail 集合必须逐条一致。
5. **每条新用例都要反向验证**：临时破坏被测行为 → 观察转红 → 还原。
   这是本项目既有纪律（见 MEMORY：验证用例真能抓 bug = 临时删那行跑红再还原）。
6. **先止血、再提速、后补缺口**：倒过来做会让前面补的测试收益被稀释。

目标：判定那 33 个前端失败是「测试的错」还是「产品的错」。这是全部后续任务的前提。

```bash

npx vitest run src/__tests__/solution-switch-isolation.spec.ts
```

| # | 交付物 | 落点 | 验收要点 |
| --- | --- | --- | --- |
| 1 | 六个文件的隔离跑结果 | 无（只读，不落文件） | 逐条记下「单独跑的成败」与「在全量里的成败」 |
| 2 | 判定表 | 本路线图 | 明确标注每个文件的定性 |

验收标准（本任务的核心产出）：

> 产出判定表 —— 单独跑过 = 测试缺陷（顺序依赖）；单独跑也红 = 产品缺陷。

## T00 结论（已产出）

已完成。结论推翻了「顺序依赖」这个方向。

| 检查 | 结果 |
| --- | --- |
| 跨文件顺序依赖 | 排除。6 个文件单独跑 vs 全量跑，失败数逐项完全相同（15 / 8 / 5 / 2 / 2 / 1，合计 33） |
| AppV2 内部顺序依赖 | 只解释 1 个。15 个逐个 `-t` 单独跑：1 个转绿、14 个仍红 |

三点附带修正：

- `workflow-store` 的失败数是 5（初稿记为 2），六文件合计 33 与总数吻合。
- 「不是 Pinia 单例残留」这一排除结论成立（五个 store 文件都在 `beforeEach` 里
  做了 `setActivePinia(createPinia())`）。
- `turnHarness` 的泄漏机制属实、危害只有 1 个：`jobHarness` 专门写了 `reset()`
  方法（第 51–67 行）而 `turnHarness` 没有，说明作者清楚跨用例泄漏、只是漏了一个。

结论：32 / 33 个失败是隔离可复现的，不是测试基础设施问题。

> ⚠️ 但隔离可复现只排除了顺序依赖，仍区分不了「源码有 bug」与
> 「测试期望写错」。这两者修法相反，必须逐条看断言才能定性 —— 即 T02a。
>
> 这条结论的直接后果：T02 的形态变了，原「补一行、修 15 个」的设想被推翻。

## T04 · backend 提速（v5.1，已完成）

目标：362.7 秒 → ≤150 秒。不测量就不许动手。

### 实测（三个实验，全部只读）

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| A | `--durations=30` | 头部 **37.22 / 18.13 / 3.16 / 3.03** 秒；top30 ≈ 95.7 秒（28.5%），其余 833 条均 0.29 秒 —— **少数极慢 + 长尾轻**（原表读成「普遍慢」是把降序输出的 `tail` 当成头部，已更正）。其中约 55 秒是**真实等待**（`llm_retry_delay` 1.5s × 重试），并行压不掉 |
| B | `init_schema` × 20 外推 | 26.7 ms/次 → ×867 = **23.1 秒（占 8%）**；模板复制 0.5 ms，只省 22.7 秒 |
| C | 逐项拆 lifespan | `client` 夹具净增 **147 ms/用例**：`init_schema` 跑了**两次**（51.6）、`run_migrations` 25.2、`reset_logging` 关线程 50.6、其余 13.7 |

### 结论：ADR-066 的假设被推翻，未改 `conftest.py`

建库+迁移合计只占 8%，就算全换成模板复制也只到 ~230 秒，够不到 150 秒。
按 ADR-066 自己定的判据，此时**不许动 conftest**，改用 A 的结果找真热点。

真热点是「每个用例起停一整套应用」：867 次 × ~147 ms。这不是夹具写法问题，
是**用例数量 × 单例启动成本**的结构问题，靠微调夹具救不回来。

### 解法：默认按 CPU 核数并行（ADR-071）

| # | 交付物 | 落点 | 状态 |
| --- | --- | --- | --- |
| 1 | 引入 `pytest-xdist` | `backend/pyproject.toml` 的 dev 组 | 已完成 |
| 2 | 默认 `addopts = "-n auto"` | 同上 | 已完成 |
| 3 | 单文件调试保留 `-n0` 逃生口 | 同上（写进注释） | 已完成 |

### 验收（四项，全部达成）

| 项 | 要求 | 实测 |
| --- | --- | --- |
| 1 | 实验 A / B / C 的数据已记录，且**基线数字来自同一次干净采集** | 见上表。362.7s 与 335.7s 是两个批次，不可混用 |
| 2 | 收集数仍为 **867**（T04 当时） | 867（两轮均一致）。**最终基线以 T15.6 的实测为准** —— 见下方账目 |
| 3 | pass / fail 集合与基线逐条一致 | **集合差异 0、结果差异 0**（junit 逐条对拍 867=867） |
| 4 | 全量 ≤150 秒 | **71~89 秒区间**：71.19s（工程师）/ 88.85s（team-lead 复测）/ 72.48s（T04 时）。三个数**都是真实测量**，差异来自**并行度与机器负载**（含双跑者效应，见规程第 0 条）。**验收线只有一条：≤150 秒**，不钉单一数值 |

**收集数账目**（让读者能自己验算，不用信结论）：

```
867 = 3063ff7 基线（该 HEAD 上全绿）
871 = 867 + 4   ← T15.1 首版守卫
875 = 867 + 8   ← T15.1 / T15.2 终版：test_database_pool.py 全部 8 条
```

两条自查命令：

```bash
grep -c "^def test_" backend/tests/test_database_pool.py   # → 8（该文件是 T15 新建，全部为净增）
uv run pytest --collect-only -q | tail -1                  # → 875 tests collected
```

> 867 → 871 → 875 是**加守卫用例**导致的正常增长，**不是回归**。
>
> 这条账按「整个文件的条数」记、而不是按「4 条规格守卫 + 2 条 P0 + 2 条 dispose/懒建」分类记，
> 是因为后者要求读者相信我们对每个用例的归类，而前者只要求他数一个文件。
> **能被独立验证的账目才有意义。**

> 第 2、3 项是硬门槛：「快了但少跑了用例」只看耗时完全看不出来。
> 并行最容易出的问题正是「总数对得上、实际少跑或串味」，所以做了逐条 junit 对拍，
> 而不是只看 `867 passed`。

### 对拍操作规程（T04b 及后续任何提速改动都适用）

「收集数 + 逐条对拍」这条门槛，只有在**受控条件**下才成立。下面六条是按踩过的坑定出来的：

| # | 规程 | 为什么 |
| --- | --- | --- |
| **0** | **对拍期间机器上只能有一个测试进程** | 已确认过一次误判：QA 与工程师同时跑全量，单条用例从 0.5s 涨到 3s+，`LogStoreHandler.close()` 的 `join(timeout=5.0)` 超时，线程存活后把 tail 批次写进下一个用例的库，于是 `test_admin_logs` 偶发红。**「另一个人在跑测试」和对拍失败，看起来完全一样。** |
| 1 | **固定 HEAD + 工作区干净** | 收集数依赖工作区快照、不依赖代码。同一份 `HEAD`（`3063ff7`）不同时刻实测两个数：**867**（已提交基线）与 **871**（+ T15 未提交的 4 条 `test_database_pool.py`）。有未提交改动先 `git stash`，或先确认改动清单再对拍 |
| 2 | **基线当前已验证为确定性**：`b127c64` 修掉 T03 竞态、T07 把线程异常改成显式断言，`3063ff7` 上全量 **867 全绿**。**白名单当前为空，且不建** | 前提没了，条款就该收掉 —— 留着就是给未来的自己留后门 |
| 3 | 若基线**重新**出现非确定性失败 → **先定位并修掉**（如 T03 那样），不是登记。确需临时白名单时才走：固定 HEAD、单跑者，`-n auto` 3 次 + `-n 0` 2 次取差集；跑不够次数不建；不得新增，新增即视为回归 | 补丁式白名单会让将来的真红被掩盖 |
| 4 | **已知不稳定用例清单必须为空**；一旦出现，**先定位而不是登记** | ⚠️ 这条约束的是「不许用白名单掩盖问题」，**不是**「不许有 flaky」。真出现低频偶发，正解仍是定位并修掉 |
| 5 | 出现新的 `PytestUnhandledThreadExceptionWarning` → **立即立项查**；`3063ff7` 时已清零 | 它是「有线程在静默失败」的唯一信号，压掉就再也看不见 |

**数字出处**（避免把「不同状态下的测量」误读成「有人算错」）：

```
3063ff7 = 上一轮交付版        b127c64 = T03 修复版（3063ff7 的父提交）
867      = 上述两个 HEAD 的收集数 —— 完全相同（T03 只修竞态，未增删用例）
871      = 3063ff7 + T15 未提交改动（+4 条 test_database_pool.py）
```

> 表现为「pytest 无输出、不结束」，**与「用例挂死」完全一样** —— 但排查方向完全相反。
> **排查顺序：先看临时目录规模，再看代码。**
>
> 顺带一条：`pytest-timeout` 对此无效（它管不到钩子等待），而本层还有一条 37s 的真实等待
> 会被全局 timeout 误杀 —— 所以**暂不装**，待 T04b 落地后重评。

### 两条没做的事（各有理由）

| 没做 | 理由 |
| --- | --- |
| 模板库 + 文件复制（原方案甲） | 假设已被实验 B 推翻。真做了只省 22.7 秒，却要给 conftest 加 session 级夹具，是拿「唯一的隔离地基」换 8% |

## T04b · 测试里的重试退避归零（v5.1，回收 55 秒长尾）

**目标**：把那两条「真实等待」用例的长尾拿回来（初估 55 秒，**实测省 59.49 秒**）。
它们不是装置开销，是 `services/stream_reply.py:256-257` 的
`await asyncio.sleep(settings.llm_retry_delay)`（默认 1.5 秒 × 约 24 次退避）。

| # | 交付物 | 落点 | 验收 |
| --- | --- | --- | --- |
| 1 | 测试里把 `LLM_RETRY_DELAY` 归零 | `backend/tests/conftest.py`（`isolated_db` 内一行 `monkeypatch.setenv`） | `test_llm_retry_is_logged` **37.12s → 0.64s**（实测）；`test_all_sections_failed_emits_error_without_done` 18.14s → 同量级下降；两文件 13 条合计 **76.37s → 16.88s（省 59.49s）** |
| 2 | （可选，若第 1 项不足）重试退避改为可注入时钟 | `services/stream_reply.py` | 新增用例可把退避设为 0 而不改产品默认值 |

> ⚠️ **第 1 项会让 `stats["rolled_back"]` 的语义更敏感**：池化后每个用例都会借还连接，
> 若有生产代码路径漏 `commit`，T15 的 teardown 断言会先炸。
> **改完 T04b 要重跑一次全量，确认 `in_use == 0` 与 `idle == size` 仍然成立。**

**验收**：收集数不变；pass/fail 集合不变；两条用例耗时下降可复现（跑 3 次取中位数）。

#### ⚠️ 动手前必读：`llm_retry_delay` 是热配置，env 只是兜底

```python
stream_reply.py:207   settings = get_runtime_config().settings   # ← 热配置，不是 get_settings()
stream_reply.py:256   if settings.llm_retry_delay > 0: await asyncio.sleep(settings.llm_retry_delay)
runtime_config.py:85  "llm_retry_delay"                          # ← 在热配置白名单里
config.py:155         default=1.5, ge=0
```

四条必须在写代码时一起交代：

1. `llm_retry_delay` 是**热配置**：`env` 只是兜底，`system_config` 的 DB 覆盖优先级更高。
   **注意 `stream_reply` 读的是 `get_runtime_config().settings`，不是 `get_settings()`** ——
   所以「改了 env 为什么不生效」的答案永远在这里。
2. 本行之所以有效：每个用例的 DB 都是全新 `tmp_path`，**没有任何覆盖行**。
3. **必须把这层写成代码注释**。否则将来出现「conftest 明明设了 0 还是慢」，
   排查方向会被 conftest 带偏，而真正的原因是某个用例在 `system_config` 里写了覆盖。
4. `ge=0` 说明 **0 是合法值**，不会被 clamp —— 顺手挡掉「设 0 会不会被当非法值忽略」这个疑问。

**⚠️ 第 1 项暂缓动手**：`backend/tests/conftest.py` 正被 T15 改（池接入、teardown 断言），
等 T15.1 / T15.2 落地后再做 —— 避免两人同改一个文件。
**接手时别改掉 T15 已有两处**：`database.reset_database()` 的调用、以及 teardown 那条
`in_use == 0` 断言。这两处是 T15 的验收地基，误删后池的泄漏会静默通过。

**明确不做**：不改 `llm_retry_delay` 的产品默认值（1.5 秒是生产行为，只改测试注入）。

> **为什么这条不能被当成「性能优化」删掉**：重试该不该发生与「等多久」无关；
> 测试等待 1.5 秒 × 24 次 = 37 秒纯属浪费，而这条等待**并行也压不掉**
> —— 单条用例不可分割，37 秒那条会把所在 worker 变成关键路径。
> 产品代码里本就有 `if settings.llm_retry_delay > 0` 的守卫，delay=0 时不进 sleep 分支，
> 行为完全等价：**这不是改行为，是去掉测试里一次无意义的等待。**
>
> 先例：`tests/test_llm_resilience.py:148` 早就这么做了，并且写明了理由
> （「重试该不该发生，与等待多久无关，测试不该为此变慢」）—— 本任务只是把它提升到全套件。

## T14 · 管理员端接口性能监测面板（v5.5，本期新增需求）

**目标**：在管理后台直观看到「哪个接口慢、错多少」，不必再去日志页一条条翻。

**数据来源：复用，不新增采集。**
`api/deps.py:202` 的访问日志已经写入了 `method` / `path` / `status` / `duration_ms`，
落在 `app_logs.extra_json`。SQLite 的 JSON1 已确认可用（`json_extract` 实测通过），
所以聚合是纯查询，**不新增表、不新增一次写放大**。

⚠️ **两处必须诚实标注，否则面板会骗人：**

1. **`duration_ms` 是「收到请求 → 开始回响应」的耗时。** 对普通请求约等于总耗时；
   但对 SSE 它只是**建流**的耗时 —— 一次 PRD 生成用了 3 分钟，这里可能只显示 40 毫秒。
   生成耗时在 `run_summary`（`services/stream_reply.py`），不在这里。
   面板上必须写清这一点，否则会被读成「生成很快」。
2. **数据窗口 = 日志保留期**（`log_retention_days` 默认 7 天、`log_max_rows` 默认 5 万），
   且 `log_db_enabled=false` 时面板**没有数据**。面板要显示实际覆盖的时间区间与开关状态，
   不能拿一个空图表让人以为是「没有慢请求」。

| # | 交付物 | 落点 | 验收要点 |
| --- | --- | --- | --- |
| 1 | 聚合接口 | `GET /api/admin/metrics/endpoints` | 按 `path` + `method` 分组：请求数、**5xx / 4xx 错误率分开算（只 5xx 染色）**、p50 / p95 / p99 / max、实际覆盖区间 |
| 2 | 慢接口排行 | 同上 | 按 p95 降序，Top N；**只收 `n ≥ 20` 的接口**（否则只调过 2 次的冷门接口霸榜） |
| 3 | 数据窗口与空态口径 | 同上 | 输出覆盖区间 / 总行数 / 是否被保留策略截断 / 落库开关 / 丢弃下界；前端按五种空态分派 |

**分位数怎么算**：SQLite 没有 `percentile_cont`。用窗口函数
（`ROW_NUMBER()` + `COUNT()` 取第 ⌈n·0.95⌉ 行）比 `NTILE(100)` 更准，
且能正确处理 n 很小的情况。

**刻意不做**：不做实时推送（手动刷新 + 切时间窗足够）；
不存历史指标快照（那会变成第二套日志系统）；
不做时间趋势分桶（`/api/admin/stats/daily` 已有，避免两个入口看同一件事）；

流式接口不与普通接口同列排行（否则 40 毫秒的建流耗时会被读成生成耗时）。

> **详细设计见 `T14-performance-panel.md`** —— 口径速查表（10 条逐项核）、接口契约与 JSON 示例、
> 分位数 SQL 与三档小样本门槛、索引三级阶梯、页面五块与五种空态、T14.1–T14.6 任务表。
