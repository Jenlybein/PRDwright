# v5 路线图：测试重构

> 排期真源本文件；架构依据见 `ARCHITECTURE.md`；决策依据见 `ADR.md`。
> 任务编号用于日常排期，版本号用于对外收口（对照见 `README.md`）。

## 0. 排期总原则

1. **诊断先行**：T00 不产出一行业务代码，但它决定 T02 及之后的形态。
   区分「测试缺陷」与「产品缺陷」只要 6 条命令，所以必须先跑。
2. **分流先于修复**（T00 结论带来的新增原则）：18 条已有机制的可以直接改，
   16 条待定的必须先按「**先改测试 → 仍红再查源码**」分流，再决定改哪一边。
   顺序颠倒会先把测试改成匹配新行为，等于销毁回归保护。
3. **绿基线先于夹具重构**：T04 要动 `conftest.py` 这个最危险的文件。
   动它之前必须有一个已知绿基线，动它之后才能对拍出「有没有少跑用例」。
   在红套件上做夹具重构，等于失去了唯一的裁判。
4. **提速的验收是对拍，不是耗时**：收集数必须与 T03 基线一致（**当前 867**；
   T06/T07 加用例之前是 863），pass / fail 集合必须逐条一致。
5. **每条新用例都要反向验证**：临时破坏被测行为 → 观察转红 → 还原。
   这是本项目既有纪律（见 MEMORY：验证用例真能抓 bug = 临时删那行跑红再还原）。
6. **先止血、再提速、后补缺口**：倒过来做会让前面补的测试收益被稀释。

## T00 · 失败归因诊断（v5.0）

目标：判定那 33 个前端失败是「测试的错」还是「产品的错」。这是全部后续任务的前提。

```bash

npx vitest run src/__tests__/AppV2.spec.ts
npx vitest run src/__tests__/solutions-store.spec.ts
npx vitest run src/__tests__/workflow-store.spec.ts
npx vitest run src/__tests__/solution-switch-isolation.spec.ts
npx vitest run src/__tests__/orphan-solution.spec.ts
npx vitest run src/__tests__/runs-store.spec.ts
```

| # | 交付物 | 落点 | 验收要点 |
| --- | --- | --- | --- |
| 1 | 六个文件的隔离跑结果 | 无（只读，不落文件） | 逐条记下「单独跑的成败」与「在全量里的成败」 |
| 2 | 判定表 | 本路线图 | 明确标注每个文件的定性 |

验收标准（本任务的核心产出）：

> 产出判定表 —— 单独跑过 = 测试缺陷（顺序依赖）；单独跑也红 = 产品缺陷。

## T00 结论（已产出）

已完成。结论推翻了「顺序依赖」这个方向。

| 检查 | 结果 |
| --- | --- |
| 跨文件顺序依赖 | 排除。6 个文件单独跑 vs 全量跑，失败数逐项完全相同（15 / 8 / 5 / 2 / 2 / 1，合计 33） |
| AppV2 内部顺序依赖 | 只解释 1 个。15 个逐个 `-t` 单独跑：1 个转绿、14 个仍红 |

三点附带修正：

- `workflow-store` 的失败数是 5（初稿记为 2），六文件合计 33 与总数吻合。
- 「不是 Pinia 单例残留」这一排除结论成立（五个 store 文件都在 `beforeEach` 里
  做了 `setActivePinia(createPinia())`）。
- `turnHarness` 的泄漏机制属实、危害只有 1 个：`jobHarness` 专门写了 `reset()`
  方法（第 51–67 行）而 `turnHarness` 没有，说明作者清楚跨用例泄漏、只是漏了一个。

结论：32 / 33 个失败是隔离可复现的，不是测试基础设施问题。

> ⚠️ 但隔离可复现只排除了顺序依赖，仍区分不了「源码有 bug」与
> 「测试期望写错」。这两者修法相反，必须逐条看断言才能定性 —— 即 T02a。
>
> 这条结论的直接后果：T02 的形态变了，原「补一行、修 15 个」的设想被推翻。

## T04 · backend 提速（v5.1，已完成）

目标：362.7 秒 → ≤150 秒。不测量就不许动手。

### 实测（三个实验，全部只读）

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| A | `--durations=30` | 最慢 1.84 秒、第 30 名 0.69 秒 —— **普遍慢，不是少数慢** |
| B | `init_schema` × 20 外推 | 26.7 ms/次 → ×867 = **23.1 秒（占 8%）**；模板复制 0.5 ms，只省 22.7 秒 |
| C | 逐项拆 lifespan | `client` 夹具净增 **147 ms/用例**：`init_schema` 跑了**两次**（51.6）、`run_migrations` 25.2、`reset_logging` 关线程 50.6、其余 13.7 |

### 结论：ADR-066 的假设被推翻，未改 `conftest.py`

建库+迁移合计只占 8%，就算全换成模板复制也只到 ~230 秒，够不到 150 秒。
按 ADR-066 自己定的判据，此时**不许动 conftest**，改用 A 的结果找真热点。

真热点是「每个用例起停一整套应用」：867 次 × ~147 ms。这不是夹具写法问题，
是**用例数量 × 单例启动成本**的结构问题，靠微调夹具救不回来。

### 解法：默认按 CPU 核数并行（ADR-071）

| # | 交付物 | 落点 | 状态 |
| --- | --- | --- | --- |
| 1 | 引入 `pytest-xdist` | `backend/pyproject.toml` 的 dev 组 | 已完成 |
| 2 | 默认 `addopts = "-n auto"` | 同上 | 已完成 |
| 3 | 单文件调试保留 `-n0` 逃生口 | 同上（写进注释） | 已完成 |

### 验收（四项，全部达成）

| 项 | 要求 | 实测 |
| --- | --- | --- |
| 1 | 实验 A/B/C 的数据已记录 | 见上表 |
| 2 | 收集数仍为 **867** | 867（两轮均一致） |
| 3 | pass / fail 集合与基线逐条一致 | **集合差异 0、结果差异 0**（junit 逐条对拍 867=867） |
| 4 | 全量 ≤150 秒 | **71.9 / 72.6 秒**（两轮；16 核，墙钟 75 秒） |

> 第 2、3 项是硬门槛：「快了但少跑了用例」只看耗时完全看不出来。
> 并行最容易出的问题正是「总数对得上、实际少跑或串味」，所以做了逐条 junit 对拍，
> 而不是只看 `867 passed`。

### 两条没做的事（各有理由）

| 没做 | 理由 |
| --- | --- |
| 模板库 + 文件复制（原方案甲） | 假设已被实验 B 推翻。真做了只省 22.7 秒，却要给 conftest 加 session 级夹具，是拿「唯一的隔离地基」换 8% |
| 把 `isolated_db` 降级为 session 级共用库 | ADR-066 已明确否决（方案乙）。并行化之后更没必要 |

风险：并行会让「顺序依赖」的用例更容易暴露（也更容易被掩盖成随机失败）。
缓解手段就是这次做的逐条对拍：集合与结果都要一模一样，不看总数。

## T07 · 死代码与不可靠用例清理（v5.2）

目标：让每一条断言都真的在跑、真的能失败。

| # | 交付物 | 落点 | 验收要点 |
| --- | --- | --- | --- |
| 1 | 删除被同名覆盖的死代码（**不是"删用例"**） | `backend/tests/test_login_lockout.py`（246–299 与 302–355 逐字节重复） | **收集数不变（仍 863）**；该文件 def 数 18→15 后与收集数相等，守卫 G1 由红转绿 |
| 2 | 抽公共辅助 | `test_admin_config_api.py:112` 与 `test_admin_stats.py:369`（`_require_login` 参数化体相同） | 两处共用一份 |
| 3 | 去重跨文件同名用例 | `test_admin_management.py:48` 与 `test_config_tables.py:66`（`test_migrations_reach_latest_version`）；`test_clarify.py:336` 与 `test_generation_job.py:788`（`test_regenerating_prd_keeps_downstream`） | 各留一份 |

验收要点：**收集数必须仍为 863**，`--collect-only` 的 diff 为空。

> 这一条曾被写成「863 → 860，−3 是预期的」，**那是错的**，已按实测更正：
> 那两段是逐字节相同的重复源码，Python 模块命名空间里同名定义后者覆盖前者，
> 而 pytest 是从模块 `dir()` 收集的 —— 所以那 3 个名字**从来没有被收集两次**。
> 删掉前一段只是删掉不可达的源码。
>
> **收集数不变才是正确结果**；若删完变成 860，说明删掉了活用的用例，必须立刻回退。
>
> 这也正好是守卫 G1 的实证：改前该文件 **18 个 def / 15 个 collected**（G1 必红），
> 改后 **15 / 15**（G1 转绿）。G1 抓的就是「def 数 ≠ 收集数」这种死代码。

风险：清理的价值在**消除误导**（下一个人会以为改前一段有效果），不在于减少收集数。

## T14 · 管理员端接口性能监测面板（v5.5，本期新增需求）

**目标**：在管理后台直观看到「哪个接口慢、错多少」，不必再去日志页一条条翻。

**数据来源：复用，不新增采集。**
`api/deps.py:202` 的访问日志已经写入了 `method` / `path` / `status` / `duration_ms`，
落在 `app_logs.extra_json`。SQLite 的 JSON1 已确认可用（`json_extract` 实测通过），
所以聚合是纯查询，**不新增表、不新增一次写放大**。

⚠️ **两处必须诚实标注，否则面板会骗人：**

1. **`duration_ms` 是「收到请求 → 开始回响应」的耗时。** 对普通请求约等于总耗时；
   但对 SSE 它只是**建流**的耗时 —— 一次 PRD 生成用了 3 分钟，这里可能只显示 40 毫秒。
   生成耗时在 `run_summary`（`services/stream_reply.py`），不在这里。
   面板上必须写清这一点，否则会被读成「生成很快」。
2. **数据窗口 = 日志保留期**（`log_retention_days` 默认 7 天、`log_max_rows` 默认 5 万），
   且 `log_db_enabled=false` 时面板**没有数据**。面板要显示实际覆盖的时间区间与开关状态，
   不能拿一个空图表让人以为是「没有慢请求」。

| # | 交付物 | 落点 | 验收要点 |
| --- | --- | --- | --- |
| 1 | 聚合接口 | `GET /api/admin/metrics/endpoints` | 按 `path` + `method` 分组：请求数、**5xx / 4xx 错误率分开算（只 5xx 染色）**、p50 / p95 / p99 / max、实际覆盖区间 |
| 2 | 慢接口排行 | 同上 | 按 p95 降序，Top N；**只收 `n ≥ 20` 的接口**（否则只调过 2 次的冷门接口霸榜） |
| 3 | 数据窗口与空态口径 | 同上 | 输出覆盖区间 / 总行数 / 是否被保留策略截断 / 落库开关 / 丢弃下界；前端按五种空态分派 |
| 4 | 前端页 | `frontend_admin` 新增 `/performance` + 侧栏导航项 | 空数据态写明原因（是没开落库，还是这段时间真没请求） |

**分位数怎么算**：SQLite 没有 `percentile_cont`。用窗口函数
（`ROW_NUMBER()` + `COUNT()` 取第 ⌈n·0.95⌉ 行）比 `NTILE(100)` 更准，
且能正确处理 n 很小的情况。

**刻意不做**：不做实时推送（手动刷新 + 切时间窗足够）；
不存历史指标快照（那会变成第二套日志系统）；
不做时间趋势分桶（`/api/admin/stats/daily` 已有，避免两个入口看同一件事）；
不加索引（v21 不开 —— 理由不是读路径快慢，而是不能让唯一可牺牲的日志旁路承担常驻写成本）；
流式接口不与普通接口同列排行（否则 40 毫秒的建流耗时会被读成生成耗时）。

> **详细设计见 `T14-performance-panel.md`** —— 口径速查表（10 条逐项核）、接口契约与 JSON 示例、
> 分位数 SQL 与三档小样本门槛、索引三级阶梯、页面五块与五种空态、T14.1–T14.6 任务表。
