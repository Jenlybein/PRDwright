# PRDwright 现状架构

> **一句话**：本地优先的 PRD 生成平台；这份文档是仓库里唯一一版架构结论，正向写「目标 → 范围（含本期不做）→ 设计 → 契约 → 取舍」。
>
> 导航：[`README.md`](./README.md) 是**时间线真源**（阶段总表、v2 七波重写、已确认的失真、复核方法）；[`roadmap.md`](./roadmap.md) 是现状排期；[`../adr/0001-architecture-docs-consolidation.md`](../adr/0001-architecture-docs-consolidation.md) 是本次文档重组的**架构决策**，[`../adr/0002-review-conclusion-and-fix.md`](../adr/0002-review-conclusion-and-fix.md) 是「审核结论随版本保存 + 按结论修复 + 输入一律服务端取」的**架构决策**；术语以 [`../../GLOSSARY.md`](../../GLOSSARY.md) 为准。
>
> v1~v9 是九个历史**层**，其目录已删除；演进史的索引是本文 §6 的九层摘要表，阶段规模与界碑只在时间线真源里写一次。**「v10」不是架构层**，它指数据库迁移版本与一批已关闭的历史 issue 编号。

## 1. 目标

1. **一处可读**：维护者打开仓库，读这一份文档就能回答「现在怎么跑、边界在哪、为什么这么选」，不必判断「哪一层说的算」。
2. **结论可追溯**：契约有编号（C-V9-1~10、C-D1~C-D6）；承重的实测数据、方言可移植性台账与恢复演练要求整段留在本文附录，不靠 git 历史当唯一依据。
3. **收口可验证**：文档里写出的每个仓库路径 `ls` 都能看见；一次改动把代码、架构文档、路线图三者同步更新。
4. **产品能力不变**：三份文档、澄清、审核、改写、技能包内容、鉴权与配额、用户端交互都按现行形态运行。

### 2.2 本期不做

| 事项 | 为什么本期不做 |
| --- | --- |
| **再引入第二个数据库后端** | v9 已收缩为 Postgres 单后端（#78）：SQLite / MySQL 的方言分支、迁移链、测试基座与部署面都已删除。再加一个后端要连迁移基线、结构对拍、测试基座与备份链一起重做，收益不抵成本 |
| **k8s / Swarm、多副本、外置运行时表或跨进程事件总线** | 目标是单机 compose，滚动更新与探针权重还没有需要它的人；多副本要先外置 `_RUNTIMES` / `JobBus`，那是另一版的工作 |
| **全库真类型化**（时间从 ISO 文本改真时间、布尔改原生） | 自带 API 时间契约变更与两个前端的适配，改动面与收益不成比例 |
| **容器内 TLS、多架构镜像、开发者热重载容器** | 证书生命周期不放进取舍受限的单机 compose；开发仍走本机 `uv run uvicorn` 与两个 `npm run dev` |
| **业务链路自动化测试 / 老数据迁移** | 容器冒烟只验「主链路可达」；不提供旧 SQLite 库的自动迁移：地址指向 SQLite / 旧 `DB_PATH` / 旧库文件时，启动即拒绝并给出迁移指引 |
| **在途任务续跑或回放** | 运行态以内存为权威；重启仍中断在途任务，数据库投影只保证可读，不保证可继续执行 |
| **重开已关闭的双后端系列** | 那批 v10 issue 是历史记录，不是架构层 |
| **按层重写演进史** | 演进史只在 §6 留九行索引；阶段规模、界碑与失真由时间线真源独占，不在本文重复 |
| **改全局映射、后端或界面交互** | 入口模式登记表只收随入口模式变化的事实；14 个视图状态 → 进度格的全局映射、后端、数据库结构、界面文案与界面交互一律不动（见 §5.8） |
| **把审核结论做成可浏览的历史列表** | 结论随**文档版本**保存，本期只在审阅页显示当前版本那一条；历史浏览是另一件事，先把「存得住、修得动」做实 |
| **按正文变化判定结论过期** | 修复入口已经按「有问题」把关；多一个「已过期」状态与文案，换不来可用性 |
| **审核结论进交付包或管理端统计** | 交付物仍只是三份正文与回执；结论服务于审阅页与修复，不改变交付形态 |
| **审核通过后自动改写** | 审核只判不改；改写只在生成管线内按严重度触发，成稿之后的改写是「修复」这个显式动作 |
| **把「缺什么、该怎么定」并进审核** | 那是**未决**，归待确认清单；审核只报**缺陷**（写错了没有），两者分工见 §3.8 与 ADR 0003。合并会让同一件事在两个面板各报一次，并让「没定义」反复触发整篇改写 |
| **在进度条、侧栏或顶部加「运行中」指示** | **运行视图**改为跟随**在途任务**之后，「看得见在跑」这件事已经由那张页本身承担（见 §5.11）；进度条六格只表达「最远已完成的里程碑」，塞进「正在跑」要改它的语义。侧栏角标与全局横幅属界面变更，另开票，本期不做 |
| **保留旧的非任务生成通道**（`POST /api/conversation/generate-*-stream` 四条） | **已删除**（#61 按 §5.5 三条判据收口）：`generate-prd-stream` / `generate-prd-from-summary-stream` / `generate-api-docs-stream` / `generate-prompts-stream` 四条直连路由、它们的请求模型与前端封装一并退役，OpenAPI 里不再出现。判据逐条成立——没有代码读它们、原先把它们当接缝的用例已迁到任务通道（`POST /api/jobs` + `GET /{id}/stream`）、删除不触碰业务逻辑。四个服务方法仍在，`prd` / `api_docs` / `prompts` 任务直接调它们（`generate_prd_stream` 即整篇生成） |

> §2.2 收自 v9 §1.3 的「本期明确不做」，并按现行形态补齐；入口模式这一轮的边界见 §5.8。

## 3. 设计

### 3.1 后端分层（api/services/repositories/core）

`backend/src/backend/` 下四层单向依赖：

| 层 | 职责 | 边界 |
| --- | --- | --- |
| `api/` | 解析 / 校验 / 封装 | Pydantic 模型集中在 `api/schemas/`（按领域拆成 9 个子模块，`__init__.py` 是唯一出口）；Router 各带完整 prefix，`main.py` 不叠加 |
| `services/` | 业务编排 | 一个业务操作 = 一个事务；事务边界唯一落点 `session_scope()`，不许在 `async def` 里跨 `await` 持有 |
| `repositories/` | 唯一碰模型与查询的地方 | 绑定 `Session` 的实例方法；返回模型对象或 frozen dataclass 投影，不返回裸 dict；不许绕过 Engine 的直连（`sqlite3` / 原生 DBAPI）、不许 `.commit()` / `.rollback()`、不许 SQL 字符串字面量 |
| `core/` | 引擎、事务、类型、时钟、限制、方言、配置 | `expire_on_commit=False` 防 `DetachedInstanceError`、`autoflush=False`（要自增 id 就自己 `flush()`）、`max_overflow=0`（池满即报错，连接数问题不推迟到服务端 `max_connections`） |

- 列类型只走 `core/types.py`（`short_text(n)` / `long_text()` / `timestamp_text()`）；大段文本上限 60KB 字节，闸门在 `core/limits.py::ensure_text_within_limit`，接在 `append_version` 与 `persist_progress/finish/fail`。
- Schema 只走 Alembic：迁移落 `backend/migrations/versions/`，入口 `core/schema.py::prepare_schema`，在 `lifespan` 里跑（重启 = 跑迁移）。v9 只有一份 Postgres 基线（`0001_baseline.py`，由 `autogenerate` 从模型生成并人工修环形外键）；**后续迁移仍要人工复核**——autogenerate 对外键 `ON DELETE`、主键 `nullable` 与表达式索引有已知的反射缺陷（见 `tests/test_schema_migration.py`）。
- 删列 / 退役列是**单向门**（回滚靠备份、不设兼容期）；**加列不是单向门**。
- 提示词只在后端；前端只能点名场景（`profile_key`），不能递剧本文本。

### 3.2 三份文档与文档版本链

一个**方案**下挂 PRD、接口文档、提示词三份**文档**。正文只住 `document_versions`（**文档版本**是正文的一次不可变快照），`documents` 只剩身份 + `current_version_id` 指针，读当前一律 `LEFT JOIN`。

- 整篇生成 = 追加新版本（不再删下游）；`optimize` / `clarify` / 手改 = 就地改当前版本；**修复** = 追加新版本（正文与审核结论同批写入）；checkpoint / **恢复** = 追加新版本。当前版本指针只前进不回拨，历史只增不改。
- **审核结论随版本保存，一版一条**（见 §3.8）：`document_versions` 上的一列，读当前文档时随列表返回；重新审核覆盖同一条，不追加版本。
- 环形外键：先空指针插 `documents` 行 → 插版本 → 回填指针（`_ensure_document()`）。
- **正文写入只有一个入口**（票 #81）：`document_store.write_document(mode=append / replace / manual, expected_version_no=…)`——手改、整篇生成、修复、恢复、就地改写全部走它，实现只有一份（`save_document` / `commit_generated` / `checkpoint` / `restore` 是薄封装）。正文 + 待确认清单 + 回执（就地改写时）同批写入；新增产出正文的路径接进 `_build_event_stream` 的 `done`。
- **统一版本锁**（票 #81）：所有会覆盖当前正文的写入都带「我以为当前是第几版」。对不上时**拒绝写入**并返回机器判据 `version_conflict`（不是「0 行 / 成功」）：手改路由回 409 + `CONTENT_CHANGED`（「正文已被更新，请刷新后重试」），就地改写的任务以 `CONTENT_CHANGED` 判失败——正文保持新生成那一版，旧内容不覆盖回去。追加版本（整篇生成 / 修复 / 恢复）不覆盖当前正文，因此不持版本期望。
- 上游正文变化（含手改，按 `content_sha`）只让下游 `stale=true` 亮黄条：不删除、仍可交付、只汇总提示不硬拦。黄条上给「**一键更新**」：先确认（写明旧版本保留在版本历史），确认后用当前上游重新整篇生成**被点的那一份**——不新增任务种类、不连带更新下游（下游自己会亮黄条），换不换仍由用户决定。
- 交付走 `GET /api/solutions/{id}/export`：ZIP = 三份 md + `README.md`；目录名消毒、上限 50MB、CSV 带 BOM。

### 3.3 生成任务与 SSE 契约

**生成任务**是一次管线运行，有独立生命周期，与「用户是否正连着看」解耦：`POST /api/jobs` 建任务 + `GET /{id}/stream` 订阅；`detach()` 只退订不取消，同一任务绝不并发订阅两次。**三份产物的生成只有这一条通道**——四条旧直连路由（`/api/conversation/generate-*-stream`）已删除（§2.2），非任务的 SSE 只剩对话与「按指令就地优化」。

- 任务种类：三份整篇生成（`prd` / `api_docs` / `prompts`）、对已有文档就地改写的三个动作（`optimize` / `clarify` / `auto_clarify`）、**按结论修复**（`review_fix`，追加新版本）、**只产结论的重审**（`review`，不碰正文）、以及对话的一轮（`chat`）。文档类任务的方案必填，**生成与修复的输入一律由服务端从库里取**（见 §3.8、§4.3）；`clarify` 的对话同样归服务端——按 `doc_kind` 定位那条澄清线程从 `chat_turns` 取。请求体只表达「做什么、对哪一份」，**唯一例外是就地改写那三个动作携带的「被改正文」**：`optimize` / `clarify` / `auto_clarify` 改的是用户眼前那一份（可能含还没落库的手改），它属于**目标**而不是上游，归服务端的只有上游与对话线程。解析在**建任务那一刻**完成（缺方案 / 缺材料直接 400，不空跑），结果随任务单走、不进 `request_params`。

- 阶段：需求澄清 → 大纲 → 撰写 → 审核 → 改写。两条信息轨是**过程字** `chunk`（可能缺标题）与**权威正文** `part`（票 #92 起只剩 `{text, replace}` 整段覆盖语义，正文 `chunk` 不带章节归属）；混用会把审核 JSON 写进正文。
- **PRD 整篇化（票 #92）**：PRD 与接口文档 / 提示词共用同一条生成路径——一次模型调用写完整篇 → 一次整篇审核 → 有问题整篇改写一次（改写后不重审）。**分章并行、章级 `stage` / `part` 归属、逐章重试与前端多章看板全部退役**：`prd_section_writer.py` / `prd_section_parallel.py` 已删除，`live_by_index` / `completed_sections` 不再参与进度写与快照（`generation_jobs.completed_sections` 列本身由 #94 的迁移 `0008` 删掉）；章节只作文档内部结构，结构真源回到技能包模板（`prd-template.md`，`job_fingerprint.PRD_TEMPLATE_VERSION` 因此升到 v2）。**用户可见的进度不回退**：阶段条（大纲 → 撰写 → 审核 → 改写 → 完成）与阶段输出对三份产物一致，PRD 不再有专属看板。
- **大纲（票 #91）**：三份产物的阶段顺序统一成「**大纲 → 撰写 → 审核 → 改写**」。大纲只**抽取**上游已有的结构、**不调模型、不发明**：PRD 从需求输入抽、接口文档从 PRD 的接口清单抽、提示词从 PRD + 接口文档抽。实现是 `backend/src/backend/services/doc_outline.py`（纯字符串，零 LLM 调用）：先按产物规范定骨架（PRD = 技能包模板章节、另两份 = 生成提示词的输出要求），再逐条从上游原文里摘锚点；摘不到的节写「**待确认**」并说明缺什么，绝不补写。抽出后过一次 `verify_outline` 后校验——锚点必须能在上游原文里逐字找到，查不到出处的条目降级为待确认；整体一条锚点都抽不到时返回 `None`，调用方把它当「这次没有大纲」直接发 `stage(writing)`，**不发 `error`**。事件对外形状不变：`stage` 只多一个取值 `outlining`，大纲正文走既有的 `stage_chunk`（与审核意见同一条过程通道，绝不混进正文 `chunk` / `done.reply`），换阶段即清空、不落库；因此大纲**不影响交付齐备判据**（仍按入口模式判定）。前端阶段条加「大纲」一格（三份一致），阶段输出面板把大纲单独一块并在正文撰写期间继续显示。
- **分批续写**（票 #93，`backend/src/backend/services/stream_reply.py::iter_continuation_events`）：撞上模型单次输出上限时**自动接着写**，直到模型自己收尾；PRD / 接口文档 / 提示词三份产物共用这一个函数。**判据是模型返回的结束原因**（`backend/src/backend/services/stream_guard.py::extract_finish_reason` 读 `response_metadata` 的 `finish_reason` / `stop_reason`，`length` / `max_tokens` 即「被截断」），**不是字数阈值**——阈值会在偏短的文档上误判，把一次正常生成拦腰截成两批。续写批次仍报同一条 `stage(writing)`，只多一个 `data.continuation`（第几批）：进度条不回起点、正文缓冲不清空，用户看到的是正文继续长。续写请求 = 原提示词 + **已写正文的尾部**（`document_service.CONTINUATION_TAIL_CHARS`，不带全文，否则续写请求自己会顶到上下文窗口）+ 一句「接着写、不要重复」（`backend/src/backend/services/prompts.py::CONTINUATION_INSTRUCTION`），三份产物共用一个构造器。**接缝不重复由代码保证而非提示词**：`_SeamGuard` 先扣住批次开头、与已写正文做逐字最长后缀匹配，只丢掉「紧挨在正文末尾、逐字存在」的那一段，其余一个字节都不动——因此「不漏字」是构造性的。**批次级重试与任务级退避不是一回事**：前者在同一批里从断点再要一次（`MAX_BATCH_ATTEMPTS` ≤ 3，不落库、不等待），后者把整条任务退回排队并等 `next_run_at`（#88）；重试用尽则整篇失败（`error`，不发 `done`），已生成的部分照旧由 #85 落成一版「部分完成」。
- SSE 分帧唯一实现 `backend/src/backend/api/sse.py::make_sse_generator`（已带 `X-Accel-Buffering: no`）：事件 `status/chunk/part/stage/review/done/error` + 末尾 `data: [DONE]`；`: ping` 心跳只能走这个出口；服务层与路由层两层异常兜底；前端用原生 `fetch` + `ReadableStream`。
- 重连先收快照再接实时流，恢复正文 = `finalized_text + live_buffer`；**带游标的续读不发快照**（客户端手里已经有那一段，见下条「过程日志与游标订阅」）；**失败 / 取消不覆写已有正文**（已生成的内容另起一版并标「部分完成」，见下条 #85）；**被取代**与**已取消**是两种不同终局；只有 `high` 严重度触发改写、改写后不重审。
- 运行态以内存为权威：`_RUNTIMES` / `JobBus`（**只作唤醒**，数据来自 `job_events`）/ runtime 配置快照（5 秒 TTL）/ 固定连接池都在进程内；请求参数、配置/供应商快照与技能包身份在建任务那一刻一次写全，收尾不再另取供应商四格；进度按 300ms / 4KB 合并写 `draft_content / phase / pending_items`（分章时代的 `completed_sections` 先停写、再由 #94 的迁移 `0008` 删列），**同一笔事务里追加 `job_events` 过程日志**（见下条 #86）。
- **创建去重**：同一 owner + 方案 + 产物（`kind` 与 `doc_kind`）+ 输入指纹的重复提交，在既有任务 `created_at` 起 **10 秒**内**复用仍在途（`pending` / `running`）的那一条**（`backend/src/backend/services/job_dedupe.py`）：不落新行、不顶替、不经状态机，第二次直接回既有 `job_id`；`start_registered_job` 对复用单是空操作，同一个 `job_id` 不会有两支协程、模型不会跑第二遍。终态任务不复用——生成已结束，再点一次是「重新生成」，照常新建并走顶替。判据带滚动时间窗，唯一索引表达不了它，故本票不加索引、不加迁移；跨请求的原子性由登记的进程内互斥锁兜住（单 worker 是部署硬约束）。没有指纹的任务（今天只有 PRD 落指纹）建单语义完全不变。
- **终态以数据库那一行为唯一裁判**：改状态只有一个入口 `backend/src/backend/services/job_state.py::transition`——**十一种事件**（抢占 / 成功收尾 / 失败收尾 / 请求取消 / 确认取消 / 取消兜底 / 启动清理排队行 / 请求顶替 / 确认顶替 / 回排队 / 判超时）+ 期望条件（哪一条任务 / 哪个方案 / 哪个 owner + 各自的前态集合）→ 一个结果。完整转换表写在模块 docstring 里，**只有那一份**。仓储的终态写一律是**条件更新**并返回影响行数，**改到 0 行就是「本次结果被丢弃」**：只留一条 `job.transition_discarded` 日志，不改内存、不重试、不重新排队。取消与顶替是**两段**（票 #84）：**单条任务**的请求取消把排队中的行一步落 `cancelled`、把执行中的行落 `cancelling`（租约不动，执行者还要用它确认）；执行者在下一个动作点确认才落 `cancelled`（半截正文与用量在这一步补一次）；租约到期的 `cancelling` 由恢复器兜底收成 `cancelled`。**批量作用域例外**（删方案 / 删账号）：方案或账号已经不存在，不会有人来确认退出，因此任意非终态**一步**落 `cancelled` + 清租约（执行者醒来时的补写改到 0 行、被丢弃；取消账在请求那一刻记一行）。顶替请求一步落 `superseded`，覆盖的前态只有 `pending` / `running`——**`cancelling` 不在其中**（用户已表达停止意图，不能被改写成「被取代」）；被顶替那一支醒来后只补一次载荷、不改状态。`cancelled` / `superseded` 都**不带状态性错误码**（AC4），`runtime.status` / `error_code` / `error_message` 的写入收口在状态机里。
- **收尾只做一次**：`_finalize` 进门先看内存状态，已是终态直接返回（不落库、不写稿、不广播）；内存闸之外还有上面那道数据库闸兜住跨进程 / 启动回收那种「别人已经收尾了」。**状态集合是七个值**（票 #84）：`pending` 排队中 / `running` 执行中 / `cancelling` 取消中 / `succeeded` 已定稿 / `failed` 失败 / `superseded` 被取代 / `cancelled` 已取消。对外 `JobSnapshot.status` / `RunSummary.status` / 列表查询直接给这七值，`?status=` 接受逗号分隔的多个取值（「在途」= `pending,running,cancelling`）；`completed` 这个名字与 `CANCELLED` / `SUPERSEDED` 两个错误码**一起退役**——取消与被取代靠 `status` 区分，错误码只解释失败原因（AC4）。
- **原子收尾**（票 #81）：成功收尾的五件事收进 `_finalize` 的**一个** `session_scope()`：① 状态机条件写（`job_state.transition(..., session=…)`，账本那一笔套在其保存点里）→ ② 正文版本（`document_store.write_document(..., session=…)`，带版本锁）→ ③ 审核结论（重审走 `commit_review(..., session=…)`；生成时结论随正文同批写入新版本）→ 提交之后才结算内存、写终态日志、广播 `run_summary`。任一步抛错 → 整批回滚、**任务仍是 `running`**（留一条 `job.closeout_rolled_back`，由恢复机制接手），不再把「写正文失败」吞成 warning 后谎报 `succeeded`。两条例外仍判失败（第二笔事务只落失败 + 账本）：重审结论写不进去（唯一产出一版没落库）、就地改写撞上版本锁（`CONTENT_CHANGED`）。账本遵循 #80 的保存点口径：审计写坏只丢那一行账，不杀结论。
- **执行账本**（`job_attempts`，票 #80）：每次「执行有结论」（成功 / 失败 / 取消 / 启动回收判死 / 租约超时被恢复器接手）记一行——第几次（`attempt_no`，同一任务内 1 起、`(job_id, attempt_no)` 唯一）、`outcome`、错误分类 + **脱敏摘要**、两列 token、`duration_ms`。写入点只在状态机收尾（`job_state.transition`）、与任务状态更新**同一事务**：任务行只留最近一次错误，完整历史查账本；**取消记账、被取代不记**（被取代不是执行结论），抢占 / 建单 / 进度合并写都不记。账本那一笔套在保存点里：写坏了只回滚这一笔并留 `job.attempt_record_failed` warning，**不许因为审计写失败把一次真实成功的生成判死**（#81 之后正文与状态在硬事务里、账本是审计——两者在同一笔收尾事务里同时满足，见本节「原子收尾」）。本期账本不进用户界面。
- **执行权是数据库里一条会到期的租约**（票 #82，`backend/src/backend/services/job_claimer.py`）：执行权由三件事共同表达——`lease_owner`（谁领的，`主机/进程`，**仅供排查**）、`lease_token`（本轮凭证，逐轮随机，**参与判权**）、`lease_expire_at`（到期时间）。**抢占**是「排队中 → 执行中」的转换，走同一条状态机入口 `job_state.transition(CLAIM, …)`；判断与修改压在**同一条 UPDATE**（`WHERE status='pending' AND (next_run_at='' OR next_run_at <= now)`），**改到 1 行才算领到**，两个进程抢同一行时只有一个改得到——不靠错开时间，靠数据库的原子性。**「排队中」只有 `pending` 一个表示**（票 #84）：建行即 `pending`，抢占只认 `pending`，回排队也写回 `pending`——不再有「`running` 加一个空租约」这种同形表达（两个真源无法分辨）。**续租**在每次模型调用前发生一次（挂在 `stream_reply._astream_chunks` 这个唯一入口，覆盖全部调用点）：租约 120 秒，把到期时间一次次往后推，于是十几分钟的长任务只要还在动就不会中途失效；**续租改到 0 行本身就是信号**——先回读那一行：状态是 `cancelling` 说明**用户已请求取消**（抛 `CancelRequestedError`，执行者跑到下一个动作点后确认取消并落 `cancelled`）；否则是被接手（抛 `LeaseLostError`，`run_job` 不再写任何结果、不广播失败、不记账本）。**回写**（收尾）带「状态 + 凭证 + 未过期」三条件：旧执行者的晚到结果改到 0 行，只留 `job.transition_discarded` 丢弃日志，不重试、不重新排队。**登记与派发已拆开**：`register_in_transaction` 只落单，派发的前置条件是先领到执行权（单进程里抢占就发生在登记之后、起协程之前，所以「提交完立刻开始生成」不变；纯队列调度循环与崩溃接手是 #83，失败退避 `next_run_at` 是 #88）。迁移 `0003` 只加这三列。
- **部分完成落成一版正文**（票 #85，`backend/src/backend/services/job_finalize.py`）：写到一半失败、重试耗尽、或用户按停止时，**已生成的内容不丢**——失败收尾走唯一写入口 `document_store.write_document(mode="append")` **追加**一版并标 `partial=true`（`document_versions.partial`，迁移 `0004`），**不覆写**当前那份完整正文；同一事务里 `review` / `review_failed_at` 显式留空（旧结论属于别的正文，摆过来会被读成本次结果），任务行同时留一份 `generation_jobs.partial`：`status=failed` 回答「这次跑成没有」，`partial` 回答「有没有东西能用」。一个字都没写出来时不落版本（空版本只是个点开是空的假产物）；**被取代**不落（那种结局的口径是本次结果不再写入）。两处取舍：就地改写（`optimize` / `clarify`）与重审 / 对话**不**升格成版本——前者追加一版半截改写会把当前正文变成残缺稿，后者根本不产正文。前端读这个标记：审阅页页首提示「这份正文不完整，已生成的部分可以先用」，版本列表标「部分完成」，审核区显示「未审核」；失败收尾若已落下这一版，落点从「运行视图」改到「审阅页」——那里能下载、能修、能重生成，标记不是禁用理由。
- **过程日志与游标订阅**（票 #86，`job_events` 表 + `backend/src/backend/services/job_events.py`）：生成过程按**既有合并写窗口**（≤300ms / 增量 >4KB）追加进 `job_events`——`id BIGSERIAL`（全局自增游标）、`job_id`（`ON DELETE CASCADE`）、`kind`（取值 = SSE 事件名 + `run_summary`）、`payload`（`{content, data, code}` JSON）、`created_at`；索引 `(job_id, id)`（迁移 `0005`）。它与进度列**同一笔事务**提交：`generation_jobs.draft_content / phase / pending_items` 仍是**快照**（冷读者一次拿走），事件表是**过程**（只增不改），两者不混。订阅 `GET /api/jobs/{id}/stream` 改为**按游标读表**：客户端带 `?cursor=`（或 SSE 规范的 `Last-Event-ID` 头）→ 只发 `id > cursor` 的事件，断线重连**不重不漏**；不带游标 → 先发 `snapshot`（其游标 = 快照内容覆盖到的最后一条事件）+ 快照游标，**不回放历史**；多个订阅者各持各的游标、互不扣减。游标只出现在 SSE 的 `id:` 行（`StreamEvent.event_id`，`exclude=True` 不进 JSON 体），对外事件形状（`status/chunk/part/stage/review/done/error` + `[DONE]`）一个字段都没变。**通知只作唤醒**：进程内 `JobBus` 与（若将来接）数据库 `NOTIFY` 同角色——有上限、无监听者即丢、不保证送达，数据永远来自表；没有通知时靠 250ms 轮询兜底，读者轮询发现表里暂无新行时会把写者内存里**未落盘**的事件补写下去（写者挂在模型调用上时进度不会卡住，但订阅者**从不写进度列**）。清理是**可直接调用的单元** `purge_expired_events(retention_days=7, now=…)`：终态任务的过程日志保留 7 天、**只删事件表**，权威正文（任务行与 `document_versions`）一个字不受影响；把它接进调度循环是 #89 的事，本票不起定时器。
- token 计量以 `ContextVar` 挂成环境值（`backend/src/backend/services/llm_meter.py`）：观测层挂在模型调用之外，**业务层调用方式不变**；没有任务上下文时计量自然无操作。预算检查在 `astream_text` 开头、记账在末尾，超顶复用 `INVALID_REQUEST`。
- 排空顺序固定：就绪探针转 503 → 停止接收新任务 → 最多等 30 秒（等待上限、不是必须等满）→ 超时者标为已取消落终态并向订阅者发错误事件 → flush 日志退出。`stop_grace_period` 必须大于 30 秒。排空是**可直接调用的单元**（不起子进程、不发真信号），用例毫秒级验证。
- **恢复器**（票 #83 / #84，`backend/src/backend/services/job_recovery.py`）：过期租约与取消中任务的收口，入口是**可直接调用的单元** `recover_once(limit) -> RecoveryReport`（不起线程、不起定时器、不 sleep——生产里由调度循环的收口周期驱动，见下条「调度循环」）。扫描只挑候选（`scan_recoverable`）：周期档找「`running` 且租约已过期」与「`cancelling` 且租约已过期 / 没有租约」两种行，启动档找库里所有**非终态**行（`pending` / `running` / `cancelling`）。判权靠**扫描时读到的旧凭证**做条件写（`LeaseFence`：凭证 + 到期时间两列一起进 `WHERE`）：凭证被换掉或刚续过租都改到 0 行——跳过、不报错、不记账，与 #82 挡「晚到结果」是同一条规则。账本行数 = 已结束的执行次数，周期档据此决定去向（`attempts + 1 >= DEFAULT_MAX_ATTEMPTS` 判失败 `failed + LEASE_EXPIRED`，否则回排队：清租约、落回 `pending`）；**`cancelling` 的行一律落 `cancelled`**（用户意图优先于「超时」，AC3），不记成失败。**启动档一律落终态**：有租约的 `running` 按 `LEASE_EXPIRED` 判失败，从没被领过的 `pending` 走 `EXPIRE_PENDING` 判失败（`INTERNAL_ERROR` +「服务重启，任务已中断」；不复用 `FAIL`，避免旧执行者的晚到失败写进已回队列的行），`cancelling` 收成 `cancelled`——因为启动那一刻不可能有执行者、而本票仍没有调度循环，回排队等于永远进行中。每收口一行记一条账本（失败写超时原因、取消写 `cancelled`），与状态更新同事务。去向判定与条件写全部经 `job_state.transition`，恢复器自己不写库。启动回收 `reap_orphans` 已收编为 `recover_once(startup=True)`，重启不再留「进行中」的尸体。
- **失败延迟退避**（票 #88，`generation_jobs.next_run_at`，迁移 `0006`；映射表在 `backend/src/backend/services/job_backoff.py`）：**回排队不等于立刻能领**。可重试失败回排队时，`next_run_at` 写成「失败时刻 + 按错误类型算出的退避时长」——限流（仓库里 HTTP 429 的稳定码 `INVALID_REQUEST`）退 **30 秒**、上游 5xx（`LLM_UPSTREAM_ERROR`）退 **10 秒**、超时（`LEASE_EXPIRED`）退 **5 秒**、其余兜底 5 秒；这张表是**全仓唯一一处**「哪个错等多久」，按 **code 值**分类（绝不看中文文案 / `detail`）。写入点只有一处：`job_state.transition(REQUEUE, …)` 把退避、清租约、`updated_at`、账本压进**同一条条件 UPDATE**（收尾之外不存在第二条写路径，也就不存在「已回排队但还能被立刻抢走」的窗口）。**到期闸门与排队顺序各只有一处定义**（仓储的 `_due_now` / `_queue_order`）：抢占条件（`claim`）与候选扫描（`claimable`）都多一条 `next_run_at = '' OR next_run_at <= now`（空串 = 立即；字典序即时间序），于是**未到期的任务一行都改不到**；顺序规则固定为——**先过到期闸门，到期之后才按 `updated_at` 排队**（回排队会把 `updated_at` 推到现在 = 排到同优先级队尾，`created_at` 不再参与），两套语义各管一段、不叠加成第三种顺序。时间只有一个入口（`core/clock.py`），`transition(now_text=…)` / `claim(now=…)` / `recover_once(now=…)` 都可注入，用例毫秒级演示 30 / 10 / 5 秒。前端读快照里的 `next_run_at`：等待态**不显示成失败、也不无限转圈**，而是「等待重试，约 xx 秒后」（到点转「即将重试」，倒计时向上取整并 clamp 到 0，不跳负数、不闪烁），且**等待期间取消仍然可用**（`POST /api/jobs/{id}/cancel` 不受到期闸门约束；等待态的任务没有运行时，所以前端取消后自己收尾本地运行态）。**退避只把「到期」这个判据落库并用例化**：谁来领由下一条「调度循环」回答（它扫到期行并派发）。超时那一路（恢复器 `REQUEUE`）是本票能真实产生的；限流 / 上游 5xx 两档要等 #84 的「可重试失败」转换送进来，映射与写入路径在这里已经全部定死。

- **调度循环**（`backend/src/backend/services/job_scheduler.py`，接管 #89 的遗留）：`claim_once`（#82 领任务）、`recover_once`（#83 收口过期租约与陷住的取消）、`purge_expired_events`（#86 清过程日志）三个单元在此**有了生产调用者**——此前只有用例在调，于是运行期三件事从未发生过：退避到期的行没人领、`cancelling` 超时无人兜底、过程日志 7 天不清理。循环是 `asyncio` 后台任务，起在 `lifespan` 末尾、**关在关闭阶段第一步**（先 `cancel()` 再 `await`，不留悬挂 task；排空期间不再有新任务被领进来）：领取约 **1 秒**一轮、收口约 **30 秒**一轮、清理约 **1 小时**一轮，三个周期都可配（`job_scheduler_*`）。它**只补漏**：新建任务仍是「登记后立刻抢占派发」，交互延迟不经过任何周期。派发前按库里的行重建任务单（`job_scheduler._resume_ticket`）：**上游输入重新解析**（`resolved_inputs` 按 C-R3 不落库，重试是一次新的执行，取新的「那一刻」）、**配置取当前生效的那一份**（DB 的 `config_snapshot` 是投影，不含量身定做的 `RuntimeConfig` 对象；「每次执行冻结一份快照」仍然成立——冻结的是这一次执行）；不能重建的种类（`chat`：上下文在 `chat_turns` 里、靠不落库的 `input_turn_id` 定位）**如实判失败**，而不是拿空历史跑一轮。重建失败（缺上游材料 / 行已不存在 / 读库出意外）走同一套状态机收口成 `failed`，不留「领到了却没人跑」的尸体。

### 3.4 技能包

`skills/` 是管线知识的唯一来源：归属与资源由 `skill.yaml` 自述（`applies_to` / `references[]`），加包 = 加目录、不加中心注册表；唯一入口 `load_skill_artifacts(kind)`，规范整段注入、不检索，改写 / 澄清按白名单 `format_rewrite_reference`。缺件返回 `None` 降级，且降级要在回执上看得见。

部署态把技能包随代码打进镜像、不挂载，`PRDWRIGHT_SKILLS_STRICT=true` 保持开启：技能包缺失时启动直接失败，而不是静默退回内置提示词。理由只有一条：**镜像即完整交付物**，挂载会让「镜像里的代码」与「挂载进来的技能包」版本不一致成为可能，而就绪探针检查的恰好是「技能包可加载」。

### 3.5 鉴权与配额

- 会话：随机 token 存库 + HttpOnly Cookie，`TokenIssuer` 封装以便替换；密码 `hashlib.scrypt` + 独立 salt；不上 JWT。单点登录 `replace_for_user` 在一条事务里先删该用户全部旧会话再插入。邀请码注册（`invite_codes.max_uses` 0 = 不限，首启播种 `INVITE_CODE`）。
- 门禁 = 中间件默认拦截 + 白名单（`/`、`/health`、`/api/auth/*`、`/api/conversation/questions`，以及 `/healthz` / `/readyz` 两条探针）；中间件必须是纯 ASGI 类；`AUTH_ENABLED` 默认 true。越权 / 不存在一律 404。未登录禁止创建任务：可浏览入口页，点入口即弹登录框。
- 主密钥只以文件形式存在（不在数据库、不在环境变量），由 `scripts/keygen/generate_keys.py` 生成与轮换；**密钥条目**密文入库、面板只回 `key_present`；轮换先重加密再换主密钥，主密钥保留每一把。
- **配额**给单个用户设用量上限；额度检查与记账在 `astream_text` 两端。管理端真边界是后端 `require_admin`，前端门禁只是体验；**审计日志**有意不随用户删除而级联清理。
- 日志唯一入口 `configure_logging`，双写轮转文件（永开）与 `app_logs`（可关）；`request_id` 由格式化器从 contextvar 现取。

### 3.6 部署形态（v9 落盘）

`deploy/` 一个目录装全部部署件：`deploy/compose.yaml`（唯一编排，全平台一份）、`deploy/.env.example`、`deploy/Makefile`、`deploy/backup.py`、`deploy/backups/`、`deploy/docker/`、`deploy/README.md`。宿主只发布 `80`，Nginx 唯一对外：`/` → 用户端 dist、`/admin/` → 管理端 dist、`/api/` 与两条探针 → `api:8000`（只 `expose` 不 `ports`）。**单域名 + 路径前缀**的硬理由是 Cookie host-only，跨子域会「后台登录了、调 API 仍 401」；`CORS_ORIGINS` 设空串。Nginx SSE 三行（`proxy_buffering off` / `read_timeout 1800s` / `gzip off`）+ 服务端 `: ping` 心跳；`assets/*` 长缓存、`index.html` 必须 `no-store`。

- **两个镜像**：应用镜像（`python:3.12-slim`，多阶段，`uv sync --frozen --no-dev`，`CMD` 写死 `--workers 1`）+ 静态站点镜像（`nginx:alpine`，node 构建两个前端）。`uv sync` 与 `npm install` 缓存键不同、两进程重启语义不同；合并成单容器会让「重启 Nginx 杀掉在途任务」。
- **单 worker 硬约束**：`_RUNTIMES` / `JobBus` / runtime 配置快照 / 固定连接池 / 技能包缓存都在进程内，多 worker 会让任务与 SSE 分属不同进程。不提供环境变量覆盖、不写 `replicas`、不引 gunicorn。
- **三个命名卷**：数据库（`pgdata`，Postgres 的整个 data 目录）、日志、密钥（只读 `master.key`）。命名卷是**语义问题不是配置问题**：数据库文件需要原生文件系统语义（fsync、目录项、锁），Docker Desktop for Windows 的 bind mount 经桥接层会丢掉它们，症状是随机 I/O 错误、启动失败或静默丢最近几分钟写入。宿主目录挂载 + Windows 专用覆盖文件因此被否决；实时库不能双击查看，可见性由备份产物与 `docker compose exec db psql` 补上。
- **两个探针**：`GET /healthz` 恒 200、不查库不查配置不发外部请求（判生死）；`GET /readyz` 判「库可写」且「技能包可加载」，任一不满足返回 503 且响应体指出是哪一项（判就绪）。两者都进认证白名单，漏了会表现为「容器永远不健康」。`/health` 语义不变（恒 200、`status` 只有 `ok` / `degraded`、三项体检），它是人看的详情页，不是机器闸门；探针也不查模型供应商配置（依赖外部网络、高频会烧额度会误报）。
- **排空**：见 §3.3。就绪探针转 503 给「摘流」留时间，新的生成请求返回明确失败而不是排进一个马上要死的队列。
- **备份**：一条命令产出带日期的 `.dump` 与同名 `.sha256`，落 `deploy/backups/`；`pg_dump -Fc` 走数据库侧一致性快照（不能拷 data 目录：WAL 与共享内存状态会让它静默缺最近写入），自检 `pg_restore --list` 可解析 + 归档表数与源库一致 + 读得到 `alembic_version` + sha256。迁移之前必须先有备份，备份没做成不许起栈；删列与改类型后的回滚方式是恢复备份，不是 `git revert`。恢复演练要求整段见附录 C。
- 启动脚本以 root 校正日志目录属主后降权 `exec`，代码层只读；起应用前先等数据库就绪（判据是真能执行一条 `SELECT`，不是端口通）；迁移只由 `lifespan` 跑一次（C-V9-4）。主密钥缺失即拒绝启动并打印生成指引，绝不自动生成。`PRDWRIGHT_MASTER_KEY_PATH` 只经 `os.environ` 读，`.env` 文件读不到，必须走 `EnvironmentFile`；`PRDWRIGHT_SKILLS_DIR` 走 `lookup_env`。日志双写 stdout + 日志卷。
- 镜像 tag 用 `git describe`；CI **只构建不推送**，整栈冒烟轮询 `/readyz` 直到响应体 `status == "ready"`（只看 200 会假绿），并断言 api 的 PID 1 以非 root uid 运行。

### 3.7 唯一部署后端：Postgres

数据库是 compose 里独立的 `db` 服务（Postgres 16），数据在 `pgdata` 命名卷里；编排是 **db / api / web 三个服务**，只发布 `80`，数据库端口不出宿主。`api` 的 `DATABASE_URL` 由编排层按 `.env` 的凭据拼出来（`db:5432`），镜像里没有可用的内置口令；`api` 用 `depends_on: db: service_healthy` 等数据库健康再起。

**为什么不再留 SQLite / MySQL**（这是 v9 的收缩决定，票 #75~#78）：双后端意味着测试基座、迁移基线、结构对拍、就绪探针与备份链各自分叉成两份，而两份里只有一份每天被跑——另一份会静默烂掉（#76 实测：非 SQLite 引擎分支无条件挂 MySQL 的 `SET sql_mode`，Postgres 接上后第一条连接就报语法错误）。单后端的代价是「不能换库」，收益是所有东西只有一份真相。SQLite 的 `mode=ro`、`VACUUM INTO`、`BEGIN IMMEDIATE`、`PRAGMA`、单写者写锁语义，以及 MySQL 的 `ON DUPLICATE KEY`、`MEDIUMTEXT`、`utf8mb4` collation 变体，全部随之删除；旧 SQLite 库既不读取也不自动迁移。

可移植性四模块边界保留 = `core/database.py`（连哪个库）/ `core/dialect.py`（语句）/ `core/types.py`（列声明）/ `core/schema.py`（迁移）。它们现在的意义不是「为换库留口」，而是「方言知识只出现在一处」：`SUPPORTED_BACKENDS` 只含 `postgresql`，非 Postgres 地址在配置阶段即拒绝并给出可操作的迁移指引；`core/dialect.py` 保留「未知方言 → `NotImplementedError`」这一层，让没适配的方言发不出语句（而不是悄悄生成一条在目标库上语法错误的 SQL）。

结构对拍用 SQLAlchemy inspector 反射（`inspector_snapshot`），期望形状由 `metadata_snapshot` 按目标方言编译模型元数据；不再有 SQLite 私有接口（`sqlite_master` / `PRAGMA`）参与「判断迁移是否安全」这件事——工具和被检查对象用同一个库的私有接口，等于没有独立验证。完整方言台账与 C-D1~C-D6 在附录 A，库结构勘察实测数据在附录 B。

### 3.8 审核结论、修复与重新审核

**审核结论**是**审核**的产出：判定（通过 / 有问题）、逐条问题（**每条带类别**）与严重度、一句总结、本次是否改写、审核时间（`reviewed_at`），以及**这次到底试没试过**（`attempted`）。它随**被审的那一版正文**一起保存，**一版一条**；重新审核覆盖同一条。**审核没跑成不写结论**——没有结论不等于通过，界面照实标「审核失败」。结论面板把「审核时间 + 这一版是第几版」一起显示（文档列表随结论带 `version_no`），因此「哪一版、什么时候审的」是界面上读得到的两个事实，而不是要靠回忆。

**三份产物同构（票 #94 收口）**：PRD / 接口文档 / 提示词套件的**审核、改写、修复走同一条链路**——`backend/src/backend/services/document_review.py` 一段审核代码（同一份提示词、同一个解析、同一个 `review_data` 形状）服务三个入口，产物差异只由 `ProductContext`（`doc_kind` / 事件 `doc_type` / 展示名 / 产出规范 / 上游材料）表达，**不分支到第二套实现**。结论形状对三份**逐字相同**：`kind / verdict / summary / issues / rewritten / reviewed_at / attempted`；分章时代那个 `failed_sections`（失败章节清单）**已随 #94 删除**（它恒为空，留着只会让人以为哪天会有值）。生成链路（`stream_review_and_rewrite`）与修复内的重审共用同一段审核，重审（`stream_review_only`）只是「不进入改写」的那一半。

**只报缺陷，不报未决**：结论里的每一条都是**缺陷**——可验证为错的地方，六类：**编造**（输入里检索不到的事实）、**矛盾**（与输入或上游章节冲突）、**结构不符**（标题层级 / 表格列 / 编号与规范不一致）、**空泛**（无法开工的描述）、**推断未标注**（推断没标「（建议）」或没给一句依据）、**清单漏登记**（该进待确认清单的项没有登记；判据要求**写清在哪一节、缺的是哪一类项**——`where` 取章节标题、`detail` 写缺项类别且不超过 40 字）。**「缺什么、该怎么定」不进结论**——那是**未决**，归待确认清单；审核最多指出「这一项该登记却没登记」，不替它判该定成什么。类别决定严重度且**不由模型自行升降**：编造与矛盾是高（生成时触发一次自动改写），其余是中（只报不改）。「推断未标注」**只判形式**（有没有标注、有没有一句依据），不评判依据强弱——那既主观，又是同一件事被反复报的来源。**两个时点两套口径**：生成过程中只判前五类（清单要到收尾才抽得出来）；**重审与修复后的重审**才判「清单漏登记」，并把当前版本的清单整份注入提示词。界面这块的标题因此是「**文档缺陷**」，折叠头给分类计数，展开按类分组、类内按严重度排序。

**读取面**：当前文档的结论随文档列表返回（含它所属的版本号），版本详情也带它；SSE 的 `review` 事件保留，负责订阅期间的即时展示，**落库的那条才是刷新 / 换设备后的唯一来源**。

**四态与它们的可读性**：面板恒渲染，判据是「通过 / 有问题 / 审核失败 / 未审核」——没有结论也画，否则「没有面板」会被读成「没问题」。**四态里有三者是库里读得到的事实**：通过 / 有问题来自版本上的 `review`，**「审核失败」来自同一行的 `review_failed_at`**（失败时间，迁移 0007）——失败不写结论（C-R1），但「这一版被审过、且没审成」本身必须活过刷新：只说在会话内存里的话，刷新后会退化成「未审核」，用户再也看不出自己审过、而且它没成功。拿到新结论时清空该列（两者描述同一版，不能并存）。**两种「审失败」写同一列**：重新审核（以及修复后的那次重审）没跑成，与**生成时的审核降级**都落 `review_failed_at`——两者都是「这份正文被审过、而且没审成」，读侧与面板不必分两套。**「审过但失败」与「压根没审」由后端显式区分**：`review` 事件带一个 `attempted` 标记，运行态照着记；显式关闭审核的入口（快捷流程，`review_enabled=false`）连 `review` 事件都不发，因此那一版保持「未审核」，不凭空多出一次失败。**三份产物的审核失败同口径**（票 #92 后 PRD 不再有章级降级）：整篇审没跑成 → 不写结论、写 `review_failed_at`。

**修复**与**重新审核**是两个任务动作，目标产物由 `doc_kind` 决定（与 `clarify` 同口径）。修复：取当前版本的结论 → 按目标产物拼上下文 → **整篇重写**（一条结论描述的就是整篇，按它修也只能整篇修）→ **只审不改** → 追加新版本（正文与结论同批写入，版本来源记为修复）。写入走 #81 的唯一入口 `document_store.write_document(mode="append")`——**追加一版，不是重生成文档**：旧版正文与它自己那条结论一起留在版本历史里，可恢复、可对比。重新审核：只审不改 → 更新当前版本的结论，**不追加版本、不改正文**。两者共用同一段审核代码，修复内的重审**只跑一次、只审不改**，不会触发改写。

**重新审核的审法与降级**：三份产物都**整篇审一次**（票 #92 前 PRD 是逐章审再汇总，那条链路已退役）；复用生成时那套提示词与解析，因此「生成时审出来的」与「重审出来的」是同一套结论形状。**需求澄清线程与生成侧同一份内容口径进提示词**（PRD 的审核提示词里带「需求澄清对话」一节）：判「有没有编造」需要的是「用户到底拍板了什么」，而拍板细节有一半只在对话里；少了它，正文里如实写了的内容也会被记成编造。**上游缺失只降级、不报 400**：PRD 没有任何需求输入（结构化摘要、自由文本、需求澄清线程都没有）时按「仅依据正文与写作规范核对」，接口文档 / 提示词缺上游材料时提示词里写明「未提供上游材料」——降级写在提示词里，不是默默按通过。**重新审核的唯一产出就是判定**，因此它没跑成按任务失败处理、不写结论（与修复内那次重审的口径相反，见下段）。

**结论只写到「被审的那一份正文」上**：重审的正文在建任务那一刻从库里取、随任务单定格，而结论要写到「收尾时此刻的当前版本」——两者之间用户手改一次，结论就会落到一份**没审过的正文**上（它看起来完全正常，却是错的）。因此写入是**条件写**：当前版本的内容指纹必须与「被审那一份」一致才写；不一致时任务判失败（`error_code=CONTENT_CHANGED`）、错误信息写明「正文已变更，本次审核结论未写入，请重新审核」，**已有结论原样保留**。判据在事前比较与写入 SQL 各有一道。**两道闸门都判任务失败**：收尾若在写不进去时只记一条日志、任务照旧 `succeeded`，用户得到的是一条「成功但结论没变」的记录——比报错更糟，他没有任何线索该重审。写入前先落终态的旧顺序因此改成「先写结论、写不成就置 failed」，失败同时向在线订阅者补一条 `error` 事件（`succeeded` 是七态里的成功终态，票 #84）。

**上下文窗口**（全量注入，超预算走既有告警、不静默截断）：接口文档看 PRD 当前版本全文；提示词看 PRD 与接口文档当前版本全文；PRD 看结构化需求摘要 + 需求澄清与文档澄清两条线程 + 当前正文 + 结论。**审核与修复都额外带当前版本的待确认清单**（生成链路不带：那时清单尚未抽出），这样「漏登记」判得出来，也不会把已登记过的项再报一遍。

**结论怎么进提示词、失败边界在哪**：重写提示词的第一节就是**当前版本那条结论**——逐条问题（PRD 的按章定位换成 `where`）+ 一句总结当修复指令；上游材料整段注入，**不骨架化**（审核看骨架是为了省 prefill，重写要照抄原文，骨架会把散文里的事实丢掉）。修复提示词另有一条硬约束：**不得为缺失编造**——缺就写「待确认」并登记清单，不能拿一个像样的默认值把洞填上（那会把「未决」变成「编造」，比不修更糟）。因此两条边界必须分开：**重写失败 → 正文与版本都不动**（任务判失败）；**重写成功但重审失败 → 正文照落库、结论留空**（任务仍成功，界面标「审核失败」，再点一次重新审核即可补上）。

**入口条件**：「**文档缺陷**」面板**恒渲染**（四种状态都画），两个动作都在折叠头常驻，**不可点时就地置灰并说明原因**——修复只在「有问题」时可点（没有问题就没有依据）；重新审核在「审核失败 / 未审核 / 通过」时可点（有问题时先修复，顺序反了只会得到同一条结论）。灰按钮的 `title` 与面板里的说明写清「为什么现在不能点」，不猜一个默认值、也不把入口藏起来。**一支修复任务在途时是例外**：三份文档的「修复 / 重新审核 / 保存编辑」一律不可用，且**不加说明文字、不弹提示**（判据与理由见 §5.11）——灰的原因不在这一份的结论上，而在别处有任务在跑，就地写一句反而让用户盯着这张页找原因。

### 3.9 交付页

**交付页**是拿走成果的地方：逐份下载 + 整包下载，交付包内容仍是三份 md 与说明文件。进入判据不再是「点了完成」：**齐备即可进入**，审阅页不再有「完成」按钮，进度条的「交付」格在齐备后可点、未齐备时不可点。**齐备的判据由入口模式决定**（完整流程与快捷流程三份、导入入口只有提示词）。**三份齐备**时全应用提示一次（每方案每会话一次），但**不自动跳转**——用户可能正在改稿。两个导入入口只要一份提示词，它们齐备时**不弹**这条提示：那句话讲的是「三份都齐了」，对只要一份的人说三份就是假的；它们的入口照旧是进度条那一格，齐备即点得动。

## 4. 契约

### 4.1 C-V9-1 ~ C-V9-10（部署与运行形态）

| # | 契约 | 破了会怎样 |
| --- | --- | --- |
| **C-V9-1** | 宿主只发布 `80`；`api` 的 `8000` 只 `expose` 不 `ports` | v7 的「后端只听回环」退化成「后端直接对外」，CORS 与 Cookie 行为随之改变 |
| **C-V9-2** | `api` 副本恒为 1，`--workers 1` 写死在镜像 `CMD`，不提供覆盖 | 任务与 SSE 分属不同进程，客户端永远等不到输出 |
| **C-V9-3** | 数据、密钥、日志**必须是命名卷**，禁止 bind mount 宿主目录 | 随机 `disk I/O error`、静默丢最近写入，Windows 上必现 |
| **C-V9-4** | 迁移只在 `lifespan` 里跑一次，启动脚本不跑迁移 | 两个入口各跑一次，迁移日志与锁行为都不可预测 |
| **C-V9-5** | 技能包打进镜像，不挂载；`PRDWRIGHT_SKILLS_STRICT=true` | 镜像与技能包版本可能不一致，就绪探针失去意义 |
| **C-V9-6** | 主密钥缺失即拒绝启动，绝不自动生成 | 换机器时旧密文永久解不开，且当场无人发现 |
| **C-V9-7** | `/health` 语义不变（恒 200）；探针一律用 `/healthz` / `/readyz` | 可降级状态被当成故障，容器被反复重启 |
| **C-V9-8** | 排空窗口 30 秒；超时的在途任务落「已取消」终态，不留 `running` | 每次重启都留尸体，只能等下一条启动的 `reap_orphans` 收尾 |
| **C-V9-9** | 备份以 `pg_dump -Fc` 产出，产物必须有 `sha256`，且 `pg_restore --list` 自检（可解析、表数与源库一致、读得到 `alembic_version`）通过 | 「备份完成」变成一句没有证据的话 |
| **C-V9-10** | CI 只构建镜像，不推送；tag 用 `git describe` | 没有凭据通道的推送会把 CI 变成不可复现的猜谜 |

### 4.2 C-D1 ~ C-D6（方言可移植性）

| 契约 | 内容 | 破了会怎样 |
| --- | --- | --- |
| **C-D1** | `upsert` 必须显式给冲突目标列，且这些列必须是该表唯一的那个唯一约束。新增表若有两个以上唯一约束，`ON CONFLICT` 只能命中给出的那一组（写错目标会命中非预期约束） | 静默写错行。三个现有调用点都已核对：`documents` 仅 `(solution_id, kind)`、`chat_sessions` 仅 `ux_chat_sessions_thread`、`system_config` 仅主键 |
| **C-D2** | 布尔列一律登记 `BOOLEAN_COLUMNS`；`is_` / `has_` 命名不作为判据 | 类型归一漏一项 → 幻影迁移。`test_schema_parity` 已在守这条 |
| **C-D3** | 时间列只允许两种形态：业务表 26 字符无 `Z`、`app_logs.ts` 24 字符带 `Z`。**`+00:00Z` 零容忍** | 勘察已捞出 16 行脏格式；转 `DATETIME` 时解析失败 |
| **C-D4** | 结构对拍只能走「目标库的反射 + 按目标方言编译的期望形状」，不接受依赖某个库私有接口（SQLite `PRAGMA` / `sqlite_master`）的实现 | 工具与被检查对象用同一套私有接口，等于没有独立验证 |
| **C-D5** | 搜索的大小写行为必须显式（`lower()` 或方言 `ILIKE`），不依赖库默认 | 换库后「搜 admin 搜不到 Admin」，被当成业务 bug 报上来 |
| **C-D6** | 业务不变量（「同方案同产物至多一个在途任务」「额度不超过上限」）不能只靠「单写者」保证。换库前每条都必须落成唯一约束、条件更新或显式锁 | 并发下静默出现两条在途任务、额度被击穿。这类错不报错，只在对账时才发现 |

### 4.3 C-R1 ~ C-R5（审核结论与输入来源）

| # | 契约 | 破了会怎样 |
| --- | --- | --- |
| **C-R1** | 审核结论随**文档版本**保存、**一版一条**；审核失败**不写结论**（没有结论 ≠ 通过），但**失败时间写在同一行的 `review_failed_at` 上**（失败是落库事实，刷新后仍可读；**生成时的审核失败与重新审核失败写同一列**，而显式关闭审核的入口不写）；结论**只写到被审的那一份正文**上（指纹不一致就判失败、不写、不覆盖，**两道闸门都判失败**） | 结论与正文错位，「按结论修复」会对着不存在的正文改；把失败写成通过则是最误导人的一条假记录；失败不落库会让「审核失败」刷一次就消失 |
| **C-R2** | **修复**追加新版本（正文与结论同批写入）；**重新审核**只更新当前版本的结论，不追加版本、不改正文；修复后的重审**只审不改** | 修复变成覆盖当前版本 → 旧正文不可回溯；重审再触发改写 → 点一次修复、模型自己改两轮 |
| **C-R3** | 生成、修复、重新审核的输入只来自服务端：库内产物取当前版本，导入材料取方案上保存的录入文本；请求体不携带上游正文与需求正文——**三份产物的生成只有任务通道**（`POST /api/jobs` + `GET /{id}/stream`），四条旧直连通道已删除。**按澄清结果改写的对话同样归服务端**（按 `doc_kind` 定位 `prd-clarify` / `api-docs-clarify` / `prompts-clarify` 线程、从 `chat_turns` 取，前端不再回传 `history`）——这是从请求体删掉 `history` 字段的直接后果，属本契约的一部分；**就地改写那三个动作的「被改正文」是唯一例外**（`optimize` / `clarify` / `auto_clarify` 的 `document` 是**目标**，可能含用户还没落库的手改） | 双真源复活：前端副本落后于库时，用旧正文当上游，而没人能发现 |
| **C-R4** | 交付页**齐备即可进入**，判据由入口模式决定；不自动跳转；**三份齐备**时提示每方案每会话一次（导入入口不弹这条提示） | 回到「必须先点完成」；或自动跳转抢走用户正在编辑的页面；或对着只要一份提示词的人说「三份已齐备」 |
| **C-R5** | 审核**只报缺陷**（编造 / 矛盾 / 结构 / 空泛 / 推断未标注 / 清单漏登记），**不报未决**；类别决定严重度、不由模型升降；「清单漏登记」只在重审与修复后的重审判，并注入当前版本清单；修复**不得为缺失编造** | 两个面板回答同一件事、用户要读两遍；「没定义」被抬成 high 反复触发改写；修复把「缺」用编造填上，比不修更糟 |

### 4.4 契约的落点

- 完整论证在附录 A（方言台账）与附录 B（库结构实测）；分层守卫 C1~C4 与 60KB 闸门在 [`docs/agents/conventions.md`](../agents/conventions.md) §2。路径即承诺是普通纪律：文档写出的每个路径都要看得见（[`../../AGENTS.md`](../../AGENTS.md) 纪律 4，复核方法见 `docs/agents/conventions.md` §1），写完逐条 `Test-Path` + `git status` 复核。
- 改探针或排空，必须同步改本文 §3.3 / §3.6 与 §4.1 的对应契约行；改审核结论、修复或输入来源，必须同步改本文 §3.8 / §3.9 与 §4.3；**一次改动要收口**：代码、架构文档、路线图三者同步，谁都不滞后。

### 4.5 C-C1（取消语义）

| # | 契约 | 破了会怎样 |
| --- | --- | --- |
| **C-C1** | **取消只保证结果不再写入，不保证停止上游计费**。取消是用户意图（`status=cancelled`、`error_code` 留空），不是失败、更不是审核失败；真正的停止点是下一个动作点（一次模型调用之前 / 下一个事件到达），已在飞行中的那次调用撤不回来，它已经烧掉的 token 照记在账上 | 把「取消」讲成「立刻停止计费」，就是对用户的一句不实承诺：他按了停止、账单还在涨，而界面上写着已取消；反过来把取消写成失败（或写 `review_failed_at`）会让用户看到一次并不存在的失败 |

## 5. 取舍

### 5.1 接受的风险（v9 §8.1）

| 风险 | 为什么接受 | 缓解 |
| --- | --- | --- |
| 单副本 → 重启必然中断在途任务 | 多副本要先外置 `_RUNTIMES` / `JobBus`，那是另一版的工作 | 排空 + `stop_grace_period` 大于 30 秒（C-V9-8） |
| 命名卷不能直接双击查看 | 数据库文件在 Windows 的 bind mount 上会丢文件系统语义，命名卷是**唯一**不坏的做法 | 备份产物落宿主目录，可见性由它与 `docker compose exec db psql` 补上 |
| 镜像体积（含 langchain 全家桶） | 多阶段构建已把构建工具剥掉 | 只装 `--no-dev`；必要时按协议拆镜像 |
| 容器内时区是 UTC | 项目本来就按 UTC 存（`backend/src/backend/core/clock.py`） | 显式 `TZ=UTC`，不继承宿主机 |
| 就绪探针不覆盖「模型供应商配置是否可用」 | 依赖外部网络，探针高频触发会烧额度、会误报 | 留给 `/health` 三项体检与人工判断 |
| 容器冒烟不跑业务链路 | 登录 → 生成的端到端在 CI 上不稳定（真模型调用） | 冒烟覆盖「可达」，业务链路由既有用例守 |

### 5.2 否决的方案（v9 §8.2）

| 方案 | 否决理由 |
| --- | --- |
| 单容器塞 Nginx + uvicorn（supervisord） | 重启 Nginx 会杀掉生成任务；两个进程的失败语义不同 |
| 把数据库塞进 api 容器（省一个服务） | 数据库的生命周期、健康判据与数据卷都和 api 不同；塞在一起会让「api 重启」与「数据库重启」绑死，数据库也无法独立备份/恢复。v9 用独立 `db` 服务 |
| 同时保留两个数据库后端 | v9 已收缩为 Postgres 单后端（#78）：双后端会让测试基座、迁移基线、结构对拍与备份链各分叉成两份，而只有一份每天被跑。再引入第二个后端要连这些都做一遍，收益不抵成本 |
| Windows 专用 compose + 宿主目录挂载 | bind mount 在 Windows 上是语义问题不是配置问题；两份编排会让「哪些目录要持久化」写两遍 |
| 技能包挂载进容器 | 让「镜像与技能包版本不一致」成为可能，而这正是就绪探针要保证的事 |
| 用 `/health` 当 `healthcheck` | 恒 200，等于没配；技能包缺失时会把还能用的容器反复踢掉 |
| 自动生成主密钥 | 换机时旧密文永久解不开，且没人会发现 |
| 容器里跑两个前端 dev server / 热重载 | 开发体验不如本机；容器只承载部署形态 |
| 用宿主机的 `pg_dump` / 数据库 CLI 做备份 | 多一个「目标机上装没装、版本对不对」的变量；脚本改用一次性 `postgres:<tag>` 容器（与服务端同主版本），还能顺手做 `pg_restore --list` 自检 |

### 5.3 风险登记

| 风险 | 缓解 |
| --- | --- |
| 排空窗口不够长，任务被硬杀 | `stop_grace_period` 大于 30 秒；实测一条真实长任务校准 |
| 就绪探针漏挂白名单 → 容器永远不健康 | 探针端点与白名单在同一个提交里改，用例钉住「未登录访问返回 200/503 而不是 401」 |
| 主密钥路径没进进程环境 | 启动即失败并给出下一步命令（C-V9-6），而不是降级到「未配置密钥」继续跑 |
| 卷被 `docker compose down -v` 删掉 | 文档把 `-v` 标为危险命令；备份产物在宿主目录，不在卷里 |

### 5.4 拆分依据：取消 1200 行阈值，改以接缝为依据

**取消单文件 >1200 行阈值、改以接缝为依据，取代 v8 附录 A §5 的 W1 口径。** 文件边界按「对外 / 内部」的**接缝**划分：包入口只露正常动作，包内互引私有名合法；行数不是判据，接缝才是。七个实现文件归入同一内部包即可，不必合并回单个大文件。原文「拆不动的就不拆——这条优先于『压到 1200 以内』」的让步随之作废，因为它预设了行数目标存在。`backend/tests/test_layering.py` 里 `_CONTRACT_LINE_LIMIT = 1200` 是 `api/schemas` 契约模型包既有的活跃护栏，管的是「拆完之后别又长回一行」，与「拿行数当拆分依据」是两回事，本轮不动它。

### 5.5 清理判据（三条同时成立才动）

1. 没有任何代码读它（`grep` 可证，不是「我觉得没人用」）；
2. 删掉它不会让用例变红；
3. 删掉它不需要改业务逻辑（需要改逻辑的属于重构，不属于清理）。

「被文档说是死的」不算证据；每次删除前自己 `grep` 一次。反向守卫在 `backend/tests/test_cleanup_dead_code.py`：它用 `assert not hasattr` 守住「名字回来就红」，将来真需要同名能力时连守卫对应的一行一起改，而不是把守卫注释掉。

### 5.6 数字与基线口径

文档里的**数字先复核再写**，对外动作与名字数量、入口模式同步点数量一律以实测为准，不沿用旧报告里的约数；**用例基线现取现算**（`cd backend && uv run pytest --collect-only -q`），连旧文档里「文本计数 / 参数化展开差额」整段一起重算。入口模式按本轮实测收口：13 个核心标识符在 `frontend/src/` 下 #44 时点实测 **154 行 / 23 文件**、#49 终检复测 **199 行 / 23 文件**；四入口字面量在 `frontend/src/__tests__` 下 #44 时点实测 **151 行 / 13 文件**、#49 终检复测 **213 行 / 13 文件**（两轮文件数一致）；新增快照字段的同步点实测**至少 8 处**。这些数字只作改写登记表前后的对照，新形态以 §5.8 的「一行一个入口」为准。**加列不是单向门；单向门指删列 / 退役列**，回滚靠备份库文件、不设兼容期。全流程离线、零 LLM Key。本轮终检实测口径见 [`docs/agents/conventions.md`](../agents/conventions.md) §10。

### 5.7 生成任务收口后的取舍

- **任务单不落库、重启中断**：**造单**是公开动作，产出无 id、不可变的任务单，不落库、不顶替旧任务、不发事件；**登记**才在一个事务里落库并当场查「方案是否仍存在」。运行态仍以内存为权威，单副本重启必然中断在途任务，数据库行只是不可变数据的完整投影，不保证续跑（见 §2.2 / §5.1）。新增列属于**加列**，不是删列 / 退役列那种单向门。
- **深还原 `thaw_object` 的边界**：任务单内部深冻结以保持不可变；跨到外部 API（事件流、DB 投影、chat 输入轮次）时统一经 `thaw_object` 递归还原成普通 dict / list，不用浅 `dict()` 回退。嵌套 `pending_items.sections` 与 `chat_tool_result.answers` 因此在提示词、库行与落库轮次里都保持原结构。
- **对外形状按实测收口**：`job_service.__all__` 实测 9 个正常动作，新三步与「等待在途」各有自己的公开面；再导出块删空、不设旧名兼容期，排空留在包外。数字口径不沿用旧报告的约数（见 §5.6）。
- **守卫落在行为接缝上**：反向守卫守住「死符号与旧入口不许回来」，分层守卫守住既有契约模型行数护栏，终检守卫守住「文档写出的路径可见、无悬空引用」。测试只跨「造单 → 登记 → 派发 → 订阅」主接缝断言外部可观察结果。
- **调度循环接上了（本票）**：三个维护单元（领任务 / 收口 / 清理）以前只被用例调用，于是「退避到期没人领」「取消中超时没人兜底」「过程日志永不清理」在运行期全都不可达。现在它们由 `job_scheduler` 的周期任务驱动（收取开关 `job_scheduler_enabled`，测试默认关，见 §3.3）。选「`asyncio` 后台任务」而不选「独立 worker / 定时器进程」：运行态（`_RUNTIMES` / `JobBus`）在进程内、单 worker 是部署硬约束（C-V9-2），另起一个进程会让「谁在跑」重新变成两个真相。**何时改回来**：真要横向扩副本时，得先把运行时登记表外置，那时循环才该变成独立角色（见 §2.2）。
- **取消 + 批量作用域单步收口**：单条任务的取消仍是两段（请求 → 执行者确认，AC2），但**删方案 / 删账号**一步落 `cancelled` 并清租约——那两个场景里「有人会来确认退出」这件事根本不存在，留 `cancelling` 只是把一行交给恢复器、等租约到期才收口（C-C1 的取消语义见 §4.5）。执行者醒来时的补写改到 0 行、被丢弃；取消账在请求那一刻记一行，所以「取消要记账」仍然成立。代价是那一轮已经烧掉的用量不再由确认方补记（那一行已经没有执行者了）。
- **`cancelling` 不被顶替**：顶替只覆盖 `pending` / `running`。正在取消的行被改写成 `superseded`，等于把「用户不要了」说成「被新任务挤掉」——两个含义相反的状态混成一个，统计与排查都再也分不开（§5.10 的取舍同源）。
- **迁移 `0007` 的旧值映射保留**：它**不迁移存量数据**（spec 原文如此）。保留那段映射是因为：① 幂等（`UPDATE … WHERE` 改到 0 行也无害），② 对空库零影响（新部署起来时它只是一条空转语句），③ 对确实停在旧形态的库（`running` + 空租约）是一次确定性收口——删掉它换不来任何收益，只让升级路径少一件已做对的事。删列 / 退役列才是单向门，这类「幂等映射」不是。

### 5.8 入口模式收成一张登记表

**目标**：四个**入口模式**的资料以**一张登记表**为唯一真源，**一行一个入口**，**七类资料为列**；原来散在各处的按入口写死改成「查这一行」，加第 5 个入口就是加一行。产品用户看到的四个入口、文案、交互与三份**文档**的产出能力保持原样。结论写在本节，不另立架构决策档案；本轮票序与依赖见 [`roadmap.md`](./roadmap.md) §1。

**范围**：登记表**只收随入口模式变化的事实**，七类资料为列：① 键、组别与卡片文案，② 选中后的落页（含改需求与返回跳哪页），③ 进度条步骤，④ 三个布尔（录入页是否在进度条上 / 是否需需求澄清 / 是否需审核改写），⑤ 完成所需**文档**，⑥ 文案（列表里的模式名、返回与改需求两个按钮的文案），⑦ 录入字段（字段名、默认值、算不算「有内容」、落库映射到哪一列）。**本期不做**：14 个**视图状态** → 进度格的全局映射（`STEP_OF_STATE` / `STEPS`）、任务种类 → 生成中状态的映射、按视图状态的阶段名与四条全局降级、方案标题的固定回落链（`frontend/src/stores/solutions.ts` 的 `computeTitle()`，不随入口分叉）、`useJob.ts` 整份、按视图状态选渲染组件的链条，一律原地不动；**后端**、数据库结构、部署形态、界面文案、**界面交互**与产品能力一律不动；不做构建期代码生成，运行时读这一行；不做「加一个入口只改一行」的自动化证明，由完整性校验与评审兜住。侧栏把模式名显示出来属于界面变更，另开票，本期不做（实况见 [`README.md`](./README.md) §4 第 18 行）。

**设计**：前端纯函数层的「流程阶段机」是唯一答问者，登记表是它的内部实现；对外只答「这个入口在此场景给什么」：落哪页、画哪几步、要不要澄清、要不要审核、完成要哪几份、列表叫什么、返回写什么、录入哪些字段、刷新存哪些。入口页要「有哪些行」时枚举 `ENTRY_REGISTRY` 的键，每行的取值仍逐条走 `entrySpecFor`，不直接读列；工作流状态存储、方案存储、文档流水线 composable、应用外壳与入口选择页都向它问，规则里不出现入口字面量。七类资料按列写全，一行填齐才算一个入口；规则只在此处判一次，不在每个调用点各判一次。

**契约**：**入口模式**可为「未选择」——用户停在入口页、或老**方案**没记入口名，都归一成这个合法状态，照常显示四张卡、照常打开与编辑保存，并按完整流程给出展示口径；前端用空值、后端契约用空串，后端契约不变。未知入口键、登记表缺行、某列缺失，都是程序员漏干活：在**问询那一刻明确失败**，不返回任何默认值，失败转成「该块界面不可用」而不是整页白屏。测试只跨两条公开接缝：**应用外壳集成接缝**（真 router + 点四张入口卡 + 只断言屏幕上看得见的结果）与**登记表完整性接缝**（喂一份只填一半的假第 5 入口，断言当场被拒）；不扫源码、不数落点、不查标识符词频。

**取舍**：选「运行时读一张登记表」而不选「各处继续写死 + 人工同步清单」：后者漏改不报错、只悄悄错位，历史上真加第 4 个入口那次提交动了 33 个文件；前者把漏配从静默行为变成当场失败，人工同步清单随之整段退役，约定文档改描述这张表（见 [`docs/agents/conventions.md`](../agents/conventions.md) §6）。选「只收随入口变化的事实」而不选「把五套互逆坐标一起重排」：14 个视图状态 → 进度格等映射是全流程共用、不随入口模式变化，搬进表里会把全局语义错按入口分叉。选「结论写进现状架构文档的取舍节」而不选新立 ADR：这是实施取舍，与路线图、约定文档和时间线真源一次收口即可追溯。已复核的数字校正与旧口径作废记录留在时间线真源 [`README.md`](./README.md) §4，不在本节重复。

### 5.10 审核结论与修复的取舍

**目标**：让**审核**的结论成为可引用、可追溯的事实，并让「按结论修复」成为一次可预期的动作；同时把「上游正文从哪来」收成单一口径。**范围**：结论的存放与读取、两个新任务动作、生成与修复的输入来源、交付页判据。**本期不做**：结论的历史列表 UI、按正文变化判定过期、结论进交付包或管理端统计、审核通过后自动改写、交付页自动跳转（见 §2.2）。

**设计**：结论挂在**文档版本**上而非独立表——修复要引用的正是「这一版的那条结论」，版本就是它的自然键，且「一版一条 + 只在审阅页显示当前版本」不需要第二处真源（§3.8）。修复与重新审核各自是一个任务种类：前者追加版本、后者只更新结论；两者都不靠隐藏开关改变版本策略（§3.3 / C-R2）。上游正文一律由服务端取：库内产物取当前版本、导入材料取方案上保存的录入文本，请求体只表达「做什么、对哪一份」（C-R3；就地改写那三个动作的目标正文仍随请求体带来，见 §3.3）。

**契约**：C-R1~C-R5（§4.3）。交付页的判据与入口模式绑定，且不再由「完成」按钮把关（§3.9）。

**取舍**：选「结论随版本保存」而不选「独立审核表」：独立表要为「当前版本那一条」再造一次查询与一致性判断，而它的收益（跨版本浏览）已列入本期不做。选「新增两个 kind」而不选「复用 `auto_clarify` / `optimize`」：kind 表达「做了什么」，复用会让版本追加策略、回执归桶与目标产物三处同时分叉。选「输入一律服务端取」而不选「前端传、给了就用」：后者在导入入口之外仍留一条绕过库的写入口，而修复要求「上下文窗口看得见上游全文」时，前端副本是否最新无人可证。选「交付页解锁 + 提示一次」而不选「自动跳转」：跳转会抢走正在改稿的页面，代价比多点一次更大。审核失败**不写结论**而不是写占位：把失败伪装成判定，比暂时没有结论糟得多；而失败**本身**要落库（`review_failed_at`，加列不是单向门）——不落的话它随刷新消失，用户会以为自己从没审过；**生成链路的审核降级也落这一列**（#61）：它对用户就是「我审了、没成」，与重审失败没有可分辨的差别，分成两套只会在界面上出现两种「审核失败」。区分「没审」与「审失败」靠事件上的**显式标记**而不是判定空串：一旦靠猜，空正文那条路也会被算成失败。重审判**失败**（而不是把旧结论当成这次结果）当正文在中途被改过：条件写失败比写一条指向别处正文的结论便宜——前者用户重审一次，后者没人会发现。旧的四条非任务生成通道（`generate-prd-stream` / `generate-prd-from-summary-stream` / `generate-api-docs-stream` / `generate-prompts-stream`）**已删除**（#61 按 §5.5 三条判据）：它们此前是仅存的、还能收上游正文的生成路径，只登记不修等于承认 C-R3 有一个例外；删掉之后「三份产物的生成只有任务通道」不再有例外，而四个服务方法仍被对应任务复用。

### 5.11 运行视图跟随在途任务

**目标**：让「这一份文档正在被写」这件事在界面上**不会因为切走一页而失联**。用户点了修复、切去看别的阶段、再切回来，落点仍然是那张正在写的页；任务还在跑而界面不显示它，是这个产品不该出现的状态。

**范围**：**运行视图**的可见性判据、一张**压制位**（用户主动要看旧版时压住兜底渲染）、**在途任务**导致的入口禁用、刷新时的归位。**本期不做**：给**进度条**加一格「运行态」（六格只表达「最远已完成的里程碑」，塞进「正在跑」要改它的语义）；侧栏**角标**；顶部全局横幅；**跨标签页**同步（沿用既有取舍）；跨进程重启的接续（重启时在途任务已被判失败，见 §2.2）；后端接口与任务状态模型的任何改动。

**设计**：**运行视图**的渲染判据从「界面停在哪一页」扩成「界面停在哪一页 **或** 当前打开的这一份文档正有一支文档动作在途」。这是**兜底渲染**：相位仍然决定一切，只有「相位已经不在运行视图、而这一份确实有动作在跑」时才接管。前一半是界面相位、后一半是服务端事实；两者都成立时才重合，这也正是为什么需要把话说清——**在途任务**在跑、而**运行视图**不存在（用户切到别的阶段），是合法的组合，不能读成「任务没了」。

**接管的范围由「这个动作发起时会不会切进运行视图」回答**，是一张登记表（`JOB_KIND_NAVIGATES_TO_RUN_VIEW`），不是在这里手写几个特例：整篇生成（三份产物）、一键更新（走生成任务）、按澄清改写、AI 自行澄清、重审、按结论修复都在表内；**就地动作不在**——优化与对话都不切阶段、正文在原页上逐字变，把它们也接管会把过期黄条与「一键更新」一起顶掉，那是退步。这张表有一条守卫盯着（`dead-code.spec.ts`）：「源码里每一处 `job.start('<种类>')` 都必须在表里有分类」，新增一个动作却漏登记时用例会红——**一键更新**与**按澄清改写**都曾因为手写特例漏在外面，用户按下去、切走再切回来就什么也看不见了。

兜底渲染只在**同一份文档**上生效：一边在修 PRD、一边在看接口文档，界面不动。用户在这份文档上点「查看当前版本」时置起**压制位**，兜底渲染让位；它**不落库**，且只在「本次停留 + 本次任务」内有效，任务收尾、换了一支任务、切换方案、离开这份文档都会让它失效——默认落点必须稳定，否则用户永远不知道回到哪儿。一支修复任务在途时，三份文档的「修复 / 重新审核 / 保存编辑」一律**不可用**（不加说明文字、不弹提示）：任务种类之间的顶替不分文档，同一方案里两份同时发起会互相掐断，只拦被修的那一份等于给用户一条能掐掉自己任务的路径。运行视图的徽标按**动作**区分（修复中 / 重审中 / 优化中 / 改写中 / 生成中），不把四件事都叫「生成中」——修复与改写都不是「生成一份新文档」，混称会让用户以为自己的稿被整篇重做了。**一处已知边界**：一键更新在任务单上与普通生成**无法区分**（同一套请求体、同一个 kind `api-docs` / `prompts`），因此它的徽标显示「生成中」而不是「更新中」。要区分得让任务单记住「这次从哪来」，属加列级改动，本期不做。

**契约**：C-R1~C-R5（§4.3）不变；任务的对内对外形状（SSE 事件、状态接口、任务单投影）不变，本次不新增接口、不改迁移。修复收尾的落点沿用「用户此刻正看着这张页才回审阅页，否则不导航、只给现有完成提示」——与 §3.9 交付页「不自动跳转」是同一条裁决的两处应用。

**取舍**：选「运行视图跟随在途任务」而不选「给进度条加运行态」：后者要把「最远已完成里程碑」这层语义掰开，六格模型会被一个动作弄坏，而用户真正要的是「回到那一页」而不是「在进度条上看见它」。**何时改回来**：当用户真的需要在「不在那张页时」也知道有任务在跑（例如同一方案里同时有多支任务、或需要跨方案概览）——那时该加的是一条独立的状态展示，而不是把运行态塞进里程碑。选「压制位只在本次停留内有效、不落库」而不选「持久记住用户想看旧版」：持久化会把一个临时阅读意图升格成配置，于是「切回来落在哪」变成要解释的状态机；而默认落点稳定本身就是可用性。**何时改回来**：如果出现「修复要跑很久、用户反复在过程中读旧版」的真实抱怨，说明默认落点该改，而不是给压制位加持久化。选「修完不抢页面、不加『已修复』横幅」而不选「跳过去或全局提示」：跳转会**抢走**用户正在做的事，交付页那次已经为同一件事裁过一次；代价是「刚修过」没有主动提示，要靠版本历史与结论自己看出来——这个代价被接受。**何时改回来**：如果用户反馈「修完了不知道、一直以为还在修」，再加受众明确的提示（这条反馈本身就是改回来的判据）。选「按任务种类禁用三份入口」而不选「只禁用被修的那一份」：禁用要与服务端的顶替判据对齐，否则界面对用户撒谎。**何时改回来**：只可能在服务端把 `doc_kind` 并入顶替判据之后。选「结论写进现状架构文档的取舍节」而不选新立**架构决策**档案：本次不改对外契约与数据模型，属实施取舍。

### 5.12 审核 / 改写 / 修复统一为整篇（spec #75 收口）

**目标**：三份产物在「审核、改写、修复」这三件事上**只有一条路径**——整篇审一次、仅高严重度改写一次且改完不重审、修复整篇重写并追加版本；结论对三份**一字不差的形状**，一版一条。同时把前几票留下的分章残骸删干净，让读代码的人不再面对「读起来像接口、其实恒为空」的字段。

**范围**：结论形状（`review_data` 一处）、生成内审核与改写的事件语义、修复的写入语义（`mode="append"`）、重审的条件写、`failed_sections` / `completed_sections` 两个字段的删除（含迁移 `0008`）、前端结论面板的「整篇一条」。**本期不做**：审核结论的历史版本浏览、结论进交付包与管理端统计、按正文变化自动判定结论过期、审核 / 改写 / 修复的续写（它们要整段结果）、分章历史数据迁移（旧值随列一起删）。

**设计**：`document_review` 是**唯一**的审核实现：`review_messages` 组提示词、`parse_review_text` 解析、`review_data` 定形状，三个入口（生成内的 `stream_review_and_rewrite`、只审不改的 `stream_review_only`、修复后的那次重审）全部经由它；产物差异只由 `ProductContext` 表达（§3.8）。改写门槛只有一个判据 `review.triggers_rewrite(settings.review_rewrite_min_severity)`（默认 `high`），改写完不回审核——「改写 → 再审 → 再改」会让一次生成变成不可预期的多轮。修复是 `fix_document_stream` 的一次整篇重写 + 一次只审不改，落库走 `document_store.write_document(mode="append")`，与「重生成」的区别只在 `source`（`review_fix`）与「旧版仍在」。重审的写入是条件写（`expected_content_sha` + 事前比较两道），正文变了就 `CONTENT_CHANGED`、原结论保留（§3.8）。前端只有**一个**结论面板（`ReviewConclusionPanel`），三份产物共用；「修复」只在「有问题」可点、「重新审核」只在其余三态可点，条件与产物无关。

**契约**：检索面向外形状 = `kind / verdict / summary / issues / rewritten / reviewed_at / attempted`（C-R1：没有结论 ≠ 通过；`attempted` 是「审失败」与「没审」的唯一分界）；`generation_jobs` 不再有 `completed_sections` 列，`RunSummary` / 快照 / 结论里都不再有 `failed_sections`（C-R4 的落点从「字段留着但恒空」改成「字段不存在」）。

**取舍**：选「删字段」而不选「留着恒空」：恒空字段是有代价的——每个读它的人都要先查一次「为什么是空的」，而它承载的概念（分章）已经不存在；删除的代价是旧部署要多跑一条迁移（`0008` 删列，单向门，回滚靠备份），这比长期留着两个假接口便宜。选「保留分节改写」而不选「改写一律整篇重吐」：改写仍然只输出受影响的那几节、拼回整篇再整段覆盖（`part{replace}` 带的是完整正文，用户看不出分节），这是同一条链路上的一次性能优化、不是第二条语义；`where` 一条都定位不到、或拼回后短于 `_MIN_KEPT_RATIO` 时自动退回整篇重写（`DOC_SECTION_REWRITE_ENABLED` 是它的一键回退开关）。选「修复整篇重写」而不选「只改有问题的那几节」：一条结论描述的是**整篇**的质量，只改几节会把「新改的几节」与「没动的其余部分」拼成一份没人审过的正文；整篇重写至少保证这一版与新结论是同一轮产物。选「三份产物共用同一个面板 / 同一套按钮条件」而不选「按产物微调」：界面上的差异会让用户以为行为不同，而实际后台是同一条链路。

### 5.13 交互手感与动效令牌（spec #96）

**目标**：用户端弹层与状态切换不再是「能用但生硬」的；全站动效收敛到一组 CSS 令牌，减少动效有明确分类策略而不是一刀切。

**范围**：用户端弹窗 / 抽屉 / 侧栏 / 菜单 / 提示浮层的过渡；按压反馈与排版细则；reduced-motion 与无障碍（焦点、aria）；触屏门控与安全区；入口、进度、主题、流式的增补动效。**本期不做**：引入动效库、视觉重设计、完整 WCAG 审计、iPad / Android 全量适配、管理端体系改造（只加弹窗面板 120ms 与 hover 门控）。

**设计**：令牌先行——`--ease-smooth`（进场 / 按压）、`--ease-drawer`（抽屉 / 侧栏）；时长表为按压 120ms / 菜单 160ms / 遮罩 180ms / 弹窗面板 220ms / 抽屉 260ms / 提示进 200ms 出 150ms。弹层统一为「遮罩动透明度、面板动缩放」，弹窗是 transform-origin 的例外（不挂在触发按钮上，保持中心）；抽屉只动 `transform`，预览加宽等宽度变化瞬变。reduced-motion 改成分类策略：关位移动画、保留透明度与颜色，`.app-spinner` 是唯一保留旋转的例外（它是状态指示，不是致晕运动）。无障碍与动效同批交付：`aria-labelledby`、焦点陷阱与关闭归还、`aria-live`、`overscroll-behavior: contain`。
**布局**：进度条（`frontend/src/components/stages/ProgressSteps.vue`）是**吸顶顶栏**——`sticky top-0` + 不透明底色 `bg-bg` + 下沿 1px `border-line`，`-mx-4 px-4` 铺到 `<main>` 左右边（正文是 `px-4`，不铺出去则栏底只盖正文宽、两侧露出滚动内容），`z-20` 低于侧栏抽屉（30/40）与弹窗（50）。它是导航不是内容面板，因此与页面同色、不另起一块浮层。

**契约**：所有过渡必须列出具体属性，禁止 `transition: all`；新增过渡不得用裸 `transition` 工具类；只用语义令牌，未定义令牌类会回落 `currentColor`；`dark:` 只留给结构性判断与遮罩；管理端手写 `:hover` 一律包在 `(hover: hover) and (pointer: fine)` 内。配色同批收口：两端各用一套暖色令牌（纸面米白 + 暖灰文字 + 陶土强调），模板里不出现 `slate/sky/emerald/amber/rose` 原生色阶，语义色只走 `success/warning/danger` 令牌。

**取舍**：选 CSS 过渡而不选引入动效库——本次全部是一次性进出与状态切换，没有手势拖拽与可中断的动量，动效库的收益覆盖不了新增依赖与包体成本。选「宽度瞬变」而不选「宽度动画」——预览加宽是内容驱动的布局变化，动 `width` 会触发布局重排，视觉收益抵不过抖动风险。选「管理端弹窗只加面板 120ms」而不选「补全遮罩动画」——粗野风的层级靠色块与描边，遮罩淡入会削弱硬边；面板微浮现只解决「瞬间闪烁」这一个真实问题。

> 配色专项（同一轮内完成）：**弃用天蓝 + slate 冷灰**。那套组合是生成式界面最常见的默认值，看起来像没有做过选择；换成暖色之后，配色本身开始表达「文档工具」的判断。同时把管理端从「粗野海报」收到「安静的纸面」——1px 描边、柔投影、无实色页头带、正文级说明文字，`.brut-*` 只留命名、不再留笔重。因这次改色，模板里 40 余处原生色阶与 `dark:` 成对变体一并删掉，前端 CSS 从 82.93 kB 降到 72.07 kB。

#### 1 目标

三件事，按优先级：

1. **收敛**：`api/` / `services/` / `repositories/` 三层不再出现任何数据库品牌的痕迹。换库时只改一个模块，不改业务代码。
2. **前置声明**：模型层把"只对某个库成立"的约束写成显式声明（`with_variant`、collation），而不是散在实现里、靠人记。
3. **保住主路径**：收敛过程对当前 SQLite 部署**零行为变化**。任何会让 975 例测试变红、或让现有库结构对拍报漂移的改动，都不进本期。

##### 为什么要做，什么时候做

做这件事的理由**不是**"将来要换 MySQL"，而是它顺带解决两个既存问题：

- `upsert` 的方言 import 散在 3 个仓库里，每个新仓库都要自己记得"用 `sqlite_insert` 而不是 `insert`"，漏了会在运行时才炸；
- `schema_snapshot.py` 那 300 行 `PRAGMA` 实现让"结构对拍"本身依赖 SQLite，而它恰恰是**判断迁移是否安全**的工具——工具和被检查对象用了同一个数据库的私有接口，等于没有独立验证。

**本期不选目标库。** 方案的可移植性只到"接口干净"为止，不做"三库都能跑"的承诺——那需要 CI 矩阵，见第 5 节取舍。

#### 3 设计

##### 3.1 三层边界

同一个"方言问题"，实际落在三个互不相通的层次上。方案对每一层的态度不同：

| 层 | 例子 | 能不能收敛 | 归谁 |
|---|---|---|---|
| **查询表达式** | `select` / `where` / `join` / `session.exec` | 已经收敛（守卫 C1~C3 禁止 SQL 字符串） | 无需动作 |
| **语句构造** | upsert 的 `ON CONFLICT` / `ON DUPLICATE KEY` | 能收敛到 1 个函数 | D1 |
| **DDL 声明** | 列长度、`MEDIUMTEXT`、collation、部分索引 | 能"提前声明"，但要改就得连基线一起改 | D3 / D4 / 3.3 |
| **实例与连接** | `PRAGMA journal_mode` / `SET time_zone` | **不能**收敛 | 永久适配点 |
| **查询语义** | `LIKE` 的大小写敏感性、`ORDER BY` 的排序规则 | 不能收敛，只能显式化 | 见 3.6 |
| **事务语义** | 隔离级别、多写者并发 | **不能**收敛，只能显式加锁 | 见 3.6 |
| **数据库能力** | `TEXT` 不能整列建索引、`TEXT` 64KB 上限 | **不能**消除，只能换数据模型 | 换库那次 |

一条判断原则：**能在"我们写的代码"里解决的，收敛；只能靠"对方数据库支持"的，声明或改模型。**

##### 3.2 收敛点：`core/dialect.py`

唯一的品牌感知模块。对外只暴露两件事：

```
upsert_values(session, model, values, *, conflict_cols, update_cols=None)
upsert_select(session, select_stmt, model, *, conflict_cols, update_cols=None)
```

- `update_cols=None` 表示"冲突就什么都不做"（DO NOTHING）；给了列表就是 DO UPDATE。
- 两个入口的差别只在于"待插入的行从哪来"：`values` 用于常量行，`upsert_select` 用于 `INSERT ... SELECT`（`document_repo._ensure_document` 的归属校验就写在 SELECT 的 WHERE 里，这条结构必须保留）。

各方言的分支：

| 方言 | DO UPDATE | DO NOTHING |
|---|---|---|
| SQLite / PostgreSQL | `ON CONFLICT (cols) DO UPDATE SET … = excluded.…` | `ON CONFLICT (cols) DO NOTHING` |
| MySQL / MariaDB | `ON DUPLICATE KEY UPDATE col = VALUES(col)` | `ON DUPLICATE KEY UPDATE <pk> = <pk>`（no-op） |

**MySQL 的 DO NOTHING 刻意不用 `INSERT IGNORE`**，尽管它更短：`IGNORE` 会把"列超长、违反 NOT NULL"这类错误一起降级成警告，等于用一个静默的写失败换一行代码。no-op 更新只吃掉唯一冲突，其它错误照常抛。

##### 3.3 模型层：提前声明，而不是提前改

**能现在做的两件（SQLite 侧零变化）：**

1. 大文本列挂 MySQL 变体，SQLite 侧仍是 `TEXT`：

   ```
   Column(Text().with_variant(mysql.MEDIUMTEXT(), "mysql"), ...)
   ```

   只挂 4 列，依据是勘察报告的字节数：

   | 列 | 实测 max | 说明 |
   |---|---:|---|
   | `generation_jobs.draft_content` | 36,919 B | 草稿正文，已达 64KB 的 56% |
   | `document_versions.content` | 24,534 B | 一整篇 PRD，11.5k 汉字 |
   | `generation_jobs.completed_sections` | 15,777 B | 刚好在 16KB 线下，留一档余量（该列已随分章链路在 #94 删除，此行保留当时的实测依据） |
   | `solutions.data` | 0 B（本地库全空） | 整份会话快照，语义上必然更大，按最坏情况声明 |

   前两行是这条决策的全部依据：**中文一字 3 字节，64KB 只够 2 万字**。一份稍长的 PRD 就能撑满，而 `TEXT` 溢出在 MySQL 严格模式下是**写入失败**，不是截断。

2. 用户名唯一性显式声明大小写敏感：

   ```
   Column(Text, unique=True, mysql_collate="utf8mb4_0900_as_cs")
   ```

   全项目只有这一列需要：`login_failures.username` 的设计前提是"`users.username` 大小写敏感"，两者必须一致。SQLite 和 PostgreSQL 默认就是敏感的，所以这条声明只在 MySQL 下起作用——**它把"默认值恰好正确"变成了"显式正确"**。

**不能现在做的：列长度。**

`VARCHAR(n)` 在 SQLite 下会改变建表语句（`TEXT` → `VARCHAR(n)`），结构对拍会全表报漂移。行为虽然等价（两者的类型亲和性都是 TEXT，且 SQLite 不校验 n），但**基线一旦动，就失去了"结构没变"这个证据**。

所以长度档位只作为实施清单存在，等换库那次连同基线一起改。勘察给出的候选档位里，唯一定不下来的就是 `users.username`：

> 实测最大值 6 字符，但 auth 层**没有任何长度校验**（`max_length` 全项目搜不到）。按 6 定 `VARCHAR(32)` 是拿"当前数据恰好短"当保证。这一列的前置条件是**先补应用层校验**，然后才能定 n。

##### 3.4 算法换位：把时区换算搬出 SQL

现状：`admin_repo.py:286` 用 `func.substr(func.datetime(created_at, '+480 minutes'), 1, 10)` 分组。这是全项目**唯一**一处既依赖方言函数、又无法用方言分支优雅解决的查询——因为 `datetime()` / `DATE_ADD` / `::timestamp + interval` 三种写法的参数形态都不一样。

换法不是"写三个分支"，而是**换掉换算发生的位置**：

- 现在：SQL 给每一行加时区偏移，然后按结果分组。
- 改后：Python 先算好每个本地日对应的 UTC 区间边界，SQL 只做 `created_at >= ? AND < ?` 的范围判断，按区间 `case` 分桶。

三条好处，顺序即重要性：

1. **零方言函数**——只用比较运算，任何库都支持；
2. **任意分钟偏移都精确**——`tz_offset_minutes` 是参数，可能不是整小时（+5:30 这种）。按小时聚合再在 Python 里合并的方案在这里是错的：整小时桶在半小时偏移下会跨本地日；
3. **顺带修一个性能问题**——`GROUP BY datetime(...)` 是对函数分组，走不了索引排序；改后过滤条件就是纯列比较。

代价是这段 SQL 会变长（每个本地日一个 `case` 分支，30 天就是 30 个）。这是显式的、可读的复杂度，换掉了一个隐式的、只在某个库上正确的函数。

验证方式：同一份 SQLite 库，新旧两版各跑一遍，逐日逐指标比对。**必须逐指标**（`task_count` / 各状态计数 / 两种 token），因为这四个数是四个独立的 `case` 聚合，错一个不会报错，只会让看板上的数字悄悄不对。

##### 3.5 结构对拍：**实测否决**，保留 `PRAGMA` 实现

原计划把 `schema_snapshot.py` 那 300 行 `PRAGMA` 实现换成 `sqlalchemy.inspect`，
理由是"去掉循环论证"——现在用 SQLite 的私有接口检查 SQLite 的库结构，
工具与被检查对象共用同一套实现。方言中立只是附带好处。

**实测之后否决。** 探测脚本对现有库跑 `inspect(engine)`，拿到了三件事：

| 项 | `PRAGMA` | `inspect()` | 差在哪 |
|---|---|---|---|
| 外键的 `ON DELETE` | `CASCADE` / `SET NULL` 都能读到 | `options` 返回 `{}` | **级联规则完全丢失** |
| 部分索引的 `WHERE` | 从 `sqlite_master.sql` 取 | `dialect_options['sqlite_where']` 有值 | 能拿到，但那本身就是方言选项 |
| 列默认值 | `dflt_value` = `"'[]'"` / `'0'` | `default` = `"'[]'"` / `'0'` | 形态接近，可归一 |

第一行是致命项。级联规则是 `assert_schema_matches_models` **最重要**的一条判据——
`documents.current_version_id` 是 `SET NULL`、`document_versions.document_id` 是 `CASCADE`，
这两个写错任何一个，删除方案时会留下孤儿正文或误删正文，而两种错都不会当场报错。

换成 inspector 之后，两边（期望快照与实际快照）都不含 `ondelete`，
`diff_snapshots` 会**判它们相等**——判据不是变宽松了，是**这一项消失了**。
这类"改着改着把判据改没了"的退化，比原计划的循环论证更危险。

而第二行说明"方言中立"这个好处也不成立：部分索引的条件只能从 `dialect_options`
里拿，那本身就是 SQLite 专属的键。所谓中立，只是把 `PRAGMA` 换成了 `dialect_options`，
再补一个"外键要从 `PRAGMA` 另行读取"的分支——特化没有减少，只是更分散了。

**结论**：保留 `schema_snapshot.py` 的 `PRAGMA` 实现。它是**测试与启动校验**的工具，
不在业务路径上，方言特化在这里的代价是"少一层独立验证"，而不是"运行时出错"。
与之相比，丢掉外键级联检测的代价大得多。

> 这条是本次实施里唯一被实测推翻的方案。它也是一个提醒：**"换成官方抽象"不等于
> "更好"**——先量一下抽象层到底给了什么、又拿走了什么，再决定换不换。

###### 事务隔离：唯一"不报错、只在并发时偶发"的一类

SQLite 是**单写者**：同一时刻只有一个事务能写，序列化由数据库保证。所以这个项目里所有"先查、再判断、然后写"的路径，**从来没被并发检验过**——它们之所以正确，是因为写锁替它们排了队。

换成多写者之后，同样的代码会暴露。全项目 `with_for_update`、`isolation_level` 各 0 处，说明没有任何显式加锁。要审的路径：

| 路径 | 依赖的不变量 | 换库后的风险 |
|---|---|---|
| `generation_job_repo.supersede_active` + 紧接着的建任务 | 「同 owner + solution + kind 至多一个在途任务」 | 两个并发请求可能各自把旧任务置 `superseded`、然后各插一条 `pending`。不变量由应用层的两步操作维持，不是数据库约束 |
| `quota_service` 的额度检查 | 「今日任务数/`token` 数不超过上限」 | 先算已用量再放行，两个并发请求会都看到"还没超" |
| `chat_turn_repo.write` | 「同 job 同 role 至多一条」 | **已防御**：SAVEPOINT + 撞唯一索引回查，逻辑本身与库无关 |
| `document_repo._ensure_document` | 「同 solution 同 kind 至多一行」 | **已防御**：走 upsert，唯一约束兜底 |

所以真正裸露的是前两条。它们在单 worker 下也很难触发（并发度低），但"很难触发"和"不会触发"是两件事——MySQL 的默认隔离级别是 `REPEATABLE READ`，还会引入间隙锁与死锁（1213），后者需要重试包装。

###### `LIKE` 的大小写

| 库 | `LIKE '%admin%'` 能否匹配 `Admin` |
|---|---|
| SQLite | 能（ASCII 默认不区分；`case_sensitive_like` 默认为关） |
| MySQL | 能（取决于 collation，`ai_ci` 不区分） |
| PostgreSQL | **不能**（`LIKE` 区分大小写，需要 `ILIKE`） |

四处 `LIKE` 里有两处是**用户可见的搜索**（管理端按用户名搜任务、按关键字搜日志）。换到 PG 之后，"搜 admin 搜不到 Admin"会被当成 bug 报上来，而代码没改过一个字。

统一的做法是显式化：搜索一律 `lower(col).like(lower(pattern))`，或者按方言映射成 `ILIKE`。前者牺牲索引（两侧都要函数），后者要在 `core/dialect.py` 加一个 `ilike()`。**这属于换库那次的决定**，本期不做，但必须写进清单——因为它和 `TEXT` 索引是同一类东西：不会报错，只会让结果悄悄变。

C-D6 是 3.6 那两条裸露路径的收口。它不要求本期就加锁（单 worker 下没问题），要求的是**换库时不能靠"我们一直这么做也没出事"作为依据**——那句依据在 SQLite 上成立，恰恰是因为写锁。

C-D3 值得单独说一句：那 16 行 `2026-10-21T16:14:03.700+00:00Z` 正是 `utc_ms_text` 的 docstring 里明确要防的形态（`isoformat()` 对带时区的值输出 `+00:00`，再拼 `Z` 就成了两头不靠）。函数已经修了，但**旧数据还在库里**。这就是"勘察"比"看代码"多出来的东西——代码读起来是对的。

#### 5 取舍

##### 为什么不追求"零方言"

因为右边那一列不属于写法问题：

- `TEXT` 不能整列建索引 —— MySQL 的索引键有长度上限，`TEXT` 必须给前缀长度，主键完全不行；
- `TEXT` 64KB —— 存储规格，不是语法；
- collation —— 实例与列的排序规则，影响的是"什么叫相等"。

这些只能靠换数据模型（改 `VARCHAR(n)`、改 `MEDIUMTEXT`）绕过去，而换模型的代价会落在**当前唯一真实运行的 SQLite 路径**上。为不存在的第二个部署形态付日常维护成本，是负收益。

##### 为什么分两段

第一段（D1~D6）的目标是"接口干净"，可以用现有 975 例自证；第二段（改列类型、ETL）的目标是"在某目标库上真能跑"，**没有目标库就无法验证**。把两者混在一起做，第二段的每个决策都只能靠猜，而且猜错的表现为"上线那天才炸"。

##### 否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 全库把 `Text` 换成 `String(n)`，一次性通用 | 与现有 SQLite 基线直接冲突，等于立刻做一次全表迁移；且 n 依赖生产数据，本地库量不出来 |
| MySQL 的 DO NOTHING 用 `INSERT IGNORE` | 会把列超长、违反 NOT NULL 一并降级成警告，用静默失败换一行代码 |
| 在各仓库里写 `if dialect == ...` | 就是收敛前的状态，只是把 `sqlite_insert` 换成更长的分支 |
| 用 `MERGE` 语句做通用 upsert | MySQL 不支持 `MERGE`；SQLAlchemy 的 `Merge` 覆盖不全 |
| 时区聚合按小时分组后在 Python 合并 | 半小时偏移（+5:30）下整小时桶会跨本地日，统计学口径会错 |

## 附录 C：恢复演练要求（v7 §8.5 原文整段搬入）

> 正文由 v7 §8.5 及其前置结论逐字移入；「T17.6」是当时的排期编号，现行落点见 `docs/architecture/roadmap.md` 与 `deploy/backup.py`。

### 前置结论（v7 §8.4 末）

**回滚 = 恢复备份，不是跑反向迁移。**

补充一条 v7 新增的推论：**恢复之后第一次启动会再跑一次 `upgrade head`。**

| 备份里的 `alembic_version` | 恢复后的第一次启动 | 说明 |
| --- | --- | --- |
| 等于当前代码 head | `upgrade` 跑空 | 正常 |
| 比代码旧 | 自动补到 head | 正常，这正是迁移的用处 |
| **比代码新**（备份来自更新的版本） | 启动失败（Alembic 找不到对应 revision） | 说明「代码退得比数据还早」。必须先升代码，或接受用不上这份备份 |

所以**恢复演练必须用当前代码跑**，而不是「用备份那天的代码跑一遍」——后者验证的是别的东西。


### 8.5 恢复演练是验收项，不是可选项


「有备份」和「能恢复」是两件事。T17.6 的验收必须包含一次**完整演练**：

1. 停掉生产实例（或换一个空闲端口）；
2. 把一份备份恢复到临时库路径，权限设成 `prdwright`；
3. 用**当前代码**起一个只监听回环的实例（`DATABASE_URL` 指向临时恢复出来的库）；
4. `/health` 三项全绿、能登录、能看到方案列表、能打开一份文档的版本抽屉。

没演练过的备份，在真正需要它的那天只是个文件。
