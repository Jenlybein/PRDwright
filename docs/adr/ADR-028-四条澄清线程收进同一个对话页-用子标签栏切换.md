# ADR-028：四条澄清线程收进同一个对话页，用子标签栏切换

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

ADR-027 把 PRD 的澄清合进了主对话线程，但只在 PRD 上做——**接口文档 / 提示词仍走独立的 `clarifying` 页面**。它自己也在 Consequences 里写明了代价：「本期同时存在两条澄清路径，心智负担暂时是双份的」，并声明机制留待扩展。

这一版把扩展做了，触发点有三：

1. **同一件事写了两遍**。`ClarifyStage` 与 `ChatStage` 都在做「消息区 + 输入框 + 底栏主操作」，改一处要记得改另一处；连入口位置都是两套（PRD 在底栏次操作组、另两份在正文下方的普通区块）。
2. **刷新行为不一致**。`chatting` 随快照恢复；`clarifying` 当初被裁决为「不降级」，刷新即丢。同一个功能，三份文档里有一份的体验更差，而原因是历史路径不同而非设计意图。
3. **聊过什么无从分辨**。三条线程的历史散在「主时间线」与 `clarifyMessages` 两个地方，用户得自己记住「这段是在聊 PRD 还是接口文档」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持 ADR-027 的双路径 | 零改动 | 同一件事两套实现；刷新行为与入口位置都不一致；用户要自己记住在哪条线程上聊过 |
| B. 也搬进 `chatting`，但不做子标签，四条线程共用一条时间线 | 改动最小，删掉 `ClarifyStage` 即可 | 四条线程的消息混在一起，「这段是在聊 PRD 还是接口文档」无法分辨；底栏主操作也无法跟着线程切——只能永远显示「生成 PRD」 |
| **C. 搬进 `chatting` + 引入子标签栏，四条线程各自独立（推荐）** | 一个页面、一套实现；刷新与入口统一；底栏按线程给动作；标签本身即地图 | 前端多一层「当前线程」状态并要进快照；底栏与进度条都要按线程算 |

### Decision

**选 C。**

1. **一个对话页，四条线程**。`ChatStage = 'requirement' | 'prd-clarify' | 'api-docs-clarify' | 'prompts-clarify'`，`ViewState` 里的 `clarifying` 整个删掉，`ClarifyStage.vue` 一并删除。
2. **消息仍共用同一个 `messages` 数组**，每条打 `stage`；**对话区只渲染当前标签那一条线程**（按 `stage` 过滤）。共用数组是为了让「哪条线程聊过什么」有一个单一真源，而不是四条各有各的数组、再各自记得同步落库。
3. **标签常驻**：四条标签永远都在，未就绪的置灰、悬停给出理由（`title`）。理由是**标签本身就是地图**——藏起来用户就不知道后面还有哪些可以聊，而「四条线程」这个结构恰恰最该被一眼看见。
4. **`chatTab`（用户意图）与 `activeChatTab`（实际显示）分开**。文档还没生成时该标签置灰，显示归落到第一条可用线程，但 `chatTab` **保持原值不回写**——否则用户上次停在「接口澄清」、这次打开时接口文档尚未生成，意图就被永久抹掉了。
5. **底栏动作按线程算**：需求澄清是「重新开始 │ 改需求 │ 生成 PRD」；三条文档线程**只有**主操作「按澄清结果改写」。**澄清线程下不放「返回审阅」**——回审阅页靠顶部进度条，理由见下一条。
6. **回审阅页的唯一落点是进度条**（`ProgressSteps`），因此它的可点范围必须包含**当前所在的那一步**：对话页停在文档线程上时，高亮的正是那份文档的格子；若把「当前步」排除，这条路就成了死胡同——澄清线程的底栏里没有「返回」，进度条又点不回去。
7. **审阅页的澄清入口统一成同一个**：三份文档都是「和 AI 确认剩下的 N 个问题」，落点都是对话页对应的标签。PRD 那条仍在底栏次操作组、并在出现时**顶替**「返回」按钮（两者落点相同、名字近似，并排会让用户不知道点哪个），且只在 `entryMode === 'structured'` 下出现——PRD 快捷 / 提示词调试没有需求澄清那一段对话可回。
8. **整篇重生成才作废下游线程**：某一份文档被整篇重生成时，它自己这条线程与它下游的线程一起清掉（`dropChatThread`）；**就地改写（`optimize` / `clarify`）不作废任何线程**。

### Consequences

- **变容易**：澄清只有一个页面、一套实现，改一处就够；刷新行为与入口位置三份文档一致；底栏按线程给动作，「现在能干什么」看底栏就知道，不必先回忆自己在哪条线程上。
- **变困难**：`chatTab` / `conversationIds` 是新增的快照字段，过期快照要迁移（`clarifyMessages` / `clarifyConversationId` / `clarifyTarget` 按 `clarifyTarget` 重分发进四条线程，`'document'` 归一为 `'prd-clarify'`）；`ViewState` 少了一个值，但 `currentStepIndex` 要多一段「停在对话页的某条文档线程 → 映射回那份文档的步骤」的现算，否则进度条会算错；四条线程各有自己的 `streaming` / `chatError`，不能共用一个「发送中」。
- **中立**：后端一行没动——`doc-clarification` 档案、`CLARIFICATION_QUESTION_RULE`、`clarify` 任务、每条线程各自一条会话（`conversationIds`）全部沿用 ADR-027 的形态。这次只动「聊天区怎么摆」，不动「澄清怎么聊」。ADR-027 的「其余走独立页」被推翻，但它的另外两条（复用主线程、后端双会话）继续成立。
