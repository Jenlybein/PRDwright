# ADR-025：澄清以「对文档的逐条问答」形式进行，而不是生成时一次问完

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P4）

### Context

有了待确认清单（ADR-023），紧接着的问题是：**这些问题什么时候问、怎么问？**

两个现成的做法都不成立。「生成时一次问完」不现实——生成的过程中用户还没看到文档，指望他在写 PRD 的同时回答「第 6.1 节的指标口径」是反的。「让用户直接在正文里手改」也不行：改完之后，「为什么这么定」这个推理过程没有留下任何痕迹，下一个接手的人只能从结果反推。

而这份清单天然适合对话：它是**有限条**结构化问题，每条都有明确的对象（哪一章）和拍板人。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 生成时一次问完 | 不用新增界面 | 用户看不到文档，回答质量低；清单往往要等看完正文才判得清 |
| B. 让用户直接改正文 | 无新增流程 | 推理过程不留痕；改完清单过期（手改不重算清单） |
| **C. 独立的澄清对话 + 按结论就地改写（推荐）** | 问题逐条聊清楚、有记录；改写受约束、只动涉及章节；清单重算 | 多一个对话档案与阶段；改写质量依赖提示词约束；澄清会话要持久化 |

### Decision

**选 C，分「对话」与「改写」两半。**

1. **对话复用既有的会话框架，新增档案 `doc-clarification`**（人设 + 开场白，占位符 `{document}` / `{pending_items}`）。它与需求澄清**共用同一段提问规则常量**（`CLARIFICATION_QUESTION_RULE`）——历史上两处各写一个数字导致口径漂移，这次由共享常量把这件事从「靠人记得」变成「不可能写错」。
2. **`profile_key` 与模板占位符都是显式契约**：档案自己声明要用哪些占位符（`opening_fields`），服务层按声明取值；未注册的档案名直接 400、**不静默回退默认人设**。校验发生在构造 SSE 响应**之前**——进了流之后状态码恒为 200，400 就没意义了。
3. **改写走 `clarify` 任务（复用 job 框架），不是一次裸 SSE 请求**：改写可能跑很久，任务化之后刷新 / 断线只断订阅，后端照跑，重连凭 `activeJobId` 接上——与三份文档的生成同一套机制，不另造一套。
4. **改写规则写死在提示词里且必须可核对**：只改澄清涉及的章节、其余**逐字保留**（不覆盖用户手改）、已解答项从正文与清单一并移除、保持标题层级与结构、不足处继续标「待确认」不编造。末尾必须附**重算后**的清单——这就是「改写后重算」的落点。
5. **澄清会话的字段与需求澄清完全分开**（`clarifyMessages` / `clarifyConversationId` / `clarifyTarget`）。混在一起的话，「从对话回填需求摘要」那道闸门（ADR-011 的闸门 1）会把文档答疑也读成需求输入，Diff 里凭空冒出条目。
6. **不新增步骤**：澄清是对「当前这一份文档」做的事，进度条停在那一格上（`clarifying` 的步骤归属**按 `clarifyTarget` 现算**，而不是查静态表——否则澄清接口文档时进度条会跳回 PRD 那一格）。

### Consequences

- **变容易**：问题逐条有对象、有记录、有结论；改写范围受约束，用户不必担心稿子被整篇覆盖；澄清会话随快照持久化，刷新后接着聊。
- **变困难**：多一个对话档案、一个阶段、三个会话字段——而**加一个 `ViewState` 要同步改四处**，漏一处不报错、只表现为进度条算错或刷新后进不去（由一条不变量测试守着）；「只动涉及章节」这条**只能靠提示词约束**，代码层面保证不了，因此它被写进提示词、也被写进页面文案（提前说明比事后解释便宜）；清单文本要由前端摊平后随请求提交，多了一处「前端参与决定给模型看什么」的落点（只做摊平，不做语义判断）。
- **中立**：澄清不改变「谁拥有正文」——它写回的仍是 `documents`（ADR-021），只是多了一条会重算清单的写入路径，且这条路径与生成路径共用同一个收尾写入。
