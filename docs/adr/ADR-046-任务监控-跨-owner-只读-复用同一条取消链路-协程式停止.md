# ADR-046：任务监控「跨 owner 只读 + 复用同一条取消链路 + 协程式停止」

> 源：v4 层（原 `docs/architecture/v4/ADR.md`，已并入本目录）｜ [索引](./README.md)

**背景**：v4.5 T5-1 要回答三个运营问题——谁在跑、有没有卡死、最近谁失败了；
并允许管理员手动掐掉卡死任务。`generation_jobs` 已有状态、时间、Token 与错误码，
本期**不加表、不加状态值**，只补查询与干预。

**一、管理面查询跨 owner，边界在 `require_admin`。**

`generation_job_repo` 原有纪律是「每个方法第一个参数都是 `owner_id`，不留不过滤的逃生口」。
监控必须跨 owner，因此新增 `admin_list / admin_count / get_for_admin` 三个方法，
并在文件里显式标注「管理面、跨 owner、安全性由路由层保证」。
不把这层判断塞进仓储：仓储若自己判身份，就同时混进了「取数」与「授权」两件事，
而授权一旦在两层各写一遍，迟早有一处漏改。`reap_running` 是同类先例（系统级维护）。

**二、「卡死」看 `updated_at`，不看 `created_at`，且由服务端判定。**

正文流式写入时 `updated_at` 会持续刷新，它停住不动恰恰说明「不再产出」；
用 `created_at` 会把「跑得久但一直在写」的长文档误报成卡死。
阈值 `STUCK_MINUTES = 30` 先用常量：够覆盖最慢的单章，也不会短到让管理员对红色脱敏。
`is_stuck / stuck_minutes / duration_seconds` 全部由服务端算一次——前端自己算会因
浏览器与服务器时钟差几分钟，出现「列表说卡死、点取消却说还在跑」的矛盾。

**三、取消复用 `job_service.cancel_job`，只多一个 `message`。**

用户点「停止」与管理员清理走**同一条链路**：标记内存运行时 + 落库
`failed + error_code='CANCELLED'`。新增的只有 `message` 参数，让 `error_message`
能区分「用户停止了生成」与「管理员手动停止了任务」——两者终态相同，但追责时要知道是谁动的手。
**不新增 `cancelled` 状态值**：状态是前后端共享契约，多一个取值意味着每处分支都要改，
漏一处界面就停在「生成中」；取消原因放 `error_code` 是代价最小的做法。

取消是**协作式**的：任务在下一个 await 点才跳出。卡在纯同步阻塞上的任务不会立刻退出，
但库里已是终态，重启后不会再显示「生成中」——卡死最多是临时的。

**四、`cancelled=false` 是正常结果，不是错误。**

管理员点取消时任务可能刚好自然结束。返回 200 + `cancelled=false`，前端提示
「已经结束了，无需取消」。若报错，管理员会以为操作失败而反复点击。
任务不存在才是 404——静默成功会让人以为「已经掐掉了」。

**五、自动刷新用轮询，不用 SSE；只在「在飞」页提供批量清理。**

监控页每 10 秒重新拉一次列表（`setInterval` + 静默加载，不闪烁加载态）。
刻意不走 SSE：T4 已评估实时尾随「风险高、收益低」，而监控页的时效要求只是「分钟级」。
「取消全部卡死」只放在「在飞」页：失败页没有 running 数据，按钮会恒为（0），
反而暗示「没有卡死任务」。

### Consequences

**变容易**

- 管理员不必翻日志或数据库就能回答「现在谁在跑、哪条卡了、刚才为什么失败」。
- 取消与用户侧共用一条链路，不会出现「后台能停、但内存里还在写」的分叉。
- 每次取消都进 `admin_audit_log`（`job.cancel` / `job.cancel_stuck`），可追责。

**变难 / 代价**

- 跨 owner 查询打破了仓储原有纪律，靠「文件内标注 + 路由守卫」维持边界；
  新增管理面查询时必须放在同一段注释下，避免被误用到用户面。
- 批量清理按「最久优先」取前 500 条 running；单机在飞任务远超 500 时可能漏清，
  但那种规模下瓶颈已不在这个页面。
- 多 worker 部署下，取消只能标记**本进程**的运行时；库里的终态仍然正确，
  但另一进程的协程要等自己的下一次检查才会退出（与用户侧取消的限制相同）。

### 验证

- `test_admin_jobs_api.py`（11 条）：状态过滤 / 卡死按 `updated_at` 判定 /
  用户名与类型筛选 / 取消落库 `failed+CANCELLED` / 已结束返回 false /
  未知任务 404 / 批量只动卡死 / 审计 / 非管理员 403。
- 前端 `jobs.spec.ts`（8 条）：卡死标红、取消二次确认、`cancelled=false` 文案、
  后端回绝原样显示、批量取消、筛选参数、自动刷新按 10 秒重拉。
- 端到端（临时库 + uvicorn + 无头 Chrome）：造「卡死 / 在跑 / 失败」三类任务，
  API 返回 `is_stuck=true, stuck_minutes=120`；取消后运行列表 3→2，
  失败列表出现 `CANCELLED / 管理员手动停止了任务`。
