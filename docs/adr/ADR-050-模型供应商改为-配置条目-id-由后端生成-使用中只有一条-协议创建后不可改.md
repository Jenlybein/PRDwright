# ADR-050：模型供应商改为「配置条目」，id 由后端生成、使用中只有一条、协议创建后不可改

> 源：v4 层（原 `docs/architecture/v4/ADR.md`，已并入本目录）｜ [索引](./README.md)

### Status

Accepted（2026-10-22）

### Context

v16 的 `model_providers` 把「一家供应商 = 一个固定空位」当成了表结构：
`id` 就是厂商名（`ark` / `openai` / `anthropic` …），六行由迁移播种，`builtin` 标记它们「不许删」。
当时的隐含假设是「一个人只接一家」。真实使用很快打破它：

1. **同一家要配多条。** 「方舟-生产」与「方舟-测试」是两条不同的 endpoint / 模型 / 参数，
   而它们协议相同。id 由协议决定时，第二条无处安放——只能改那条共用的，于是测试一改
   生产就跟着变。
2. **「内置」这个锚点没有实际用处。** 它存在的理由只是「回到出厂状态」，而六行里
   五行是用户永远不用的。列表被它们占满，「哪些是我真配的」反而看不出来。
3. **回执说不清走了哪条。** 计量只记 `provider`（协议名）。同一协议两条配置时，
   「这次是谁在花钱」在账上无法回答，而事后改配置名就再也追不回来了。

三个候选：

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| A 保留六行，允许改 id | 让管理员把 `ark` 改名成 `ark-prod` | id 进了历史计量与任务回执，改名等于**重写历史**；而且「第二条」仍然只能靠在 id 里加后缀 |
| B 加 `(protocol, slot)` 唯一约束 | 一家允许多个固定槽位 | 槽位数是多少？没有答案；且「槽位 2 空着」是纯粹的表结构噪声 |
| **C 配置条目** | `id` 由后端生成（`cfg_xxx`），`name` 必填可重名，协议只属于这条配置 | —— |

### Decision

取 **C**，并把连带的口径一次定齐：

1. **`id` 由后端生成**（`cfg_` + 10 位十六进制）。同一协议可以有多行，让管理员手填 id
   只会撞名；而撞名后唯一可做的决定是「谁让」，没有业务价值。碰撞靠
   `sqlite3.IntegrityError` 重试 3 次兜底，而不是「先查再写」（后者有竞态）。
2. **`name` 必填、允许重名**。它只是给人看的标签（「方舟-生产」），**身份是 id**。
   拦重名会逼人起「方舟-2」这种谁也记不住的名字。
3. **`protocol` 创建后不可改**，改它显式报 400，而不是让仓储层静默丢字段。
   换协议等于换一家厂商：`max_tokens` / `thinking_enabled` / `extra` 的语义全变，
   就地改会留下「半新半旧」的字段，而错误要到某次生成才以「参数不认」的形式出现。
   静默丢的结果是「200 但没改」，比报错难查得多。
4. **「使用中」唯一，真源仍是 `system_config.active_provider_id`**（不在表里加
   `is_active`：那会允许「两行都是 1」）。⚠️ 判断某条是否使用中，读**原始指针**，
   不用 `config.active_provider`——那条配置一旦被停用，解析会回退到别的一条，
   于是「按解析结果判断」就会把悬空指针放过去，删完库里留下一个指向已删行的 key。
5. **所有条目一视同仁**：只有「使用中」的不能直删，其余随时可删。不再有
   「内置行」与「回到出厂状态」的锚点，`builtin` 列保留但一律为 0 且**代码不再读取**。
6. **`PRESETS` 降级为表单模板**，字段 `id` 改名 `key`。它只是「选一家自动填好协议、
   地址与变量名」的初值，创建后由后端发 id。名字必须与 id 区分开，否则前端会拿它当
   id 发请求。
7. **计量落 4 个快照列**（`generation_jobs`：`provider_protocol` / `provider_config_id` /
   `provider_name` / `provider_model`），**不是外键**。快照而非指针是这一层的既有纪律
   （`prompt_tokens` 同理）：配置事后改名或删掉，历史账单不该跟着变。
   `RunMeter` 与 `RunSummary` 同步拆成 `protocol` / `provider_config_id` / `provider_name`。
8. **迁移 v19（`provider_config_entries`）**：
   - 给 `generation_jobs` 补 4 列（`PRAGMA table_info` 守卫，`ADD COLUMN` 没有 `IF NOT EXISTS`）；
   - 从历史 `usage` JSON **回填** `provider_*`：`json_valid` + `json_type` 双重守卫，
     坏值跳过而不让整次迁移失败；只填 `provider_protocol = ''` 的行（幂等）；
   - 清掉六条播种行，判据是**四个条件同时成立**：
     `builtin = 1` **且** `created_at = updated_at`（从没被编辑过）**且** id 在播种清单里
     **且** **不是当前使用中的那条**。最后一条不能省——少了它会把用户唯一在用的
     那行删掉，装完就空了；
   - 其余 `builtin = 1` 一律置 0；指针指向已不存在的行时清空指针。
9. **回执解析只留一份**（`frontend/src/utils/runSummary.ts`）。事件与
   `documents.last_run_summary` 是**同一个 dict**（都是 snake_case），而前端原先两处各写
   一套、落库那侧直接断言成 camelCase 的 `RunSummary`，结果是**刷新页面后回执整块消失**
   且不报错。归一化两种键都认，缺字段只退化那一项。

### 本期不做

| 本期不做 | 理由 |
| --- | --- |
| 配置条目的「复制一份」按钮 | 与「新增时选同一个模板再改」等价，先看真实使用频率 |
| 按协议分组的折叠列表 | 条目数在个位数时分组只是多一层点击；等真到十几条再说 |
| `model_providers` 与任务的**外键** | 快照语义要求「配置删了账单还在」，外键会让删除变得不可能 |
| 管理员改密钥值（而非变量名） | 需要先解决加密存储与轮换（ADR-042 仍有效），与「多条配置」正交 |
| 把 `token_budget.evaluate(provider=...)` 参数改名为 `protocol` | 它的值域同时接受厂商名（`anthropic` / `openai` / `ark`）与协议名（`openai_compatible`），叫 `protocol` 反而不准；改为在 docstring 里写清值域并加一条守门用例 |
| 已删除配置的「撤销删除」 | 重新新增一条即可（30 秒的事），而回收站要引入软删除与清理策略 |

### Consequences

- **变容易**：同一家想配几条配几条；列表里只剩用户真配过的条目；回执上写得出
  「火山方舟 · doubao-…」，同一协议两条配置也能在账上分开。
- **变困难 / 必须记住**：
  - **装完列表是空的**。此时生成退回 `env:` 合成的降级项（`active_provider_id` 形如
    `env:ark`），它不是可编辑的条目。验收与排查的第一句话要改成「先在后台建一条」。
  - **`id` 不再是可读字符串**。凡是想「按 id 猜协议」的代码都会静默落空——
    `_resolve_active_provider` 的回退因此改成**按协议**匹配第一条可用条目，
    并保留 `openai → openai_compatible` 的别名表。
  - 测试里再没有「直接拿 `ark` 当 id 用」的写法：先 `create` 一条，再用返回的 id 操作。
    这不是用例啰嗦，而是真实前提——列表本来就是空的。
  - 消费方（前端、脚本）不得再读 `builtin`；接口已不返回，读到 `undefined` 的分支会静默失真。
- **迁移是不可逆的**（这是数据清理型迁移，与 schema 型不同）：六条播种行删除后无法从库里
  恢复，只能重新新增。因此删除判据刻意收紧到「四条件 AND」，并配套
  `test_v19_deletes_only_factory_seeds`（断言 `ark` 与被编辑过的行都活下来）与
  `test_v19_clears_dangling_active_pointer`。
- **测试陷阱（真踩过 / 想得到）**：
  - 「改坏也不红」的典型：删除判据少了「不是使用中」这一条，用例若只断言「播种行没了」
    就会绿着通过，而真实用户升级后列表被清空。
  - 回执解析只测 camelCase 夹具会全绿，而线上永远是 snake_case——真正的回归用例
    必须用后端那份形状（`runSummary.spec.ts` 的第一条 + `document-service.spec.ts`
    的「刷新后仍能读出」）。

### 补充（同日）：新增表单由「供应商」驱动

实现时确认的一处遗漏：v19 把「供应商」降级成一个标着「模板（只用来填表）」的下拉，
旁边还并排着协议、`base_url`、密钥变量名三个手填框。结果是**选了供应商仍然要手打
`ARK_API_KEY`**——而这三个字段本来就是「这家怎么接」的一组知识，拆开填只会得到
「ark 协议 + 火山地址 + DEEPSEEK_API_KEY」这种照抄文档都发现不了的错配。

定为：

1. **「供应商」是这张表单唯一的入口**（必选）。选中后协议、地址、变量名一起定下来。
   **没选供应商不给提交**：否则会得到一条「协议默认 `openai_compatible`、地址空着」的配置，
   看着建成了，第一次生成才报错，而报错里还看不出当初少选了一步。
2. **协议与密钥变量名都不进表单**。
   - 协议由供应商决定、创建后也不可改；
   - 变量名同样由供应商决定，它只是「去哪个环境变量取密钥」的指针——不是需要人
     来做的一个决定。管理界面不显示它，也就没有填错的机会。
   - 判据是**只读/禁用也算「给用户看见了」**：灰掉的下拉、`readonly` 的输入框都在暗示
     「这里本该能改」。真要表达「不可改」，就不渲染它，把信息放到展示区
     （协议在列表行与编辑面板标题、变量名在列表行元信息）。编辑面板同步照此办理，
     请求体里也不发这两个字段。
3. **下拉里没有「其他 / 自定义」**：预设即全部入口。要接自建接入点，选
   「本地 vLLM / Ollama」（不要密钥）或「自建网关（OpenAI 兼容，需密钥）」再改地址。
   这两条预设并列，正因为「要不要密钥」无法从协议推出来。
   ⚠️ 代价：**没被预设覆盖的厂商只能在预设上改地址**，而它的变量名也随预设走
   （例如接 Groq 得选带密钥的那条、把地址改掉）。这一取舍是为了让表单只剩能改的项。
4. **变量名取自预设并原样提交，包括空串**。前端不渲染它，但绝不能漏发：
   漏了配置照样建得出来，第一次生成才以「未指定密钥环境变量名」失败，而界面上无从修。
5. **`PROTOCOL_KEY_ENV_VARS` 只管「没传」**（脚本/第三方调 `POST /providers` 且
   `api_key_env_var=None`），按协议补默认值；**显式空串不补**——那是「不要密钥」的表达。
6. **空变量名 = 不需要密钥**，不是「配置漏了」。`lookup_provider_key` 给它占位值
   （OpenAI 兼容客户端要求 `api_key` 非空）。变量名写了、环境里没值的仍然报错并带
   变量名——那才是真正需要去 `.env` 补一行的情况。早先这里对空变量名直接抛错，
   等于把「本地模型」这条预设变成必挂的摆设。
