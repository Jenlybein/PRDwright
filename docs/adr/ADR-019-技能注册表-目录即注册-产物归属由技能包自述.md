# ADR-019：技能注册表——目录即注册，产物归属由技能包自述

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-15 裁决，随 R2-T9-1 落地）

### Context

到 R2-T7 为止，「哪个产物该用哪个技能包」这件事写在 Python 里，具体是三处：`job_service._resolve_skill_refs()` 里的 `if kind != "prd": return []`、`prd_skill.PRD_SKILL_NAME`、以及 `prd_skill.PRD_SKILL_ARTIFACTS`（列举了包内哪三个文件是必需的）。

后果不是「不好看」，而是一连串**耦合的代价**：想给接口文档也配一套规范，就得改这三处代码；改代码要重启后端；而重启会触发 `reap_orphans()`，把当时正在跑的生成任务一并判死。一个本该是「加个目录」的动作，被拖成了「改代码 + 重启 + 顺手废掉别人正在跑的生成」。

同一个毛病在 RAG 知识库（`core/api_doc_knowledge.json`）那里还有一份拷贝：它同样挂着进程级缓存、同样在缺失时静默降级，只是换了个文件埋着。**这两处的病根是同一个——「生成器该读哪套规范」这件事对程序是不可见的。**

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 维持现状（写死在 Python） | 零改动 | 加一个技能包要改三处代码并重启；重启会废掉正在跑的任务 |
| B. 新建集中注册表 `config/skills.yaml`（原设计稿主张） | 一处看全所有技能包 | 加技能包要同时加目录**和**改这个文件——即「两处同步」，而这正是要消灭的东西；`config/` 目录此前已随重构删除，重开一层目录成本更高 |
| **C. 技能包自述 + 扫描建索引（推荐）** | **加技能包 = 加目录**，只有一处真相；体检与启动日志自动跟上 | `skill.yaml` 从「给人看的元数据」升级为「给人看 + 给程序读的契约」，字段改动要当真 |
| D. 用正则读 `skill.yaml` 的新字段 | 不引依赖（当时只用正则读一个 `version`） | 要读的是嵌套列表（`references` 里每项的 `path`/`key`），正则一旦失配是**静默的**——正是本轮要消灭的那类问题 |

### Decision

**选 C，并且为它引入 PyYAML。**

1. **产物归属写在技能包的 `applies_to` 里**（取值与任务类型 `kind` 一致）。程序扫 `<skills 根目录>/*/skill.yaml` 建索引，`job_service` 不再有任何种类判断。**「目录即注册」，没有第二处需要同步修改的地方。**
2. **必需资源清单写在 `references` 里**，每项的 `key` 是生成管线取用时的语义键。缺 `key` 时按文件名推（`references/writing-rules.md` → `writing_rules`）——这是确定性规则而非猜测，但显式写出来更稳：它意味着改文件名不会悄悄改掉契约。
3. **显式引入 PyYAML**，不再用正则。理由不只是「嵌套列表难解析」，而是**正则失配是静默的**：格式一变，读到的是空列表而不是报错，于是技能包看起来「加载成功但没有资源」。把隐式依赖变成显式依赖，比省一个依赖划算。
4. **两类缓存，但资源存在性不进缓存**：资源内容与元数据解析结果都按文件戳缓存（沿用 ADR-017 的口径），可**资源删没删不进缓存**——删文件不会改 `skill.yaml`，把存在性判定缓存起来就会出现「文件已经没了却还在报一切正常」，那正是这套机制最该避免的静默。
5. **问题一律显式**：元数据读不动、必需资源缺失、**同一产物被多个技能包声明**，三类都进 `SkillProblem` 清单，由启动日志、`/health` 与 `PRDWRIGHT_SKILLS_STRICT` 消费。多包抢同一产物时行为是确定的（按名字取第一个），但仍然报出来——它几乎一定是配置出错。
6. **`prd_skill` 相应瘦身**：定位、加载、指纹、自检这些**所有技能包共用的能力**整体搬进 `skill_registry`；`prd_skill` 只留 PRD 专属的材料格式化与提示词拼接。资源清单不再在本文件里冗余一份。

### Consequences

- **变容易**：加一个技能包 = 加一个目录。体检和启动日志会自动列出它、它认领的产物、以及它是否完整，不必回来改代码。新增的产物类型只要有一个技能包声明 `applies_to`，回执上就会出现它的身份。
- **变困难**：`skill.yaml` 的字段从此是**契约**——改 `key` 等于改接口；多了一个 PyYAML 依赖；多了一层「扫描 → manifest」的间接，理解成本从「读常量」变成「读一个模块」。
- **中立**：**指纹口径刻意保持不变**（`sha256(版本 + 各资源路径与内容)[:12]`，按 `key` 排序）。于是仓库里 `prd-generator` 的指纹在重构前后仍是同一个值——历史回执上那个指纹继续可对得上，重构没有把「过去那份文档是按哪套写的」变成悬案。这一条在改动时被当成约束而不是巧合：它由一条断言真实技能包能注册的用例守着（防的是 `skill.yaml` 格式漂移）。
