# ADR-071：提速改判——不改 conftest，改默认并行（推翻 ADR-066 的假设）

> 源：v5 层（原 `docs/architecture/v5/ADR.md`，已并入本目录）｜ [索引](./README.md)

> 状态：已评审，已完成（T04）

### 背景：ADR-066 的假设被它自己定的实验推翻

ADR-066 推定「362.7 秒的主因是 863 次建库」，并把它写成方案甲（模板库 + 文件复制）
的前提。T04 按 ADR-066 自己定的判据先做测量，结果否掉了这个前提：

| 实验 | 结果 | 对假设的意义 |
| --- | --- | --- |
| A `--durations=30` | 头部 **37.22 / 18.13 / 3.16 / 3.03** 秒；top30 合计 ≈ 95.7 秒（28.5%），其余 833 条平均 0.29 秒/条 | **少数极慢 + 长尾轻**，不是「普遍慢」（原表述读错了，见下方更正） |
| B `init_schema` × 20 | 26.7 ms/次，× 867 = **23.1 秒** | 只占 8%，与 362 秒不同量级 → **假设不成立** |
| C 拆 lifespan 各步 | `client` 夹具净增 **147 ms/用例** | 真热点 = 起停整套应用 |

实验 C 的拆解（每个用例，单位 ms）：

| 步骤 | 耗时 |
| --- | --- |
| `init_schema`（`isolated_db` 调一次） | 25.8 |
| `init_schema`（lifespan 又调一次） | 25.8 |
| `run_migrations`（lifespan） | 25.2 |
| `reset_logging`（关日志线程的 join） | 50.6 |
| `ensure_bootstrap` + `reap_orphans` + `ensure_skills` | 13.7 |

> ⚠️ **更正：实验 A 的原表述读错了输出。** `--durations` 输出的是**降序**列表，
> 最初用 `tail -25` 看，读到的是**第 30 名**（1.84 秒），却被当成了「最慢 1.84 秒」，
> 于是写成「普遍慢，不是少数慢」。真实头部是 37.22 / 18.13 / 3.16 / 3.03 秒。
> **教训一句话：`--durations` 要看 `head`，不是 `tail`。**
>
> 提速决策不变（并行对长尾与中位数同时有效），但**归因修正**：存在 55 秒级的真实等待长尾
> （`llm_retry_delay` 默认 1.5s 叠加重试），不是「普遍慢」。这条长尾**并行压不掉**
> （单条用例不可分割），另立任务处理：测试注入 `LLM_RETRY_DELAY=0`、重试封装加可注入时钟。

**一处已定位的可回收成本（留给后续任务）**：那 37.22s 与 18.13s 的根因不是装置开销，是
`services/stream_reply.py:256-257` 的 `await asyncio.sleep(settings.llm_retry_delay)`，
默认 1.5 秒 × 约 24 次退避。`tests/test_llm_resilience.py:148` 已经用
`monkeypatch.setenv("LLM_RETRY_DELAY", "0")` 归零并写明理由（「测试不该为此变慢」）；
把它提到 `conftest.py` 的 `isolated_db`，**一行可换约 55 秒**，且产品代码里本就有
`if settings.llm_retry_delay > 0` 的守卫，delay=0 时不进 sleep 分支，行为等价。

### 顺带更正 ADR-066 的一处事实错误

ADR-066 方案甲的安全性论证第 2 条写「conftest 本来就不跑迁移（20 步迁移只在
`test_migrations.py` 里跑）」。**这条不成立**：`isolated_db` 只调 `init_schema`，
但 `main.py` 的 lifespan 每次都会调 `init_schema()` + `run_migrations()`，
所以每个用 `client` 的用例都真的把 20 步迁移铺了一遍（25.2 ms）。

也就是说方案甲没有它声称的那么「零行为变更」——它省得掉建库，省不掉迁移。

### 决策：默认按核数并行，三个数都不改

- 引入 `pytest-xdist`（dev 依赖），`addopts = "-n auto"`；
- 单文件调试用 `-n0` 关掉并行。Windows 上并行启动固定多花约 4.5 秒
  （实测单文件 5.9 → 10.4 秒），只跑十几个用例时那笔开销比省下的时间还多；
- **不改 `conftest.py`**、不动 `isolated_db` 的隔离粒度、不改产品代码。

为什么是并行，而不是继续压单例启动成本：

1. 单例成本里最大一块是 `reset_logging` 的 50.6 ms，而那是**产品的关服路径**
   （日志线程按 50 ms 切片等停止信号）。为测试去改产品关服逻辑，方向是反的；
2. 剩下要动的是 `init_schema` × 2 与 `run_migrations`，都在 lifespan 里——
   那是生产的启动路径，同样不该为测试让步；
3. 并行不改变任何一条用例的行为，只改变它们**在几个进程里跑**。
   用例本来就靠 `tmp_path` 做进程内隔离，跨进程隔离只会更强。

### 验收：不看总数，看逐条

| 项 | 要求 | 实测 |
| --- | --- | --- |
| 收集数 | 867 | 867 |
| 用例集合 | 与单进程基线一致 | 差异 **0** |
| 每条结果 | 与单进程基线一致 | 差异 **0** |
| 耗时 | ≤150 秒 | **71.9 / 72.6 秒**（两轮） |

并行最容易犯的错是「总数对得上、实际少跑或串味」，所以验收用 junit xml 逐条对拍，
不认 `867 passed` 这一行。

### 取舍

| 方案 | 否决理由 |
| --- | --- |
| 模板库 + 文件复制（原方案甲） | 只值 22.7 秒，却要往 conftest 加 session 级夹具；拿唯一的隔离地基换 8% |
| session 级共用库（方案乙） | ADR-066 已否决，并行之后更没必要 |
| 改产品代码压 `reset_logging` | 那是关服路径，为测试让步属于反向依赖 |
