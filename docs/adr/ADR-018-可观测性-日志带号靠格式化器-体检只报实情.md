# ADR-018：可观测性——日志带号靠格式化器，体检只报实情

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-15 裁决，随 R2-T7 落地）

### Context

`request_id` 早在 R1-T5 就贯通了：中间件生成、`ContextVar` 传递、响应头回写、回执上展示并允许用户选中复制。**唯独日志里没有它。** 后端一直在用 `logging` 的默认兜底输出——没有时间戳、没有来源、没有请求号，出问题时只能按时间顺序猜「这几行属于哪一次生成」。同一个号出现在响应头上、却在日志里搜不到，追踪链断在最后一步，那个号也就白给了。

另一半是 `/health`：它只回 `{"status":"ok"}`。可「进程活着」和「东西能用」是两回事——数据库连不上、密钥没配、技能包文件丢了，这三种情况下它都会高兴地回 `ok`，而这三种恰好覆盖了「明明起着却用不了」的绝大多数场面。

三个具体取舍需要裁决：日志默认用什么格式、请求号怎么进日志、体检要不要发真实调用。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 日志只输出 JSON | 一条路，没有分支差异 | 本地开发读一屏 JSON 极其痛苦，而排查绝大多数发生在本地 |
| B. 日志只输出文本 | 可读性最好 | 生产上没法直接喂采集端，将来接日志系统要返工 |
| **C. 双格式，同一组字段（推荐）** | 本地读文本、线上喂 JSON；切换只改一个环境变量 | 两个格式化器要一起维护，**字段集必须保持同步** |
| D. 请求号由每个 `logger.xxx` 调用手写 `extra` | 显式、不依赖隐式上下文 | 将来新增一处日志就会漏一处，且漏了不报错、只是静默少一个字段 |
| **E. 请求号由格式化器从上下文变量现取（推荐）** | 业务代码零改动；加/改字段只发生在一个地方 | 隐式依赖 `ContextVar`，后台任务里取不取得到要理解上下文复制机制 |
| F. `/health` 发真实调用探活 | 能发现密钥过期、额度耗尽这类静态检查看不出的问题 | 探针高频触发会按次烧额度；网络抖动会把可用的服务判成不健康 |
| **G. `/health` 只校验配置就位（推荐）** | 零成本、零抖动 | 查不出「密钥在但已失效」，**必须在文案里说清这一点** |

### Decision

**日志取 C + E，体检取 G。**

1. **双格式、同一组字段**：`LOG_FORMAT` 取 `text`（默认，给人看）或 `json`（部署建议）。两种格式带**完全相同的字段集**，所以「本地能看懂」与「线上能检索」不冲突——切换格式不丢信息。格式名认不出时退回 `text`：一个拼错的配置不该把服务拦在启动之外。
2. **请求号由格式化器现取，业务代码一行不改**：`request_id` 从 `ContextVar` 读，调用方写 `logger.info("...")` 就够了。这不只是图省事——**它把「漏字段」从「每处调用点都可能犯的错」变成了「一处不可能犯的错」**。同理，`extra=` 挂的业务字段（`job_id` / `step` / `status` …）按「排除 `LogRecord` 标准属性」的办法自动带出：将来新增字段不需要回来登记，而白名单式做法漏登记就静默丢字段。
3. **访问日志写在最外层中间件里**：`RequestIdMiddleware` 已是最外层，日志记在它的 `finally` 里，于是**被认证拦下的 401 也有记录**——排查「用户说打不开」时，第一个要确认的正是「请求到底有没有到过后端」。耗时口径是「从收到请求到**开始**回响应」，对 SSE 就是建立流的耗时；整段生成多久由 `run_summary` 记，两者刻意不混：混成一个字段会让人以为「一次 PRD 生成只花了 40 毫秒」。
4. **`uvicorn.access` 的级别抬到 WARNING**：它那条访问日志的信息量是我们这条的子集，而且拿不到 `request_id`（它在协议层记录，不经过请求中间件，上下文变量早已还原）。留着就是同一次请求两行、一行有号一行没号。抬级别而不是 `disabled = True`，因为后者会让「我的访问日志去哪了」变成一个要翻代码才能回答的问题。
5. **体检三项、恒返回 200**：数据库 / 供应商 / 技能包分开报，`status` 取 `ok` 或 `degraded`。不返回非 200——技能包缺失时服务仍可降级运行，把状态码打成失败会让编排器踢掉还能用的容器；而数据库挂了也不该靠状态码表达，调用方看 `checks` 就能分清，这正是这个接口存在的意义。
6. **供应商一项只校验配置、不发真实调用**，`detail` 里如实写明「仅校验配置，未发起真实调用」。**不诚实的绿灯比红灯更贵**：它会让人在明知失败的时候先去怀疑别的地方。不报「备用供应商」是因为自动 failover 已随 ADR-016 取消，预警没有了对象。

### Consequences

- **变容易**：拿到回执上那个号就能在日志里搜出这一次生成的全部记录；「用不了」时第一眼分清是数据库、密钥还是技能包；日志结构化之后，将来接采集端不必改业务代码。
- **变困难**：两个格式化器要一起维护、字段集必须同步（靠测试守住：同一条记录在两种格式下都要取到同一组字段）；`request_id` 走隐式上下文，理解它依赖对 `ContextVar` 任务复制的认识。
- **中立**：仓库里已有的 `logger.warning(...)` 调用点**没有一个是为此改的**——它们自动获得请求号，这正是取 E 而不是 D 的回报。反过来，任何「靠上下文悄悄生效」的机制都有同一个代价：不看格式化器就看不出号是从哪来的，所以 `core/logging_setup.py` 的模块文档写清了整条链路。
