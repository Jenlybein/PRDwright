# ADR-034：快捷流程并入同一条管线，审阅页的澄清入口拆成「自己去答」与「让 AI 拍板」

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-17 裁决并落地）

### Context

ADR-031 把入口页重排成两组四叶子之后，「快捷流程」是一条**岔出去的短链**：一段话 → 直接逐章
生成 PRD，进度条只有四步、没有对话、没有澄清、只要 PRD 就算交付完成。实际用下来暴露两个问题：

1. **它省掉的正是最有价值的那一步**。结构化表单的作用是「把话说全」，而走快捷入口的用户往往说得
   最少——真正该补的是追问，不是省掉追问。同一段话走快捷流程产出的 PRD 明显更空，「待确认」
   也更多，用户拿到手还得自己回头找答案。
2. **两条链的差异散落在十来处配置里**（`MODE_STEP_IDS` / `REQUIRED_DOCS` / `STEP_OF_STATE` /
   完成判定 / 审阅页文案……），每加一个阶段要在两个地方各改一次；漏一处**不报错**，只表现为
   进度条算错或完成条件不认。

与此同时，审阅页的澄清入口只有一个按钮：**「回到对话，确认剩下的 N 个问题」**。它把**条数**写进
按钮文案，N 一变按钮宽度就抖；更关键的是它默认「澄清 = 用户自己去聊」，而很多待确认项（分页上限、
超时时间、重试次数）本来就是「给我一个行业默认值就行」的问题，把用户拽进一轮对话是浪费。

### Options

**关于快捷流程**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 保持现状（短链） | 快 | 省掉的正是补全需求的机会；两条链继续各自演化 |
| B. 给快捷流程单独复制一份对话页/进度条 | 两边互不牵连 | 复制的是**最容易写歪**的那部分（断线重试、半截内容、消息分线），改一处漏一处 |
| **C. 并进同一条管线，只换第一步的输入（推荐）** | 「有对话、有澄清、三份齐备」全部免费获得；差异只剩输入映射与两个开关 | 需要一处「极简输入 → 答案字典」的映射，且要保证不把空字段当成「用户答了空」 |

**关于澄清入口**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 保持一个按钮，条数留在文案里 | 改动最小 | 按钮宽度随条数抖动；只有一个出口，不想自己答的人没有退路 |
| B. 拆成两个按钮，条数放按钮旁 | 出口清晰（自己答 / 让 AI 拍板）；动作与状态分离 | 多一个任务类型 |
| C. 两个按钮 + 新开一个「AI 拍板」页面 | 可以展示拍板过程 | 又是一条新链路（新 ViewState、新阶段），与 ADR-015「操作只在底栏」冲突 |

### Decision

**快捷流程选 C，澄清入口选 B。**

> ⚠️ **本文有两处已被文末「修订（2026-10-20）」改动**：决策 1/2 里的「快捷流程也有需求澄清对话」
> 当天被撤回（改为「一段话直接进生成」），相关文案与进度条步数一并调整。照读决策 1/2 会看到
> 已经不成立的说法——以修订段为准。

1. **快捷流程 = 同一条管线，只换第一步输入**。`MODE_STEP_IDS['prd-quick']` 与 `structured`
   同值、`REQUIRED_DOCS` 同值、`STEP_OF_STATE['prd-quick'] = 'form'`、`hasRequirementChat()`
   认它。复用靠**共享配置**达成，不靠任何「if 快捷流程」的分支散落各处。

2. **差异只有三处，且都在数据层**：① `buildQuickAnswers` 只映射两个题号（`product_name` /
   `problem_to_solve`），其余题目对后端就是「问了没答」，正好成为追问清单；② 跳过闸门①
   （快捷入口没有结构化摘要可供回填）；③ 请求体带 `review_enabled: false`。

3. **关掉逐章审核就必须连 `review` 结论事件一起关**。没审却报一句「共 0 个待处理问题」，
   会被读成「审过了、没问题」——那是**假信号**，比不报更糟。`review_enabled` 走**请求体**
   而不是改共享单例：`_get_section_writer(None)` 才返回缓存实例，显式值构造临时实例，
   避免两个并发的 PRD 任务互相污染开关。

4. **审阅页拆两个按钮**：「前往澄清问题」（进当前那份文档的澄清线程）与「AI 自行澄清」；
   剩余条数是**独立芯片**（`#hint` 槽）。按钮名一旦带数字，宽度会随条数抖动，而按钮是**动作**、
   数字是**状态**，两者分开才读得清。落点相同的两种布局规则（顶替「返回」/ `keepBackButton`
   时并存）不变。

5. **「AI 自行澄清」是一个 `auto_clarify` 任务，不开对话**。它拿正文 + 清单，用
   `AUTO_CLARIFY_PROMPT` 让模型以「资深产品负责人」身份逐条拍板：必须给结论、取最保守的通用
   默认值、**不编造具体数字/主体/域名**、只改受影响的地方、清单只留真答不了的。落地视图复用
   `generating-<kind>`，完成后回审阅页——不新开一条链路。

6. **两条改写链路共用一段收尾**（`_rewrite_stream`）：流式 `chunk` 先过抑制器、`done` 时再
   `extract` 一次，得到干净正文 + 重算后的清单。澄清改写与 AI 拍板只差**提示词**；收尾各写一遍，
   「换了正文却忘了重算清单」就有了落脚点。

7. **清单以结构化数据交给后端**（`pending_items: list[dict]`），渲染成人话由
   `format_pending_items()` 负责。它与 `render_spec()` 是一对——后者教模型**产出**清单，
   前者把**已有的**清单念给它听。前端依旧不参与任何措辞（ADR-010）。

### Consequences

- **变容易**：快捷入口自动获得「AI 对话 → 需求澄清 → 三份齐备」的完整能力；进度条、完成条件、
  交付判定全都只有一份实现。用户不想答的问题有了另一个出口。
- **变困难 / 新债**：① 「AI 自行澄清」多一次模型调用，且**结果不可预本地校验**——它可能把
  一个本该由用户提供的事实「编」出来。目前只靠提示词规则兜（不编造数字/主体/域名）与
  「清单只留真答不了的」，没有硬校验；② `DocKind` 多了一个**动作**（`auto-clarify`），
  与两份「东西」并列，判断「哪一份」仍必须用 `isDocumentKind`；③ 快捷入口的主按钮与页面标题
  都改了文案（「直接生成 PRD」→「一句话描述需求」/「提交需求，开始 AI 澄清」），凡引用旧文案的
  地方都要同步。
- **中立**：后端 schema 只加了两列可选字段（`pending_items` / `review_enabled`），既有
  `clarify` 路径逐字节不动；`format_pending_items` 是纯新增函数。
- **用例**：后端 **498**、前端 **601**（后端新增 12 例：`test_auto_clarify.py` 7、
  `format_pending_items` 4、「审核关闭不发结论」1；前端新增 3 例：`autoClarify` 端到端 2、
  「快捷流程不显示需求澄清标签」1，另有 `hasRequirementChat` 1 例与按新语义订正的既有用例；
  `buildQuickAnswers` 的 4 例随该函数退役一并删除）。

### 修订（2026-10-20）：快捷流程**不要**需求澄清对话

决策 1/2 里「快捷流程复用需求澄清对话」这一半，当天就被撤回了。用户的原话是
「输入完极简需求之后直接进入 PRD 生成」——**选快捷入口的人就是不想多聊几轮**，
把追问塞回来等于取消这条路存在的理由。

改动只有三处，方向都是「减」，因此不改既有结论的其余部分：

1. **`hasRequirementChat()` 只认 `structured`**。快捷入口不再有那条线程；`MODE_STEP_IDS['prd-quick']`
   同步去掉 `chatting` 一格（六步 → 五步）。⚠️ **如实少一格**，而不是留一格永远点不亮的步骤：
   进度条是地图，画一条走不通的路比少画一条更糟。文档澄清仍走对话页，但它不是主线上的独立
   一站——停在文档线程上时进度条按那份文档的审阅步算（`stores/workflow.ts::currentStepIndex`
   的既有特例），因此去掉 `chatting` 不会让它错格。
2. **`AppV2` 不再给对话页传四条线程**：`chatTabs` 按模式过滤，快捷流程与两个导入入口只有三条
   文档线程。刻意**不渲染成禁用态**——`ChatThreadTabs` 的「常驻 + 置灰给理由」是为「以后会就绪」
   设计的，而这一格永远不会就绪，留着只会让人以为少了什么。
3. **入口按钮回到「生成 PRD」**，页面标题回到「直接生成 PRD」；`handleGenerateQuickPrd` 撤销，
   统一走 `handleGeneratePrd`（它把「快捷流程」的分支放在 `canGeneratePrd` 守卫**之前**——
   那条守卫的前提是「需求线程里至少有一轮 AI 回复」，快捷流程压根没有需求线程）。
   `buildQuickAnswers` 随之退役（它只为「提交答案开对话」而存在），连同 4 条用例一起删除。

**决策 2 不变**：`review_enabled: false` 依旧——「不追问」与「不审不改」是两件事，用户要的是两者。
缺的信息因此全部落到「待确认」清单上，正好由审阅页的「AI 自行澄清」一把拍板（决策 5）。

### 修订（2026-10-20 深夜）：两个澄清按钮叠成一列、加确认框、撤掉重复的「返回」

三处都是形状上的收敛，不动任何决策的实质：

1. **两个按钮上下叠成一列，合起来仍只占一个按钮的高度**（`h-[38px]`，即 `AppButton` 的 `md`
   实测高度，含边框）。它们回答的是同一个问题「这批待确认项怎么办」，只是出面的人不同；
   并排时四个元素挤在一行，叠起来又把底栏撑高一倍。折中是**带分隔线的双行块**——
   `divide-y` 加在子元素上（不额外插 div，否则两行高度不等），容器锁高、`flex-1` 均分。
2. **「AI 自行澄清」先弹确认框**。它会**直接改写正文**且就地改当前版本（不自动留旧稿），
   一次点击就发生太轻了。弹窗写清三件事：会做什么（逐条拍板并写进正文）、按什么规矩做
   （最保守的默认值、不编造具体数字/主体/域名）、不会做什么（真需要用户提供事实的仍留在
   清单里），并提示「想留原稿先在『版本』里存一版」。⚠️ 这句提示是**必须**的：就地改写不留
   旧版本，不能让用户以为随时能回滚。
3. **撤掉与进度条重复的「返回」**。两个从零创建的入口，录入页就是进度条第 1 步「描述产品」，
   点一下就回去，底栏再放一个「返回描述 / 返回对话」纯属重复。判据抽成
   `inputPageOnBar(mode)` → 审阅页 / **生成中** / **交付页**三个视图的 `hideBack`（漏掉后两个，
   用户在生成中与交付页仍会看到一个「返回描述」）。**两个导入入口照留**：它们的录入页
   （贴 PRD / 贴两份）不在进度条上，删了就是死路。生成中那一页的特殊之处是**整条底栏都不渲染**
   ——那里原本只有「返回」一个按钮，只藏按钮会留下一条空栏。
   ⚠️ 配套修了一处真 bug：`handleStepClick` 原来把步骤 id 直接当阶段用，快捷流程点
   「描述产品」会被送到**结构化表单**——而这一格正是撤掉「返回描述」后的唯一退路，送错等于没给退路。
### 修订（2026-10-21）：两处口径回补——「AI 对话」那格补回、快捷流程的后两份也一遍过

上一版修订把 `MODE_STEP_IDS['prd-quick']` 里的 `chatting` 去掉了，方向对了一半，但落下两个坑：

1. **「AI 对话」那一格必须补回**（六步而不是五步）。去掉它之后的症状不是「少一格」这么轻：
   `stepIndexOf('chatting', 'prd-quick')` 找不到该步就返回 `-1` 并归零，于是**用户在文档澄清
   页里聊天时，进度条高亮的是第 1 步「描述产品」**——一个明显错位的状态。修正后这一格的含义
   也就明确了：快捷流程没有**需求澄清**线程（`hasRequirementChat` 依旧只认 `structured`），
   但「AI 对话」承载的是**文档澄清**那三条线程——它们本来就在同一个对话页上。
   ⚠️ 教训：进度条是「阶段 → 位置」的映射表，删一格之前先问「这个阶段还可能被谁访问到」，
   而不是只看主线顺序。
2. **快捷流程的「不审不改」只对 PRD 生效过**。接口文档与提示词走的是另一条整篇链路
   （`generate_api_docs_stream` / `generate_prompts_stream` → `stream_review_and_rewrite`），
   它们的 `review_enabled` 从来没被接进去，因此快捷流程里 PRD 一遍过、后两份照样「审一次 →
   再改一轮」。修复方式是把同一个请求字段接到底：`job_service._build_event_stream` 对
   `api_docs` / `prompts` 两种 kind 也透传 `review_enabled`，两份产物各自在
   `review_enabled_for_whole_document()` 里判定。
   - 默认口径与 PRD **故意不同**：这两份没有对应的配置开关，`None` 一律视为**开启**
     （「只有 `False` 才是关」）——漏传字段不能悄悄把产出质量降一档；
   - 关掉时**连 `review` 结论事件一起不发**，与 PRD 侧同口径：只跳调用、照样发一条「通过」的
     结论，会被读成「审过了、没问题」，是假信号。
### 修订（2026-10-21 续）：界面上的「审核 / 改写」也要一并撤掉

后端跳过调用之后，前端还留着两处「画了走不通的路」的阶段指示，一并按入口裁剪：

1. **`DocPhaseProgress`（接口文档 / 提示词的胶囊条）**：原本写死「生成 → 审核 → 改写 → 完成」。
   快捷流程下后两格永远走不到，用户会读成「还没审到」而不是「这次不审」。
   现在由 `withReview` 决定：为 false 时只画「生成 → 完成」两格。
2. **`PrdProgress`（PRD 管道看板）**：四列「生成 / 审核 / 改写 / 定稿」，快捷流程下中间两列恒为 0，
   同样裁成「生成 / 定稿」两列（网格列数随之从 `grid-cols-4` 变 `grid-cols-2`）。

判据收在状态机里（`hasDocumentReview(mode)`，只有 `prd-quick` 为例外），由 `AppV2` 传给
`GeneratingStage`，再由它转发给两个子组件——**不允许**子组件自己去看入口模式。
写成黑名单而不是白名单：将来加新入口默认带上复核，漏配的代价只是多等一会儿，反过来则悄悄
把产出质量降了一档。

⚠️ **踩到一个 Vue 陷阱，值得记**：`withReview?: boolean` 这种「默认该开」的布尔 prop，
**未传时会被 Vue 自动转成 `false`**（Boolean casting），于是「没传」等于「关掉复核」，
完整流程的四车道被悄悄砍成两条——第一批用例正是靠这个才发现。修法是**显式给默认值**
（`withDefaults(..., { withReview: true })`）。本项目里凡「默认开」的开关 prop 都照此办理。
