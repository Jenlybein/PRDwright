# ADR-095：大段文本上限 = 60KB（字节），闸门在应用层

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：已定（v8）。实施于 `core/limits.py`。

### 背景

四列大文本（`document_versions.content`、`generation_jobs.draft_content`、
`generation_jobs.completed_sections`、`solutions.data`）此前只有"数据库容得下"
这一条约束：SQLite 不校验长度，MySQL 的 `TEXT` 是 64KB、`MEDIUMTEXT` 是 16MB。
产品层没有口径，于是"能存多少"完全由列类型决定。

两种可选口径：

1. **按字符**（"最多 6 万字"）——贴近人的直觉；
2. **按字节**（"最多 60KB"）——贴近数据库的计量方式。

### 决策

**按字节，上限 60 × 1024 = 61,440。**

理由是"决定能不能存下的是字节"：中文一个字 3 字节，按字符设限会让同一条规则
在中英文上给出三倍容量差——"6 万字"的中文是 180KB，早就越过 MySQL `TEXT` 的 64KB。

闸门放在 `core/limits.py::ensure_text_within_limit`，由仓储入口调用；超限抛
`AppError(INVALID_REQUEST)`，文案带**实际字节数与上限**（只说"太长了"会让人反复试）。

复用 `INVALID_REQUEST` 而不新增错误码：`core/errors.py` 明确要求成员数保持 9 个，
且前端对"内容太长"与"请求不合法"是同一个处理分支。

### 为什么不用列类型当闸门

列类型是**容量**，不是**约束**。列仍然是 `MEDIUMTEXT`，意义是"别让类型成为最后一道
报错的地方"——万一某条写入路径漏了校验，16MB 的余量让人还有机会在日志里发现，
而不是当场 `Data too long`。60KB 只由 `core/limits.py` 一个常量执行。

### 推论

1. `solutions.data` **已退役**（`solution_repo.create` 写空串、`update` 刻意不碰它），
   不设闸门。列类型保留大容量只是"别再为它改一次基线"。
2. 超长会让 `persist_progress`（每 300ms 一次）抛错，进而让生成任务失败。这是**有意**
   的：静默截断会丢掉用户唯一在乎的产物，"存了一半"比"没存进去"更糟。
3. **余量偏紧，需要留意**：现有数据最大 36.9KB，60KB 只有 1.6 倍余量；而导出测试
   原本造的是 128KB 正文，说明有人预期这个量级。若线上真出现超限，第一反应应是
   评估把上限提到 256KB（仍在 `MEDIUMTEXT` 内，只改一个常量），而不是改列类型。
4. `persist_progress` 每 300ms 写一次，闸门因此带快速路径：字符数不超过
   `60KB / 4` 时直接放行，不做 `encode` 几十 KB 的浪费。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 按字符设 6 万 | 中英文容量差三倍，且 6 万汉字已越过 `TEXT` 上限 |
| 只在文档正文上卡，草稿不卡 | 草稿是正文的来源，源头不卡等于没卡 |
| 超限时截断并告警 | 静默丢内容，用户拿到的是"看起来成功"的半篇 PRD |
| 用 `VARCHAR(61440)` 当容器 | utf8mb4 下 `VARCHAR(61440)` 最大 245,760 字节，超过 MySQL 行上限 65,535，建表直接失败 |
