# ADR 0004：用户端可读性与文案纪律

- 编号：**0004**
- 状态：已采纳（代码已落地于工作区，未提交；守卫用例 `src/__tests__/readability.spec.ts` 已生效）
- 范围：用户端（`frontend/`）的字号下限、文案取舍、必填类颜色的语义化、正文行长、点击区与窄屏溢出
- 参照：`design/prdwright-clone`（与真实前端逐屏对齐的静态复刻稿，带 `tokens.css` 与体检脚本）

---

## 决策

1. **字号下限 12px**：`text-[10px]` / `text-[11px]` 在组件里全面退役（38 处 → 12px）。
   放不下就改布局，不许靠缩字号塞内容。守卫用例扫描 `components/**/*.vue`，出现即为红灯。
2. **文案纪律**：删三类字——① 标语（品牌副标题、页面标题下的说明段、入口分组的副标题）；
   ② 解释已知内容的提示句（「可分别下载为 Markdown」「若不满意选项，可以自行在输入框输入想法」）；
   ③ 重复的次要标签（「必填，AI 主要依据这些信息生成文档」——徽标已写「必填」）。
   **信息不是填充**：破坏性动作的后果（「停止后已写出的内容会保留」）、续写状态（「正文较长，已自动续写到第 N 段」）、
   校验错误与空态说明一律保留。
3. **必填类提示走语义令牌**：`text-red-500` / `text-rose-500` 与 `bg-red-50 … ring-red-200` 换成
   `text-danger-fg` / `bg-danger-surface` / `ring-danger-line`，删除成对的 `dark:` 变体（令牌自己换值）。
   对比度从 3.5–3.8:1 抬到 7.6:1，暗色下同样达标。守卫用例禁止裸 `text-(red|rose)-500` 回流。
4. **暗色两处取值修正**：`--ui-on-accent` 由 `#2b1508` 改为 `#ffffff`（深棕压陶土主色只有 2.9:1）；
   `--ui-subtle` 由 `#9d9488` 抬到 `#a8a29a`（4.3 → 5.2:1）。守卫用例断言这两条。
5. **正文行长按元素收，不动骨架**：`max-w-3xl`（768px）是整页骨架，收它会连带所有卡片。
   - 审核问题描述：`<p>` 加 `max-w-[44em]`（14px × 44 ≈ 616px ≈ 44 个汉字），左边那根规则线仍由 `ul` 画满；
   - 文档正文：卡片保持满宽，`px-5` 换成 `px-[clamp(1.25rem,8vw,3.75rem)]`，以内外边距做版心，窄屏自动收紧。
6. **点击区 ≥24×24**：模块 chip 的「×」由 8×16 改为 24×24；「批量粘贴导入」文字按钮补 `px-1 py-1`。
7. **窄屏不截断**：进度条 nav 加 `overflow-x-auto`，390px 下第 5/6 格不再被切掉。
8. **文案改动必须同步测试**：四类断言（登记表组说明、指路文案、粘贴页解释句、大纲图例）改为
   「不再出现」的断言，而不是整条删掉——把「决定」也钉住。

---

## 背景

这一轮的输入不是需求票，而是**设计复刻稿的体检结果**：把 `frontend/` 逐屏复刻成静态稿后，用无头浏览器按真实尺寸实测，
查出四类事实：

- 38 处 10–11px 标签，中文下糊成一片；
- 必填星号与「必填」徽标只有 3.5–3.8:1（`text-red-500` on white / `bg-red-50`），暗色主按钮 2.9:1（深棕压陶土）；
- 正文与缺陷描述一行 46–49 字（`max-w-3xl` 内 14px 铺满）；
- 模块 chip 的「×」点击区 8×16，390px 下进度条溢出屏幕。

同时暴露「靠解释句支撑页面」的问题：入口页靠一段话解释四条路的区别、对话页靠一句指路说明可以去底部输入框写、
粘贴页靠两句话解释接口文档与提示词的关系。这些都在**替布局说话**，而不是提供新信息。

---

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 全站 `max-w-3xl` → `max-w-2xl`/`xl` | 一改所有卡片同时变窄；规格上仍不达 45 字（2xl=672px ≈48 字），改完既没达标又要重排整套页面 |
| 缺陷列表整块收 `max-w-xl` | 试过：左边规则线只画半截、文档页缩成卡片里一小块白纸，比多 4 个字更难看 |
| 缩字号凑行长 | 与决策 1 直接冲突；11px 是这次要清掉的问题本身 |
| 保留文案，只调字号颜色 | 「解释已知内容」的句子会越写越多，下一轮还是同样的体检结果 |
| 用 inline style 写行长（静态稿的做法） | 真实前端由 Tailwind v4 现编任意值，用类名才能被 `check_classes` 之外的构建链统一管理 |

---

## 后果与代价

- **与设计稿解耦风险**：`design/prdwright-clone` 是这次的事实来源，但它不进构建。改动后两边必须同时更新，
  否则下一轮复刻又会带回旧文案。约定：**改文案先改 `frontend/`，再跑一次设计目录的 `node build.mjs`**。
- **视觉验收强度有限**：本地没有 Postgres，`vite dev` 只能看到入口页与登录弹窗；内页靠单测 + 类型检查 + 构建兜底。
  若要真机验收，需要起 `deploy/compose.yaml`。
- **管理端未同步**：`frontend_admin/` 是零共享的独立体系（Sky Brutalism），这次不动；12px 下限若要推广，另开一轮。
- **测试基线上升**：+1 文件、+3 用例（`readability.spec.ts`），文案类断言由「含某句」改为「不含某句」。
