# ADR-015：交互控件收口到 `components/ui/`，底栏是全站唯一操作落点

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-13 已落地：组件库 `08743c2`、底栏统一 `70ac82f`；2026-10-14 补记；2026-10-16 补记：内容行工具集与手改落库）

### Context

两个独立但同源的问题：

**控件各写各的**——12 处主按钮、10+ 处次按钮各自写一份样式；`AuthDialog` 手写 Teleport 与聚焦陷阱；保存提示 `flashSavedTip` 是内联药丸。改一个圆角要动十几处。

**操作散落**——主操作时而右对齐、时而整宽居中，次操作时而底部左侧、时而卡片头部右上，「清空 / 重新开始」更是四屏四个位置。用户每换一屏都要重新找「下一步该点哪」。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 建 `ui/` 基础件 + 底栏作为唯一操作落点** | 视觉与交互各有单一落点；新增阶段不必重新设计操作区 | 底栏成为瓶颈，所有新操作都要挤进来 |
| B. 只建 `ui/`，操作仍各屏自管 | 改动小 | 「找不到下一步」的问题原样保留 |
| C. 引入第三方组件库（Element Plus / Naive UI） | 开箱即用 | 体积与设计语言不受控，且要覆盖已有 400 处样式，迁移成本反而更高 |

### Decision

**选 A。**

- **`components/ui/` 11 个基础件**：`AppButton` / `AppCard` / `AppIcon` / `AppBadge` / `AppDialog` / `AppToast` / `AppSpinner` / `AppEmpty` / `AppInput` / `AppActionBar` / `ThemeMenu`。
- **`AppActionBar.vue` 是全站唯一操作栏**，最多两行：
  - **内容行**（`#tools`，有内容才出现）：对「当前这份内容」做的事——文档工具（AI 优化 / 复制 / 下载）、对话输入框。
  - **流程行**（永远存在）：三段式且顺序不可变——`[破坏性] │ [返回 / 次操作 + 说明文字] ……… [主操作，永远最右且唯一]`。
  - 不合并成一行的理由：审阅页一行要塞 6 个按钮，对话页还要塞输入框，物理上放不下；分两行后每行职责单一、宽度稳定。
- **`DocumentReview.vue` 只渲染卡片、自带零控件**，通过 `defineExpose` 把能力交给底栏——「下载」的判据是「有正文」而不是「改过」。
- **吸底用 `fixed` 而不是 `sticky`**：`sticky` 的活动范围被包含块框住，滚到底时只能停在包含块底边，与窗口下缘裂出约 40px 的缝，正是「滚到底又不吸底」的观感来源。
- 底栏高度由 `ResizeObserver` 写进 `--shell-action-bar-h`，供 `<main>` 底部留白与窄屏浮动按钮避让读取（底栏最多两行、高度不固定，写死留白必然在某一头出错）。

### 实施现状（如实记录）

- 已接线：`AppButton` 在 **12** 处业务组件使用，`AppActionBar` 在 **12** 处使用。
- **未接线**：`AppDialog` / `AppToast` / `AppEmpty` / `AppInput` 目前**零外部引用**——`AuthDialog.vue` 仍手写 Teleport，表单输入仍是 `RequirementsForm` 自绘。组件库处于「已建、部分接线」状态，这四个是 v3 的收敛项。

> **现状注（v8 / #2 之后）**：上面点名的三项 `AppToast` / `AppEmpty` / `AppInput` 已于 #2 删除（`grep` 零命中）；`AppDialog` 实际仍被审阅页引用，故保留——「零外部引用」这句对它不成立。逐项证据见 `docs/architecture/v8/CLEANUP.md` 的 A3~A5 与 §8 偏差记录。

- ⚠️ 底栏读子组件句柄有个坑：**模板 ref 在首次渲染之后才赋值**，首帧读到 null 要兜底；测试断言状态前必须 `await nextTick()`。

### Consequences

- 变容易：新增阶段不必重新设计操作区；改视觉改基础件即可。
- 变困难：「唯一落点」意味着任何新操作都必须进底栏，而两行是硬上限——超出时必须重新划分阶段，而不是加第三行。
- 中立：四个未接线的组件是已知债，不影响功能，但会让「改样式只改一处」的收益打折。

> **补记（2026-10-16）：内容行第三个工具由「保存」改为「下载」，手改正文改为自动防抖落库**
>
> 起因是一个「按钮点了没反应」的观感问题：审阅页的「保存」既不下载、平时也看不出它做了什么。查下去发现更实质的事——**当时根本不存在自动落库**：`documents.save(` 在生产代码里只有一个调用点，而它唯一的触发器就是这个按钮。store 里的防抖（800ms）/ 单飞 / `pending` / `changeEpoch` 记账早已写好并有测试覆盖，缺的只是「打字 → 入队」这一步。于是这次改动 90% 是接线。
>
> **不写新 ADR 的理由**：`stores/documents.ts` 开头就把「防抖 + 单飞」定为既定方案，本次只是**补上唯一缺失的触发点**，是既有决策的兑现；真正被改动的是本条 ADR 里「内容行工具集」与「『保存』判据」两句话，记回这里最连贯。
>
> 1. **按钮改名与数据源**：内容行第三个工具「保存」→「下载」，位置与外观不变（底栏内容行右端，紧邻「预览 / 编辑」）。载荷取**组件里的草稿**（`DocumentReview` 通过 `defineExpose` 交出的 `draftContent`）而不是 store 的工作副本——防抖窗口内工作副本还落后半拍，下载必须给出用户眼前这一版。完成页的下载仍读工作副本，两者共用 `utils/icons.ts` 的 `DOWNLOAD_ICON`，出口不同（一个是落库那一版、一个是当前草稿）。判据仍是「有正文」而非「改过」：空内容时 `downloadFile` 会静默返回，禁用态避免一次「点了没反应」的死点击。
> 2. **自动落库的触发与守卫**：`DocumentReview` 的草稿变化事件（`draftChange`，原名 `save`）驱动 `documents.save`，**逐次输入如实上报**、不在组件里自建第二层去抖。两道守卫：生成中不上报（可编辑区根本没渲染），草稿与 `props.content` 相等时不上报（那是父组件把权威正文同步下来，不是用户敲的）。守卫充分性依赖**注册顺序**——props 同步 watch 先于草稿 watch，同一 `pre` 队列按创建顺序执行，同步完再判等即恒成立；而 `documents.save` 会同步回写工作副本，使一次按键恰好一次上报，不会自激。
> 3. **静默，只在失败时提示**：成功不弹提示——每敲几秒弹一次会把界面淹没。失败由 `documents.saveError` 承载，`AppV2` 监听它闪一条**红色**药丸（`flashSavedTip` 增了 `variant`，图标随档位二选一；此前它只会渲染成功态的对勾，直接拿去报错是错的）。同一原因反复失败不重复闪，成功一次后再失败视为新问题重新提示。
> 4. **三处补冲未落库的草稿**：`solutions.openSolution()` 拉取文档之前、`beforeunload`、`onBeforeUnmount`。**顺带修掉一个既有缺陷**：`openSolution` 原先不冲文档队列，而 `loadAll` 会把未落库的 `pending` 盖在新方案的响应之上，防抖定时器随后把旧稿 PUT 到**新** `solutionId`——800ms 窗口内切换方案就会串稿。冲盘必须发生在 `loadAll` 之前，用的是此刻仍是旧值的 `solutionId`。
> 5. **阶段切换（`goTo`）不冲**：文档队列是 store 内部状态，不随组件卸载消失，切阶段没有丢稿风险；在那里冲等于每点一次进度条就多发一个 PUT。
> 6. **落库路径不变**：仍走 ADR-021 确立的唯一写入口（后端 `documents` 表 + `PUT /api/solutions/{id}/documents/{kind}`），前端新增的只是一条触发它的输入源。
>
> 已知残余风险（本期记录、不修）：一次旧稿 PUT 的在途时间若恰好跨越任务收尾（`finishDoc → setLocal`），旧稿可能盖回任务成果。该竞态在改动**前后概率相同**（今天「点保存后立刻点 AI 优化」同样会撞上），本次并未加剧它；彻底关闭需在 5 处 `job.start` 之前统一冲盘，回归面偏大，留待后续。
