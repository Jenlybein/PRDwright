# ADR-096：退役列直接删，不设兼容期

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：已定（v8 / T18.8）。清单见 `CLEANUP.md`。

### 背景

两列已经"退役"但还躺在表里：

- `solutions.data`：`solution_repo.create` 写空串、`update` 刻意不写；`solution_service`
  文件头写着「不再写、不再读，旧值留作历史备份」；
- `model_providers.builtin`：`models.py` 的注释是「v19 起一律为 0，**代码不再读取**，
  保留是为了不重建表」。

两条注释的措辞都指向同一个理由：**"保留是为了不重建表"**。

### 决策

**直接删，不设兼容期、不做双写、不留 `deprecated` 标记。**

### 理由

1. **那条理由已经不成立了。**「不重建表」是 v6 之前手写 DDL 时代的话——当时改结构要
   自己写建新表 + 拷数据 + 换名。v6 起结构只走 Alembic，删列就是一条
   `op.drop_column`（SQLite 下由 batch 模式自动完成同样的三步）。成本已经从
   "一次手工手术"降到"一条迁移"。
2. **保留的成本不是零。** 每多一列：读模型的人要判断一次能不能用；`diff_snapshots`
   多一条可能的假阳性；换库时要为它单独决定类型（`solutions.data` 就被列进了
   `MEDIUMTEXT` 变体名单，理由是"不知道它会多大"）。这些成本天天发生。
3. **兼容期没有服务对象。** 单实例部署、没有外部系统读这个库、没有第二个进程。
   兼容期是为了"新旧代码同时读写"设计的，而这里不存在那个场景。
4. **`deprecated` 标记不会导致删除。** 它只会把"要不要判断这一列"变成"要不要判断
   这一列和它的标记"，成本反而更高。

### 关键约束（不可逆性）

删列**不可逆**：删完之后旧代码读不到列，启动即报错。所以：

- 回滚方式是**恢复备份**，不是 `git revert`（ADR-057 的推论在删列场景下同样成立）；
- 三步必须在同一个窗口：`VACUUM INTO` 备份 + 自检 → 跑迁移 → 全量用例；
- 备份没做成不许跑迁移。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 保留列，标 `deprecated` | 标记不会导致删除，只是把判断成本翻倍 |
| 先双写再删（新旧字段并存一段时间） | 没有第二个消费者，双写没有对象 |
| 只删模型字段、保留库列 | 结构对拍立刻红（模型没有、库里还在），等于把问题推给下一次启动 |
| 删列前先导出一份 CSV 存档 | 没有导出需求；真要存档，备份文件里本来就有 |

### 推论

- `CLEANUP.md` §3 那条「文档写了、文件没落盘」是同一类问题的另一面：**声明与实现
  不一致**。所以 T18.8 的验收加了一条硬要求——文档里出现的每个路径，`ls` 必须能看见。
