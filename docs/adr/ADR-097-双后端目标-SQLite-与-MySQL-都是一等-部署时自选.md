# ADR-097：双后端目标 = SQLite 与 MySQL 都是一等（部署时自选）

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：已定（v8 第二阶段）。完整设计见 `MULTI-BACKEND.md`。部分取代 ADR-091。

### 背景

ADR-091 的结论是"保留 SQLite，换库推迟"，理由是换库收益为零、代价落在唯一真实
运行的路径上。那个判断在当时成立：换库的唯一大收益（多副本）被 `_RUNTIMES` 锁死。

现在目标变了：**部署时由 `DATABASE_URL` 自选 SQLite 或 MySQL**。这不是"为了容器化
顺手换库"，而是一个独立的产品诉求——有的人要零运维（SQLite），有的人已经有
MySQL 实例、希望数据进自己的库。

于是 ADR-091 的理由不再适用：收益不再是"多副本"，而是"覆盖两类部署场景"。

### 决策

**两个后端都按"正式支持"对待**，判据三条（缺一条就只是"试过"）：

1. CI 有 SQLite + MySQL 两个 job，同一份用例；
2. 并发用例**在 MySQL 上**跑（SQLite 单写者跑不出竞态）；
3. 新代码的评审默认问题是"MySQL 上呢"。

结构上收敛到四个职责正交的模块：`core/database.py`（连哪个库）、`core/dialect.py`
（语句怎么写）、`core/types.py`（列怎么声明）、`core/schema.py`（结构怎么演进）。
判据：**任何与具体数据库有关的代码，必须落在这四个文件之一。**

### 关键不可妥协项

| 项 | 为什么不能省 |
|---|---|
| 列类型必须给长度（`short_text(n)`） | 不改，MySQL 上建表就失败（`TEXT` 不能整列建索引/做主键） |
| 大文本列去掉 `server_default` | MySQL 的 `BLOB/TEXT` 不接受字面量默认值，建表报 `can't have a default value` |
| 两条「先查后写」路径加锁 | 这是唯一**不报错**的一类：并发下静默出现两条 `running`、额度被击穿 |
| 死锁重试（1213/1205） | 间隙锁是 `REPEATABLE READ` 的固有行为，无法通过写法规避 |
| `LIKE` 改 `dialect.ilike()` | 换库后"搜 admin 搜不到 Admin"会被当业务 bug 报上来 |
| 测试基建改 SQLAlchemy Connection | 不改就永远是"SQLite 真跑、MySQL 偶尔试" |

### 为什么不做"更省"的 PostgreSQL

技术上 PG 的迁移代价更小：`ON CONFLICT` 与 SQLite 同语法、`TEXT` 索引无长度限制、
部分索引原生支持。但每纳入一个后端，CI 多一条矩阵、每个语义差异多一套验证。
**两个后端已经覆盖"零运维"与"有 DBA"两种场景**，第三个只增加维护面。
本文的四个模块边界是按"方言能力"切的，将来纳入 PG 不用改结构。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 只支持 MySQL，弃用 SQLite | SQLite 是零运维形态（个人自部署、单机演示），砍掉等于放弃一类场景 |
| 用 ORM 抽象抹平一切、不做显式分派 | 实测过：`inspect()` 会丢 `ondelete`（ADR-094）。抽象层给的是"共同子集"，而我们要的是"两边都完整" |
| 保留 `TEXT` + MySQL 前缀索引 | 前缀唯一 ≠ 全值唯一，`username` / `token_hash` 这类列的语义会变 |
| 时间戳改成 `DATETIME` | 波及 `clock.py` 与所有比较点；字典序=时间序是承重设计（ADR-077），收益不足以抵消 |
| 运行时切库 | 需要回答"在途任务往哪写""旧连接池怎么处置""迁移何时跑"，且没有使用场景 |

### 推论

1. **P1（装配层）必须先单独做完**：装好开关之后，后续每一阶段都能在两个后端之间
   切换验证；否则每个阶段都要手工改代码才能试 MySQL。
2. 改列类型是一次**结构重基线**（SQLite 侧 `TEXT` → `VARCHAR(n)`），与 T18.8 的删列
   合并成同一次发布——反正都要重建表。
3. `DIALECT-PORTABILITY.md` §3.6 的不收敛清单，第 5~15 项由本文接手；清单本身仍是
   换库前的检查表。
