# ADR-072：数据访问层收敛为 `Database` 对象 + 单元事务，锁由「恒定连接数」取代

> 源：v5 层（原 `docs/architecture/v5/ADR.md`，已并入本目录）｜ [索引](./README.md)

> 状态：已评审，待落地（T15）

### 背景

`core/db.py` 的 `connect()` 每次操作新建连接（92 处调用点），并在引导时用一把
`_bootstrap_lock` 串行化「建连接 + 三条 PRAGMA」。这把锁是 ADR-071 遗留的悬空点：

- 它要防的是 Windows 上「多线程同时首次映射 WAL `-shm`」报 `SQLITE_READONLY`；
- 但该故障**当前已无法复现**（两套探针 15 轮、摘锁跑用例 10 轮均干净），
  也没有任何守卫能证明这把锁有用；
- 「无法验证的防御代码」本身是一种债：谁都可以随手删掉，且删了不会有测试变红。

同时，查看代码时发现另一处更值钱的问题：**事务边界止步于仓库函数**。
44 处 `.commit()` 散在 `repositories/` 里，服务层调两个仓库就是两个事务。
`job_service` 的收尾就是典型：更新任务状态与写入正文分属两个事务，
中间失败会留下「任务已完成、正文没落地」的中间态。

### 决策

把访问层收敛到一个 `Database` 对象，用**结构性不变量**取代那把锁：

1. **连接数恒定**：`open()` 在启动期（单线程）一次性建满 `size` 条，
   运行期不扩容、不新建。于是「多线程同时首次映射 `-shm`」**没有发生的时机**。
2. `connect()` 保留为兼容入口，内部委托 `Database.acquire()`（92 处调用点不用改）。
3. **归还即回滚**：`conn.in_transaction` 为真就 `rollback()` 并计入统计。
   池化之后这是硬要求——否则漏提交的事务会跟着连接传给下一个借用者。
4. **事务边界上移到服务层**：仓库函数接受传入连接（`conn=None` 缺省自开），
   服务层用 `db.transaction()` 拥有边界。28 个函数**分批**迁移，未迁移的语义不变。
5. **删掉 `_bootstrap_lock`**，改由 G-DB1 守卫（引导只发生在 `open()`）继承其使命。
6. `SQLITE_BUSY` 与 `SQLITE_READONLY` 分开处理：前者有界重试，后者不重试直接上抛。

### 为什么不是「保留锁 + 接池」

锁已经没有保护对象了。留着它会让人误以为「并发引导仍可能发生」，
从而在别处重复加锁。**不变量能表达的事，不要用锁表达。**

### 为什么池不做动态伸缩

一旦允许运行期扩容，扩容那一刻就是「多线程建连接」，竞态原样回来；
要么给扩容加锁（锁没删掉），要么预建满。8 条 SQLite 连接的代价可忽略，选预建。

### 取舍

| 方案 | 否决理由 |
| --- | --- |
| 换 SQLAlchemy `QueuePool` | 为 8 条 SQLite 连接引入 ORM 生态，依赖与心智成本不对等 |
| 换 Postgres / aiosqlite | 单写者与同步调用链是项目既定边界；换存储是另一个量级的事 |
| 一次性改完 92 处调用点 | 无法分批验收；`conn=None` 缺省可让迁移逐仓库推进 |
| 保留锁作为「双保险」 | 见上：没有保护对象，且会误导后来者 |
