# ADR 0003：审核只报缺陷，未决归待确认清单

- 编号：**0003**
- 状态：已采纳（文档先行；代码已落地于 `ticket/63-review-defects-impl`，基于 `integration/spec-63` 的 `6c6e4bc`）
- 范围：审核的判定口径、结论的条目形状、修复的约束、两个面板（文档缺陷 / 待确认清单）的分工

---

## 决策

1. **审核只报「文档缺陷」**：可验证为错的地方，共六类——**编造**（写了输入里没有的事实）、**矛盾**（与输入或上游章节冲突）、**结构不符**（标题层级/表格列/编号与规范不一致）、**空泛**（无法开工的描述）、**推断未标注**（推断没标「（建议）」或没给一句依据）、**清单漏登记**（该进待确认清单的项没有登记）。**「缺什么、该怎么定」不进审核**——那是未决，归**待确认清单**。
2. **类别决定严重度，不由模型升降**：编造与矛盾 = 高（生成时触发一次自动改写）；结构、空泛、未标注、漏登记 = 中（只报不改）。
3. **两个时点两套口径**：生成过程中只判前五类（那时清单还没抽出来）；**重审与修复后的重审**才判「清单漏登记」（此时当前版本的清单已存在）。
4. **审核要读到待确认清单**（重审/修复时）：否则既无法判断漏登记，也无法去重。
5. **「推断未标注」只判形式**：有没有标「（建议）」、有没有一句依据；**不评判依据强弱**（那是主观，也是同一件事被反复报的来源）。
6. **修复不得为缺失编造**：修复提示词明确「缺就写『待确认』并登记清单」。
7. **旧结论不追溯**：历史结论保持原样，界面上没有类别的归「未分类」；用户点一次重审即按新口径重算。
8. **界面**：审核结论这块的标题改为「**文档缺陷**」，折叠头给分类计数，展开按类分组、类内按严重度排序。

---

## 背景

线上一次真实审核给出了 17 条「问题」，其中大半是「未定义 / 依据不足 / 未登记到清单」这类**未决**，真正可验证的缺陷只有少数。根因有三条：

- 审核提示词里同时写着「正文写『待确认』是正确的、不构成问题」，和「该确认未确认 = 高」。两条规则打架，模型就按「能不能开工」自行发挥，把「没定义」抬成高。
- 审核**根本读不到待确认清单**（它只收到写作规范、需求输入、上游章节、待审正文），却报出了「未登记到文末待确认清单」——这类条目是猜的。
- 清单与审核都在回答「这里不确定」，于是用户看到两套重叠的问题列表，而「修复」会把整篇重写一遍，其中「缺」的部分又可能被编造填上。

真正的切分不是「结构 vs 内容」：**编造与矛盾是审核不可替代的价值**（清单只装「不知道」，装不下「写错了」），而「缺什么、依据够不够」才是清单的地盘。所以按**缺陷 vs 未决**切。

---

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 审核只审结构/格式 | 会丢掉「编造」——最危险的一类错误从此没人守；而它恰恰是清单表达不了的 |
| 保留「该确认未确认」，只把它降成 medium | 与待确认清单永远重叠：同一件事在两个面板各报一次，用户要读两遍 |
| 不加类别字段，只靠 `detail` 文字 | 无法分组、无法筛选「只看编造」，也无法按类固定严重度 |
| 严重度继续交给模型自定 | 同一类问题这次 high 下次 medium，改写门槛随之漂移 |
| 生成时就查「清单漏登记」 | 逐章审核时清单还没抽出来（收尾才生成），跨章条目必然误判为漏登记 |
| 把旧结论拿去重分类 | 旧结论本身是按错口径判的，改标签不改变判断质量；重审才是唯一诚实的做法 |
| 只改 PRD 的审核口径 | 接口文档/提示词走同一段审核代码，两套口径会立刻分叉 |

---

## 后果

- 审核提示词与解析要加**类别**；结论 JSON、文档列表与版本详情的读取面、前端类型与面板随之扩展（旧数据无类别 → 「未分类」）。
- 重审与修复的输入要带上当前版本的待确认清单；生成链路不带。
- 线上旧结论不会自动变干净：用户会继续看到按旧口径产生的条目，直到点一次重审。这是有意的——不假装历史是对的。
- 「缺陷」成了与「待确认清单」并列的领域概念，两者**不得互相代答**：审核不判该怎么定，清单不判写错了没有。
- 修复的约束更强（不得编造），代价是遇到「缺」时产出的正文仍会留着「待确认」——这是正确结果，不是修复失败。
