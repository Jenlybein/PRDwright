# ADR-043：管理员身份的授予/撤销只留**一条**规则，且「撤销自己」不算违规

> 源：v4 层（原 `docs/architecture/v4/ADR.md`，已并入本目录）｜ [索引](./README.md)

### Status

Accepted（2026-10-21）

### Context

T1 实现到「后台能不能授予/撤销管理员」时，冒出两个问题：

1. **规则写在哪？** `auth_service.set_admin` 里已有一条「不能撤销最后一位管理员」，
   而运维脚本 `auth_cli.py demote` 走的就是它。后台若另写一份校验，两条路迟早
   有一处漏改——后台就会成为绕过不变式的后门。
2. **「不能撤销自己」算不算一条独立规则？**

第 2 个问题的初稿答案是「算」，理由是「撤销自己 = 当场把自己踢出后台」。实现时
发现这个理由站不住：

- 管理员交接、临时让渡权限是**真实场景**。只要系统里还有别的管理员，
  撤销自己就是一次正常的「卸任」，而且**可逆**——另一位管理员随时能重新任命。
- 更关键的是：它和「不能撤销最后一位管理员」在 HTTP 路径上**必然重合**。
  只要操作者是管理员，「最后一位」就只可能是他自己。于是两条规则会互相遮蔽，
  报错信息也会打架（到底是「不能撤销自己」还是「最后一位管理员」）。

### Decision

1. **规则只有一条**，由 `auth_service.set_admin` 独家实现：
   不能撤销最后一位管理员。后台（`admin_service.set_admin`）只做委派，
   CLI 与后台共用同一份实现。
2. **「撤销自己」不被单独拦**。只要还有别的管理员，撤销自己是允许的；
   真正被拦的只有一种——撤销之后系统里一个管理员都不剩。
3. 相应地，**删号 / 停用自己**仍然单独拦（403）。这两件事性质不同：
   删号和停用会毁掉或冻结自己的账号，撤销管理员只是换了个角色。
4. 后台那侧的状态码用 `FORBIDDEN`（403）而不是 `AUTH_FAILED`（401）：
   401 在前端意味着「该去登录了」，而这里登录也没用。

### Consequences

**变容易**

- 后台与 CLI 的行为**逐条一致**，不存在「命令行能绕、后台不能」或反之。
- 管理员交接不用绕到命令行。
- 错误信息只有一种说法（「这是最后一位管理员，不能撤销」），管理员一眼知道该做什么。

**变难 / 代价**

- 管理员可以在后台里把自己降级，从而立刻失去后台访问权。这是**有意为之**：
  它是显式动作（点了「撤销管理员」），且可逆。刻意不做「禁止自降级」的保护，
  是因为那会挡住真实的交接场景。

**验证**

- 后端用例钉住两条：撤销最后一位 → 403；**有第二位时撤销自己 → 200**。
- 端到端冒烟走真实 HTTP：授予 → 撤销第一位（有第二位，200）→ 撤销最后一位（403）。
