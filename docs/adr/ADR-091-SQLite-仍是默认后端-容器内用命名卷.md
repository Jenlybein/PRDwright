# ADR-091：SQLite 仍是默认后端，容器内用命名卷

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：**部分被 ADR-097 取代**（v8 第二阶段正式支持 MySQL，部署时自选）。

本 ADR 中「容器化不必顺带换库」的论证仍然成立——那条针对的是"为了容器化而换库"，
结论是"容器化与换库是两条轴"。但「换库推迟」这个结论作废：现在换库是**独立的
产品需求**（部署时自选），不再是"容器化的副产品"。

### 背景

容器化很容易被顺手做成"顺便换个正经数据库"。评估过三条路：

1. 保留 SQLite；
2. 换 MySQL；
3. 换 PostgreSQL。

### 决策

**取 ①**。三条理由，按分量排序：

1. **换库的最大收益拿不到**。多副本横向扩展需要把 `_RUNTIMES`、`JobBus`、
   runtime 快照外置（Redis + 任务队列），那是 v9 量级。在此之前 `api` 副本恒为 1，
   MySQL 的并发写能力没有服务对象。
2. **改造代价落在唯一真实运行的路径上**。改列长度、改 upsert、加锁重试、重写测试基建，
   全部会让 SQLite 这条路径变复杂，而收益是零。
3. **容器里 SQLite 完全可用**，前提是命名卷。真正的坑是挂载方式，不是数据库本身。

### 推论（重要）

- 数据库目录**必须**是命名卷。Docker Desktop for Windows 的 bind mount 不支持
  SQLite 需要的文件锁与 WAL `-shm` 的 mmap，症状是随机 `disk I/O error`（C-V8-2）。
- 若将来换库，`DIALECT-PORTABILITY.md` §3.6 的台账就是执行清单。其中
  "事务隔离"一项必须在换库**之前**处理——单写者的隐形保护在任何一个多写者库上都不存在。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 换 MySQL | 五处硬缺口（`TEXT` 主键/索引、部分唯一索引、带目标的 upsert、64KB、`length()` 语义），且收益为零 |
| 换 PostgreSQL | 改造量远小于 MySQL，但同样拿不到多副本收益；留到真需要横向扩展时再做 |
| SQLite + 多个 worker 共享同一文件 | WAL 允许多读单写，但 `_RUNTIMES` 决定了多 worker 本身不成立 |
