# ADR-024：会话用单点登录，不做 revision 乐观锁

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-15 裁决并落地，P5）

### Context

「同一账号多端登录」这件事需要一个明确的处置：多端并存时，一个端改了密码、或者用户怀疑账号在别处被人用着，怎样才能干净地收回登录态？

原先倾向的做法是 **revision 版本号 + 乐观锁**：会话记录带一个版本号，客户端每次请求带上它，写时比对、不一致就重试。它能让多端并存且各自感知「自己落后了」。但推演下来，它要新增的东西不少：会话表加列、每次请求带版本号、冲突时的重试语义、以及前端「版本落后」的界面表达——而这些问题**全都是为了支持多端并存**才存在的。

真正要问的是：**这个产品需要多端同时在线吗？** 产品定位是单机需求工作台，真实使用场景是「一个人、一台设备、一份方案」。为它维护一套并发会话一致性机制，属于拿复杂度换一个用不到的能力。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. revision 乐观锁 | 支持多端并存，冲突可感知、可重试 | 多一列 + 每次请求带版本 + 重试语义 + 前端冲突 UI；而多端并存本身用不到 |
| **B. 单点登录：新登录吊销该用户此前全部会话（推荐）** | 零 schema 变更、语义一句话说完、天然覆盖「改密码/怀疑被盗」 | 多设备会互相踢下线（**明确接受的残余风险**） |
| C. 保持现状（多端并存，互不影响） | 零改动 | 账号被多处使用时无法收回；会话表随登录次数增长 |

### Decision

**选 B。**

1. **`AuthSessionRepository.replace_for_user()` 在一条事务里「先删后插」**（`DELETE FROM auth_sessions WHERE user_id = ?` → `INSERT`）。必须在同一事务：分开做的话，任何一步失败都会把用户留在「旧的已删、新的没立」——刚登录成功却判定未登录。插失败（如哈希撞主键）时**不提交**，连接关闭即回滚，旧会话照旧可用。
2. **刻意不按过期时间挑着删**：单点登录的语义是「新登录让旧的立刻失效」。只清过期记录等于留下一个可用的第二登录态，那正是要消灭的东西。
3. **登录与注册都走 `replace()`**。注册时该用户本来没有旧会话，这一步是空操作——但它保证「凡是签发登录态的地方只有一个入口」，不给「某个入口忘了吊销旧会话」留缝。
4. **零 schema 变更、中间件零改动**：`idx_auth_sessions_user` 已存在；旧 token 在新会话立起来后查不到 → 中间件判定未登录 → 401 → 前端 `onUnauthorized` 弹登录窗。整条回收链路复用的是既有机制。

### Consequences

- **变容易**：账号回收语义变成一句话；不需要维护版本号、冲突重试与「版本落后」的界面表达；会话表里「一个用户至多一条记录」成为可核对的不变量（`list_by_user` 即为此提供的第一手证据）。
- **变困难**：**多设备互相踢下线是明确接受的代价**，登记为残余风险——手机上看完的需求，回到电脑前要重新登录。这不是「暂时没做」，是范围决策。
- **中立**：仍保留「多端并存」的能力（`issue()` 还在，改动它只是一行），因此将来若真出现多端需求，反悔的成本极低——这一点也是选 B 的理由之一：**它的反转成本和它的实现成本一样小**。
