# ADR-092：健康检查分两条，`/health` 不改

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：已定（v8 / T18.6）。

### 背景

v7 明确写了一条契约：`/health` **恒返回 200**，`status` 只有 `ok` / `degraded`，
用来区分"能不能用"而不是"进程活没活"（`api/health.py` 的 docstring）。

容器编排需要两个不同的信号：liveness（卡死就重启）与 readiness（没准备好就别接流量）。
`/health` 两个都不适合：它恒 200，当 liveness 等于没配；它聚合了"模型未配置"
这类可降级状态，当 readiness 会让容器在能服务时被判为不可用。

### 决策

**保留 `/health` 语义不变，新增两条**：

| 路径 | 语义 | 判定 |
|---|---|---|
| `GET /healthz` | 进程活着 | 固定 200，不查库、不查配置 |
| `GET /readyz` | 能接业务请求 | 连库 + `alembic_version == head` + 池已预热，任一不满足即 503 |

两条都要加进认证白名单——探针不带 Cookie，不在白名单里会被拦成 401，
表现为"容器永远不健康"，而这个症状会让人去查数据库，方向全错。

池预热为什么算 readiness：`max_overflow=0` 下"池没建满"意味着第一个并发请求会超时，
属于"还没准备好接客"，不是"服务挂了"。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 改 `/health` 的语义（加 503） | 会动到已有的监控、文档与 v7 契约；且它承载的是"可降级"语义 |
| 只配 liveness，不配 readiness | 重建容器期间流量会打到还没迁移完的实例上 |
| readiness 只查 `SELECT 1` | 迁移没跑完时库是通的，但业务会因缺列而 500 |
