# ADR-033：澄清提问产出「结构化选择题」，前端渲染成可点选项卡

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-16 裁决并落地）

### Context

澄清对话里 AI 的提问一直是一段 Markdown 自由文本，用户只能自己组织一句话回答。
而 `CLARIFICATION_QUESTION_RULE` 早就要求「**提问要带引导**：先给一个可判断的参照，再问用户
怎么看」——参照已经给了，但**用户仍然只能打字**。参照越是几个并列方向，打字越累、答得越随意
（「都行」「看情况」），而这三个字对后续文档没有任何信息量。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 前端解析 Markdown 里的 A/B 列表 | 不必动后端 | 那是模型自由发挥的产物，解析规则只能靠猜；哪天它写成「方案一 / 方案二」就**静默失效**，没有报错、只是卡片不再出现 |
| B. 新增一种 SSE 事件类型携带结构化问题 | 语义最清晰（事件名本身就说清了） | 要动 SSE 契约与各事件消费点；而 `done` 的 `data` 本来就是任意 dict，加一个键即可 |
| C. 让模型直接输出 JSON 全文 | 结构最规整 | 用户要能读那段解释——纯 JSON 读不了，等于把「解释每个选项」这件事挤掉 |
| **D. 正文照常写 + 末尾附哨兵块，`done` 带上结构化数据（推荐）** | 复用已被验证的「哨兵块 + 流式抑制」机制；正文可读、数据可解析；哨兵是 HTML 注释，漏出也不可见 | 提示词变长；模型可能不产块（功能退化） |
| E. 复用待确认清单（`pending_items`）那条通道 | 零新机制 | 两者生命周期不同（那份要落库、要按 P0~P6 排序）；混在一起会让两套正交的校验互相牵连 |

### Decision

**选 D。**

1. **哨兵块**：`<!-- ASK:BEGIN -->` / `<!-- ASK:END -->`，与待确认清单同范式。抑制器**复用**
   `PendingBlockSuppressor`（只把哨兵参数化）——那段状态机的全部难度在「哨兵被切在 chunk
   边界」，复制一份等于把这个坑复制一份。
2. **数据挂在消息上**（`ChatMessage.asks`），**不加顶层快照字段**：消息经 `parseSessionSnapshot`
   是整对象展开的，未知字段天然保留；而加顶层字段要同步四处快照逻辑、还要改契约测试钉住的键清单。
3. **只有当前线程的最后一条消息可交互**。判据刻意**不是**「最后一条 assistant 消息」——
   用户一作答，推入的是 user 消息，用后者会让卡片一直可点（同一个问题能被反复回答）。
   用「最后一条消息」还顺带解决了流式期间的可点性：流式气泡挂在末尾，提问那条自动退成只读。
4. **作答是「先点选、再点提交回答」**。一轮可能问 1~2 题（`CLARIFICATION_QUESTION_CAP`），
   一次答完再发才成立——点一下就发的话，第二个问题没机会答。选项与「都不合适、我自己写」
   **互斥**而不是分优先级：两者并存再去定谁赢，用户永远不知道提交的到底是哪个。
5. **提交走既有的 `sendMessage`**：它就是一封普通的用户消息（带 `stage`、进本线程历史、
   `chatStreaming` 期间禁止再发）。分两条通道只会多出一处要同步的守卫。
6. **写回会话历史的是剥离后的干净正文**。带块的原文一旦回流，下一轮会被当作 assistant 消息
   喂回模型——既污染上下文，又会让模型学着继续吐块。
7. **选项的 `label` 与 `id` 由后端分配**（同「不信任模型给的 `id`」）；`multiple` 只认真正的
   布尔真，字符串形式的 `"true"` 一律按单选——把单选题渲染成多选，用户第一眼就会察觉不对。
8. **校验从宽、降级不报错**：坏项逐条丢弃（选项不足 2 个、没有题干、选项没有正文），
   但**绝不让这一轮失败**——退化成纯文本提问即可。「不产块」是常态，不是异常。

### Consequences

- **变容易**：带引导的提问终于能一键作答；提交文本自带题干与选项标号，模型不必猜「他答的是哪题」。
- **变困难**：多了一条**提示词 ↔ 解析器**的跨文件契约——规格文本由
  `clarification_ask.render_ask_spec()` 生成、提示词引用它（见 `prompts.py` 的导入注释），
  而不是两边各写一遍。⚠️ 另一处新债：**模型不产块时功能静默退化**，只在日志里留下空数组；
  这是刻意接受的（宁可退化，不能报错），但要靠观测去发现。
- **中立**：`api/schemas.py` 未变（提交的仍是 `content: str`）；待确认清单那套完全不动，
  连抑制器都只是参数化（默认行为逐字节不变，既有用例全绿）。

### 修订（2026-10-16，同日）

**「自行填写」的入口形态改了**——决策 4 提到的那个入口，原实现是「一行文字按钮『都不合适，我自己写』，
点它就地展开输入框、按钮文案变『收起』」。用户当天反馈：**不该靠一个按钮去调出输入框**，
直接在选项卡片下面放一张**同款卡片**、卡片里就是输入框即可（`placeholder` 恰为「都不合适，我自己写」）。
已按此改：

- **常驻**，没有展开/收起状态——`drafting` 状态与那个按钮一并删除。理由与决策 3 同源：
  「还能自己写」本该**一眼看见**，收在按钮后面等于没有。
- 卡片复用选项的视觉（圆角 / 边框 / 背景 / 内边距 / 阴影 / 字号逐项对齐），内嵌输入框**去掉自身边框与背景**——
  否则会出现「框里还有框」的双层边框。已有自填文字时整卡走高亮配色，与「选中了某个选项」同一种可见性。
- **互斥的判据从「原始输入非空」收紧到「去空白后非空」**（`setDraft` 里的 `text.trim()`）。
  改之前两处口径不一致：卡片高亮用的是 `.trim()`（纯空白不高亮），清选项用的却是原始输入——
  于是「点 A → 误敲一个空格」会把 A 的选中态静默清掉，而此刻**没有任何有效作答**（提交按钮仍是
  `disabled`），用户落到「什么都没选、也交不上去」。改完 **「卡片亮 ⇔ 该题选项已让位」恒等**。
  诚实记一笔：它**不**解决「敲了真实字符之后又删光」（那时已在首个真实字符处清掉了），
  只消除「空 → 空格 → 空」这类纯噪声触发。
- 只读态（历史消息）**不渲染这张卡片**——与「历史消息的选项本来就点不动」同一个取舍，
  再留一张打不了字的空框只是噪声。
- 决策 4~8 与降级口径**不受影响**：作答仍是「先点选 / 先写字，再点提交回答」，提交仍是一条普通用户消息。

### 再修订（同日，第二次调整）

**那张自填卡片被撤掉了。** 用户看过实际效果后反馈：「去掉选项卡附带的输入框吧，直接在选项提交按钮标注一行
『若不满意选项，可以自行在输入框输入想法』」。已按此改：

- 组件内**不再有任何输入框**：`drafts` / `setDraft()` / 互斥判据一并删除；`answered()` 只认「有选中项」，
  `answerOf()` 只剩选中项这一种写法（`（自填）…` 分支随之消失）。
- 提交按钮旁**常驻**一行指路文案：`若不满意选项，可以自行在输入框输入想法`（「输入框」指页面底部的聊天输入框）。
  它取代了原来 `answeredCount === 0` 那句「选一个选项，或自己写」——那句指的正是不再存在的卡片。
- 多题未答那句动态提示保留（`还有 N 题未作答，也可以先提交`）；这一行改用 `flex-wrap`，窄屏允许折行
  （实测：宽屏三者同行，窄屏自动折到第二行，不挤压）。

**为什么不做「两个输入框共存」**：底部聊天输入框**一直都能**直接打字作答，卡片里再放一个，会让人以为
「必须在这儿写才算数」，还多出「两个框以谁为准」的问题。**把既有的一条路说出来，好过再造一个控件。**

⚠️ 前一节修订（常驻卡片方案）**原样保留**，是因为它完整记下了「先做卡片、看过之后否掉」这个判断过程——
与本文其余部分一样，**决策的历史比决策的结论更值钱**。本日两次调整的净结果：
选项卡组 = 选项卡片 + 提交回答 + 一行指路，且**组件内零输入框**。

### 再修订（2026-10-19：提问机制整体换成原生工具调用）

**这是机制级更换，不是调参。** 起因是线上那个 bug：续聊几轮之后选项卡**静默不弹**。定位结论是模型停止产出
`<!-- ASK:BEGIN -->` 块——它在历史里见过自己「只写 A/B/C 文字、不附块」的写法之后，就会照着那个样式继续写。
哨兵机制把「结构」寄托在模型的**自由文本习惯**上，而习惯是会漂移的；更要命的是决策 8 那条「校验从宽、降级
不报错」在这里成了帮凶——退化得**毫无声音**，只在日志里留一个空数组。

改成原生 function calling（对齐 Claude Code `AskUserQuestion` / Codex `request_user_input`）：题目走**独立的
工具调用通道 + schema 强约束**，不再依赖模型「记得在自由文本里附标记」。正文照常写给人看，两者互不干扰——
正文天然干净，连抑制器都不再需要（它回到只服务待确认清单）。

**分三步落地**（Step 0 是硬闸门）：

0. **spike 先证**：一次性脚本直连 `doubao-seed-2-1-turbo-260628`，打印流式 `delta.tool_calls` 的**真实分片格式**
   ——不看真实分片就动手，等于拿猜的去写解析器。
1. **提问侧**：`build_ask_tool()`（1~2 题、每题 2~6 个选项，schema 里的数字与 `MIN_ASK_OPTIONS` /
   `MAX_ASK_OPTIONS` 同源，防漂移）；`render_ask_tool_instruction()` 取代 `render_ask_spec()`，仍由提示词
   **引用**（跨文件契约只此一处）。绑定口径 `tool_choice="auto"`（收尾轮 / 复述轮本来就不该提问，**不能强制**）
   + `parallel_tool_calls=False`（一轮至多一次调用 ⇒ 作答只需回一条工具结果）。
2. **作答侧**：`ConversationContinueRequest.tool_result = { tool_call_id, answers: [{ask_id, labels, question,
   texts}] }`，后端把它作为 `ToolMessage` 回给发起提问的那次调用。**这是「完整对齐」的关键**——只做提问侧的话，
   工具调用只是一条更华丽的传输通道，作答仍是人话，白白背上契约成本却没消掉退化。

**ark 怎么接**：`VolcanoArkChatModel` 从自写包装类改成 **`BaseChatModel` 子类**（`_llm_type` / `_generate` /
`_astream` / `bind_tools`），仍走官方 arkruntime SDK，thinking / `include_usage` / finish_reason 的既有语义一行
不动。为什么不直接换 `ChatOpenAI`：官方 SDK 那层我们还依赖着，换掉等于把方舟特有的东西再实现一遍。
`delta.tool_calls` 映射成 `AIMessageChunk.tool_call_chunks`，**分片拼装交给 LangChain**——那段拼接的坑在于
index 与参数分片，LangChain 已经踩过，不必自己再踩一次。

#### 作答侧四条容易写错的规则（都有用例钉住）

| 规则 | 为什么 | 位置 |
| --- | --- | --- |
| ⚠️ 流式工具调用要**逐片相加** | 只有 `AIMessageChunk.__add__` 会按 `index` 归类、**拼接 `args` 字符串**、补齐 `name`/`id`。把全部分片塞进一个 chunk 再读 `.tool_calls` 是**逐个分片独立解析**：首片（`args=""`）变空对象、残片各自解析失败，一次完整调用被拆成「一条空调用 + 若干条废调用」。真实代价：模型明明调了工具，题目却一个都取不到，**选项卡一张不弹**——详见下面那条诚实记录 | `stream_reply._merge_tool_calls` |
| ⚠️ 工具应答必须与发起调用**相邻成对** | `_reminded_history` 会往历史末尾插一条「格式重申」系统消息，它就排在悬空调用之后。按**下标插入**、不能追加到列表尾，否则上游 API 直接报错 | `conversation_service._build_lc_messages` |
| ⚠️ 作答轮**不再投喂人话** | 带 `tool_result` 时不再追加 `HumanMessage`。同一份作答在上下文里出现两次，模型会以为用户强调了两遍 | 同上 |
| 自由文本要能**兜住悬空调用** | 用户没点卡片、直接在底部输入框打字时，那段文本包成工具应答。否则历史里留下「调了工具却没人应答」的结构——**上游 API 直接报错**，这不是风格问题 | 同上 |
| 配不上就**降级** | `tool_call_id` 缺失或对不上任何悬空调用，一律降级成普通用户消息。绝不发一条没有对应 `tool_call` 的 `ToolMessage` | 同上 |

**落库**：assistant 条目带 `tool_calls`，作答轮把 `tool` 条目（含 `tool_call_id` + `tool_result`）插在提问
assistant 之后、不再另记一条 user 消息。⚠️ **这两件事必须一起上**——只落 `tool_calls` 不落应答，历史里就出现
悬空的 tool_call；这也是 Step 1 特意**不**落库的原因（宁可先不落，也不留半截）。

**待确认清单不跟着改**：它跟着**生成的文档**落库、进快照、按 P0~P6 排序，是文档产物的第一类元数据，生命周期
与选项卡完全不同（后者只随 `done` 下发）。`PendingBlockSuppressor` 保留给它，哨兵参数化不动（默认值不变 ⇒
既有用例逐字节仍绿）。

**前端定下的两条收敛口径**（顺带记下来，后面还会用到）：

- **持久化结构从严**：`ChatMessage` 曾短暂加过 `role: 'tool'` 与 `tool_call_id` / `tool_result`，最后**删掉**了
  ——前端根本不产生 tool 消息（`ToolMessage` 是后端拿请求体自己落的），而 `utils/workflow.ts` 的 `isChatMessage`
  白名单又不认 `'tool'`，于是「类型说可以、快照恢复时整条消息却被静默丢掉」。**类型与运行时打架比少一个字段更危险。**
- **接口契约镜像从宽**：`StreamResult`（`done` 事件的解析结果）保留 `toolCallId` / `toolCalls`——它不进快照、不被
  形状断言，契约发了什么就解析什么。真正的配对走 `asks[].tool_call_id`（一轮多题时每题带自己的来源调用，比顶层
  那个更准）。

### Consequences（本次修订带来的变化）

- **变容易**：选项卡不弹这类退化从根上消失（不再依赖模型的自由文本习惯）；正文天然干净，「半截块漏给用户」
  与「带块原文回流污染上下文」两类隐患一并消失。
- **变困难 / 新债**：① 多了一条「工具 schema ↔ 提示词 ↔ 解析器」的跨文件契约，改一头要动三处；
  ② 题目跨多个 tool_call 拼接时（`parallel_tool_calls` 被上游忽略的极端情况）题目 id 连续但 `tool_call_id` 各异，
  作答只回当前那一次；③ `extract_asks` / `render_ask_spec` **已退役**，文档里凡提到它们的都要改口径
  （本次已一并订正 `v3/README.md` 与 `v3/roadmap.md`）。
- **诚实记一笔**：这次改造**没有**证明「模型一定会调工具」——`tool_choice="auto"` 下它仍然可能不调，
  那时退化成纯文本提问（与旧机制不产块的表现相同）。区别在于：现在「不调工具」与「调了但参数坏」是**两件能分开
  观测**的事（日志里 `tool_called` 与 `asks_count` 两个信号），而旧机制下这两者都只是「没有卡片」。
- **再记一笔（上线后立刻暴露的回归）**：改造完成、前后端全绿之后，用户实测发现**选项卡一张都不弹**，
  比改造前还糟。根因就在上面那张表的第一行：把分片塞进一个 chunk 读 `.tool_calls`，参数从来没被拼起来。
  ⚠️ **真正的教训不在那行代码，而在测试**：所有假模型都是「一整片发完工具调用」——那种数据下错写法也照样通过。
  假模型必须复现**真实的分片形态**（首片带 `name`/`id`/空 `args`，随后每片只带一小段 JSON），
  否则测的是「理想世界」而不是生产环境。现已补 `_ShardedLLM` 与三条分片用例钉住。
- **用例**：改造后后端 **452**（新增 19 例：工具链组装语义、两轮往返、落库形状、四种降级、契约 schema、路由映射）、
  前端 **572**（新增 21 例：卡片结构化载荷与降级、接口收发、composable 挂载与反向断言、端到端 emit 链）。

### 修订（2026-10-21）：题干与选项说明改由卡片承载

**症状**。用户实际使用中发现卡片上只有几个短语：

```
AI：…P0 级还有一个关键流程点需要确认：
    A 填完点按钮一次性生成
    B 分章节逐步生成
    C 实时随填随生成预览
    D 都不合适，我补充
```

不知道在答什么，也看不出四个选项差在哪。原口径是「卡片只放选项名，题干与逐条解释交给正文」，
甚至有一条 `v-if="asks.length > 1"` 把**单题**的题干也省掉（理由是「正文里刚写过」）。

**根因**。这两条都依赖「模型会在正文里把题干和逐条解释再写一遍」，而它常常只写一句过渡话就
调工具。这与本 ADR 当初把哨兵块换成工具调用是**同一个教训**：凡是「要模型记得再写一遍」的东西
都会这样退化。而题干、背景本来就在工具参数里——载荷有，界面却不用，等于白拿。

**决定**。

1. **卡片自足**：题干与 `background` 总是显示（删掉 `asks.length > 1` 这个条件），
   每个选项渲染「标题 + 一句说明」两行。数据全来自载荷，不依赖正文。
2. **选项新增 `description`**（≤40 字，一句话说清「选它意味着什么 / 代价是什么」），
   schema 里**必填**——让它可选就等于允许模型省掉。只给标题时用户等于没得选。
3. **正文只写过渡**：一两句「为什么现在要问这件事」，**不再逐条列 A/B/C**。
   同一段话印两遍，用户还得来回对照。
4. **「名字：一句解释」里的尾巴挪进 `description`，不再丢掉**。旧实现直接删冒号后半段，
   前提是「解释归正文」；前提不成立时说明就两头落空——用户反馈的正是这个。
5. 模型漏写说明时**不让这一轮失败**：`description` 给空串、界面不渲染空行，
   同时打一条 `ask.option_without_description` 告警，便于事后统计发生率。

**代价**：卡片比从前高（每题多一行题干、每选项多一行说明），一屏能放的选项变少；
换来的是「用户不必先读正文才知道自己在答什么」。后者是硬需求，前者可以靠 `MAX_ASK_OPTIONS=6` 与
两题上限控住。

**被否决的替代方案**：只改提示词、让模型务必在正文复述题干与解释。否决理由是这条路已经试过
两轮（哨兵块、以及本 ADR 的正文解说口径），退化只是时间问题；而且它把「界面是否可读」押在
模型的自由文本上，本来就不该这么设计。

### 再修订（2026-10-21 续）：作答回执也要带上下文

上一版把卡片补成自足之后，**作答回执**还是老样子——一行「你选了 A」，刻意不重复题干与选项文本。
用户回看历史时否掉了这条：**卡片一作答就整块消失**（`interactive` 为 false 时整块不渲染），
题干与选项文本再没有第二个地方可看，只剩几个不知所谓的字母。

现在回执是一张轻卡：题干压到两行 + 一行「你选了 A 第一版就做离线同步」。数据全部来自已有的
`ClarificationAnswerItem`（`question` / `labels` / `texts` 本来就在载荷里），**不改契约、不动后端**。

1. **只列选中项**，不把未选中的选项搬上来——回执回答的是「我选了什么」，不是把卡片再印一遍。
2. **压缩交给 CSS**（`line-clamp-2`），不截断字符串：短题干一个字都不丢，长题干自动省略，
   前端也不必猜「多少字算短」。
3. **读屏文案与界面同口径**（`aria-label` 取「题干 + 标号 标题」）。只读标号时，读屏用户遇到的
   正是视力用户刚反馈的那个问题。
4. **残缺数据兜底**：`texts` 为空、题干为空时只渲染标号，不报错、也不用空行占位。

⚠️ 记一条教训：**「用户刚读过」是一次性理由，不是长期结构**。凡是「这段信息只在某个会消失的
界面上出现过一次」，就不能拿「刚看过」当作不落地的依据——回看、刷新、切线程都会把那个前提抹掉。

### 再修订（2026-10-21 三改）：档位式选项必须写清覆盖范围

**症状**。卡片上三个选项只有「轻量版 / 标准版 / 详尽版」，没有说明。这是**同一毛病第三次**出现：
题干与 `background` 已经补上了（见上一节），说明位也留好了，唯独 `description` 是空的。

**诊断**。这一类不是「模型忘了写」，而是「模型认为不必写」——档位词看起来自带含义。上一节定的规则是
「一句话说清**选它意味着什么 / 代价是什么**」，它对「想法快速录入」这种具体做法有效，对抽象档位词
基本失效：**代价是什么**？三档都是「写 PRD」，代价几乎一样，于是模型无话可写，就空着。

**决定（本期只改提示词）**。

1. **把判据从形容词换成可比较的量**：标题是档位 / 程度 / 策略名时，`description` 必须写**覆盖范围**
   ——含什么、不含什么，落到章节数 / 字段数 / 是否含接口与数据模型。
2. **给一组完整的三档示例**（正是用户截图里那道题的形状）：模型模仿整组示例比照抽象规则写更稳，
   单给一条正例不够。
3. **调用前逐题自查**，定义不出来的选项**删掉**：留一个裸标题，比少一个选项更糟。
4. **正文不描述界面形态**（不写「我列了几个选项」「请点选」）：卡片由参数渲染，正文一旦承诺，
   和实际渲染出来的东西就对不上——这也是上一节「正文只写过渡」的延伸。
5. schema 里 `options[].description` 的字段说明、以及续聊轮的 `CLARIFICATION_ASK_REMINDER`
   各补一句同一规则——后者是长对话里最先退化的位置。

**本期刻意不做**（用户明确要求先只动提示词）：

| 未做 | 它能买到什么 | 为什么先不做 |
| --- | --- | --- |
| `strict` 模式（约束解码） | 保证参数形状必然合规，是「第一次就对」唯一机制 | 需先 spike 验 Seed 2.1 + 方舟 tools 是否支持；且它只保证字段存在，保不了非空 |
| 后端准入（缺说明整题丢弃） | 「卡片上的选项必有说明」成为**不变式**，不依赖模型配合 | 会改变行为（模型不合格时这一轮没有卡片），先看提示词够不够 |
| 后端补写说明 | 缺失也能补上 | 用户明确否决：要求第一次生成就带解释，不接受事后补 |

⚠️ 诚实记一笔：提示词对模型是**概率约束**，改完不等于必然生效。观测点是既有的
`ask.option_without_description` 告警——若它仍在刷，就说明这条路到头了，该上「准入校验」
（缺说明的题不进 `asks`），而不是继续往提示词里加字。
