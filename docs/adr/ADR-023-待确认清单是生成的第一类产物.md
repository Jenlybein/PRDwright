# ADR-023：待确认清单是生成的第一类产物

> 源：v2 层（原 `docs/architecture/v2/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：Accepted（2026-10-15 裁决并落地，C 层 P3）

### Context

文档里「待确认」原本只是正文中的一句自然语言（「分页上限：待确认」）。若想让它成为可操作的东西——列出来、逐条问清楚、答完回到文档里——就必须把它变成**结构化数据**。

难点在于**它和正文的同步**。清单若由正文之外的某个环节单独产出，就必然出现「正文换了一版、清单还是上一版的」这种状态：生成、优化、澄清改写三条路径都要记得重算，而漏掉任何一条都不会报错，只会静默留下过期结论。同一份文档里，正文说「已确认 50 条」而清单仍列着「分页上限取多少」，是最糟的一种不一致——它让用户以为问题还没定。

### Options

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 前端从正文文本里解析「待确认」段落 | 后端零改动 | 解析口径在两端各写一遍；正文措辞一改就失配，且失配是静默的 |
| **B. 模型在正文末尾附标记块，收尾时剥离并解析（推荐）** | 清单与正文**来自同一次调用**，天然同步；与正文同一次写入落库 | 提示词要带格式说明；模型可能不守规矩，必须有降级 |
| C. 生成完再单独调一次模型产出清单 | 正文与清单互不干扰 | 多一次 LLM 调用；两次调用对同一份文档的理解可能不一致；仍要处理同步 |

### Decision

**选 B。**

1. **标记块用 HTML 注释哨兵**（`<!-- PENDING:BEGIN -->` … `<!-- PENDING:END -->`），块内是 JSON 数组。选 HTML 注释而不是别的定界符，是因为它有个兜底性质：**即使抑制逻辑漏了，Markdown 渲染里也不可见**，不会把半截 JSON 当正文闪现给用户。
2. **`services/pending_items.py` 是唯一实现**（`extract` 剥离 + 解析、`render_spec` 生成提示词说明、`PendingBlockSuppressor` 流式抑制）。三条生成线与澄清改写都调它，不各写一份。
3. **`id` 由后端分配**（`{章节 id}-{序号}`），不信任模型给的 id：保证全文档唯一、稳定，且能与正文位置对应。
4. **流式也要干净**：抑制器是有状态的、逐 chunk 的——块外态尾留「哨兵长度 − 1」个字符以应对哨兵被切在 chunk 边界；块内整段丢弃；流结束仍在块内则什么都不输出（半截 JSON 绝不能当正文）。
5. **降级不污染产物**：没找到块、JSON 非法、块未闭合 → 正文不受影响、生成不失败，只记一条 warning 并让该次清单为空。与「审核失败按通过处理」同一口径。
6. **清单与正文同批写入**（`commit_generated` 的 `pending_items` 参数），因此**「换了正文却忘了重算清单」在结构上没有落脚点**——所有会重生成正文的路径都走同一条收尾写入。唯一不重算的是用户手改，那是显式接受的（他改的是正文，没有声称清单是按新正文算的）。

### Consequences

- **变容易**：清单永远与正文同源；用户可以逐条澄清并写回；前端只需要展示，不解析、不重算。
- **变困难**：提示词里必须有一份「块长什么样」的说明（它是新增的、必须与实现同步的契约，由测试断言占位符存在守住）；必须为「模型不附块」准备降级路径；`generation_jobs` 与 `documents` 各多一列 JSON。
- **中立**：把清单做成「生成的第一类产物」而不是「正文的衍生物」，代价是提示词更长、解析逻辑更重，但换来的是**不需要任何同步机制**——同一处写入天然一致。
