# ADR-089：可移植性分两段，本期只做接口收敛

> 源：v8 层（原 `docs/architecture/v8/ADR.md`，已并入本目录）｜ [索引](./README.md)

**状态**：已定（v8 / T18.0 ~ T18.4）。

### 背景

"让项目能换库"可以是一次性的大改造（改所有列类型 + 改所有查询 + ETL），
也可以只做前半段（把方言收进一个模块，不改行为）。

两者的差别不在工作量，在**能不能验证**：前半段可以用现有 975 例自证；
后半段需要一个真实的目标库，否则每个决策都只能靠猜，猜错的表现为"上线那天才炸"。

### 决策

**分两段。**

- **本期（第一段）**：接口收敛 + 模型层声明。不改列类型、不做 ETL、不选目标库。
  判据是"现有用例一条都不用改"。
- **换库那次（第二段）**：改列长度、清洗脏数据、补 `username` 长度校验、ETL 对账。
  判据是"在目标库上跑通全部用例 + 结构对拍"。

`DIALECT-PORTABILITY.md` §3.6 的不收敛清单是第二段的输入，本期只负责把它写全——
**清单不完整比清单难做更危险**。

### 推论

1. 本期不引入 `VARCHAR(n)`。它会让 SQLite 的建表语句变化，结构对拍从全绿变全红，
   "结构没变"这个证据就没了。
2. 本期可以声明 `MEDIUMTEXT` 变体与 `mysql_collate`——两者在 SQLite 侧都不改变任何东西，
   属于"提前声明"，不是"提前改"。
3. 结构对拍换 inspector 放在第一段末尾单独一轮：它自身就是"判断迁移是否安全"的工具，
   改它等于改判据，必须单独验证。

### 被否决的方案

| 方案 | 理由 |
|---|---|
| 一次做到"三库都能跑" | 需要 CI 矩阵与目标库；本期没有对象，是纯抽象税 |
| 只做容器化，方言一概不动 | upsert 的方言 import 与结构对拍的循环依赖是**现在**的维护成本，不是将来的 |
