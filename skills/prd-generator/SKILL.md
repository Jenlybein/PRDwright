# PRD 生成

## 用途

将模糊的产品想法（问卷答案、对话记录、口头描述）转化为可交付给研发的结构化 PRD。
核心约束是**不编造输入中没有的信息**：所有推断标注为建议，所有缺口标注为待确认。

## 工作流

按顺序执行四个阶段。每个阶段的输入、动作与判断依据如下。

### 阶段一：校验输入

1. 读取 `references/field-schema.json`，取得字段契约与必填清单。
2. 收集输入。常见来源：
   - 本项目的需求澄清问卷答案（字段名见 `backend/src/backend/core/question_config.json`）；
   - 与用户的对话记录（用户可能在对话中补充或修正问卷答案，以对话中更晚的表述为准）；
   - 用户直接给出的结构化 JSON 或自由文本。
3. 逐项校验：
   - 必填字段缺失 → 先尝试从其他来源补齐；确实无法补齐则**停止生成，向用户提问**，
     不要带空占位符硬输出整篇文档。
   - 类型不符（如 `mvp_features` 传成字符串）→ 进入阶段二归一化，不直接判失败。
   - `mvp_features` 为空数组 → 视为「用户未提供功能清单」，**不中断生成**：先看 `ui_pages`
     是否给出了页面 / 模块 / 关键交互，能推导就按 `references/writing-rules.md` 产出一份
     逐条标注「（建议）」的候选功能清单；`ui_pages` 也为空时再标注「待确认」。
4. 记录校验结论：哪些字段缺失、哪些是推断得来。该结论在阶段四复用。

### 阶段二：归一化需求

按 `field-schema.json` 的 `x_source_aliases` 与 `x_normalization_rules` 把输入统一成规范形态：

- 别名映射（如问卷的 `problem_to_solve` → `product_goal`，`platform_type` → `platform`）；
- 结构统一（功能项统一成 `name` / `module` / `description` / `priority` / `acceptance`）；
- 合并重复项、`target_users` 切分为角色数组。

归一化只做**改名与结构调整**，不补充任何内容。所有内容层面的补全都必须走
`references/writing-rules.md` 的缺失信息处理流程。

### 阶段三：按模板渲染章节

1. 读取 `references/prd-template.md`，按其六个章节与顺序渲染：
   产品概述 → 功能需求 → 页面设计 → 技术规格 → 非功能需求 → 项目范围。
2. 渲染时严格遵守 `references/writing-rules.md`（不增删章节、不跨章节重复描述、
   区分事实与建议、缺失走「待确认 / 不适用 / 建议」三档、禁止编造业务信息）。
   本文件不复述这些规则，生成前必须加载该文件并逐条对照。
3. 表格类章节按数组字段循环渲染；数组为空时按模板注释处理，不删除章节。
4. 文末汇总「附：待确认问题」，与正文中的每一处「待确认」一一对应。

### 阶段四：生成后质量检查

1. 对照 `references/writing-rules.md` 末尾的「输出前自检」清单逐条核对。
2. 补充三项结构性检查：
   - 功能编号连续、唯一、无跳号；
   - 第 6 章的范围清单与第 2.1 章的功能编号完全一致；
   - 推断得来的功能项在第 2.1 节与第 6.1 节的「（建议）」标注一致，且已在待确认清单登记；
   - 阶段一记录的缺失字段，全部在正文或待确认清单中有交代，没有静默消失。
3. 若用户要求评审报告或 PRD 为正式交付物，复制 `assets/review-report.md` 作为报告骨架，
   填入检查结果（通过项 / 问题项 / 待确认项 / 结论），与 PRD 一并输出。
4. 任一项不通过则先修正正文，再重新检查；不要带着已知问题交付。

## 资源

| 文件 | 用途 | 何时读取 |
| --- | --- | --- |
| `references/field-schema.json` | 输入字段契约、别名表、归一化规则 | 阶段一与阶段二必读 |
| `references/prd-template.md` | 六章节正文骨架与渲染说明 | 阶段三必读 |
| `references/writing-rules.md` | 写作规范与自检清单（结构化、去重、事实/建议区分、缺失处理、禁编造） | 阶段三与阶段四必读 |
| `assets/review-report.md` | 质量检查报告模板 | 仅在需要输出评审报告时读取 |

## 输出约定

- 正文为 Markdown，直接输出文档内容，不写「好的，以下是 PRD」之类的客套话。
- 文档头部保留状态行（文档状态 / 版本 / 最后更新）。
- 无待确认项时，「附：待确认问题」写「无」，不要删除该节。
- 同时给出 PRD 与评审报告时，PRD 在前，报告在后。
