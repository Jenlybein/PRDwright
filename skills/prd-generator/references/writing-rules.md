# PRD 写作规范

生成 PRD 正文时必须遵守本文件的规则。规则之间冲突时，以「禁止编造」优先。

## 1. 结构化表达

- 严格按 `references/prd-template.md` 的六个章节与顺序输出，不增删章节、不改标题层级。
- 优先使用表格承载枚举型信息（功能清单、技术规格、页面清单），用列表承载并列条款，
  用段落承载需要解释的判断。
- 每条功能需求必须包含：编号、名称、优先级、描述、验收标准。编号形如 `F-01`，全文唯一且连续。
- 验收标准要可观测、可验证：写「在什么条件下、做什么操作、得到什么结果」，
  禁止「体验流畅」「性能良好」「界面美观」这类无法验收的表述。
- 功能描述具体到研发可开工：禁止「用户管理」「数据看板」这类空泛名词，
  要写成「支持通过手机号 + 验证码登录，登录态保持 7 天」。
- 一句话一条信息。同一段落里不堆砌多个诉求。

## 2. 内容去重

- 同一条需求只在文档中出现一次完整描述；在其他章节引用时只写编号与名称，
  不复述描述、不复制表格行。
- 功能需求（第 2 章）与项目范围（第 6 章）共享同一份功能清单：
  第 6 章只列编号与名称，第 2 章才是完整描述的唯一出处。
- 页面设计（第 3 章）不重复描述功能逻辑，只描述页面结构、模块与交互结果，
  涉及具体功能时引用功能编号。
- 合并语义重复的输入项（如「导出数据」与「下载数据」）后再渲染，避免同一件事写两遍。
- 允许必要的交叉引用，禁止整段复制粘贴。

## 3. 事实与建议的区分

- **事实**：来自输入字段、问卷答案或对话中用户明确确认的内容。直接陈述，不加修饰词，
  可标注来源（如「依据需求输入」）。
- **建议**：模型基于事实做的推断、补全或方案选择。必须显式标注「（建议）」并给出一句依据，
  读者要能一眼看出这不是用户说的。
- **待确认**：事实不足、需要用户拍板的点。写入对应章节并汇总到「附：待确认问题」。
- 三者不得混写在同一句话里。判断不出属于哪一类时，一律降级为「待确认」，不要假装是事实。

## 4. 缺失信息处理

按缺失字段的影响程度分三档处理：

1. **可合理默认**：缺失不影响交付判断，且行业有通行做法（如未说明的错误提示方式）。
   按默认值写，并标注「（建议，默认做法）」。
2. **必须确认**：缺失会导致研发无法开工或范围不清（如认证方式、数据存储、验收标准）。
   在对应位置写「待确认：<具体要确认什么>」，并列入文末清单。
3. **不适用**：该章节对本产品无意义（如纯 API 服务的页面设计）。写「本节不适用」并说明原因，
   不要留空、不要硬写内容。

必填字段（`product_name` / `product_goal` / `target_users` / `platform` / `mvp_features`）
缺失时，先尝试从其他输入来源归一化补齐；确实无法补齐的，**先向用户提问再生成**，
不得带着空占位符输出整篇文档。

## 5. 禁止编造业务信息

以下信息不得凭空生成，用户未提供时一律走「待确认」：

- 业务数据与目标值：用户量、日活、转化率、市场规模、增长预期、营收与定价。
- 时间信息：上线时间、里程碑、排期、SLA 承诺。
- 技术细节：具体框架 / 语言 / 数据库 / 云厂商 / 第三方服务选型，以及未经确认的接口与字段。
- 竞品与市场结论：竞品名称、对比结论、行业惯例数据。
- 组织与流程信息：团队规模、分工、审批流程、责任人。
- 合规与法务：资质要求、数据出境、隐私政策条款、行业标准符合性。
- 用户偏好与习惯：未说明的使用频率、使用场景细节、用户画像数字。

禁止把「合理推测」写成陈述句。需要给出方案时，写「建议采用 X，理由是 Y，请确认」。

## 6. 语言与风格

- 全文使用简体中文，术语首次出现时给出中文全称，后续可用英文缩写。
- 客观陈述，不使用「我们觉得」「显然」「毫无疑问」等主观修辞。
- 不写客套话与过程说明，不输出「好的，以下是……」「希望对你有帮助」之类内容。
- 不使用表情符号与装饰性分隔符。
- 同一概念全文用词一致（如统一称「用户」或「客户」，不交替使用）。
- 产品名称全文统一，不得改名或另起别名。

## 7. 输出前自检

逐条核对，全部通过后再交付：

- [ ] 六个章节齐全、顺序正确、标题层级未改动。
- [ ] 每条 MVP 功能都有唯一编号、优先级、描述、验收标准（或明确的「待确认」）。
- [ ] 无跨章节重复描述，第 6 章只做编号引用。
- [ ] 所有推断性内容都带「（建议）」标记，所有不确定项都带「待确认」标记。
- [ ] 未出现编造的数据、时间、技术选型、竞品结论（含文档头部的「最后更新」日期：
      填真实生成日期，无法确定时写「待确认」）。
- [ ] 模板中的渲染说明（HTML 注释）未被写进正文。
- [ ] 文末「待确认问题」清单与正文中的「待确认」一一对应，无遗漏。
- [ ] 全文用词、产品名称、编号一致。
