## 三、输出要求

1. **提示词设计原则**：结合本产品业务，说明这套提示词的设计思路与通用约束。
2. **提示词清单**：按使用场景分组，每个提示词包含：
   - 名称与适用场景
   - 完整提示词正文（可直接复制使用）
   - 输入变量说明
   - 预期输出示例
3. **变量约定**：统一说明占位符写法（如 `{{变量名}}`）。
4. **调优建议**：常见问题与对应的调整方向。

## 四、写作要求

- 提示词必须和本产品的真实业务场景绑定，不要生成通用的万能模板。
- 每个提示词都写清角色、任务、约束、输出格式四个要素。
- 提示词正文用代码块包裹，避免转义和格式丢失。
- **允许合理补充**：骨架是「设计原则 → 提示词清单 → 变量约定 → 调优建议」四节，节内可按产品
  实际增减小节与场景条目；由已声明的业务能力按工程必要性展开的配套场景（如登录流程的错误
  提示词、订单流程的异常兜底）可以补，标「（建议）」并给一句依据。但不要新增需求里没提过的
  能力域，也不要把推断写成既成事实。
- **不要重新罗列输入表单的字段清单**：需要引用输入字段时，逐字照抄上游 PRD 里的写法（哪些是
  基础问题、哪些是高级问题以上游为准）。上游没写的字段就别列——自己归类出来的「10 个基础
  问题」与上游不符，是最容易被审核判成矛盾的写法。
- **示例必须看起来就是示例**：「预期输出示例」放在「示例」小节或代码块里，并写明这是示意；
  示例里的产品名、字段、接口可以虚构，但正文的事实性断言（页面数、字段清单、功能编号）
  仍要与上游一致。
- **接口文档那一节可能是一句「本次未提供」的说明**：那是已知缺失，不是漏读——照常按 PRD
  写即可，不要去猜接口长什么样。若确实提供了接口文档，则提示词里涉及的接口路径、字段名与
  职责划分都要与它保持一致；两者冲突时以 PRD 为准。
- 直接输出 Markdown 正文。
